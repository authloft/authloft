- 本文只定义代码架构、目录结构、每个文件的职责边界、实现规范与单元测试方式，不写实现代码，也不复制接口契约的字段清单。

- 标记为（脚手架）的文件（`go.mod`、`Makefile`、`Dockerfile` 等）不逐个展开。
- 冲突优先级：接口文档 > 需求 > 架构文档。

## 1. 总体架构

### 1.1 技术栈

| 层 | 选型 |
|----|------|
| 语言 / 框架 | Go + Gin |
| ORM | GORM |
| 主库 | MariaDB 10.5+ |
| 缓存 | Redis（含 Lua 脚本） |
| 序列化 | Protobuf 为**接口报文与固定 schema 的唯一结构源**；JSON 视图由 protojson 输出（§1.6）；透传结构用 msgpack |
| 契约生成 | `buf` + `protoc-gen-go`（Go 结构体）、`protoc-gen-es`（前端 TS + 二进制编解码），产物提交进仓库（§2） |
| 密码哈希 | argon2id |
| 对象存储 | S3 兼容 SDK（minio-go）+ 本地文件系统 |
| 配置 | YAML（默认 `authloft.yml`，按进程 cwd 解析，`--config` 可指定，`gopkg.in/yaml.v3`）：启动时读取一次，**运行期不可变**，不支持热加载（§3.2） |
| 静态资源 | 前端构建产物 embed 进二进制（`server/assets`，`//go:embed dist`），由 Go 统一以 `/assets/**` 提供；可配 CDN 基址（§3.13） |

### 1.2 分层

```
HTTP 入口
  middleware   链路 ID / 访问日志 / panic 恢复 / HTTP 指标、Origin/Referer 校验、CSP nonce、gateway Token（REST 豁免域）；Connect 域另有 interceptor（会话 / 管理员 / RPC 签名 / 错误包装，§3.14）
    ↓
  handler      Connect 域：生成 handler 绑定入参（框架解码）→ 调 service → 返回响应消息 / connect.Error → 写 Cookie / 设响应头；REST 豁免端点按原方式输出
    ↓
  service      业务编排（orchestrator 步骤引擎、会话、OIDC、账号、管理后台…）
    ↓            ↓                    ↓
  factor       provider            repo
  认证因子实现   外部服务适配器      GORM / Redis / Storage
    ↓
  infra        异步队列、Redis 脚本、Crypto、配置热更新、事件日志
```

依赖方向单向向下：`factor` 与 `provider` 不知道 HTTP 的存在；`service` 不依赖 Gin（handler 层把 `*gin.Context` 转成 `context.Context` + 输入结构后传入）。Connect 域的编解码由 connect-go 框架承担，`service` 及其下层既不知道 JSON 也不知道 Protobuf。

### 1.3 三条主线与两条扩展轴

| 原则 | 落地方式 |
|------|----------|
| 统一建模 | 第三方登录、人机校验、短信、邮件、存储全部落 `provider` 表，用 `category` 区分，用 `provider_key` 唯一引用 |
| 接口抽象 | 每类能力一个接口 + 一张类型注册表；新增渠道 = 新增一个文件 + 一行注册 |
| 配置驱动 | 登录页显示什么、每种方式要填什么、走什么流程，由 `__AUTHLOFT_INIT__.methods` 注入快照决定（接口文档 §2.1）；该列表无 HTTP 接口 |

| 轴 | 落地 | 新增一件东西要改什么 |
|----|------|---------------------|
| 外部服务（Provider） | 一张 `provider` 表 + 每类一个接口 + 一张注册表 | 新增渠道 = `internal/provider/<category>/<type>/` 一个包 + 一行 `init()` 注册（§15.3） |
| 认证因子（Factor） | `Factor` 接口（§6.3）+ 注册表 | 新增因子 = `internal/factor/<name>/` 一个包 + 一行注册 |

两条轴都不得反过来让 service 层出现 `switch type`。

向下兼容：所有 Protobuf 结构、数据字段都必须尽可能保证向下兼容（接口文档 §12.8）。

### 1.4 Token 加密方案

封装格式、AAD 构造与各类载荷定义**见 §11.6**，此处只列实现侧约束：

- `security/token.go` 是唯一编解码实现，多类令牌共用；`purpose` 常量集中在 `security/purpose.go`，禁止跨 purpose 解令牌
- 不同场景令牌独立密钥（配置项分离），AAD 里的 `purpose` 是第二道保险
- `keystore` 按 `version+kid` 取密钥，支持轮换期新旧并存；算法固定 AES-256-GCM + 12B 随机 nonce，不做算法协商

### 1.5 第三方库

可适当使用第三方库以减少重复代码。技术栈级选型事实：WebAuthn 校验 `github.com/go-webauthn/webauthn`；微信小程序 SDK `github.com/medivhzhan/weapp/v3`（pin v3.8.4）；JSONata 求值 `github.com/recolabs/gnata`（pin v0.6.2，统一求值、不自行实现）；Connect `connectrpc.com/connect`（锁 v1.21.1）。版本策略：库版本由实现时联网核实后 pin 进 `server/go.mod`，本文不写死（已 pin 的除外）。

> 依赖引入准则、选型理由与可替换性约束见《CODE_GUIDE》§2.3。

### 1.6 序列化与传输（connect-go）

接口报文结构**只定义一次**：`.proto`（`server/proto/api/**`，约定见接口文档 §12.9）。Go 结构体与前端 TS 类型都由它生成，两份架构文档都不手抄字段。sso / account / admin / rpc / setup 五个业务域的 HTTP 接口全部走 **Connect 协议**（`connectrpc.com/connect` **v1.21.1**，handler 由 `protoc-gen-connect-go` 生成）；OIDC、gateway、页面路由、`/metrics`、头像直传 multipart 保持 REST / 原生输出（豁免清单见接口文档 §1.0）。

| 环节 | 实现 |
|------|------|
| 传输与路由 | connect-go handler：`POST /api.<域>.v1.<XxxService>/<Method>`；handler 天然同时服务 Connect / gRPC / gRPC-Web 三协议，对外契约只承诺 Connect 协议；承载传输见 §3.1 监听模式——未配 TLS 为 HTTP/1.1 + H2C（明文 HTTP/2），配置 cert+key 后为 HTTP/1.1(TLS) + H2(TLS)，`Connect-Protocol-Version` 头语义不受影响 |
| 编解码 | Connect 内建：请求 `Content-Type` 决定（`application/json` ↔ `application/proto`），响应与请求同编码；JSON 为**标准 protojson 映射**（lowerCamelCase、省略零值字段、int64 输出十进制字符串，接口文档 §1.12），未知请求字段拒绝（400 `invalid_argument`） |
| 请求体上限 | connect-go `WithReadMaxBytes(1 << 20)`，**固定 1 MiB、不可配置**（不读 config、无 `max_body_bytes` 字段；超限 `resource_exhausted`） |
| 错误模型 | 业务失败 = `connect.Error`（标准码 → HTTP 映射见接口文档 §1.5）+ `api.common.v1.ErrorInfo` detail（`domain` / `code` / `message` / `retry_after` / `attempts_left`）；协议级错误由框架生成 |
| 鉴权拦截 | session / admin / rpc HMAC / 错误包装为 **Connect interceptor**（`internal/connect`）；gateway HMAC 与 Origin/CSRF 留在 **Gin 中间件**（gateway 域本身是 REST 豁免，Origin 在请求进入 connect handler 前拦截） |
| `X-Request-Id` | 所有响应统一回写（含豁免端点），由 Gin 全局链的 requestid 中间件写入响应头；错误体内不携带（接口文档 §1.1） |

约束：

- **不引自定义 codec**：JSON 口径完全遵循标准 protojson（lowerCamelCase + 省略零值），前端对缺失字段按零值兜底；这是双端生成链的共同约定，任何一端不得自行改写序列化选项
- 整型只用 `int64`（接口文档 §1.12），protojson 天然输出十进制字符串；`buf lint` 自定义规则拦 `int32` / `uint32` / `fixed32`，**规则仅作用于 `proto/api/**`**——存储模型 proto（`provider/ext.proto`、`credential/meta.proto`、`token/**` 等，接口文档 §12.1～§12.3 与 §11.6）豁免
- handler 只返回 / 返回错误消息与 `connect.Error`，禁止绕过生成 handler 手写 HTTP 响应（§22 约束 6）
- 流式 RPC 本期不使用（路径仍为 unary POST）；压缩协商不启用（Connect 协议内建能力，需要时另开卡）

生成链（CI 门禁见 §21.4）：

1. `buf generate`（配置在 `server/buf.gen.yaml`，插件 `protoc-gen-go` + `protoc-gen-connect-go`）→ `server/gen/go/api/**`（Go 消息 + `*_connect.go` handler）与 `web/src/gen/proto/**`（TS，前端 connect client 直接消费）
2. 产物**提交进仓库**：部署与前端构建不依赖本地 protoc 环境
3. CI 校验 `buf generate` 后工作区无 diff（防止有人改生成物或忘记重新生成）
4. `.proto` 变更过 `buf breaking --against '.git#tag=pre-connect'`（Connect 改造基线 tag），只增字段、不改字段号（接口文档 §12.8）

## 3. 文件职责清单

### 3.1 `cmd/authloft` 与 `internal/app`

| 文件 | 职责 | 约束 |
|------|------|------|
| `main.go` | 解析 flags、加载配置、构造 App、注册信号、阻塞运行 | 极薄，不含业务 |
| `bootstrap.go` | 启动分支：配置文件（路径见 §3.2，默认进程 cwd 下 `authloft.yml`，`--config` 可指定）**不存在 → setup 模式**——不加载 config、不初始化 DB / Redis、不起业务链路，只启动 `internal/setup`（§3.15）；**存在 → 正常装配**：config → DB → **迁移检查（migrate up，幂等，§3.16）** → Redis → 密钥 → provider/factor 注册表（触发 `init()` 注册）→ settings 预热 → 队列 worker → cron → router | 注册表导入在此处统一 `_ import`，保证自注册被执行 |
| `app/router.go` | 全站路由与中间件分组：`/api/**` 与页面路由分离（接口文档 §8）；公开组 / 登录组 / 会话组 / 管理员组 / 网关组 / RPC 组。`/assets/**` 不走 gin 链——由 `server/assets` 挂顶层 `http.ServeMux`，正常 / setup 两模式恒在（§3.13） | 唯一知道路由表的文件 |
| `app/app.go` | `Run()` 与 `Shutdown(ctx)`：先停接收 → flush 队列（超时 10s 强退，§5.2）→ 停 worker/cron → 关连接 | 优雅关闭顺序固定 |
| `app/health.go` | 存活 / 就绪探针（含队列长度与 dropped 计数） | — |

启动与监听口径（装配层 = `bootstrap.go`，Go 1.26 标准库实现）：

- **顶层分流用标准库 `http.ServeMux`**：Connect handler 按路径前缀挂到 mux（`mux.Handle(path, connectHandler)`），`/assets/` 前缀同样挂 mux（`server/assets`，§3.13，正常 / setup 两模式恒在），其余全部交给 Gin（`mux.Handle("/", ginEngine)`），Connect 请求不再经 `gin.NoRoute` 兜底（§3.3 / §3.14 同此口径）
- **监听模式由 server 段 TLS 配置决定（同端口双协议）**：未配置 `cert_file` + `key_file` → 同端口 HTTP/1.1 + H2C（明文 HTTP/2），`min_tls_version` 不生效；已配置 → 同端口 HTTP/1.1(TLS) + H2(TLS)，`min_tls_version` 为最低 TLS 版本
- **实现用 Go 1.26 标准库原生 `http.Server.Protocols`**：明文 `SetHTTP1 + SetUnencryptedHTTP2`；TLS `SetHTTP1 + SetHTTP2`，ALPN 由标准库协商；`TLSNextProto` 保持 nil、不手写 `NextProtos`、Protocols 不用 `golang.org/x/net/http2` / h2c
- **该分流链上禁挂 gzip / body-capture 类中间件**（破坏 h2c / 流式语义）
- **setup 模式同样读取 server 段环境变量**（`AUTHLOFT_SERVER_LISTEN` / `AUTHLOFT_SERVER_MIN_TLS_VERSION` / `AUTHLOFT_SERVER_CERT_FILE` / `AUTHLOFT_SERVER_KEY_FILE`），只读 server 段、其他段不读；setup 无配置文件可加载，server 段取值 = 默认值 + env 覆盖（§3.15）

### 3.2 `internal/config`（YAML 启动配置）

配置文件路径由启动参数 `--config <path>` 指定，**读取与写入（安装流程写回，§3.15）共用该路径**；缺省为**当前工作目录下的 `authloft.yml`**，相对路径按进程 cwd 解析；全量示例为 `server/configs/authloft.yml.example`。**只在启动时读取一次，运行期不可变**：不监听文件变更、不提供刷新接口，改任何一项都必须重启；改完不重启不会有任何效果。需要热更新的项（阈值、开关、域名列表、Cookie 名与 TTL、队列参数）一律走 `settings`（接口文档 §5.6），**不进本文件**。其中 `sso_domains` 的每个元素是**完整 URL 前缀**（含 scheme 与 `host[:port]`，可含可选路径，形如 `https://example.com/prefix`，末尾不带 `/`）；实现方拼同步地址时必须写成 `{prefix}/sso/sync_cookie`（展开规则见 §11.2），不得把元素当作完整同步地址直接拼接。

```yaml
server:
  listen: ":8080"                # 监听端口
  min_tls_version: ""            # 最低 TLS 版本："1.2" / "1.3"，空 = 标准库默认；未同时配置 cert_file + key_file 时不生效
  cert_file: ""                  # TLS 证书 PEM 路径，与 key_file 成对配置
  key_file: ""                   # TLS 私钥 PEM 路径，与 cert_file 成对配置
db:
  dsn: "authloft:pass@tcp(127.0.0.1:3306)/authloft?charset=utf8mb4&parseTime=true&loc=Local"
  max_open_conns: 50
  max_idle_conns: 10
  conn_max_lifetime: 1h
redis:
  addr: "127.0.0.1:6379"
  password: ""
  db: 0
  pool_size: 50
authloft:
  root: "https://authloft.example.com" # al_root，只填主域名，用于拼回调 / 多域名同步地址；允许 http://（约定 7）
  rp_id: "authloft.example.com"        # WebAuthn RP ID
sign_key:                                           # 各类令牌 / 载荷独立密钥，支持多 kid 轮换（§1.4）
  session:      { key: "<base64-32B>", kid: 1 }     # session token
  login:        { key: "<base64-32B>", kid: 1 }     # login token
  ticket:       { key: "<base64-32B>", kid: 1 }     # ticket（含 al:ticket 存储值，§11.4）
  cookie:       { key: "<base64-32B>", kid: 1 }     # al_login_state（§11.6.1）
  sync_payload: { key: "<base64-32B>", kid: 1 }     # 多域名同步载荷（§11.2）
oidc:                                               # OIDC RS256 签名密钥集（§14.3）；与顶层 sign_key（AES 对称）是两套密钥，不得混用
  jwt_keys:                                         # 列表首项为当前签发密钥，其余为轮换期仅验签的历史公钥
    - kid: "1"
      private_key_pem: "<base64(PKCS#8 PEM)>"       # base64 编码的 RSA 私钥 PEM（PKCS#8，2048/3072/4096 位）
argon2: { time: 3, memory: 65536, threads: 4, key_len: 32 }
log: { level: info, format: json }
```

| 文件 | 职责 | 约束 |
|------|------|------|
| `config.go` | 上表结构体 + `Validate()` | 字段与 YAML 一一对应；新增字段必须同步 `authloft.yml.example` 与默认值说明 |
| `loader.go` | 读文件 → 应用环境变量覆盖（`AUTHLOFT_<SECTION>_<FIELD>` 全字段显式表，环境变量优先；空值跳过、未知忽略、非法值 fail-fast；`authloft` 段双前缀 `AUTHLOFT_AUTHLOFT_*`）→ `Validate()` | 启动期一次完成；缺项 / 非法即 fail-fast 退出，不提供运行期兜底默认值（唯一例外：配置文件不存在且首次运行时自动生成 `sign_key` 并写回，见约定 4） |

约定：

1. 业务代码不得直接读 YAML 以外的全局变量；`*config.Config` 由 `bootstrap.go` 注入（构造参数），测试可传自造实例（§20）
2. 与 `settings` 的分界：**改了要重启才安全的进 YAML**（地址、端口、密钥、`rp_id`、argon2 参数、日志），**改了要即时生效的进 settings**（开关、阈值、Cookie 名、`static_base` 等）；同一语义不得两处都有
3. 密钥类字段不得出现在日志与 `/api/**` 响应中（§22 约束 7）
4. `sign_key` 各场景均为 AES-256-GCM **对称单密钥**（非密钥对），只在安装流程中生成（§3.15）：全新安装随机生成并写入；上传已有 config 缺 `sign_key` → 拒绝（`config_invalid`，§3.15）。**文件已存在但任一关键项缺失 / 非法** → fail-fast 退出，不自动补写。多实例部署由部署方自行保证各实例配置文件一致（密钥不一致会导致令牌跨实例不可解）
5. server 段 TLS 字段语义：`min_tls_version` 取字符串 `"1.2"` → `tls.VersionTLS12`、`"1.3"` → `tls.VersionTLS13`；空串 / 未配置 = 不设最低版本（标准库默认）；非法取值启动 fail-fast。`cert_file` / `key_file` 必须成对配置且路径可读，单边配置 / 不可读 fail-fast；**两者未同时配置 → 不启用 TLS，`min_tls_version` 不生效**（监听模式见 §3.1）。env 注入按既定口径（`AUTHLOFT_<SECTION>_<FIELD>` 全字段显式表）随 YAML 字段对应增删，server 段现有 env：`AUTHLOFT_SERVER_LISTEN` / `AUTHLOFT_SERVER_MIN_TLS_VERSION` / `AUTHLOFT_SERVER_CERT_FILE` / `AUTHLOFT_SERVER_KEY_FILE`
6. `oidc.jwt_keys` 为 **RS256 非对称签名密钥集**，与顶层 `sign_key`（AES-256-GCM 对称单密钥，约定 4）严格分离，两者不得互用：
   - **来源**：只用两种等价写法——全新安装由 `internal/setup` 随机生成并写入（§3.15）；上传已有 config 时由运维在 `oidc.jwt_keys` 内直接提供同一格式私钥。**不读外部 PEM 文件路径**，启动期不生成密钥。
   - **格式与校验**：`kid` 为非空字符串且整个列表内唯一；`private_key_pem` 为 base64 编码的 PKCS#8 RSA 私钥 PEM（2048/3072/4096 位）。列表为空、base64 解码失败、PEM 解析失败、非 RSA、位数不足、`kid` 重复 → `Validate()` 返回错误，启动 **fail-fast 退出**，不回退、不自动补写、不改用对称密钥。
   - **轮换**：列表**首项**为当前签发密钥（新令牌 `kid` 取首项），其余项只发布公钥到 JWKS 供旧令牌验签；轮换 = 把新密钥置于首项并保留旧项，旧项至少保留「实际最大 Access Token TTL + `5min` 时钟偏移」——默认 TTL 为 `3600s`（接口文档 §4.7），客户端 `access_token_ttl` 可配置更大（§4.5 `oidc_client`），须按实际最大 TTL 计；建议保留 24h，之后可删。改 YAML 后必须重启（配置运行期不可变）。
   - **env 覆盖**：`oidc` 段不参与 `AUTHLOFT_<SECTION>_<FIELD>` 注入（密钥集为列表型，私钥不应经 env 传递），只从 YAML 读取。
   - **issuer**：不设独立配置项，`iss` 固定取 `authloft.root`（§14.1 / §14.3）。
7. `authloft.root` 允许 `http://`（明文 HTTP 部署为一等公民，接口文档 §1.1）：`config.go` 的 `Validate()` 只校验「可解析 URL 且 scheme 为 `http` 或 `https` 且 host 非空」，**不强制 HTTPS**。明文部署的适用场景（内网 / 测试 / 反代 TLS 终止后明文直连）与安全提示见接口文档 §1.1；会话 Cookie 的 `Secure` 属性由 settings 键 `https_deployment`（接口文档 §5.6 / §1.9）驱动，与本字段无耦合；HTTP→HTTPS 强制跳转与 HSTS 由网关层负责，Authloft 不提供。

### 3.3 `internal/middleware`

| 文件 | 职责 | 约束 |
|------|------|------|
| `origin.go` | 校验 `Origin` 与当前域名相同，跨站 403；无 `Origin` 时校验 `Referer`（`servicewechat.com/{appid}` 白名单 = 已启用 `wechat_mp` / `wechat_mp_scan` provider 的 `Ext.app_id` 集合，§13.0；接口文档 §1.1） | 登录相关接口与写接口强制启用；**免检组**：`/api/oidc/**`、rpc 域（Connect 路径 `/api.rpc.v1.**`）、`/api/gateway/**`（接口文档 §1.1 例外）；Content-Type 校验由 Connect 框架与 OIDC 各自处理，不设独立中间件 |
| `csp.go` | 生成每请求 nonce，写入 ctx，并输出 CSP 响应头；Provider 经 `CSPSupporter` 声明 CSP 源（§12.1；captcha 侧注册契约见 §9.4），中间件只做聚合与去重——同名指令按指令名聚合后单条输出（CSP 规范同名指令仅首条生效、非取并集；基线源在前、支持者按装配序），禁止按厂商名 / type 特判 | nonce 必须 per-request 随机 |
| `gateway.go` | `X-Gateway-Token` 校验（接口文档 §6） | 仅 `/api/gateway/**`（REST 豁免域，留在 Gin 中间件，不上 interceptor） |
| `requestid.go` / `logger.go` / `recover.go` / `metrics.go` | 链路 ID、结构化日志、panic 恢复、HTTP 指标 | 日志不得打印 login_token / 密钥；requestid 服务端自生成（`crypto/rand` 16 字节 hex/32 字符），不读不透传入站头、**所有响应统一回写 `X-Request-Id` 响应头**（成功 / 失败 / 豁免端点，接口文档 §1.1；错误体内不携带），rand 失败留空串（不伪造值），写入 ctx 供 logger 与 connect 错误包装读取；metrics 零第三方依赖：热路径仅 `sync/atomic` 原子计数（3 个包级变量：累计请求数 / 累计耗时纳秒 / 当前在途数），禁 mutex、禁每请求 map 写、禁热路径字符串分配；`/metrics` 端点挂全局 engine（不进业务路由）、读取时才格式化纯文本（运维端点），快照近似值可接受 |

挂载顺序（全局链，挂载顺序即执行顺序，`server/router.go` 已按此落地）：`recover`（最外层，兜住全链 panic）→ `requestid`（先于一切错误出口，所有响应统一回写 `X-Request-Id` 头）→ `logger`（访问日志要取到 request_id）→ `metrics`（最内层，defer 累加，panic 经 unwind 也计数）→ `origin`（对业务域生效，Connect 请求在进入 connect handler 前被拦截）。Connect 域的 handler 由 `internal/connect/server.go` 装配、经装配层按路径前缀挂入顶层 `http.ServeMux`（§3.1 分流口径，页面 / 静态路由走 Gin 不受影响）；session / admin / rpc HMAC / 错误包装 interceptor 在 handler 注册时按域挂载（§3.14）。`/metrics` 挂全局 engine、不进业务路由。

### 3.6 `internal/service/orchestrator`（步骤引擎，核心）

| 文件 | 职责 | 约束 |
|------|------|------|

### 3.13 静态资源与 CDN（`server/assets`）

前端四 entry（`login` / `account` / `admin` / `setup`）的构建产物**嵌入二进制**，不依赖外部 web server。**实态校准（2026-11-06）**：`server/assets` 包与 `/assets/**` 路由均未实现，下表标注【施工】的条目为施工口径（明确设计决定），其余为已核实的仓库实态；仓库无 Makefile、无 `make web`、无 `app/assets.go`，构建入口是 `web/package.json` 的 `pnpm build`（`modern build && node scripts/sync-templates.mjs`，assets 入驻步骤见下）。

| 项 | 约定 |
|----|------|
| 产物布局（实态） | `web/dist` **扁平布局，无 `{entry}/` 子目录**：JS 全在根级——entry 主文件 `{entry}.{contenthash}.js`、共享 chunk（`builder-runtime.*.js` / `lib-react.*.js` / `lib-polyfill.*.js` / `lib-router.*.js` 等）、数字 / 单字母异步 chunk（如 `0.f4c926c461.js`）；CSS 在 `web/dist/static/css/{entry}.{contenthash}.css`；HTML 产物在 `web/dist/html/{entry}/index.html`（仅作壳层模板源，不入驻 assets）；根级另有 `.map`、`.LICENSE.txt` 与构建元数据 JSON（`modern.config.json` / `route.json` / `nestedRoutes.json`）。壳层模板引用形态与此一致（实态 `server/internal/pages/templates/login.html`）：`{{AUTHLOFT_STATIC_BASE}}/login.{hash}.js`、共享 chunk `{{AUTHLOFT_STATIC_BASE}}/builder-runtime.{hash}.js`、CSS `{{AUTHLOFT_STATIC_BASE}}/static/css/login.{hash}.css`——占位符后直接根级文件名 |
| 壳层 HTML 模板 | 落位 `server/internal/pages/templates/{entry}.html`——前端构建产物 `dist/html/{entry}/index.html` 经 `sync-templates.mjs` **仅原样复制 + 纯校验对账（fail-fast、零改写）**落位，三占位符由前端构建期 config 注入产物（前端架构 §1.5，契约见接口文档 §8），`internal/pages` 以 `//go:embed templates` 嵌入，缺失即编译失败（防漏构建）。**已实做**：`server/internal/pages/render.go`（统一渲染入口 + 三占位符替换 + `no-store`） |
| 入驻与嵌入【施工】 | 新包 `server/assets`：`embed.go` 以 `//go:embed all:dist`（`all:` 前缀使 `.gitkeep` 等点文件计入嵌入匹配）嵌入 `server/assets/dist/` 并提供 `Register(mux *http.ServeMux)`。入驻动作并入 `pnpm build` 构建链尾段——新增 `web/scripts/sync-assets.mjs`（与 sync-templates.mjs 并列；落地前允许等价复制命令人工执行）把 `web/dist` 复制到 `server/assets/dist`。**复制**：根级 `*.js`、`*.LICENSE.txt` 与 `static/**`（CSS 及图片 / 字体等媒体）；**不复制**：`html/`（壳层模板已由 sync-templates 另行落位）、`*.map`（sourcemap 不入二进制）、根级 `*.json`（构建元数据，运行期零引用）。`server/assets/dist` 产物不入库、`dist/.gitkeep` 占位入库（.gitignore 条目随实装落地）——占位入库保证空仓 `go build` 恒过。构建顺序固定：前端 build → 入驻 → `go build`；仅当 `dist` 目录整体缺失（含 `.gitkeep` 被删）才触发编译失败（go:embed 硬约束）；产物未入驻时运行期表现为 `/assets/**` 全 404（不 panic），入驻完整性由 sync-assets 链尾对账保证（施工口径）。入驻文件名全部带 contenthash（`.LICENSE.txt` 随 chunk 名带 hash），统一长缓存安全 |
| 路由【施工】 | `server/assets.Register(mux)`：**正常模式**在 `server/bootstrap.go` 装配段（`buildHandlerWithSSO` 构造 `http.ServeMux` 处，与 Connect 前缀同层）调用；**setup 模式**在 `server/internal/setup/setup.go` 的 `NewServer` mux 构造处调用——**两模式恒在**（setup 壳当前资源 404，即缺此挂载）。无鉴权、不进 gin 全局链与 session / Origin / admin 中间件，也不套 Connect 前缀中间件链；与 API 前缀不冲突 |
| 404 与穿越防护【施工】 | embed FS 以嵌入根为边界，天然无目录穿越；校验点：请求路径经 `path.Clean`、拒绝 `..` 逃逸；目录请求（如 `/assets/`、`/assets/static/css/`）一律 404、**禁止目录列举**；未命中统一 404，不回退到壳层页、不泄露文件存在性 |
| URL 前缀 | 取 settings 的 `static_base`（接口文档 §5.6，默认 `/assets`，可为 CDN 绝对地址）；**只影响 HTML 输出的前缀与 `__AUTHLOFT_INIT__.static_base`，不影响 Go 的路由**——配了 CDN 时 Go 侧仍提供 `/assets/**`，供 CDN 回源与内网直连。setup 模式无 settings 可读，取常量 `/assets`（`internal/setup` 的 `setupStaticBase`） |
| 缓存头【施工】 | `/assets/{file}`（扁平路径，无 `{entry}` 段）：`Cache-Control: public, max-age=31536000, immutable`（入驻文件名均带 contenthash）；壳层 HTML 仍 `no-store`（接口文档 §8） |
| CSP | 与接口文档 §8 壳层 CSP 统一口径逐项一致：`default-src 'self'`；`script-src 'nonce-…' 'strict-dynamic'`（配 CDN 时追加 CDN 源，服务旧浏览器回退）；`style-src 'nonce-…' 'self'`（内联 `<style>` 经 nonce 放行；配 CDN 时追加 CDN 源）/ `font-src 'self'`（配 CDN 时追加 CDN 源）；`img-src 'self' data: https:`（`data:` 覆盖 captcha base64 图；`https:` 覆盖管理员自托管的渠道图标，域名不可预知，接口文档 §2.7.1）；`connect-src 'self'`；captcha provider 贡献源（§9.4）按「当前生效 Provider」聚合进各指令单条输出，同名指令合并语义见接口文档 §8（同名指令仅首条生效，非并集拼接） |
| 版本号 | 无资源版本号：缓存失效由 contenthash 文件名 + HTML `no-store` 承担 |

### 3.14 `internal/connect`（Connect 装配与拦截器）

Connect 域的 handler 注册、鉴权拦截与错误包装的唯一出口。传输与编解码由 connect-go 框架承担（规则见 §1.6），此处只列文件边界。

| 文件 | 职责 | 约束 |
|------|------|------|
| `server.go` | 注册各域生成的 connect handler（`*_connect.go`），交装配层按路径前缀挂入顶层 `http.ServeMux`（§3.1 分流口径，页面 / 静态 / OIDC / gateway 路由走 Gin 不受影响）；setup 模式下仅注册 `SetupService` | handler 注册时按域挂 interceptor（见下）；不在此处写业务逻辑 |
| `interceptors.go` | session interceptor（会话解析 + 重签下发，复用 `session` 包纯函数）／ admin interceptor（`uid==1` 判定）／ rpc HMAC interceptor（**按方法名分流**：写接口 nonce 去重 → 五项签名校验；读接口五项签名校验（nonce 参与签名、不去重）；复用 `cache/nonce`，接口文档 §7）／ 错误包装 interceptor（最内层） | session / admin 判定与 Gin 中间件共用同一实现，禁止复制；**写接口**（方法名 `Update`/`Delete`/`Set`/`Create`/`Revoke` 开头）nonce 去重必须在签名校验前，**读接口**不做去重；错误包装不透出内部错误文本 |
| `errors.go` | `ErrorInfo` 构造助手：业务失败 → `connect.NewError(标准码, …)` + `ErrorInfo{domain, code, message, retry_after, attempts_left}` detail | `code` 只允许接口文档 §1.6 词汇表与域内定义值；`request_id` 不进错误体（走 `X-Request-Id` 响应头） |

约定：

- `connect` 包只依赖 connect-go、生成的 handler 接口、`session` / `cache` 包接口，不 import `service`（保持 §1.2 的依赖方向）；请求体上限经 connect-go `WithReadMaxBytes(1 << 20)` 由**装配层（bootstrap）**注入，**固定 1 MiB、不可配置**（不读 config、不设 `max_body_bytes`），包自身不读 config
- 错误包装 interceptor：非 `connect.Error` 的返回错误一律包成 `internal`（无 ErrorInfo、无细节）；`connect.Error` 无 detail 时按需补挂 ErrorInfo
- 页面路由（`page.go` 的空壳 HTML）、`/assets/**`、OIDC 的 `x-www-form-urlencoded`、gateway 纯响应头、multipart 头像直传**不走本包**，各自按原方式输出
- setup 域复用同一套 connect 装配（`internal/setup` 在 setup 模式下仅注册 `SetupService`，正常模式不注册任何 setup handler）

### 3.15 `internal/setup`（安装与首次运行初始化）

启动分支见 §3.1：配置文件（§3.2，默认进程 cwd 下 `authloft.yml`，`--config` 可指定）不存在即首次启动，只启动本模块——不初始化 DB / Redis、不起业务链路，HTTP 侧仅暴露 `/setup` 空壳页与 `SetupService` connect handler（接口契约见接口文档 §13；正常模式下不注册，请求 404）。

| 文件 | 职责 | 约束 |
|------|------|------|
| `setup.go` | setup server 与路由：渲染 `/setup` 空壳页——读取壳层模板 `internal/pages/templates/setup.html`（与业务三端同一模板与占位符契约，接口文档 §8；模板由前端构建产物经 `sync-templates.mjs` 原样复制落位，禁手改——`pnpm build` 覆盖写入）并替换运行期占位符、注册 `SetupService` connect handler（接口文档 §13） | 仅 setup 模式存活；config 写入并重启后永久退出；渲染输出的 CSP 头与正常模式同基线（接口文档 §8）；监听与 TLS 取 server 段口径——无 config 可加载，取值 = §3.2 默认值（监听默认 `:8080`）+ env 覆盖（`AUTHLOFT_SERVER_LISTEN` / `AUTHLOFT_SERVER_MIN_TLS_VERSION` / `AUTHLOFT_SERVER_CERT_FILE` / `AUTHLOFT_SERVER_KEY_FILE`，只读 server 段，见 §3.1） |
| `paths.go` | 两条安装路径的执行与状态机（见下） | 每步失败即终止并返回明确错误，不产生半初始化状态；迁移幂等（版本表）+ 管理员存在性判定（§3.16） |
| `writer.go` | config 生成与**原子写入**：写临时文件 → `rename` 覆盖，权限 `0600`；全新安装随机生成全部 `sign_key`（`security/rand.go`）与 `oidc.jwt_keys`（RSA 2048 位 PKCS#8，每套安装一把，`kid: "1"`） | 密钥与密码不出现在日志与响应；未列举配置项取 `authloft.yml.example` 默认值 |

两条路径（执行顺序即状态机，每步成功才进下一步）：

- **A 上传已有 config**（`POST /api/setup/config`）：① 完整性校验——复用 `internal/config` 的结构与 `Validate()`，不自建一套（失败 → `config_invalid`；缺 `sign_key` / `oidc.jwt_keys` 同属配置不完整，直接拒绝）② DB / Redis 连接性检查（失败 → `db_unreachable` / `redis_unreachable`）③ 执行迁移 `migrate up`（§3.16，幂等、已最新秒过；失败 → `migration_failed`）④ 管理员（ID=1）存在性检查——版本已最新但管理员缺失 → `admin_missing`（提示改走全新安装）⑤ 原子写入 config → 触发重启
- **B 全新安装**（`POST /api/setup/install`）：① 字段校验（`root` 必填 + host 域名校验、`rp_id` 缺省推导后同校验；IP / 非法 → `config_invalid`，接口文档 §13.3）② 连接性检查 ③ 执行迁移 `migrate up`（§3.16；失败 → `migration_failed`）④ 插入管理员用户（固定 ID = 1，已存在则跳过（幂等）；用户名 / 密码校验复用 `security/policy.go` 与接口文档 §2.3 / §5.6 规则）⑤ 生成完整 config（用户所填项 + 随机密钥 + 其余默认值）原子写入 ⑥ 触发重启

实现要点：

- `root` 必填且 host 必须为域名 / `localhost`，拒绝 IP（接口文档 §13.3）；`rp_id` 缺省取 `root` 的 host（去 scheme 与端口），不再自动读取请求 Host；两者任一为 IP / 非法域名 → `config_invalid`
- 重启机制：进程正常退出（exit 0），由 supervisor / Docker restart policy 拉起，**不做 self-exec**；触发前确保 config 已完整落盘
- 并发防护：不引入一次性令牌、不做并发防护；部署约束为**首启应单实例**（与 §3.2 多实例配置一致性同属部署侧责任）
- setup 状态不落盘：进程中断后重跑安装，按同一路径继续（迁移幂等 + 管理员存在性判定兜底，§3.16）
- 日志：记录各步骤开始 / 结束与失败原因；不打印 DSN 密码段、`admin_password`、密钥明文
- 安装侧域名校验从源头保证 `rp_id` 合法；管理员事后手工改 config 把 `rp_id` 配成 IP 时，启动期 WebAuthn 初始化失败进入**降级窗口（fail-closed）**——进程不退出、其余功能可用，但窗口期内凡需 webauthn 的操作一律拒绝（§8.3）

测试要点：两路径逐步成功与各步失败矩阵；版本已最新 + 管理员已存在时路径 A 秒过、路径 B 跳过插入；写入中断不落半截 config（临时文件 + rename）；setup 路由在正常模式 404；管理员固定 ID = 1；缺 `sign_key` 的上传被拒；敏感值不出现在日志。

**安装决策摘要（2026-11-03 / 2026-11-05）**

| 事项 | 结论 |
|---|------|
| 管理员固定 ID | `1`（`BIGINT`，显式写入；沿用 `uid == 1` 判定） |
| "自动重启"机制 | 进程正常退出（exit 0），由 supervisor / Docker restart policy 拉起；不做 self-exec（裸跑部署需手动重新运行） |
| WebAuthn RP ID 默认推导 | `rp_id` 缺省取 `root` 的 host（去 scheme 与端口）；**安装 `root` 必填且必须为域名 / `localhost`，拒绝 IP**（2026-11-05 定稿，取代 2026-11-03 的请求 Host 推导口径） |
| 启动期 WebAuthn 初始化失败 | **降级不退出 + 窗口期 fail-closed**：进程照旧不退出、其余功能可用；窗口期内凡需 webauthn 的操作一律拒绝（唯一可用 MFA 因子为 webauthn 的登录、通行密钥绑定 / 解绑 / 管理 → `method_disabled`），绝不静默放行 / 跳过 MFA / 改用更弱因子（§8.3；2026-11-05 定稿，推翻早前"仅禁用因子 + 其余照常"口径） |
| 上传 config 缺 `sign_key` | 属配置不完整，直接拒绝（`config_invalid`） |
| 一次性令牌 / 并发首启防护 | 不引入令牌、不做并发防护；部署约束为**首启应单实例** |
| setup 状态落盘 | 不落盘；进程中断后重跑安装，按同一路径继续（迁移幂等 + 管理员存在性判定兜底，§3.16） |

### 3.16 `migrations/`（数据库迁移，goose v3）

**选型**：`github.com/pressly/goose/v3`，版本 **v3.24.0**（落地前需联网核实最新版本与维护状态）。理由：

1. 直接跑在 `database/sql` 之上——GORM 初始化得到的 `*sql.DB` 直接交给 goose，不引入独立 driver 抽象，与 `go.mod` 克制风格一致
2. v3 Provider API 对 `embed.FS` 一等支持（`goose.NewProvider` + `WithFS`），迁移文件随二进制分发，部署零外部依赖
3. 版本表 `goose_db_version` 无 dirty 标志：失败的迁移不记录版本、重跑即重试同版本，恢复路径直白，无 force 类人工解锁步骤
4. up / down 均按工具标准支持；以 library 形态内嵌使用（不用 CLI），单依赖体积小

排除 golang-migrate：source / database 双 driver 抽象（iofs + mysql）拼装更重；失败置 dirty 后必须人工 `force` 解锁恢复，运维负担更高。

**执行时机**（唯一锚点：连上 DB 之后、settings 预热之前）：

- 正常模式：bootstrap 装配顺序在 DB 之后执行一次 `migrate up`（§3.1；幂等，版本已最新时秒过、只读版本表）
- setup 两条路径：各自触发 `migrate up`（§3.15 状态机）

**已初始化判据**：迁移版本表已到最新 **且** 管理员（ID=1）存在；缺任一即视为未完成初始化。

**失败与恢复**（goose 标准行为）：

- 失败暴露：正常模式迁移失败 → 启动 fail-fast（日志含失败版本与 SQL 错误）；setup 路径 → `error.code = migration_failed`（单一码，细节进 `error.message` 与服务端日志）
- MariaDB DDL 非事务，失败可能残留半成品 DDL；该版本未写入版本表，**修复 / 回滚半成品 DDL 后重跑 `migrate up` 即重试同版本**
- 人工修复：比对版本表与实际 schema；必要时将版本表回退到上一已应用版本再重跑
- `down` 按工具标准提供（回退一版），日常升级不使用；**数据备份责任归部署方**，执行迁移前自行备份

**迁移文件与目录**：

- 位置 `server/migrations/`；命名 `NNNNNN_name.sql`（goose 规范，单文件内 `-- +goose Up` / `-- +goose Down` 注解分段；`NNNNNN` 六位递增版本号）
- 版本表 `goose_db_version`（goose 默认，不自定义）
- `migrations/embed.go`：`//go:embed *.sql` 进二进制，经 goose Provider（`WithFS`）加载
- 首版迁移：§4 全部 11 张表的 DDL（provider / user / user_profile / user_credential / user_credential_webauthn / user_thirdparty_bind / sso_client / oidc_client / oidc_refresh_token / event_log / settings），列定义以 §4 为准
- 种子数据边界：迁移只管结构——默认 settings 由启动预热补齐（§4.7），管理员 ID=1 由 setup 代码插入（§3.15），迁移 SQL 不含 INSERT

**并发**：goose 不内建跨实例锁，幂等依赖版本表的已应用记录；**升级与首启期间应单实例执行**（与 §3.15"首启应单实例"同一条部署约束）。正常模式多实例同时启动时版本已最新、迁移检查只读版本表，无竞态。

## 4. 数据模型（MariaDB）

### 4.0 结构化字段的统一约定

见接口文档 §12.0：固定 schema 用 Protobuf（`provider.ext`、`user_credential.meta`、`oidc_client.redirect_uris`），透传结构用 msgpack（`user_profile.extra`、`user_thirdparty_bind.extra`、`event_log.detail`），一律存二进制列（**短结构用 `VARBINARY`，长度不可预估的用 `MEDIUMBLOB`**），不使用 JSON 列。

落地约束：

- msgpack 字段只在应用内读写，不参与任何 SQL 条件；需要检索的信息一律提为真实列
- 存储层与传输层解耦：库里的 Protobuf / msgpack 只服务持久化，接口报文编码由 connect-go 框架按请求 `Content-Type` 决定（§1.6），换存储格式不动接口契约
- 所有字段均明文存；访问控制靠视图分离（`dto/view.go`，§3.5）
- 二进制列不做静默截断：写入前按上限校验（`VARBINARY` 用声明长度，`MEDIUMBLOB` 用 1 MiB 业务上限）。管理端写入（`provider.ext`）超限直接报错拒绝；非业务必需的旁路数据（`user_thirdparty_bind.extra`）超限整条丢弃并记 `warn`，不阻断登录 / 绑定

### 4.1 `provider` —— 外部服务统一表

结构原则：跨类型共有的属性作真实列（要用于筛选、排序、索引）；凭证、端点、存储配置、厂商长尾字段全部进 Protobuf 扩展字段，序列化后存 `ext`（定义见接口文档 §12.1）。

```sql
CREATE TABLE provider (
  id             BIGINT       PRIMARY KEY AUTO_INCREMENT,
  provider_key   VARCHAR(64)  NOT NULL COMMENT '全局唯一标识，逻辑引用使用',
  union_provider VARCHAR(64)  NOT NULL COMMENT 'Union ID 归属 Provider',
  display_name   VARCHAR(128) NOT NULL COMMENT '展示名，如“QQ”“阿里云短信”',
  category       VARCHAR(32)  NOT NULL COMMENT 'oauth|captcha|sms|email|storage|notify|union',
  type           VARCHAR(64)  NOT NULL COMMENT 'qq|wechat_mp|turnstile|aliyun_sms|s3|local|...',

  enable_signin  TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '允许用于登录',
  enable_signup  TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '允许该渠道建号；关闭则未绑定用户不能建号（登录仍返回 binding_required，信封 binding.allow_signup=false，前端置灰建号入口）',
  auto_bind      TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '按邮箱/手机号自动绑定已有账号',
  auto_bind_fields VARCHAR(128) NOT NULL DEFAULT 'email,phone',
  is_enabled     TINYINT(1)   NOT NULL DEFAULT 1,

  ui_group       VARCHAR(32)  NOT NULL DEFAULT 'social' COMMENT 'social|enterprise|dev|other',
  sort_order     INT          NOT NULL DEFAULT 0,
  icon_url       VARCHAR(512) NOT NULL DEFAULT '',

  ext            MEDIUMBLOB   COMMENT 'provider.Ext 序列化后（Protobuf，业务上限 1 MiB，写入前校验，见 §4.0）',

  remark         VARCHAR(512) NOT NULL DEFAULT '',
  created_at     DATETIME     NOT NULL,
  updated_at     DATETIME     NOT NULL,
  UNIQUE KEY uk_provider_key (provider_key),
  KEY idx_category_enabled (category, is_enabled),
  KEY idx_type (type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> `icon_url` 提到主表的原因：列表接口需要直接用，避免每次反序列化。其余展示类长尾放扩展。`icon_url` 由管理员**自行上传到任意可访问位置后手填绝对 URL**（不提供上传接口，也不做本地图标回落）；未配置时信封 `icon`（字段映射：DB `icon_url` ↔ 信封 `icon`，接口文档 §2.7.1）为空串，前端渲染通用占位图标。

读写约定（接口文档 §12.1）：`provider_key` 是唯一对外契约（字符集 `[a-z0-9_]`，创建后不可改）；敏感字段不做二次加密，前台公开接口永不返回 `ext` 中凭证字段。`ext` 用 `MEDIUMBLOB` 而非 `VARBINARY(8192)`：`cert`（支付宝公钥 PEM）单条即 2~3 KB，叠加 `user_mapping`、`metadata` 长尾键无上限，8 KB 会随机溢出；写入前按 1 MiB 上限校验，超限直接拒绝（接口文档 §5.2 走统一 `bad_request`）。

要点：

- `username` 为 `NOT NULL`：用户名是必选项（需求 §4.1.1），注册与三方免密建号都必须提交 `username`
- `password` 一行：`secret` = argon2id 哈希串（含参数与盐）；改密 = UPDATE 这一行
- `totp` 一行：`secret` = TOTP 密钥
- `webauthn` 每个凭据一行；`credential_id` 唯一
- `recovery_code` 一行（每用户至多一行）：`meta` 存 10 条**明文**恢复码（`CredentialMeta.recovery_codes`，结构见接口文档 §12.2）；格式 = 8 位 Crockford Base32 小写字符（字符集 `0-9a-z` 去掉 `i/l/o/u`），`crypto/rand` 生成，展示形如 `xxxx-xxxx`；一次性消费 = 命中即从该行删除该条并**同步写回**（不走 §5.2 延迟队列，删空即失效）；`meta` 对该 kind 语义为 NOT NULL（生成时一次写入 10 条，重生成整行覆盖，禁止写 NULL / 空数组）；**消费命中删空后允许写回空数组 `recovery_codes: []`（表示已用尽，等价该 kind 不可用）**——「禁止写 NULL / 空数组」仅约束生成 / 重生成路径，不约束消费写回路径；明文存储为既定设计，但导出 / 日志 / 审计 / 接口响应均不得回显存量明文，明细接口（接口文档 §3.5 GetMfa）只返回剩余数量与签发时间
- `mfa_setting`：每用户至多一行，行存在 = 用户已开启两步验证；CredentialMeta.`mfa_methods` 存启用因子集（GetConfig `mfaPolicy` 摘要数据源，写入端归 SetMfa）
- `epoch` 回绕规则：递增结果 **> 30000 时置 1，不回绕到 0**。`0` 是初始值，回绕到 `0` 会让回绕前签发、仍在有效期内的旧会话 / 令牌重新匹配通过（等于把全部旧令牌复活）；`1..30000` 循环下，任一令牌要重遇同一值至少需再过 30000 次凭证变更。回绕与递增同一事务写出，`al:pwdep:{uid}` 缓存同步更新

> 管理员 = 安装时创建的固定 ID 账号（`user.id = 1`，安装流程见 §3.15 / 接口文档 §13）：不加 `is_admin` 列、不设角色表，判定集中在 admin interceptor（internal/connect）与 `GET /api/admin/me`。注册链路不产生管理员。

### 4.6 事件日志（登录日志与审计日志合并）

登录日志与审计日志合并为一张 `event_log`，用 `event` 字段区分：两者结构重合，分开存会重复两套写入路径与清理策略；合并后一次批量 INSERT 即可，管理后台按 `event` 筛选即可还原两种视图。

```sql
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,

  actor_type VARCHAR(16)  NOT NULL COMMENT 'user|admin|system',
  actor_id   BIGINT       NOT NULL DEFAULT 0 COMMENT 'user=该用户 uid；admin=操作管理员 uid；system=0（见下方记录范围）',

  client_id  VARCHAR(64)  NOT NULL DEFAULT '' COMMENT 'OIDC 客户端，登录类事件填充',
  amr        VARCHAR(128) NOT NULL DEFAULT '' COMMENT '登录类事件：通过的认证方法，如 pwd,otp,mfa',

  ua         VARCHAR(512) NOT NULL DEFAULT '',
  target     VARCHAR(128) NOT NULL DEFAULT '' COMMENT '操作目标，如 provider_key',

  created_at DATETIME     NOT NULL,
  KEY idx_actor_time (actor_type, actor_id, created_at),
  KEY idx_user_time  (user_id, created_at),
  KEY idx_event_time (event, created_at),
  KEY idx_time (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

记录范围：

- 记录：成功登录（`login_success`）+ 各类敏感操作
- 不记录：登录失败（失败统计由 Redis 计数承担，见 §8.1）
- `actor_type=system` 的事件（目前只有 `oidc_authorize_no_state`，接口文档 §4.2）：`actor_id=0`、`user_id=0`，`client_id` 填本次请求的 `client_id`，`ip` / `ua` 照常记录。`actor_id` 因此带 `DEFAULT 0` 而非 `NOT NULL` 无默认值——写入方不必为系统事件编造一个用户 id，`idx_actor_time` 仍可用，筛"系统事件"直接按 `actor_type=system`（接口文档 §5.6 的 `actor_type` 过滤）

`detail` 字段（msgpack，按事件类型各异）：

| 事件 | detail 内容 |
|------|-------------|
| `login_success` | `{factor, mfa_factor, session_id, device_hint}` |
| `change_password` / `reset_password` | `{pwd_epoch}` |
| `bind_phone` / `bind_email` | `{target_masked}` |
| `enable_mfa` / `disable_mfa` | `{methods:[...]}` |
| `thirdparty_bind` / `unbind` | `{provider_key, open_id}` |
| `provider_create` / `update` | `{provider_key, changed_fields:[...]}` |
| `settings_update` | `{keys:[…], before:{…}, after:{…}}`（仅变更项；键为接口文档 §5.6 白名单键，如 `login_methods`、`gateway_tokens`）。由 `POST /api/admin/settings` 写入成功后投递，操作者为管理员（`actor_type=admin`，`actor_id` = 操作管理员 uid） |

写入策略：全部事件、以及 `user.last_login_at` 更新，投递到 §5.2 的延迟写入队列，登录主链路零同步写库。队列按 200 条或 2 秒批量 INSERT，并对同一 `user_id` 的 `last_login_at` 做同键合并。

清理：定时任务按 `eventlog_retention_days`（默认 180 天）删除超期数据。

### 5.2 延迟写入队列

所有不影响当次响应正确性的写入统一走这里，避免主链路被辅助写入拖慢。

适用写入（白名单）

| 类型 | 内容 | 合并策略 |
|------|------|----------|
| Redis | 密码失败计数清零 `DEL al:pwf / al:pwban` | 同 key 合并 |
| MariaDB | `event_log` 批量 INSERT（登录 + 审计） | 攒批 |
| MariaDB | `user.last_login_at` UPDATE | 同 user_id 合并，只保留最新时间 |
| MariaDB | WebAuthn `sign_count` UPDATE | 同 credential 合并，取最大值 |
| 对象存储 | 扫码码图删除、头像旧文件删除 | 同 key 合并 |

不适用（必须同步）：验证码 `GETDEL`、授权码 `GETDEL`、图形码 `GETDEL`、ticket 写入与读取、建会话、限流计数、恢复码消费（一次性失效，§4.2）——这些是安全或正确性依赖，不能延迟。

实现形态

```
handler → asyncqueue.Push(task)   // 非阻塞，ring buffer
                 ↓
        N 个 worker（默认 4，可配）
                 ↓
        攒批：满 200 条 或 距上次 flush 满 2 秒
                 ↓
        合并：按 key 去重，只写最终值
                 ↓
        执行：Redis pipeline / MariaDB 批量 INSERT-UPDATE
```

约束（写进实现规范）

1. 并发可控：worker 数量与攒批参数后台可配，队列总长固定（默认 8192），防止内存无界增长
2. 优雅关闭：收到 SIGTERM 先停止接收，flush 完剩余任务再退出，超时（默认 10s）后强制退出
3. 降级：队列满时，非关键项（日志、计数清零、文件删除）直接丢弃并累加 `uc_dropped_total` 计数告警；绝不因此对登录主链路返回错误
4. 可观测：队列长度、`dropped` 计数、平均 flush 耗时在管理后台"系统状态"页可见（接口文档 §5.6）

## 6. 认证模型：因子 × 步骤

### 6.1 两个正交维度

```go
// 维度一：认证因子（凭证类型）
type FactorKind string
const (
    FactorPassword   FactorKind = "password"
    FactorOTPSMS     FactorKind = "otp_sms"
    FactorOTPEmail   FactorKind = "otp_email"
    FactorWebAuthn   FactorKind = "webauthn"
    FactorTOTP       FactorKind = "totp"
    FactorRecovery   FactorKind = "recovery_code"
    FactorThirdParty FactorKind = "thirdparty"
    FactorDevice     FactorKind = "device"   // 已登录设备，内部实现，不对外暴露
)

// 用途：主因子 / 二次因子
type Usage string
const (
    UsagePrimary   Usage = "primary"
    UsageSecondary Usage = "secondary"
)

// 维度二：步骤形态（前端怎么渲染这一步）—— 取值与含义见接口文档 §1.4 的 kind 枚举，步骤序列见接口文档 §1.10
type StepKind string
const (
    StepForm      StepKind = "form"      // 渲染输入框并提交
    StepChallenge StepKind = "challenge" // 无输入，向后端要挑战数据
    StepRedirect  StepKind = "redirect"  // 浏览器跳转（第三方）
    StepExternal  StepKind = "external"  // 调宿主能力取 code（wx.login）
    StepQRCode    StepKind = "qrcode"    // 展示码图
    StepPoll      StepKind = "poll"      // 长轮询等待
)
```

### 6.2 因子 → 步骤序列表

**见接口文档 §1.10**（`method` × 主/二次因子 × StepKind 序列的唯一定义）。后端约束：

- 每个因子 `Steps()` 的返回值必须与接口文档 §1.10 对应行完全一致，否则注入快照与前端分派会漂移（单测逐因子断言，§21.2 B）
- `device` 是内部因子：不出现在注入快照，也不出现在任何对外响应
- 完整登录链：`主因子` →（可选）`二次因子` → `完成 SSO`

### 6.3 统一接口

```go
type Factor interface {
    Kind() FactorKind
    Usages() []Usage
    Steps() []StepKind

    // Start 处理 challenge 步：下发验证码 / 生成 WebAuthn options / 产出跳转 URL
    Start(ctx *FactorContext) (*StepResult, error)
    // Verify 校验提交结果，返回通过 / 失败 / 需要重试
    Verify(ctx *FactorContext) (*VerifyResult, error)
}
```

- `password` 是单步特例：`Steps() = [StepForm]`，`Start` 直接返回字段 schema，`Verify` 完成校验
- 所有因子（含 password）实现同一接口，编排层只有一份状态机

## 7. 登录流程编排

### 7.1 登录过程态 `login_token`

传递规则见接口文档 §1.8，载荷见 §11.6.2，加密见 §1.4。实现要点：

- 密钥来自配置项 `sign_key.login`；签发 / 解析 / 重签集中在 `orchestrator/state.go`，`exp` 固定 10 分钟
- 统一为响应体返回 + 前端内存变量，不使用 Cookie；第三方跳转回调时才生成，由响应体返回，不塞进 URL
- CSRF 防护（`login_token` 在 body 里，不受 `SameSite` 保护）依赖 §3.3 的 Origin 校验 + 只接受 `application/json`
- 防篡改 / 防重放由加密与 `exp` 保证；验证码、挑战数据的一次性消费由 Redis 侧保证（§10）

### 7.2 步骤引擎编排

编排规则（6 步）**见接口文档 §2.2**；注册 / 重置复用同一引擎（§7.4）。

`orchestrator/engine.go` 的实现顺序与接口文档 §2.2 一一对应，落地时补两处后端专属判定：

- 第 1 步解析失败 → `status=token_invalid/token_expired`，流程回到第一步，不返回细节
- 第 3 步不满足 → `status=step_invalid`；captcha 拦截统一走 `captcha/gate.go`（触发表来自接口文档 §2.5）

`status=mfa_required` 时返回可选的二次因子列表（含 `maskedTarget`），目标只能取自 `uid` 的已绑定资料。

### 7.3 核心场景与正确性校验点

以"邮箱验证码登录 → 触发 MFA → 改选短信 → 完成登录"为例（完整时序见接口文档 §10.2）：

| # | 请求 | 后端动作 |
|---|------|----------|
| 1 | 打开 `/sso/login`（空壳页注入） | `orchestrator/methods.go` 按 `login_methods` 过滤已启用因子；快照附带当前 captcha Provider 与 `siteKey` |
| 3 | `challenge`（otp_email） | ① 校验 captcha ② 校验冷却与日限额 ③ 邮箱存在性检查（不存在：返回 `status=user_not_found`，跳过 ④⑤⑥，§10.2） ④ 生成 6 位码 → `SET al:code:...` ⑤ 异步发信 ⑥ 签发 login_token |
| 4 | `verify`（otp_email） | ① 解 login_token 取 `tid`、`ch.target` ② Lua `GETDEL` 比对 code 与 `tid`（不匹配 → `tries+1` 回写；超 5 次不回写即作废）③ 查用户 ④ 已启用 MFA → 重签 login_token（`passed`、`uid`）⑤ 生成 `mfa.methods` |
| 6 | `challenge`（otp_sms，MFA） | ① 校验 `uid` 非 0、`passed` 非空（否则拒绝）② 校验 captcha（每次下发都要新的）③ `phone` 从 uid 的已绑定资料取，不接受请求传参 ④ 限额 + 存码（purpose=mfa）⑤ 重签 login_token |
| 7 | `verify`（otp_sms） | ① 校验 `ch.purpose=mfa` 且 `ch.target` 与码内 target 一致 ② `GETDEL` 比对 ③ 全部通过 → 建会话（1 次写）④ 投递登录日志 + `last_login_at` ⑤ 若有 `oidc` 载荷 → 生成授权码 `SET al:oidc:code:{code} EX 120`，拼 `syncCookieUrl` 与 `redirectTo` |

实现时必须逐条覆盖的校验点：

- [ ] 邮箱不存在时，返回 `status=user_not_found`，不写 `al:code`、不发信、不签发 login_token
- [ ] 步骤 4 的 `passed` 与步骤 6 的 `uid` 校验：任何一步缺失都拒绝，杜绝"直接打 MFA 接口绕过主因子"
- [ ] 步骤 6 的手机号只能来自 `uid` 的绑定资料
- [ ] 验证码绑定 `purpose` 与 `tid`：登录收到的码不能用于 MFA，A 会话的码不能用于 B 会话
- [ ] 步骤 7 成功后登录态成立，`login_token` 本身无状态，靠 10 分钟 `exp` 兜底
- [ ] MFA 阶段总时长受 `exp` 约束（10 分钟），超时回到第一步

### 7.4 注册与密码重置

端点与步骤见接口文档 §2.3、§2.4。请求 / 响应信封与登录端点完全同构，仅 `flow` 不同（`register` / `reset`）。后端复用同一套步骤引擎、验证码组件、captcha 校验与限流组件；禁止为注册 / 重置另写一套编排。

| flow | 要点 |
|------|------|
| `register` | 步骤与载荷见接口文档 §2.3；`password` 是否必填按 `login_token.tp` 判定（接口文档 §2.7.5）。用户名规则见接口文档 §2.3（此处不复述），设置后不可改。接受的 `login_token.flow` 为 `register` 与 `login`（后者即绑定中间态免密建号，不得因 flow 不匹配而拒）。建号写入在同一事务内完成；`set_password` 可跳过 `challenge` / `verify` 直达（用户名 + 密码注册入口，接口文档 §2.3） |
| `reset` | 仅当用户已设置密码且已绑定邮箱 / 手机号时可用；`challenge` 目标必须是已绑定且已验证的；`allow_password_reset=false` 时 `challenge` 与后续各 step 一律返回 `status=reset_disabled`，不发码、不校验（接口文档 §2.4）；成功后递增 `al:pwdep:{uid}`（使全部会话与刷新令牌失效），异步写审计 |

## 8. 各因子实现规范

### 8.1 密码（password）

- 单步 `form`；字段 `username` / `password` / `captcha`（条件必填）
- 校验顺序：`al:pwban` 键存在 → 直接 `status=locked` → 查 `user_credential(kind=password)` → argon2id 验证 → 失败 `INCR al:pwf:{ref}:{yyyymmdd}`（首次 `EXPIRE` 到当日 24:00）
- 失败处理：
  - `al:pwf` ≥ N1（默认 3）→ 后续请求必须带 `captcha`，缺失返回 `status=captcha_required`；校验失败 / 已使用返回 `status=captcha_invalid`
  - `al:pwf` ≥ N2（默认 6）→ `SET al:pwban:{ref} 1 EX Zs（默认 21600）`，返回 `status=locked`（`retry_after` = 剩余秒数）
  - N1 / N2 / Z 即 `pwd_fail_capture` / `pwd_fail_ban` / `pwd_ban_ttl`（键名与默认值见接口文档 §5.6），走热更新，改动只对后续请求生效（同 §9.3 口径）
  - `user_ref` = `user_id`（用户存在）或 `ip + 输入账号哈希`（用户不存在）
- 管理员解锁（接口文档 §5.4 `/users/{id}/unlock`）：清 uid 维度键，并按该用户当前手机号 / 邮箱重算 `ip + 账号哈希` 维度键一并清除（否则"账号不存在"阶段种下的封禁清不掉）
- 成功 → 投递 `DEL al:pwf:{ref}` / `DEL al:pwban:{ref}` 到延迟队列，主链路零额外写；队列满时该项可丢弃，最坏结果是依赖 TTL 自然过期，不影响正确性
- 除接口特殊标注外，账号不存在与密码错误同码：均返回 `status=invalid_credentials`，文案由 `error.message` 下发；账号被禁用单独返回 `status=user_disabled`（接口文档 §1.6）

### 8.2 一次性验证码（otp_sms / otp_email）

- 步骤 `challenge` → `form`；两个 method 共用一份实现，仅 target 类型不同
- 主因子场景：`challenge` 需传目标（phone/email）+ captcha
- MFA 场景：`challenge` 只传 captcha，目标取 `uid` 的已绑定资料（接口文档 §2.6）
- 验证码生成与校验见 §10.1
- 账号域（bind）额外校验：码内 `owner` 必须等于当前会话 `uid`，否则 `status=invalid_code`（接口文档 §3.4）
- 短信 / 邮件发送走 Provider（§15.2），发送失败不回滚已写的码，允许 60s 后重发

### 8.3 通行密钥（webauthn）

- `challenge` 通过 `challenge_data` 下发 WebAuthn 标准 **options 对象**（类型即 `PublicKeyCredentialCreationOptions`，MDN）；注册 / 创建凭据场景整体交给 `navigator.credentials.create()`，登录 / 断言场景为同族 `PublicKeyCredentialRequestOptions`，整体交给 `navigator.credentials.get()`。字段承载完整结构（`challenge`、`rp`（登录为 `rpId`）、`user`、`pubKeyCredParams`、`timeout`、`excludeCredentials`（登录为 `allowCredentials`）、`authenticatorSelection`、`attestation`、`extensions` 等），**不是任意字符串，也不是无定义 / 无约束的 map**；前端不解析字段，只整体透传给 WebAuthn API。proto 表达统一为 `google.protobuf.Struct`（理由见接口文档 §12.9）。以下约束不变：
  - challenge 由服务端生成 32 字节随机，绑定 `login_token`（存 `ch.nonce`），默认 120 秒有效，通过相应字段下发。账号域注册场景（用户中心绑定）改用独立原子 token，载荷只使用 `nonce` 与 `uid`（见本节末条）。**「可随意」仅指下发给前端的展示类字段**（`timeout`、`userVerification` 等可按实现调整）；**服务端必须校验的四项固定**：challenge 匹配（`ch.nonce`）、`rpId`、`origin`、断言签名与 `signCount` 递增（见 `verify` 条），任一不过即失败
  - `rpId` 固定为 Authloft 根域名（配置项），`origin` 服务端强校验
  - 只有 usernameless 一种模式：`allowCredentials` 恒为空 → 注册时必须创建 resident key / discoverable credential；请求中的 `username` 一律忽略
- `verify`：校验断言签名、challenge 匹配、`origin`、`rpId` hash；`signCount` 必须递增（防克隆）。验证通过不阻塞响应，把 `UPDATE user_credential_webauthn SET sign_count=?` 投递到延迟队列，按 credential 同键合并取最大值
  - `sign_count` 只在下一次登录时用于检测克隆，延迟 2 秒内落库不影响当次正确性；同一凭据被并发使用时合并后写入的是最大值，不会误判
- 既可作主因子也可作二次因子，靠 `usage` 配置区分，代码一份
- 账号域注册场景（`/api/account/webauthn`，接口文档 §3.6）无 `login_token`：`challenge` 步改而签发独立原子 token——复用 `LoginTokenPayload` 结构与加解密实现（本质上不是 `login_token`），载荷 `purpose = "webauthn"`、`uid` = 当前会话 uid、`ch.nonce` = 本次 challenge，`exp` 与挑战有效期一致（120s，随响应 `expires_in` 下发），AAD purpose 取对应场景值不与 login_token 互解；`verify` 由服务端解析校验（篡改 / 无效 → `invalid_request`，过期 → `code_expired`），前端不感知结构
- **启动期初始化失败降级（窗口期 fail-closed）**（2026-11-05 定稿，推翻早前 fail-open 口径）：`rp_id` 为 IP / 非法域名导致 `go-webauthn` 库初始化失败（RPID 校验要求 must be a domain and not an IP）时，进程**照旧不退出**、其余功能可用，进入降级窗口——置哨兵 `ErrWebauthnDegraded`（engine / thirdparty 双组装点），启动失败 **WARN 一次**（含失败原因）。窗口期内**凡需 webauthn 才能完成的操作一律拒绝**，绝不静默放行、不跳过 MFA、不改用更弱因子：
  - **登录**：主因子选 webauthn 一律拒绝；用户**唯一可用 MFA 因子为 webauthn** 时直接拒绝——统一返回 `method_disabled`，文案明示「通行密钥暂不可用，请联系管理员」语义（status 词汇表见接口文档 §1.6）
  - **通行密钥管理**：绑定 / 解绑 / 管理通行密钥在窗口期内直接拒绝（account 域 webauthn 四 RPC 当前未实装、天然 fail-closed；**实装后必须带窗口期拒绝**）
  - **可观测**：每次因窗口被拒的请求**逐次**打 ERROR/WARN，注明原因是 webauthn 不可用
  - **行为边界**：未启用 webauthn 的账号与无关功能行为不变

  安装接口的域名校验（接口文档 §13.3、§3.15）从源头避免该场景，降级为管理员手工改 config 填 IP `rp_id` 的兜底

### 8.4 动态口令（totp）与恢复码

- `totp`：单步 `form`，按 RFC 6238 校验，允许 ±1 个时间步
- `recovery_code`：单步 `form`；`user_credential(kind=recovery_code)` 一行存 10 条**明文**恢复码（8 位 Crockford Base32 小写，展示 `xxxx-xxxx`，存储 / NOT NULL / 安全边界见 §4.2），命中一个即同步删除该条并写回（不可复用），删空即失效
- 恢复码错误语义（取值限接口文档 §1.6 封闭集合，不新增 `status`）：格式非法（非 8 位 Crockford Base32，或展示形 `xxxx-xxxx` 解析失败）→ `invalid_request`；码不匹配 → `invalid_code`；无该 kind 行 / 未启用 / `meta` 为空 / 已消费尽 → `code_expired`
- 均只作二次因子

### 8.5 已登录设备（device）

- 内部因子，不对外暴露：用户已持有有效 `al_session` 时访问 `/sso/login`，直接进入"完成登录"，不再走因子
  - 无 redirectTo 时跳 account 页面
- 多域名场景下通过 `/sso/sync_cookie` 同步 Cookie 后即可实现

## 9. 人机校验（captcha）

### 9.1 建模

统一为 `category=captcha` 的 Provider，扩展字段见接口文档 §12.1（`site_key` = `client_id`，`secret` = `client_secret`，`endpoint` = 自定义校验地址）。

| type | 来源 | 后端校验 |
|------|------|----------|
| `image` | 系统自绘图形验证码（两位数加减法） | 查 `al:cap:{id}` 并删除 |
| `turnstile` | Cloudflare | 调 sitesVerify |
| `recaptcha` | Google | 调 siteverify |
| `hcaptcha` | hCaptcha | 调 siteverify |

**降级判定**（规则见接口文档 §2.5）：当前生效的 captcha Provider 无可用项（`enable=0` / 未配置 / 健康检查失败）时，取内置 `image`：`providerKey=builtin_image`、`type=image`、`siteKey=""`。降级不新增端点、不新增 `status`，取图仍走 `POST /api/sso/captcha/image`。

- `captcha` 配置对象（`providerKey` / `type` / `siteKey`）由 `captcha/gate.go` 统一生成，注入快照、`GET /api/account/config`、`captcha_required` / `captcha_invalid` 响应三处共用同一出口，每次生成时重新判定，不缓存 → 下发与拦截永远同源
- 健康检查失败只在"生成配置 / 校验凭据"时按失败处理并降级，不做后台轮询

### 9.2 自绘图形码与校验

提交格式（两类 Provider 统一，`provider_key` 必填）、自绘图形码接口与响应**见接口文档 §2.5**，本文不复制。实现要点：

- 自绘图形码：`SET al:cap:{id} {answer} EX 300`，校验时 Lua `GETDEL`（1 读 1 删）
- 第三方 token 的一次性由厂商保证，Authloft 侧零存储
- 降级（接口文档 §2.5）复用本节实现，不另写校验路径：`type=image` 时同样按 `id` + `answer` 核 `al:cap:{id}`，一次性语义与第三方 `token` 一致
- 缺失 → `status=captcha_required`（`error` 提示刷新）；校验失败 / 已使用 → `status=captcha_invalid`（语义见接口文档 §1.6）

### 9.3 触发规则（统一拦截）

**触发表见接口文档 §2.5**（唯一定义，本文不复制）。后端落地：

- `captcha/gate.go` 是唯一拦截点：所有 `challenge` 步与密码登录都经它判定；触发时由它附带响应顶层 `captcha` 配置（§9.1）
- 阈值走 `settings` 热更新，改动只对后续请求生效；键名与默认值见接口文档 §5.6（`pwd_fail_capture` / `pwd_fail_ban`）
- 降级不改触发表：降到 `image` 后仍需按本表校验，`status` 取值不变

### 9.4 CSP 源注册（provider 贡献源，接口文档 §8）

三家第三方 captcha（Turnstile / reCAPTCHA v3 / hCaptcha）由前端 adapter 动态加载厂商 JS 与 iframe，壳层基线 CSP 不足以放行（2026-11-06 定稿；参考源清单见接口文档 §8）。注册契约：

- captcha Provider 类型**注册时声明**自身所需 CSP 源：按指令分组的数据登记（`CSPSupporter` 一类可选接口，§12.1），**非按 type / 厂商名的分支判断**——`csp.go` 禁止出现 `if provider == xxx` 一类特判
- **Catalog 系「当前生效 Provider」唯一判定点**：CSP 贡献与下发配置（§9.1 `gate.go`）、拦截校验同源，热更新语义一致；未启用 / 未配置的 Provider 不贡献任何域名
- CSP 中间件只做**聚合与去重**，不做特判：同名指令按指令名聚合后单条输出（CSP 规范同一 policy 内同名指令仅首条生效、非取并集；基线源在前、支持者按装配序）；可扩展指令白名单仅 `frame-src` / `connect-src` / `style-src` / `img-src`，`script-src` 维持 `'nonce-…' 'strict-dynamic'` 不放通

## 10. 一次性验证码与限流

### 10.1 存储与消费

```
发码： SET  al:code:{target}:{purpose}  {json}  EX 300        # 1 次写
       SET  al:rl:send:{target}         1       NX EX 60      # 1 次写（冷却）
       INCR al:rl:sendday:{target}:{date}   + EXPIRE          # 1 次写
       INCR al:rl:ipday:{ip}:{date}         + EXPIRE          # 1 次写
校验： GETDEL al:code:{target}:{purpose}   （Lua 原子，1 次往返）
```

> 四个发送侧写入可用一段 Lua 合并为 1 次 Redis 往返，实现时优先采用。

归属标识（`owner`）：`al:code:{target}:{purpose}` 的值形如 `{code, owner, tries, sent_at}`。`owner` 按场景二选一，两套场景共用同一段 Lua，仅传入值语义不同：

| 场景 | `owner` | 校验时与什么比对 |
|------|---------|------------------|
| 登录 / 注册 / 重置 / MFA（有 `login_token`） | `tid` | 当前 `login_token.tid` |
| 账号域绑定 / 换绑（无 `login_token`，仅会话） | `uid` | 当前会话 `uid` |

> 语义约束：登录链路禁止用 `uid` 作归属标识（会把 A 会话的码喂给 B 会话），账号域禁止用 `tid`（无 `login_token` 可解）。

校验：Lua 脚本原子 `GETDEL`（键由请求里的 target 拼出，因此发码 target 与校验 target 天然必须一致）；比对 `code` 与 `owner`；失败则 `tries+1` 后 `SET` 回去（仅当 `tries < 5`，即尝试次数上限为 5：第 5 次错码后键作废、不再回写）。

### 10.2 未绑定目标 / 账号不存在的错误口径

- 主因子登录 `password` → `status=invalid_credentials`（与账号不存在同码，接口文档 §1.6）
- 验证码主因子 `challenge`（`otp_sms` / `otp_email`）目标未绑定任何账号 → 显式返回 `status=user_not_found`，不签发 login_token、不生成与发送验证码（实现口径见 §7.3 步骤 ③）
- 注册 `challenge` 的目标已绑定他人 → `status=target_taken`（与用户名占用同一取值，§1.6）
- 重置 `challenge` 前提不满足（目标未绑定 / 未验证）→ `status=user_not_found`
- MFA 不可能出现用户不存在 / 目标未绑定的情况（目标取 uid 绑定资料），不定义
- 账号被禁用走 `user_disabled`

### 10.3 频率限制默认值（后台可配）

> 键名与默认值以《接口文档》§5.6 为准，本表为速查。

| 项 | 默认值 |
|----|--------|
| 重发冷却（`otp_resend_interval`） | 60s |
| 单目标日限额（`otp_daily_limit_target`） | 10 次 |
| 单 IP 日限额（`otp_daily_limit_ip`） | 50 次 |
| 验证码有效期（`otp_ttl`） | 300s |
| 验证码最大尝试次数（`otp_max_attempts`） | 5 |
| 密码失败触发验证码阈值（`pwd_fail_capture`） | 3 |
| 密码失败封禁阈值（`pwd_fail_ban`） | 6 |
| 密码失败封禁时长（`pwd_ban_ttl`） | 6h（21600s） |

## 11. 会话与单点登录

### 11.1 会话令牌与校验

令牌结构见 §11.6.3，独立密钥 `sign_key.session`，带 `kid`。

会话令牌**自包含、不落盘**：校验只依赖令牌自身与 `epoch`，不查任何会话记录。**本期不支持服务端主动逐出**：登出仅清除客户端 Cookie，已签发令牌在有效期内仍然有效；架构预留逐出扩展点（后续可在校验链插入「已逐出 / 已失效 sid」检查，本期不实现、不引入相关键空间），落地前不得出现「校验时查会话记录」的路径。

- 会话 Cookie 的名称 / 属性 / 有效期以接口文档 §1.9 为准（`Secure` / `SameSite` 受 settings 键 `https_deployment` 驱动，接口文档 §1.9 / §5.6），此处不复述；实现只固定 `Path=/`、`Domain=<根域>`；**全部 Cookie 下发点（会话 Cookie、`al_login_state`、`/sso/sync_cookie` 接收端）的 `Secure` / `SameSite` 必须取自同一个 Cookie 属性构造器**，不得各自写死
- 修改密码 / 重置密码 / 管理员禁用 → 会话内 `epoch` 与 Redis 计数器 `al:pwdep:{uid}` 比对不一致即失效

校验逻辑（每请求）

1. 解 session_token（验 kid → 取密钥 → 解密，失败即未登录）
2. `exp` 校验
3. 比对 `epoch`：
   ```
   cur := localCache.Get(uid)                  // 进程内，TTL 60s
   if miss { cur = GET al:pwdep:{uid} → 缺失则回源 DB }
   if token.epoch != cur → 会话失效，清 Cookie
   ```
4. 通过 → uid/amr 直接可用（RPC / OIDC 无需再查 Redis）

### 11.2 多域名会话同步

走**跳转式同步（redirect-based）**：链路状态全部装在服务端加密的载荷里，不落 `localStorage`、不存服务端会话，也不区分登录 / 登出（接收端只管写 Cookie）。实现要点：

**发起端**（登录终点与 `GET /sso/logout` 共用同一段代码）：

1. 按 `sso_domains` 顺序生成待同步地址数组（每个元素是**完整 URL 前缀**（含 scheme 与 `host[:port]`，可含可选路径，末尾不带 `/`），由实现方展开为 `{prefix}/sso/sync_cookie`；首跳与 `remaining` 均记展开后的完整 URL，不得把原始前缀写进载荷；登录终点与登出共用同一展开逻辑），末尾追加最终跳转地址（登录为 `redirectTo`，登出为 `post_logout_redirect_uri`）
2. 取出数组第一个 URL 作为**首跳**，它不写进载荷（避免自跳循环）
3. 构造 `SyncCookiePayload`：Cookie 名 / 值 / TTL、剩余地址 `remaining`、最终地址 `final_url`、`exp`
4. 用 `sign_key.sync_payload`（`AAD purpose=sync_payload`，封装见 §11.6.1）加密载荷，拼到首跳 URL 后：`{URL}?{payload}`
5. 登录：把该 URL 作为响应字段 `syncCookieUrl` 返回，**由前端 `location.replace` 跳转**（登录接口是 JSON 响应，后端不 302）；登出：后端直接 302 到该 URL

**接收端**（`GET /sso/sync_cookie?{payload}`，每个根域各部署一份同一实现）：

1. 解密载荷；失败或 `now > exp` → 直接返回空（不带 `Location`），链路就此中断
2. **一律写入（覆盖）本域 Cookie**：`cookie_name` / `cookie_value` / `cookie_ttl`；登出场景由发起端把 `cookie_value` 置空、`cookie_ttl` 置 `"0"`，接收端按同样逻辑写入即等价于清除，**不需要知道本次是登录还是登出**
3. `remaining` 非空 → 取下一个 URL，按发起端步骤 3～4 重新生成载荷（`exp` 按剩余地址数重算）并 302 过去
4. `remaining` 为空 → 302 到 `final_url` 结束；`final_url` 不带载荷，不会再回到本端点

`exp` = 签发时刻 + `30s × 地址总数`（首跳 + `remaining` 个数 + `final_url`）。跳转本身应在数秒内完成，超时即视为链路作废，接收端不得再写 Cookie。

```protobuf
message SyncCookiePayload {
  string cookie_name        = 1;  // 会话 Cookie 名称
  string cookie_value       = 2;  // 会话 Cookie 值；登出场景为空串
  string cookie_ttl         = 3;  // 会话 Cookie 有效期；登出场景为 "0"；接收端原样透传给 Set-Cookie，不解析数值
  repeated string remaining = 4;  // 剩余未跳转的同步地址（不含本次首跳）
  string final_url          = 5;  // 最终跳转地址，不带载荷、不会再被本端点处理
  int64  exp                = 6;  // 载荷过期时间（Unix 秒）
}
```

- 该结构只服务服务端之间的跳转，**前端不解析**，故定义在本节、不进接口文档 §12（结构归属口径见接口文档 §12 前言）
- 载荷内 `cookie_value` 与会话令牌同源，虽已加密，但会随 URL 落进各域访问日志：部署侧需对该路径的 query 做脱敏（或关闭记录），并置 `Referrer-Policy: no-referrer`

### 11.3 登出

接口见接口文档 §2.9（`GET /sso/logout`）。实现要点：

- `GET /sso/logout?post_logout_redirect_uri=...`（可选 `id_token_hint`，用于校验身份并确认最终回跳；校验后即丢弃，不沿跳转链传递）
- `post_logout_redirect_uri` 需在回调地址白名单内；不在则落回默认页
- 清本域会话 Cookie → 按 §11.2 生成登出载荷（`cookie_value` 空、`cookie_ttl="0"`、`final_url=post_logout_redirect_uri`）→ 302 进入跳转链，逐域覆盖为过期 Cookie。**登出不使已签发的 session_token 失效**：令牌自包含、本期无服务端逐出（§11.1），令牌至自然到期为止有效
- 不影响业务系统已持有的 OIDC 令牌（账号中心登出只结束本站会话；业务系统持有的令牌按自身有效期到期，或由业务系统调 `POST /api/oidc/revoke` 吊销）

### 11.4 ticket 登录

- `GET /api/sso/login/ticket?ticket={ticket}&poll=…`：长轮询，单次等待上限见接口文档 §2.8
- `POST /api/sso/login/ticket {ticket_id, session?}`：`session` 缺省取 Cookie `al_session`，两者并存以 body 为准且须与 Cookie 同一 uid，否则 `invalid_request`（接口文档 §2.8）；校验会话有效 → 写入 `TicketResult`
- 存储值与常量见 §11.6.5（`TicketResult`），此处不复述
- ticket 不落库，仅 Redis；用后即销毁

### 11.5 会话续期策略

每次请求（会话校验通过后）均重签 session_token：`iat` / `exp` 刷新、`epoch` / `sid` 不变，纯计算、**无任何存储写入**；下发渠道按接口文档 §1.9（Cookie 来源 → `Set-Cookie`；Header 来源 → `X-Authloft-Token` 响应头；RPC `TokenService/DecodeSession` 的令牌来自请求体 → 响应报文 `renewed_token`，接口文档 §7.1）。在 middleware 内完成；RPC 域不走 middleware 续期，重签在 handler 的 session 校验通过后完成，`renewed_token` 是报文层字段、不写入 `SessionTokenPayload`（§11.6.3）。

### 11.6 令牌与内部载荷结构（Protobuf）

本节是 `login_token` / `session_token` / `ticket` / `al:ticket` 存储值 / `al_login_state` / 多域名同步载荷 / **OIDC 授权码载荷（`OidcCodePayload`）**的**唯一定义处**。这些结构都由服务端签发并由服务端解析，前端只把它们当作不透明串透传（判定口径见接口文档 §12 前言），故定义在本文而非《接口文档》。`.proto` 源文件仍与接口报文同批生成（`server/proto/`，§1.6）。

#### 11.6.1 通用封装

令牌共用同一封装与编解码实现（`security/token.go`）：

```
token = base64url( prefix || nonce || ciphertext || tag )

prefix     2B   [version:1][kid:1]
nonce     12B   crypto/rand
ciphertext  nB   AES-256-GCM(protobuf_payload)
tag       16B

AAD = "al/" || prefix || purpose        purpose ∈ {session, login, ticket, bind, webauthn, cookie, sync_payload, oidc_code}
```

- `version` + `kid` 进 AAD → 防降级、防跨类型串用
- `purpose` 进 AAD → 即使将来各类令牌共用一把钥匙，`login_token` 也变不成 `session_token`
- `purpose` 是**存储加密的 AAD 前缀**，取值封闭为 `{session, login, ticket, bind, webauthn, cookie, sync_payload, oidc_code}`：`bind` = 账号域绑定的一次性 token、`webauthn` = 通行密钥注册的一次性 token（接口文档 §3.4 / §3.6）、`cookie` = `al_login_state`（接口文档 §2.7.2）、`sync_payload` = 多域名同步载荷（§11.2）、`oidc_code` = OIDC 授权码值（§11.6.6，接口文档 §4.2）；`al:ticket` 存储值加密（§11.6.5）复用同一口径取 `ticket`。它与 §11.6.2 载荷内的 `challenge.purpose`（令牌内业务字段，枚举 `login/register/reset/mfa`）是**两套概念**，互不约束
- 不同场景令牌用独立密钥（`sign_key.*`，§1.4；`security/keystore.go` 按 `version+kid` 取），AAD 里的 `purpose` 是第二道保险
- 算法固定 **AES-256-GCM + 12B 随机 nonce**

#### 11.6.2 `LoginTokenPayload` —— 登录过程态（`login_token`）

加密后经响应体下发、前端存内存变量、后续在请求体顶层回传（接口文档 §1.8）。

```protobuf
message LoginTokenPayload {
  string tid      = 1;   // 会话标识，用于绑定验证码 / 日志关联
  string flow     = 2;   // login|register|reset
  string factor   = 3;   // 当前因子
  repeated string passed = 4; // 已通过因子
  int64  uid      = 5;   // pending user_id，0 = 主因子未通过
  Challenge  ch   = 6;   // nil = 无进行中的挑战
  ThirdParty tp   = 7;   // nil = 非三方流程
  Oidc       oidc = 8;   // nil = 非 OIDC 流程
  repeated string amr = 9; // 认证方法
  int64  iat = 10;
  int64  exp = 11;       // 固定 10 分钟
}

message Challenge  { string purpose = 1; string target = 2; string nonce = 3; }
message ThirdParty { string provider_key = 1; string open_id = 2; string union_id = 3;
                     string nickname = 4; string avatar_url = 5; }
message Oidc       { string client_id = 1; string redirect_uri = 2;
                     string scope = 3; string nonce = 4; string code_challenge = 5;
                     string code_challenge_method = 6; string state = 7; }
```

约束：

- `tid` 用于把验证码、图形码、日志与本次登录会话绑定；`purpose` ∈ `login` / `register` / `reset` / `mfa`
- `purpose` 枚举扩充说明：复用本结构签发的独立 token 的 purpose 值 `bind` / `webauthn` 保留于本枚举命名空间（bind = 账号域绑定，接口文档 §3.4；webauthn = 通行密钥注册，§3.6），但不属于 `login_token` 的合法取值，login 校验时见到即拒绝
- 账号域绑定场景无 `login_token`：其 token 只是复用本结构（含加解密实现）签发的另一种 token，并非 `login_token`，不走本节 login_token 的生命周期约定（该 token 的取值与用途见接口文档 §3.4 / 本文 §12.6），故此处 `purpose` 不含 `bind`；该 token 复用 §11.6.1 加解密实现时 AAD purpose 取对应场景值（`bind` / `webauthn`），不与 `login_token` 互解
- `tp` 只存精简三方身份（去掉 `Raw`），三方原始资料落 `user_thirdparty_bind.extra`；每次三方成功都覆盖 `tp`，保证"仅最后一次可绑定"
- `oidc` 载荷来自 `/auth/authorize` 的原始参数，是登录成功后生成授权码的唯一来源；三方跳转场景的落盘与回传见接口文档 §2.7.2
- 前端**不解析**其内容，只做"收到就替换、请求就带上"

#### 11.6.3 `SessionTokenPayload` —— 会话令牌（`session_token` / `al_session`）

```protobuf
message SessionTokenPayload {
  int64  id        = 1;  // UID
  int64  epoch     = 2;  // 用户安全版本号（al:pwdep:{uid}）
  repeated string amr = 3;  // ["pwd","otp"]
  string sid       = 4;  // Session ID
  int64  iat       = 5;
  int64  exp       = 6;
}
```

- `epoch` 与 `al:pwdep:{uid}` 比对，不一致即会话失效；改密 / 重置 / 管理员禁用递增该计数（登出不递增）；递增到 > 30000 时回绕为 1、不回到 0（§4.2）
- 浏览器写 Cookie `al_session`（接口文档 §1.9）；小程序 / 宿主环境由响应体下发，用 Header `X-Authloft-Token` 回传（接口文档 §1.2）

#### 11.6.4 `TicketPayload` —— 扫码票据（`ticket`）

```protobuf
message TicketPayload {
  string ticket_id = 1;   // 全链路统一名：响应字段 / Redis 键 / 轮询回传
  string provider_key = 2;
  string scene = 3; // login（默认）| bind，决定小程序端写什么、PC 端走哪条轮询（接口文档 §3.7.1）
  int64  iat = 4;
  int64  exp = 5;   // 默认 600s
}
```

- `ticket` 加密串是 **PC 端轮询通道**的状态载体：请求携带完整加密串，过期由服务端解 ticket 判断
- 小程序端提交通道（`SsoService/LoginOauth`）的 wire 仅携带 `ticket_id`（微信码图 scene 上限 32 字符仅容 `ticket_id`，小程序端物理拿不到完整加密串）→ CreateQrcode 时同步写快照键 `al:ticket:payload:{ticket_id}`（1 次写，TTL = `exp` − `iat`，默认 600s；§5.1），服务端据此校验 scene / expiry / provider_key，快照缺失即不存在 / 已过期
- `ticket_id` 控制在 **24 字符以内**（微信 `scene` 上限 32）——本值与 TTL **在本节唯一定义**，其余章节一律引用 §11.6.4
- 授权结果写 `al:ticket:{ticket_id}`，TTL 与 `ticket.exp`（默认 600s）对齐，轮询命中后 `GETDEL`

#### 11.6.5 `TicketResult` —— `al:ticket:{ticket_id}` 的存储值

键为 String 类型，值为**整值加密**后的 `TicketResult` JSON（复用 §11.6.1 的封装实现，`purpose=ticket`），Redis 内不留明文；读取方 `GETDEL` 后解密。取值含第三方原始资料（`thirdparty_identity.raw`），故整值加密。

```jsonc
{
  "v": 1,                       // 结构版本，读取方遇未知版本按失败处理
  "scene": "login",             // login | bind，取自 TicketPayload.scene，不由客户端指定
  "status": "success",          // scanned | success | failed（映射到轮询的 ticket.status，见接口文档 §1.6）
  "provider_key": "wechat_mp_scan",
  "channel": "qrcode",          // 写入通道，当前仅 qrcode
  "created_at": 1761800000,
  "expires_at": 1761800600,     // 与 ticket.exp 一致
  "consumed": false,            // false = 就绪待消费；消费方 GETDEL 原子取走即视为已消费
  "login_result": {             // 仅 scene=login
    "uid": 10086,               // 命中的本地账号；未绑定为 0
    "binding_required": false   // true 时轮询方用 thirdparty_identity 签发 login_token 并返回 binding_required 信封
  },
  "thirdparty_identity": {      // login（binding_required=true 时）与 bind 共用
    "open_id": "oX…",
    "union_id": "uN…",          // 无则空串
    "nickname": "微信用户",
    "avatar_url": "https://…",
    "raw": { }                  // 第三方原始资料，绑定场景落 user_thirdparty_bind.extra
  }
}
```

- 写入方：小程序端 `POST /api/sso/login/oauth`（带 `ticket_id`；`stage=scanned` 写 `status=scanned` 的空结果，`stage=complete` 整体覆盖为 `status=success` / `failed`，接口文档 §2.7.4）、已登录设备 `POST /api/sso/login/ticket`（接口文档 §2.8，直接写 `status=success`）
- 读取方：`GET /api/sso/login/ticket`（`scene=login`）与 `GET /api/account/thirdparty/ticket`（`scene=bind`）；`scene` 不匹配的轮询一律拒绝
- **一次性消费**：结果写入时 `consumed=false`；读取方以 `GETDEL` 原子取走并删除键，等价于置 `consumed=true`，无需二次写。同一 ticket 只有一个读取方能取到结果，其余轮询因键不存在得到 `expired`
- 除 `thirdparty_identity` 外不含任何凭证 / 令牌；`login_result` 只为轮询方"建会话或签 `login_token`"提供最小输入，不回传登录流程信封本身

#### 11.6.6 `OidcCodePayload` —— OIDC 授权码载荷（`al:oidc:code:{code}`）

授权码对客户端是不透明串，服务端解密后的载荷如下（复用 §11.6.1 加解密，AAD `purpose=oidc_code`）：

```protobuf
message OidcCodePayload {
  string client_id              = 1;  // 签发该码的客户端 ID
  string redirect_uri           = 2;  // 授权请求原始 redirect_uri
  int64  uid                    = 3;  // 授权通过的用户 ID
  string scope                  = 4;  // 生效 scope（缺省 openid profile email）
  string nonce                  = 5;  // 授权请求原始 nonce，写入 ID Token
  string code_challenge         = 6;  // PKCE，未启用时为空串
  string code_challenge_method  = 7;  // 仅 S256，未启用时为空串
  repeated string amr           = 8;  // 授权时实际通过的认证方法
  int64  auth_time              = 9;  // 认证完成时间（Unix 秒）
  int64  iat                    = 10; // 授权码签发时间（Unix 秒）
  int64  exp                    = 11; // 过期时间 = iat + 120s，与 Redis TTL 一致
}
```

- 唯一定义处为本节：接口文档 §4.2 只引用字段清单，字段语义以本节为准
- `client_id` / `redirect_uri` 由 `POST /api/oidc/token` 解出后与请求参数比对（不一致拒绝）；`code_challenge` / `code_challenge_method` 供 PKCE `S256` 校验（§14.2 步骤 6）
- `state` / `prompt` **不入载荷**：`state` 仅在授权跳转时原样回传，`prompt` 只影响授权端点分支
- `amr` 供 ID Token 的 `amr` claim（接口文档 §4.7）；`auth_time` 是认证事实时间，与 `iat`（授权码签发时间）区分
- `.proto` 归属 `server/proto/token/`（包名 `token`），与 `LoginTokenPayload` 等同批由 `buf generate` 生成（§1.6），属存储载荷、不受 `buf lint` 整型规则约束

### 12.4 跳转场景的状态传递

> 第三方跳转登录仅可用于首次登录，不可用于登录后的 MFA 验证；已登录用户「绑定已有账号」复用同一套跳转机制，但 `state` 前缀为 `b`（§12.6）

```
GET /api/sso/authorize?provider={provider_key}&scene=login|bind
  → 后端生成带前缀的随机 state（l = 登录，b = 绑定），写入 `al_login_state` Cookie（服务端加密）
  → 接口返回 authorize_url，前端跳转（不做后端 302）
```

> **该接口只收 `provider` 与 `scene` 两个参数**（接口文档 §2.7.2）。OIDC 上下文（`client_id`/`scope`/`nonce`/`code_challenge`/`code_challenge_method` 等，来自 `/auth/authorize`）**不带进本接口**：由前端在跳转前落 `localStorage`，回调后随 `POST /api/sso/login/oauth` 的 body `oidc` 字段回传（见下方实现要点与接口文档 §2.7.4）。后端拿到 OIDC 上下文的时机是 `POST /api/sso/login/oauth` 写入 `login_token.oidc` 之后——后续 MFA 续走 `/api/sso/login/default`（沿用登录流程信封）时它已在 `login_token` 内，登录终点据此生成授权码。

`al_login_state` Cookie 的字段、属性、`state` 前缀表（`l` / `b`）与 OIDC 上下文的落盘回传约定**见接口文档 §2.7.2**。实现要点：

- Cookie 只含 `state`（带前缀）、`b` 场景的 `uid`、服务端加密（`AAD purpose=cookie`，内嵌 10 分钟过期兜底）；不含 scene、不含 OIDC 上下文
- 属性 `HttpOnly` / `SameSite=Lax` 恒定、会话级（不设 `Max-Age`）；`Secure` 受 settings 键 `https_deployment` 驱动（接口文档 §1.9 驱动口径，同一构造器，§11.1）；回调校验通过或失败后立即删除，重新签发即覆盖
- 加密方式见 §11.6.1（使用密钥 `sign_key.cookie`）
- OIDC 上下文的流向（接口文档 §2.7.2）：`/auth/authorize` 未登录跳登录页时注入 `__AUTHLOFT_INIT__.oidc`（接口文档 §4.2、§8）→ 前端在 `location.replace` 跳第三方之前把它落 `localStorage`（键 `al_oidc_ctx`）→ 回调后读出，随 `POST /api/sso/login/oauth` 的 body `oidc` 字段回传 → 服务端写入 `login_token.oidc`，读完即清（登录端只允许落盘 `oidc` 一类数据，不含任何凭证；多域名同步的链路状态全部装在载荷里，不落盘）；`nonce` / PKCE 校验不在三方登录链路，仍在 OIDC 侧承载——授权码以 `login_token.oidc` 为唯一来源签发（§14.2 步骤 5），`code_verifier` 校验在 `POST /api/oidc/token`（§14.2 步骤 6）

回调：

- 页面 `GET /sso/oauth/callback/{provider_key}?code=...&state=...` 不做任何业务逻辑，由前端把 `location.search` 原样 POST 出去，按 `state` 首字母分派：`l` → `/api/sso/login/oauth`，`b` → `/api/account/thirdparty/oauth`（接口文档 §2.7.3）
- 后端：校验 `al_login_state` 与 `state` 是否一致（不一致 → `status=state_mismatch` 并清 Cookie）→ Exchange / FetchUser → 查 `user_thirdparty_bind`
- 登录场景：无需 MFA 则直接建会话、设 `al_session` Cookie；若有 MFA，则创建 `login_token`（body `oidc` 若有已写入其中）并沿用登录流程信封，后续流程与普通登录相同
- 绑定场景：走 §12.6

### 12.5 绑定中间态

三方身份解析成功后、无绑定记录时：

1. 重签 login_token，载荷写入精简三方身份 `tp`（去掉 `Raw`，只留 pk / openid / unionid / nickname / avatar），返回 `status=binding_required`（信封 `binding.allow_signup` 由该 Provider 的 `enable_signup` 列映射而来，字段映射见接口文档 §2.7.5）
   > `Raw` 不进载荷（体积与每请求传输开销约束）：走 Cookie 的回调场景上限 2KB，纯内存场景上限 4KB。绑定完成时以本次请求内的原始资料为准落 `extra`；走中间态时 `extra` 为空可接受（昵称头像已在 `tp` 中）
2. 前端只渲染两个选项，契约**见接口文档 §2.7.5**；不提供"绑定已有账号"分支，由用户先正常登录、再从安全中心发起绑定（§12.6，`state` 前缀 `b`）
3. 选「创建新账号」→ 校验该 Provider 的 `enable_signup=1`（否则拒绝）→ 走 `POST /api/sso/register` 的 `set_password` 步，仅提交 `username`（`login_token.tp` 非空即免密，服务端忽略 `password`）→ 写绑定 → 完成 SSO
   > 该 `login_token` 的 `flow` 仍是 `login`（由登录流程进入），`POST /api/sso/register` 必须接受 `flow=login`（接口文档 §2.7.5）
4. 选「退出并使用其他账号登录」→ 前端清空 `login_token` 并跳 `/sso/login`，不发请求，服务端无状态可清理

自动绑定：`auto_bind=1` 时，按 `auto_bind_fields`（默认 `email,phone`）匹配已有用户并直接绑定，跳过绑定页。默认关闭——开启后存在账号接管风险（第三方返回的邮箱若未验证）。

### 12.6 绑定已有账号（`scene=bind`）

已登录用户从安全中心把第三方身份绑到当前账号（接口契约与两通道时序**见接口文档 §3.7.1**）。支持两个通道，共用同一个 `BindToCurrentUser` 内核：

| 通道 | 载体 | 请求链路 |
|------|------|----------|
| `redirect` | `al_login_state` Cookie + `state` 前缀 `b`（§12.4） | `GET /api/sso/authorize?provider={key}&scene=bind` → 第三方 → `GET /sso/oauth/callback/{key}` → `POST /api/account/thirdparty/oauth` |
| `qrcode`（§13.2b） | `TicketPayload.scene=bind` | `POST /api/sso/qrcode {scene:"bind"}` → 小程序扫码 → `POST /api/sso/login/oauth`（写 ticket）→ `GET /api/account/thirdparty/ticket`（轮询完成绑定） |

`BindToCurrentUser(ctx, uid, identity)`，两个通道共用（`service/account/thirdparty.go`）：

1. 校验载体并取出 `uid`：
   - redirect：解 `al_login_state` Cookie，校验 `state` 一致且前缀为 `b`（前缀不符 → `invalid_request`）；Cookie 中记录的 uid 与当前会话 uid 比对，不一致 → `invalid_request`（防"发起绑定的是 A、回调时会话已换成 B"的串号）
   - qrcode：轮询接口自带当前会话 uid（无需载体校验，ticket 的 `scene` 已在拉码时确定）
2. 校验 Provider：`is_enabled=1` 且 `enable_signin=1`，否则 `provider_disabled`
3. 取 `ExternalIdentity`：redirect 通道现算（`Exchange` / `FetchUser`）；qrcode 通道从 `al:ticket:{ticket_id}` 取出（小程序端已解析并写入）
4. 查 `user_thirdparty_bind`（`provider_key` + `open_id`）：
   - 已绑当前 uid → 幂等成功（`status=success`）
   - 已绑其他 uid → `status=target_taken`（接口文档 §3.7.1）
   - 未绑定 → 写入绑定行（含 Union 联动，§12.7）；`extra` 落 `Raw`
5. 投递 `thirdparty_bind` 事件到延迟队列（主链路零同步写库）
6. 返回 `status:"success"` + `provider_key` / `display_name`（接口文档 §1.0 信封）；不签发 `login_token`、不 Set-Cookie、不重建会话

约束：

- 支持 `redirect` 与 `qrcode` 两个通道；`api` 通道不用于绑定（宿主内直接完成登录，无"已登录"前提）
- 绑定不触发 MFA：用户已持有有效会话，主因子与二次因子都已通过
- 绑定不检查 `enable_signup`（那是对"建号"的约束），只检查 `enable_signin`
- 写绑定后无需失效 Provider 缓存（绑定关系不在 Provider 缓存内）
- 小程序端（qrcode）只写 ticket，绝不写绑定关系：绑定只能由持有会话的一端发起（§13.2b）

### 12.7 Union ID 归并（最终口径）

> 数据库表 `user_thirdparty_bind` **不设独立的联合身份列，也不建对应联合索引**。Union 归并由**额外一行 Union Provider 绑定记录**承担，该行 `open_id` 即 unionid 值（§4.3）。载荷（`login_token.tp` / `thirdparty_identity`）**仍保留 `union_id` 字段**，其值来源为 Union 行的 `open_id`；DB 列与载荷字段是两回事。

- Provider 表以 `union_provider` 列把普通 Provider 关联到 Union Provider（`category=union`，§4.1）；Union Provider 是虚拟 Provider，仅用于归并，不直连任何外部渠道
- 普通 Provider 的绑定行只存渠道 `open_id`（openid），**不存 unionid**
- Union 行的 `open_id` 即 unionid；`uk_provider_openid (provider_key, open_id)` 保证同一 unionid 全局只归并到一个账号
- 写入时机：首次登录 / 绑定写入普通行时，若该 Provider 关联了 Union Provider 且适配器返回 unionid，则同事务追加写 `Union Provider + unionid` 行（即 Union 行的 `open_id=unionid`）
- 登录命中：普通 Provider 按 `(provider_key, open_id)` 查绑定；Union 行**不能单独登录**（Union Provider 无登录入口、不出现在 `available`，接口文档 §3.7）
- Union 行**不计入已绑定数**、**不能单独解绑**（包含解绑判定与前端置灰口径，接口文档 §3.7）
- 解绑普通 Provider：删除该普通行；若该用户已无任何非 Union 绑定行，则连带删除对应 Union 行（否则保留，供其他关联 Provider 继续归并）

例：

- 创建 Union Provider：`wechat_union`
- 创建小程序 `wechat_mp_1` 和 `wechat_mp_2`，并把两者的 `union_provider` 指向 `wechat_union`
- 用户在 `wechat_mp_1` 登录后，适配器返回 openid 与 unionid
- `user_thirdparty_bind` 表写两行：`wechat_mp_1 + openid`（普通行）与 `wechat_union + unionid`（Union 行，其 `open_id` 就是 unionid）
- 后续用户从 `wechat_mp_2` 登录：openid 不同但 unionid 相同 → 命中 `wechat_union + unionid` 行，归并到同一账号
- 解除任一普通 Provider 时按上面的连带规则处理 Union 行；`wechat_union` 无单独登录入口与解绑入口

## 13. 微信小程序

### 13.0 AppID / AppSecret 来源（唯一口径）

> 微信 AppID 来自**已启用的 mp provider 实例**，不是启动配置文件（§3.2）的静态配置字段。启动配置文件与其环境变量覆盖表在本文档中**没有**任何 `wechat` / `app_id` 项，也不得新增。

- **载体**：`provider` 表（§4.1）中 `category=oauth`、`type ∈ {wechat_mp, wechat_mp_scan}`、`is_enabled=1` 的实例；小程序 AppID = `provider.Ext.app_id`（类型 `string`，接口文档 §12.1；管理后台表单标注「小程序 AppID」，接口文档 §5.3），AppSecret = `provider.Ext.client_secret`（明文存 `ext`，公开接口永不返回，§12.3）。
- **注册路径**：适配器在 `internal/provider/oauth/wechat_mp/`、`internal/provider/oauth/wechat_mp_scan/` 包内 `init()` 自注册（§12.2、§15.3）；provider 记录由 `AdminService/CreateProvider` / `UpdateProvider` 写入（接口文档 §5.2），`provider_key` 是稳定引用。
- **取值时机**：**装配期**按 `provider_key` 从 provider 缓存（§15.3：本地 LRU + singleflight，TTL 60s，`al:prov:ver` 版本失效 + `al:prov:chg` 订阅）取记录，经 `NewAdapter(provider)` 构造适配器实例；**运行期**一律从该实例取 `app_id` / `client_secret`，不每请求回读 YAML，也不写入 `settings`。
- **优先级**：① 显式 provider 配置（`Ext.app_id` / `Ext.client_secret`）＞ ② 无环境变量、无静态默认值。二者皆空 → 该 provider 视为未配置，登录、拉码、Referer 校验按失败处理，不回落到其他 provider 或全局默认值。
- **Referer 白名单**：`internal/middleware/origin.go`（§3.3、接口文档 §1.1）的 `servicewechat.com/{appid}` 白名单 = 上述所有已启用 provider 中 `Ext.app_id` 非空值的集合，由装配层注入 provider 查询函数并随 provider 变更热更新；**不是** config 字段，也不在启动时生成一次性快照。
- **SDK 选型**：调用 `code2session` / `GetwxacodeUnlimit` 的微信服务端 SDK 定为 `github.com/medivhzhan/weapp/v3` **v3.8.4**（module path 沿用旧名、仓库现名 `royalrick/weapp`，Apache-2.0；选型理由、风险与备选见 §1.5 第三方库，实现卡据此版本 pin 进 `server/go.mod`）；本节只锁定 AppID 的**来源（provider 实例）、类型（`string`）、字段（`Ext.app_id`）与取值时机**，不锁定调用方式。唯一可引用该 SDK 的包是 `internal/provider/oauth/wechat_mp*`，service / orchestrator 不暴露其类型（可替换性同 §1.5）。

### 13.1 接口方式（channel=api）

- `POST /api/sso/login/oauth {provider_key, code, ticket_id?}`
- `code` → `code2session`（AppID / AppSecret 见 §13.0）→ `ExternalIdentity`
- 若带 `ticket_id`（扫码场景）→ 走 §13.2；否则作为独立登录，直接完成 SSO。小程序端的交互由小程序自行实现，Authloft 前端不承载
- 同样受 `enable_signin` / `enable_signup` / 绑定中间态 / MFA 约束
- 区别：小程序端 `session_token` 直接作为接口返回，不写 Cookie（接口文档 §1.2）

### 13.2 扫码方式（channel=qrcode）

接口与时序**见接口文档 §2.8、§10.6**；`TicketPayload` 见 §11.6.4。实现要点：

- `ticket` 用 `sign_key.ticket` 加密；PC 端轮询（请求带完整加密串）由服务端解 ticket 判断过期；小程序端提交仅携带 `ticket_id`，服务端取 `al:ticket:payload:{ticket_id}` 快照校验（§11.6.4、§5.1）
- 拉码：`ticket_id` 长度上限见 §11.6.4 → `GetwxacodeUnlimit` → JPEG 有损压缩（75%）→ `Storage.Put`（码图始终走中转模式，与 `upload_mode` 无关）
- 状态机 `pending → scanned → success / failed`，另有终态 `expired`（分层与语义见接口文档 §1.6）：`scanned` 由小程序端 `POST /api/sso/login/oauth` 的 `stage=scanned` 写入（1 次写、幂等、不覆盖已存在的 `success`），`stage=complete` 整体覆盖为 `success` / `failed`（接口文档 §2.7.4）；轮询未命中且未过期 → `pending`，已过期 → `expired`；`failed` 时结论在信封 `status`。轮询响应的顶层 `status` 表达本次轮询结论（`pending` / `scanned` / `expired` / `success` / 失败类），与 `ticket.status` 同步取值，`success` 仅在结果就绪时出现（接口文档 §1.6）
- 每次拉码都要一次 captcha（触发规则见接口文档 §2.5）
- Authloft 不负责小程序端实现，只提供码图生成、解 code、状态读写接口；前端工程里不放置任何小程序宿主桥接组件
- 小程序端无 `Origin`，服务端校验 `Referer`（`servicewechat.com/{appid}` 白名单，来源见 §13.0；接口文档 §1.1）
- MFA × 扫码：用户已启用 MFA 时，小程序端收 `mfa_required` 信封、不写 ticket，PC 端轮询至 `expired` 终态（唯一定义见接口文档 §2.8）

### 13.2b 扫码绑定（scene=bind）

登录与绑定共用拉码接口与小程序端提交接口，靠 `TicketPayload.scene` 分派（接口文档 §3.7.1 B）：

| 环节 | `scene=login` | `scene=bind` |
|------|---------------|--------------|
| 拉码 `POST /api/sso/qrcode` | 无需会话 | 需会话（否则 401）；`scene` 写入 ticket |
| 小程序端 `POST /api/sso/login/oauth` | 写 `al:ticket` = `TicketResult{login_result}` | 写 `al:ticket` = `TicketResult{thirdparty_identity}`（含 `raw`，绑定要落 `extra`）；不建会话、不查绑定、不写绑定关系 |
| PC 端轮询 | `GET /api/sso/login/ticket` → 走登录逻辑 | `GET /api/account/thirdparty/ticket` → 走 `BindToCurrentUser`（§12.6） |

服务端要点：

- 小程序端提交仅携带 `ticket_id`（无加密串可解）：服务端取 `al:ticket:payload:{ticket_id}` 快照（§11.6.4）校验 `scene` / expiry / `provider_key` 再决定写什么；`scene` 由加密保护，客户端不可篡改
- 绑定判定一律推迟到 PC 端轮询：小程序端没有 PC 端会话，无法也不应代做绑定
- PC 端轮询命中后：`GETDEL al:ticket:{ticket_id}` → 用当前会话 uid 执行 §12.6 的 `BindToCurrentUser`，两条通道共用同一函数
- 绑定场景同样支持 `scanned` 中间态（由 `stage=scanned` 写入，接口文档 §2.7.4，`scene=bind`）；`expired` 由服务端解 ticket 判断（与登录一致）
- 码图删除（`qrcode_auto_delete`）逻辑与 scene 无关，沿用 §13.3

### 13.3 码图自动删除

由该 auth provider 的扩展字段 `qrcode_auto_delete` 控制，默认关闭。

- 开启后：PC 端完成 SSO 时，服务端用同一个 `storage_path` 模板 + `ticket_id` 重算出 object key（无需任何额外存储），把删除任务投递到延迟写入队列，由后台 worker 调用 `Storage.Delete`
- 删除失败不影响已完成的登录；失败可重试 N 次后丢弃并告警
- 关闭时：码图保留在对象存储，靠不可猜测路径 + ticket 的短有效期（§11.6.4）保证安全

## 14. OIDC

### 14.1 端点

见接口文档 §4.1。实现分布：`oidc/authorize.go`（授权）、`oidc/token.go`（令牌）、`oidc/jwt.go` + `jwks.go`（签发与密钥集）、`oidc/revoke.go`（吊销）、`handler/oidc.go`（路由与 well-known）。

- **issuer 唯一口径**：`iss` 固定取 `authloft.root`（§3.2 `authloft.root` 去掉末尾 `/`）；`/.well-known/openid-configuration` 的 `issuer` 字段与 JWT 的 `iss` 必须逐字相同。**不设独立 issuer 配置项**，discovery 不另算。`root` 携带 scheme：`authloft.root` 为 `http://`（§3.2 约定 7）时 `iss` 同为 `http://…`，**issuer 不受 settings 键 `https_deployment` 影响**。
- **JWKS 唯一来源**：`/.well-known/jwks.json` 由 `oidc/jwks.go` 从 `config.oidc.jwt_keys` 派生，发布列表内**全部**密钥的公钥（`kty=RSA`、`kid`、`n` / `e`、`alg=RS256`、`use=sig`）；私钥不出现在任何响应与日志中（§3.2 约定 6）。

### 14.2 授权流程

1. `/auth/authorize` 校验 `client_id`（存在且启用）、`redirect_uri`（白名单，支持 `*` 通配，整段匹配防子域名陷阱）、`scope`；`state` 可选（推荐传）：存在则原样回传，缺失不报错、不做 CSRF 比对、记一条审计事件 `oidc_authorize_no_state`
2. 参数错误：`client_id` / `redirect_uri` 非法 → HTTP 400，Go 直接渲染错误页，**不跳转**；`redirect_uri` 校验通过后 `scope` 含未支持值 → 302 回 `redirect_uri?error=invalid_scope&state=...`
3. 有有效会话 → 调注入的 `orchestrator.OIDCCodeIssuer` 实例方法（`oidc.CodeIssuer` 实现，`Issue` 与 `IssueCode` 同义）签发授权码：`SET al:oidc:code:{code} <密文> EX 120`（1 次写；值 = §11.6.6 `OidcCodePayload` 按 §11.6.1 加密后的不透明串，AAD `purpose=oidc_code`）→ 302 到 `redirect_uri?code=...&state=...`，不渲染页面、不经过前端；`prompt=login` 忽略，`prompt=none` 且无会话 → 302 回 `redirect_uri?error=login_required&state=...`
4. 无会话 → 直接渲染登录空壳页（URL 保持 `/auth/authorize`），OIDC 原始参数注入 `__AUTHLOFT_INIT__.oidc`（`handler/page.go`）→ 前端首次请求（尚无 `login_token`）以 body 顶层 `oidc` 回传 → 服务端写入 `login_token.oidc`
5. 登录成功（含 MFA）→ `terminal.go` 在同一请求上下文调同一注入的 `OIDCCodeIssuer` 生成授权码（同键同 TTL，值 = §11.6.6 `OidcCodePayload` 加密串，字段清单见接口文档 §4.2）→ 信封 `redirectTo = redirect_uri?code=...&state=...`
6. `POST /api/oidc/token`：`GETDEL al:oidc:code:{code}` → 校验 `client_id`、`code_verifier`（PKCE）、`redirect_uri` → 签发 ID Token / Access Token / Refresh Token
7. 刷新令牌：校验库中记录未吊销未过期 → 签发新 Access Token（Refresh Token 轮换可选）

> 两条路径共用同一注入的 `OIDCCodeIssuer`（`oidc.CodeIssuer` 能力），不得各写一份生成逻辑。本期无同意页（consent），首方 SSO 下授权即视为同意，`scope` 直接生效。

### 14.3 令牌

令牌形态 / 有效期 / 存储**见接口文档 §4.7**，本文不复制。实现要点：

- ID Token / Access Token：RS256 签发（`oidc/jwt.go`），密钥集与轮换在 `oidc/jwks.go`；Access Token 含 `epoch` 供业务方自校验
- 签名密钥：取 `config.oidc.jwt_keys` **首项**，JWT header 固定 `alg=RS256`、`kid` = 首项 `kid`；`iss` = `authloft.root`（§14.1，与 discovery 逐字一致）
- 验签密钥集：启动期一次性解析 `config.oidc.jwt_keys`（bootstrap 阶段、router 之前），**首项签发、全列表发布**；验签接受列表内任一 `kid`，未知 `kid` 直接失败
- 轮换：只改 YAML 并重启；旧密钥至少保留「实际最大 Access Token TTL + `5min` 时钟偏移」（默认 `3600s`，客户端 `access_token_ttl` 可更大，§4.5 / 接口文档 §4.7），建议 24h，窗口内 JWKS 同时含新旧公钥，超窗后方可从列表删除
- 失败策略：`oidc.jwt_keys` 缺失 / 非法 → 启动 fail-fast 退出（§3.2 约定 6）；**不生成临时密钥、不回退对称算法、不接受 RS256 之外的签名算法**
- Refresh Token：opaque，sha256 后落 `oidc_refresh_token`；刷新时校验未吊销未过期，轮换可选
- Authorization Code：`SET al:oidc:code:{code} EX 120`，`GETDEL` 一次性消费
- 修改密码 → 递增 `al:pwdep:{uid}`，令牌校验时比对 epoch；同时批量标记该用户 refresh token 为 revoked
- 业务系统登出 → 调吊销端点：仅影响对应令牌，不影响 SSO 会话
- `grant_type` 不按客户端限制：固定支持 `authorization_code` / `refresh_token`，其他取值返回 `unsupported_grant_type`（接口文档 §4.3）

### 14.4 Claims 来源映射

Claim 的语义与取值范围**见接口文档 §4.5**，本表只定义取值来源：

| Claim | 来源 |
|-------|------|
| `sub` | `user.id` |
| `name` | `user.nickname` |
| `email` / `email_verified` | `user.email` / `user.email_verified` |
| `phone_number` / `phone_number_verified` | `user.phone` / `user.phone_verified` |
| `picture` | `user.avatar_url` |
| `amr` | 登录链路中实际通过的因子 |

Authloft 格式的 `GET /api/oidc/get_user_info` 返回接口文档 §3.1 的用户信息结构，与 `/api/account/profile`、`/api/rpc/account/{uid}/profile` 共用同一结构。

`phone_number` / `email` 的呈现遵循接口文档 §3.1 掩码矩阵（默认掩码）。

## 15. 外部服务 Provider

### 15.1 存储 Provider（category=storage）

```go
type Storage interface {
    Put(ctx context.Context, key string, body []byte, contentType string) (url string, err error)
    Get(ctx context.Context, key string) ([]byte, error)
    Delete(ctx context.Context, key string) error
    URL(key string) string   // 拼接 domain / CDN

    // PresignPut 直传模式：签发一个有时效的 PUT URL，前端据此直传对象存储
    PresignPut(ctx context.Context, key string, contentType string, size int64) (uploadURL string, headers map[string]string, err error)
}
```

两个实现：

| type | 覆盖 | 说明 |
|------|------|------|
| `s3` | MinIO、腾讯云 COS、阿里云 OSS、七牛、AWS S3 | 均兼容 S3 协议，一个 Adapter 覆盖；`endpoint` + `path_style` 区分 |
| `local` | 本地磁盘 | 写入本地目录，由 Nginx 静态分发。不支持直传模式（无预签名能力），配置为 `direct` 时自动回退 `proxy` |

上传两种模式（`proxy` / `direct`）的流程与适用场景**以接口文档 §10.8 为唯一定义**（接口契约见其 §3.2），本节只列存储 Provider 侧实现要点；按 Provider 扩展字段 `upload_mode` 选择，同一个 bucket 可分别配置。

后端要点：

- `presign`：校验登录态、MIME 在 `allowed_types` 内、size ≤ `max_size`；生成 object key（服务端决定，不接受前端传路径）；签发 PUT 预签名 URL（TTL = `presign_ttl`）
- `commit`：仅记录"该 key 已上传"，不重新下载校验（避免多一次对象存储读）；随后可异步做一次 HEAD 校验大小与 MIME
- 直传模式必须在对象存储侧为该 bucket 配置 CORS（允许 Authloft 站点的 PUT），部署文档需写明

渠道图标不在 Authloft 内上传（接口文档 §5.3）：`icon_url` 由管理员自行托管后手填，后端只做 `^https?://` 格式校验，不读写对象存储，也不提供删除 / 替换逻辑。

小程序码路径：

- 扩展字段 `storage_path` 支持 JSONata 表达式，内置变量 `ticket_id`、`timestamp`；表达式求值统一走 `internal/jsonata` 封装层（gnata，§3.12 / §1.5）——非法表达式在保存时被 `CreateProvider` / `UpdateProvider` 编译预校验拒绝（admin 域 `invalid_request`），运行时求值失败归一为 sso 域既有兜底（接口文档 §1.6），均不透出库原始错误
- 例：`'qrcodes_' & $.ticket_id & '.jpg'`；渲染后的 key 再拼 `path_prefix`
- 码图始终走中转模式（由 Authloft 调微信接口取到二进制后 `Put`），与 `upload_mode` 无关；`upload_mode` 只影响头像等用户上传场景
- 开启 `qrcode_auto_delete` 时，删除用的 key 由同一模板 + `ticket_id` 重算（§13.3）

### 15.2 消息 Provider（category=sms / email）

```go
type Sender interface {
    Send(ctx context.Context, to string, tpl string, params map[string]string) error
}
```

- `sms`：`aliyun_sms`、`tencent_sms`、`twilio` 等
- `email`：`smtp`（通用）、`ses`、`sendgrid` 等
- 模板内容存 `metadata` 或系统配置，支持多语言（`internal/i18n`）
- 发送异步化（内存队列 + 重试），不阻塞登录主链路；发送失败不影响验证码已生成的状态（§8.2）
- 管理后台提供"发送测试"验证配置（接口文档 §5.2），前端无直接交互

### 15.3 注册表与配置热更新

- 注册表：`Register(type, meta, factory)` + `NewAdapter(p)`；`meta` 同时驱动管理后台 `/schema`（接口文档 §5.3）——动态 schema 由适配器声明（`provider.Ext` 字段的标签、渲染类型与默认值，`key` 与 Ext 字段同名），admin 表单按 schema 渲染，不硬编码字段
- 加载：本地 LRU + singleflight（TTL 60s）
- 写 Provider → `DEL al:prov:v:{key}` → `INCR al:prov:ver` → `PUBLISH al:prov:chg {key}`
- 各实例：后台协程每 5s 比对 `al:prov:ver`；订阅 `al:prov:chg` 实现秒级生效
- 系统配置（`settings`）：写 `settings` 表（§4.7）→ 刷新本实例内存 → `PUBLISH al:settings:chg`；各实例订阅后重载，秒级生效

| 系统配置 | 登录方式开关（`login_methods`）、MFA 策略（`mfa_enabled` / `mfa_methods`）、captcha 阈值、密码失败锁定阈值（`pwd_fail_capture` / `pwd_fail_ban` / `pwd_ban_ttl`）、注册开关、重置入口开关 `allow_password_reset`、验证码限流五项（`otp_resend_interval` / `otp_ttl` / `otp_max_attempts` / `otp_daily_limit_target` / `otp_daily_limit_ip`）、密码策略（键见下）、会话有效期 `session_ttl`、Cookie 名 `cookie_name`、多域名列表 `sso_domains`、队列参数、当前 Captcha/SMS/Email Provider / 头像 Storage Provider、网关 Token `gateway_tokens`、事件日志保留 `eventlog_retention_days`、静态资源基址 `static_base`、HTTPS 部署形态 `https_deployment`（string 三态 `true` / `false` / `auto`，默认 `auto`，驱动会话 Cookie `Secure` / `SameSite` 属性，接口文档 §1.9）；键名与默认值**全部**见接口文档 §5.6，落库见 §4.7。改动热更新，只对后续请求生效 |

## 17. 网关与 RPC（后端实现）

接口契约见接口文档 §6、§7。

| 项 | 实现要点 |
|----|----------|
| 网关 decode | `ANY /api/gateway/decode`：`X-Gateway-Token` 校验 → 解 session_token（优先级 `X-Authloft-Token` Header → Cookie）→ 以响应头返回 `X-Session-Status` /`X-Session-ID` / `X-Session-Epoch` 等字段。**纯响应头、无响应体**（REST 豁免，接口文档 §1.0） |
| RPC 鉴权 | 头部与签名串规范**见接口文档 §7**；实现在 `internal/connect` 的 rpc HMAC interceptor（复用 `cache/nonce`），按方法名分流：**写接口**（`Update`/`Delete`/`Set`/`Create`/`Revoke` 开头）nonce 去重 TTL 30s + 五项签名；**读接口**五项签名（nonce 参与签名、不去重） |
| 校验顺序 | **写接口**（`Update`/`Delete`/`Set`/`Create`/`Revoke` 开头）：nonce 去重 → 签名 → session；**读接口**：签名 → session（nonce 参与签名但不去重；「命名决定校验」长期口径，接口文档 §7） |
| RPC 编码 | 服务间调用**推荐 Protobuf**（`Content-Type: application/proto`）：报文体积与 CPU 都更省；JSON 仍可用，两种编码语义一致（§1.6） |
| 资料读写 | `UserService/GetUserProfile` / `UserService/UpdateUserProfile`，响应结构与接口文档 §3.1 共用同一消息；`UpdateUserProfile` 入参除 `uid` 外与接口文档 §3.2 `UpdateProfile` 同构，同为 proto3 optional 口径（2026-11-06 定稿）：has 位区分「未设置 = 不修改」与「显式设值 = 覆盖（含 0 / 空串，`gender` 可改回 0）」，合并逻辑禁止按零值猜「未传」 |
| 会话解码 | `TokenService/DecodeSession`：handler 内 session 校验（`session/verify.go`）→ 通过则 `session/renew.go` 重签（纯计算、无存储写入）→ 响应 `SessionResponse` 平铺载荷 + `renewed_token`（接口文档 §7.1）；无效 / 过期 → 401 `unauthenticated`（接口文档 §1.5），不重签 |

## 23. 部署与容器镜像（Docker Hub 发布）

### 23.1 `docker/` 目录与双基础镜像

| 文件 | 运行时基础镜像 | 用途 |
|---|---|---|
| `docker/Dockerfile` | `debian:stable-slim` | **默认镜像**：glibc 环境，兼容性与排障便利优先 |
| `docker/Dockerfile.alpine` | `alpine:3` | **体积优先**：musl 环境，镜像最小化 |

两份文件除运行时阶段外结构一致，均为**镜像内多阶段构建**（参考 Casdoor 的 FRONT / BACK / 运行时三段式）；前端产物由 CI 前序 `web-build` job 产出、经 `web-dist` artifact 交给镜像，**镜像内不再跑 `pnpm install` / `pnpm build`**：

1. **web 阶段**（`node:24`）：`COPY web/dist ./dist` 承接预构建产物，同时向 server 阶段提供运行 `sync-templates.mjs` 所需的 node 运行时（同源 bookworm 基础）
2. **server 阶段**（`golang`，版本随 `server/go.mod`）：复制 `server/` 与上阶段 `web/dist` → `node web/scripts/sync-templates.mjs` 落位壳层模板与静态资产（§3.13）→ `CGO_ENABLED=0 GOAMD64=v1 go build -ldflags "-s -w"` 静态编译单二进制（前端产物经 `server/assets` embed 进二进制，§1.1）
3. **运行时阶段**：只 `COPY` 二进制；安装 `ca-certificates` 与 `tzdata`（出站 TLS 校验与时区）；建**非 root 用户**运行；`EXPOSE 8080`（默认监听，§3.2）

- 构建上下文固定为**最小上下文目录**（CI 中由 `docker-publish` job 组装为 `.docker-build/`，只含 `server/`、`web/dist`、`web/scripts/sync-templates.mjs`，以及平铺到上下文根的当前变体 `Dockerfile`）：本地 `docker build -f .docker-build/Dockerfile .docker-build`；CI 走 `docker/build-push-action` 的 `context=.docker-build` + `file=.docker-build/Dockerfile`。上下文已只含 Dockerfile 实际 `COPY` 的输入，天然排除 `node_modules` / 本地构建残留，**不再需要 `.dockerignore`**；debian 与 alpine 两个 matrix job 各自组装一份同布局上下文（内容一致，各自使用独立的 `type=gha` 缓存 scope，§23.3）。本地构建需先 `pnpm --dir web build` 产出 `web/dist`，再按同一布局组装 `.docker-build/`（组装命令见 `docker-publish` job 的 `Prepare minimal build context` 步骤）
- **CGO 口径**：全流程 `CGO_ENABLED=0` 静态链接（与手动构建 CI 的 linux-amd64-v1-static 产物同口径），alpine（musl）与 debian（glibc）运行同一形态二进制
- **版本注入**：二进制内无版本变量、**不做 `-X` 注入**；镜像版本只以 tag 表达（§23.3）
- **HEALTHCHECK 暂不设置**：存活 / 就绪探针端点（§3.1 `app/health.go`）尚未落地，落地后补

### 23.2 容器启动与配置口径

- **入口固定传 `--config`**：`ENTRYPOINT ["/usr/local/bin/authloft", "--config", "/conf/authloft.yml"]`——容器内配置路径恒定，不随 cwd 变化；读取与安装写回共用该路径（§3.2）
- **`/conf` 由镜像保证存在**（`RUN mkdir -p /conf`）；**建议挂载整个目录**（`-v ./conf:/conf`），不要只挂单文件：安装写回是「临时文件 + rename」原子写（§3.15 `writer.go`），单文件 bind mount 会使 rename 失败导致安装无法落盘
- **配置文件缺失 = setup 模式**：`/conf/authloft.yml` 不存在（首次启动 / 未挂载）时按 §3.1 / §3.15 进入 setup 模式，仅暴露 `/setup` 与 `SetupService`，安装完成写回同一路径并触发重启——容器编排需配置重启策略（如 `restart: always`）让进程退出后自动拉起进入正常模式

### 23.3 CI 发布（`.github/workflows/build-manual.yml`）

在现有 `workflow_dispatch` 上追加 Docker 发布，**依赖 `web-build` 并复用 `web-dist` artifact**（镜像内不再做前端构建），经 `docker/login-action` + `docker/setup-buildx-action` + `docker/build-push-action` 推送到 Docker Hub：

- **新增输入**：
  - `docker`（boolean，默认 `false`）：为 `true` 时执行 docker 构建与推送 job；为 `false` 时行为与现状完全一致
  - `docker_tag`（string，可空）：自定义镜像 tag；留空则取 `github.ref_name`（当前分支 / 引用名），其中 `/` 等 Docker tag 非法字符替换为 `-`
- **镜像名与 tag 规则**：镜像名全小写，namespace 取组织变量 `vars.ORG_DOCKERHUB_USERNAME`，repo 名取 `github.event.repository.name`（当前为 `authloft`）；不带 `docker.io` 前缀时默认即 Docker Hub。解析值 `T` = `docker_tag` 非空 ? `docker_tag` : 清洗后的 `ref_name`；debian 推 `<namespace>/authloft:T`（**无后缀，默认镜像**），alpine 推 `<namespace>/authloft:T-alpine`，分别由 `docker/Dockerfile` 与 `docker/Dockerfile.alpine` 构建
- **凭证与权限**：`docker/login-action@v4` 不指定 registry（默认登录 Docker Hub），用 `vars.ORG_DOCKERHUB_USERNAME` + `secrets.ORG_DOCKERHUB_TOKEN`（PAT）登录；workflow `permissions` 只需 `contents: read`，**不再需要 `packages: write`**（那是 ghcr.io + `GITHUB_TOKEN` 的旧口径）
- **matrix 并行**：`docker-publish` 用 `matrix`（`debian` / `alpine` 两项，`fail-fast: false`）拆成两个并行 job，各自经 `docker/build-push-action@v7` 一次完成 build + push 自己的 tag，**两个变体互不等待**；tag 不同，Docker Hub 并发推送无冲突，单个变体失败不取消另一个
- **buildx 与缓存**：`docker/setup-buildx-action@v4` 建 docker-container 驱动（默认 docker 驱动无法导出缓存）；`cache-from: type=gha,scope=authloft-<variant>` + `cache-to: type=gha,scope=authloft-<variant>,mode=max`，按变体分 scope 避免两个并行 job 写同一缓存 key。setup 步骤（checkout / login / 下载 artifact / 组装上下文）仍各跑一次
- **artifact 复用与上下文**：每个 `docker-publish` job 下载 `web-dist` 到 `web/dist`，再把 Dockerfile 实际 `COPY` 的输入组装成 `.docker-build/` 作为唯一构建上下文（§23.1）；当前变体的 Dockerfile 平铺为 `.docker-build/Dockerfile`，正好对上 build-push-action 的默认 `file`；`.docker-build/` 即全部上下文，无需 `.dockerignore`，镜像内只保留 `sync-templates.mjs` 与 go 编译
- **明确不做**：不推 `latest`；不做多架构（不指定 `platforms`，沿用 runner 的 `linux/amd64`；buildx 仅用于缓存导出，不做跨架构构建）
