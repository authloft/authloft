## 1. 总体架构

### 1.1 技术栈

| 层 | 选型 |
|----|------|
| 语言 / 框架 | Go + Gin |
| ORM | GORM |
| 主库 | MariaDB 10.5+ |
| 缓存 | Redis（含 Lua 脚本） |
| 序列化 | Protobuf 为**接口报文与固定 schema 的唯一结构源**；JSON 视图由 protojson 输出（§1.6）；透传结构用 msgpack |
| 契约生成 | `buf` + `protoc-gen-go`（Go 结构体）、`protoc-gen-es`（前端 TS + 二进制编解码），产物提交进仓库（§2） |
| 密码哈希 | argon2id |
| 对象存储 | S3 兼容 SDK（minio-go）+ 本地文件系统 |
| 配置 | YAML（`configs/config.yaml`，`gopkg.in/yaml.v3`）：启动时读取一次，**运行期不可变**，不支持热加载（§3.2） |
| 静态资源 | 前端构建产物 embed 进二进制（`server/assets`，`//go:embed dist`），由 Go 统一以 `/assets/**` 提供；可配 CDN 基址（§3.13） |

### 1.2 分层

```
HTTP 入口
  middleware   Origin/Referer 校验、Content-Type 校验、响应编码协商、CSP nonce、鉴权（会话 / 管理员 / 网关 Token / RPC 签名）
    ↓
  handler      Gin：绑定入参（经 codec 解码）→ 调 service → 组装响应消息 → 经 codec 写出 → 写 Cookie / 设响应头
    ↓
  service      业务编排（orchestrator 步骤引擎、会话、OIDC、账号、管理后台…）
    ↓            ↓                    ↓
  factor       provider            repo
  认证因子实现   外部服务适配器      GORM / Redis / Storage
    ↓
  infra        异步队列、Redis 脚本、Crypto、配置热更新、事件日志
```

依赖方向单向向下：`factor` 与 `provider` 不知道 HTTP 的存在；`service` 不依赖 Gin（handler 层把 `*gin.Context` 转成 `context.Context` + 输入结构后传入）。`codec` 只被 `middleware` 与 `handler` 使用，`service` 及其下层既不知道 JSON 也不知道 Protobuf。

### 1.3 三条主线与两条扩展轴

| 原则 | 落地方式 |
|------|----------|
| 统一建模 | 第三方登录、人机校验、短信、邮件、存储全部落 `provider` 表，用 `category` 区分，用 `provider_key` 唯一引用 |
| 接口抽象 | 每类能力一个接口 + 一张类型注册表；新增渠道 = 新增一个文件 + 一行注册 |
| 配置驱动 | 登录页显示什么、每种方式要填什么、走什么流程，由 `__AUTHLOFT_INIT__.methods` 注入快照决定（接口文档 §2.1）；该列表不再提供 HTTP 接口 |

| 轴 | 落地 | 新增一件东西要改什么 |
|----|------|---------------------|
| 外部服务（Provider） | 一张 `provider` 表 + 每类一个接口 + 一张注册表 | 新增渠道 = `internal/provider/<category>/<type>/` 一个包 + 一行 `init()` 注册（§15.3） |
| 认证因子（Factor） | `Factor` 接口（§6.3）+ 注册表 | 新增因子 = `internal/factor/<name>/` 一个包 + 一行注册 |

两条轴都不得反过来让 service 层出现 `switch type`。

向下兼容：所有 Protobuf 结构、数据字段都必须尽可能保证向下兼容（接口文档 §12.8）。

### 1.4 Token 加密方案

封装格式、AAD 构造与各类载荷定义**见 §11.6**，此处只列实现侧约束：

- `security/token.go` 是唯一编解码实现，多类令牌共用；`purpose` 常量集中在 `security/purpose.go`，禁止跨 purpose 解令牌
- 不同场景令牌独立密钥（配置项分离），AAD 里的 `purpose` 是第二道保险
- `keystore` 按 `version+kid` 取密钥，支持轮换期新旧并存；算法固定 AES-256-GCM + 12B 随机 nonce，不做算法协商

### 1.5 第三方库

可适当使用第三方库以减少重复代码（如 `@simplewebauthn/server` 侧的 WebAuthn 校验、JSONata 求值、S3 SDK 等）。

### 1.6 序列化与内容协商（`internal/codec`）

接口报文结构**只定义一次**：`.proto`（`server/proto/api/**`，约定见接口文档 §12.9）。Go 结构体与前端 TS 类型都由它生成，两份架构文档都不手抄字段。JSON 与 Protobuf 是同一份消息的两种字节表示，**业务代码感知不到差异**。

| 环节 | 实现 |
|------|------|
| 请求解码 | 按 `Content-Type`：`application/json` → protojson 解码；`application/octet-stream` → `proto.Unmarshal`；其余在中间件 415（§3.3 `contenttype.go`） |
| 响应编码 | 按 `Accept` 协商，规则见下表；协商与写出**只在 `internal/codec` 一处** |
| JSON 编码 | `protojson.MarshalOptions{UseProtoNames: true, EmitDefaultValues: true, AllowPartial: false}` |
| JSON 解码 | `protojson.UnmarshalOptions{DiscardUnknown: false}`（未知字段 → 400，契约严格；服务端不偷偷吞字段） |
| 二进制 | `proto.Marshal` / `proto.Unmarshal`；`Deterministic: true` 只在 golden 生成与测试里开启 |
| 整型 | `.proto` 中只用 `int64`（接口文档 §1.12）→ protojson 天然输出十进制字符串；`buf lint` 加自定义规则拦 `int32` / `uint32` / `fixed32` |
| 错误体 | `api.Error`（接口文档 §1.5），与成功响应走同一出口、同一协商结果 |

两个选项不能省：

- `UseProtoNames`：protojson 默认输出 lowerCamelCase，会把 `login_token` 写成 `loginToken`，与既有 JSON 契约直接冲突
- `EmitDefaultValues`（不是 `EmitUnpopulated`）：让标量字段恒存在（`""` / `"0"` / `false`）、未设置的 message 字段被省略、`repeated` 输出 `[]`，正好对上接口文档 §1.1 的"字段恒存在 / 不随意省略"

协商算法（`codec/negotiate.go`）：

| `Accept` | 结果 |
|----------|------|
| 含 `application/octet-stream` 且 q 值 ≥ `application/json`（含缺失 json 的情况） | Protobuf |
| 其余一切（缺失、`*/*`、仅 json、无法识别） | JSON |

- 免协商白名单：`/api/oidc/**`、`/api/gateway/**` 恒 JSON（接口文档 §1.1.1）
- 响应必写 `Vary: Accept`；Protobuf 响应额外写 `Content-Length`（`proto.Marshal` 后长度已知，避免 chunked）
- **不返回 406**：协商失败一律回落 JSON，宁可多传文本，也不给调用方一个解码不了的响应
- 协商结果写入 `*gin.Context` 后不得被 handler 覆盖；handler 不读 `Accept`、不判断格式

边界与性能：

- 每个响应只 marshal 一次：handler 只调 `codec.Write(c, status, msg)`，禁止 `c.JSON` / `c.ProtoBuf` / 手拼 `[]byte`（§22 约束）
- 不为任何接口写"两种格式各一套"的分支；不做 `application/grpc`、不做流式、不做压缩协商——大响应靠分页控制体积（接口文档 §1.7）
- `codec` 只依赖 `proto.Message` 与 `*gin.Context`，不 import `service`（保持依赖方向，§1.2）

生成链（CI 门禁见 §21.4）：

1. `buf generate`（配置在 `server/buf.gen.yaml`）→ `server/gen/go/api/**`（Go）与 `web/src/gen/proto/**`（TS）
2. 产物**提交进仓库**：部署与前端构建不依赖本地 protoc 环境
3. CI 校验 `buf generate` 后工作区无 diff（防止有人改生成物或忘记重新生成）
4. `.proto` 变更过 `buf breaking --against '.git#branch=main'`，只增字段、不改字段号（接口文档 §12.8）

## 3. 文件职责清单

### 3.1 `cmd/authloft` 与 `internal/app`

| 文件 | 职责 | 约束 |
|------|------|------|
| `main.go` | 解析 flags、加载配置、构造 App、注册信号、阻塞运行 | 极薄，不含业务 |
| `bootstrap.go` | 按固定顺序装配：config → DB → Redis → 密钥 → provider/factor 注册表（触发 `init()` 注册）→ settings 预热 → 队列 worker → cron → router | 注册表导入在此处统一 `_ import`，保证自注册被执行 |
| `app/router.go` | 全站路由与中间件分组：`/api/**`、`/assets/**` 与页面路由分离（接口文档 §8）；公开组 / 登录组 / 会话组 / 管理员组 / 网关组 / RPC 组 | 唯一知道路由表的文件 |
| `app/app.go` | `Run()` 与 `Shutdown(ctx)`：先停接收 → flush 队列（超时 10s 强退，§5.2）→ 停 worker/cron → 关连接 | 优雅关闭顺序固定 |
| `app/assets.go` | `/assets/**` 从 `assets/embed.go` 的 `http.FileSystem` 提供 SPA 产物；产物名带 contenthash 故用长缓存 | 无鉴权；与接口前缀不冲突；找不到即 404，不回退到空壳页 |
| `app/health.go` | 存活 / 就绪探针（含队列长度与 dropped 计数） | — |

### 3.2 `internal/config`（YAML 启动配置）

配置文件 `configs/config.yaml`（示例 `configs/config.yaml.example`）。**只在启动时读取一次，运行期不可变**：不监听文件变更、不提供刷新接口，改任何一项都必须重启；改完不重启不会有任何效果。需要热更新的项（阈值、开关、域名列表、Cookie 名与 TTL、队列参数）一律走 `settings`（接口文档 §5.6），**不进本文件**。

```yaml
server:
  listen: ":8080"                # 监听端口
  read_timeout: 30s
  write_timeout: 30s
db:
  dsn: "authloft:pass@tcp(127.0.0.1:3306)/authloft?charset=utf8mb4&parseTime=true&loc=Local"
  max_open_conns: 50
  max_idle_conns: 10
  conn_max_lifetime: 1h
redis:
  addr: "127.0.0.1:6379"
  password: ""
  db: 0
  pool_size: 50
authloft:
  root: "https://authloft.example.com" # al_root，只填主域名，用于拼回调 / 多域名同步地址
  rp_id: "authloft.example.com"        # WebAuthn RP ID
sign_key:                                           # 各类令牌 / 载荷独立密钥，支持多 kid 轮换（§1.4）
  session:      { key: "<base64-32B>", kid: 1 }     # session token
  login:        { key: "<base64-32B>", kid: 1 }     # login token
  ticket:       { key: "<base64-32B>", kid: 1 }     # ticket（含 al:ticket 存储值，§11.4）
  cookie:       { key: "<base64-32B>", kid: 1 }     # al_login_state（§11.6.1）
  sync_payload: { key: "<base64-32B>", kid: 1 }     # 多域名同步载荷（§11.2）
argon2: { time: 3, memory: 65536, threads: 4, key_len: 32 }
log: { level: info, format: json }
```

| 文件 | 职责 | 约束 |
|------|------|------|
| `config.go` | 上表结构体 + `Validate()` | 字段与 YAML 一一对应；新增字段必须同步 `config.yaml.example` 与默认值说明 |
| `loader.go` | 读文件 → 应用环境变量覆盖（`AUTHLOFT_DB_DSN`、`AUTHLOFT_REDIS_ADDR`…，环境变量优先）→ `Validate()` | 启动期一次完成；缺项 / 非法即 fail-fast 退出，不提供运行期兜底默认值 |

约定：

1. 业务代码不得直接读 YAML 以外的全局变量；`*config.Config` 由 `bootstrap.go` 注入（构造参数），测试可传自造实例（§20）
2. 与 `settings` 的分界：**改了要重启才安全的进 YAML**（地址、端口、密钥、`rp_id`、argon2 参数、日志），**改了要即时生效的进 settings**（开关、阈值、Cookie 名、`static_base` 等）；同一语义不得两处都有
3. 密钥类字段不得出现在日志与 `/api/**` 响应中（§22 约束 7）
4. 启动时检查配置项 sign_key 是否配置完整；若不完整，生成新的密钥对，并写入 YAML

### 3.14 `internal/codec`（序列化出口）

全站唯一的"消息 → 字节"出口。规则与选项见 §1.6，此处只列文件边界。

| 文件 | 职责 | 约束 |
|------|------|------|
| `negotiate.go` | `Negotiate(r *http.Request) Format`：解析 `Accept`（含 q 值）→ 返回 `FormatJSON` / `FormatProto`；作为中间件挂到 `/api/**` 组，结果写入 ctx | 白名单（`/api/oidc/**`、`/api/gateway/**`）恒 JSON；协商失败回落 JSON，绝不 406 |
| `write.go` | `Write(c, status, msg proto.Message)`：按 ctx 里的 Format 编码、设 `Content-Type` / `Vary: Accept` / `Content-Length`、写状态码 | 全站只此一处写响应体；编码失败直接 500 + `internal_error`，禁止半截输出 |
| `bind.go` | `Bind(c, msg proto.Message) error`：按 `Content-Type` 选择 protojson 或二进制解码；失败返回统一 400 | 限制请求体大小（`server.read_timeout` 之外再加 `http.MaxBytesReader`）；未知字段按严格模式拒绝 |
| `error.go` | `WriteError(c, status int, code, message string)`：构造 `api.Error`，`request_id` 取自 `middleware/requestid.go`，复用 `write.go` 编码 | `code` 只允许接口文档 §1.5 的封闭集合；不把内部错误文本透出 |

约定：

- `codec` 是**叶子包**：只依赖 `proto.Message`、`gin`、`api.Error`，不 import `service` / `dto` / `config`（保持 §1.2 的依赖方向）
- 不做 content-encoding 协商（不 gzip）、不做 `application/grpc`、不做流式响应
- 页面路由（`page.go` 的空壳 HTML）、`/assets/**`、OIDC 的 `x-www-form-urlencoded` 与 multipart 上传**不走本包**，各自按原方式输出

## 4. 数据模型（MariaDB）

### 4.0 结构化字段的统一约定

见接口文档 §12.0：固定 schema 用 Protobuf（`provider.ext`、`user_credential.meta`、`oidc_client.redirect_uris`），透传结构用 msgpack（`user_profile.extra`、`user_thirdparty_bind.extra`、`event_log.detail`），一律存二进制列（**短结构用 `VARBINARY`，长度不可预估的用 `MEDIUMBLOB`**），不使用 JSON 列。

落地约束：

- msgpack 字段只在应用内读写，不参与任何 SQL 条件；需要检索的信息一律提为真实列
- 存储层与传输层解耦：库里的 Protobuf / msgpack 只服务持久化，接口报文编码由 `codec` 按 `Accept` 协商（§1.6），换存储格式不动接口契约
- 所有字段均明文存；访问控制靠视图分离（`dto/view.go`，§3.5）
- 二进制列不做静默截断：写入前按上限校验（`VARBINARY` 用声明长度，`MEDIUMBLOB` 用 1 MiB 业务上限）。管理端写入（`provider.ext`）超限直接报错拒绝；非业务必需的旁路数据（`user_thirdparty_bind.extra`）超限整条丢弃并记 `warn`，不阻断登录 / 绑定

### 4.1 `provider` —— 外部服务统一表

结构原则：跨类型共有的属性作真实列（要用于筛选、排序、索引）；凭证、端点、存储配置、厂商长尾字段全部进 Protobuf 扩展字段，序列化后存 `ext`（定义见接口文档 §12.1）。

```sql
CREATE TABLE provider (
  id             BIGINT       PRIMARY KEY AUTO_INCREMENT,
  provider_key   VARCHAR(64)  NOT NULL COMMENT '全局唯一标识，逻辑引用使用',
  union_provider VARCHAR(64)  NOT NULL COMMENT 'Union ID 归属 Provider',
  display_name   VARCHAR(128) NOT NULL COMMENT '展示名，如“QQ”“阿里云短信”',
  category       VARCHAR(32)  NOT NULL COMMENT 'oauth|captcha|sms|email|storage|notify|union',
  type           VARCHAR(64)  NOT NULL COMMENT 'qq|wechat_mp|turnstile|aliyun_sms|s3|local|...',

  enable_signin  TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '允许用于登录',
  enable_signup  TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '允许该渠道建号；关闭则未绑定用户不能建号（登录仍返回 binding_required，信封 binding.allow_signup=false，前端置灰建号入口）',
  auto_bind      TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '按邮箱/手机号自动绑定已有账号',
  auto_bind_fields VARCHAR(128) NOT NULL DEFAULT 'email,phone',
  is_enabled     TINYINT(1)   NOT NULL DEFAULT 1,

  ui_group       VARCHAR(32)  NOT NULL DEFAULT 'social' COMMENT 'social|enterprise|dev|other',
  sort_order     INT          NOT NULL DEFAULT 0,
  icon_url       VARCHAR(512) NOT NULL DEFAULT '',

  ext            MEDIUMBLOB   COMMENT 'provider.Ext 序列化后（Protobuf，业务上限 1 MiB，写入前校验，见 §4.0）',

  remark         VARCHAR(512) NOT NULL DEFAULT '',
  created_at     DATETIME     NOT NULL,
  updated_at     DATETIME     NOT NULL,
  UNIQUE KEY uk_provider_key (provider_key),
  KEY idx_category_enabled (category, is_enabled),
  KEY idx_type (type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> `icon_url` 提到主表的原因：列表接口需要直接用，避免每次反序列化。其余展示类长尾放扩展。`icon_url` 由管理员**自行上传到任意可访问位置后手填绝对 URL**（不提供上传接口，也不做本地图标回落）；未配置时信封 `icon`（字段映射：DB `icon_url` ↔ 信封 `icon`，接口文档 §2.7.1）为空串，前端渲染通用占位图标。

读写约定（接口文档 §12.1）：`provider_key` 是唯一对外契约（字符集 `[a-z0-9_]`，创建后不可改）；敏感字段不做二次加密，前台公开接口永不返回 `ext` 中凭证字段。`ext` 用 `MEDIUMBLOB` 而非 `VARBINARY(8192)`：`cert`（支付宝公钥 PEM）单条即 2~3 KB，叠加 `user_mapping`、`metadata` 长尾键无上限，8 KB 会随机溢出；写入前按 1 MiB 上限校验，超限直接拒绝（接口文档 §5.2 走统一 `bad_request`）。

### 4.2 用户与凭证

```sql
CREATE TABLE user (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  username       VARCHAR(64)  NOT NULL COMMENT '用户名必选，设置后不可改（需求 §4.1.1）',
  phone          VARCHAR(32)  DEFAULT NULL,
  email          VARCHAR(128) DEFAULT NULL,
  phone_verified TINYINT(1)   NOT NULL DEFAULT 0,
  email_verified TINYINT(1)   NOT NULL DEFAULT 0,
  nickname       VARCHAR(128) NOT NULL DEFAULT '',
  avatar_url     VARCHAR(512) NOT NULL DEFAULT '',
  status         TINYINT      NOT NULL DEFAULT 1 COMMENT '1正常 0禁用',
  mfa_required   TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '系统强制该用户启用两步验证',
  epoch          SMALLINT     NOT NULL DEFAULT 0 COMMENT '安全版本号，改密/重置/管理员禁用时递增；递增结果 > 30000 时回绕为 1（跳过 0，由后端逻辑控制，不由DB控制）',
  last_login_at  DATETIME,
  created_at     DATETIME     NOT NULL,
  updated_at     DATETIME     NOT NULL,
  UNIQUE KEY uk_username (username),
  UNIQUE KEY uk_phone (phone),
  UNIQUE KEY uk_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE user_profile (
  user_id    BIGINT PRIMARY KEY,
  gender     TINYINT      DEFAULT 0,
  birthday   DATE,
  locale     VARCHAR(16)  DEFAULT '',
  timezone   VARCHAR(64)  DEFAULT '',
  extra      VARBINARY(2048) COMMENT 'msgpack 序列化的扩展资料',
  updated_at DATETIME NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 统一凭证表：一行一种凭证，新增凭证类型不加列
CREATE TABLE user_credential (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id       BIGINT       NOT NULL,
  kind          VARCHAR(32)  NOT NULL COMMENT 'password|totp|webauthn|recovery_code',
  secret        VARBINARY(1024) NOT NULL COMMENT 'password=argon2id 串；totp=Base32 明文密钥',
  label         VARCHAR(128) NOT NULL DEFAULT '' COMMENT '用户自定义名称，如“MacBook Touch ID”',
  meta          VARBINARY(2048) COMMENT 'credential.Meta 的 Protobuf 序列化',
  is_enabled    TINYINT(1)   NOT NULL DEFAULT 1,
  last_used_at  DATETIME,
  created_at    DATETIME     NOT NULL,
  updated_at    DATETIME     NOT NULL,
  KEY idx_user_kind (user_id, kind)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- WebAuthn 额外有一个凭据表
CREATE TABLE user_credential_webauthn (
  id            BIGINT PRIMARY KEY COMMENT '主键，与 user_credential.id 保持一致',
  user_id       BIGINT       NOT NULL,
  kind          VARCHAR(32)  NOT NULL DEFAULT 'webauthn',
  public_key    VARBINARY(2048) COMMENT 'webauthn 公钥（COSE）',
  credential_id VARCHAR(512) NOT NULL DEFAULT '' COMMENT 'webauthn 凭据 ID（base64url）',
  sign_count    BIGINT       NOT NULL DEFAULT 0 COMMENT 'webauthn 签名计数，防克隆',
  UNIQUE KEY uk_kind_credid (kind, credential_id),
  KEY idx_user_kind (user_id, kind)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

要点：

- `username` 为 `NOT NULL`：用户名是必选项（需求 §4.1.1），注册与三方免密建号都必须提交 `username`
- `password` 一行：`secret` = argon2id 哈希串（含参数与盐）；改密 = UPDATE 这一行
- `totp` 一行：`secret` = TOTP 密钥
- `webauthn` 每个凭据一行；`credential_id` 唯一
- `recovery_code` 一行：`meta` 存 10 个哈希（结构见接口文档 §12.2）；消费一个 = 更新该行（1 次写，走延迟队列）
- `epoch` 回绕规则：递增结果 **> 30000 时置 1，不回绕到 0**。`0` 是初始值，回绕到 `0` 会让回绕前签发、仍在有效期内的旧会话 / 令牌重新匹配通过（等于把全部旧令牌复活）；`1..30000` 循环下，任一令牌要重遇同一值至少需再过 30000 次凭证变更。回绕与递增同一事务写出，`al:pwdep:{uid}` 缓存同步更新

> 管理员 = 第一个注册成功的用户（`user.id = 1`）：不加 `is_admin` 列、不设角色表，判定集中在 `middleware/admin.go` 与 `GET /api/admin/me`。判定的原子性：注册写入的同一事务内 `SELECT COUNT(*) FROM user`（或 `INSERT ... SELECT ... WHERE NOT EXISTS`），`COUNT(*) = 0` 才赋予管理员身份，并发由事务隔离 + `uk_username` / `uk_phone` / `uk_email` 唯一约束保证；第三方免密建号、扫码建号走同一判定。注册开关 `allow_registration` / `allow_signup_password` / `allow_signup_phone` / `allow_signup_email` 见接口文档 §5 / §5.6。

### 4.6 事件日志（登录日志与审计日志合并）

登录日志与审计日志合并为一张 `event_log`，用 `event` 字段区分：两者结构重合，分开存会重复两套写入路径与清理策略；合并后一次批量 INSERT 即可，管理后台按 `event` 筛选即可还原两种视图。

```sql
CREATE TABLE event_log (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  event      VARCHAR(48)  NOT NULL COMMENT 'login_success|change_password|reset_password|bind_phone|bind_email|enable_mfa|disable_mfa|webauthn_register|webauthn_delete|thirdparty_bind|thirdparty_unbind|admin_disable_user|admin_reset_password|provider_create|provider_update|...',
  actor_type VARCHAR(16)  NOT NULL COMMENT 'user|admin|system',
  actor_id   BIGINT       NOT NULL DEFAULT 0 COMMENT 'user=该用户 uid；admin=操作管理员 uid；system=0（见下方记录范围）',
  user_id    BIGINT       NOT NULL DEFAULT 0 COMMENT '被操作对象；自身操作时与 actor_id 相同',
  client_id  VARCHAR(64)  NOT NULL DEFAULT '' COMMENT 'OIDC 客户端，登录类事件填充',
  amr        VARCHAR(128) NOT NULL DEFAULT '' COMMENT '登录类事件：通过的认证方法，如 pwd,otp,mfa',
  ip         VARCHAR(64)  NOT NULL DEFAULT '',
  ua         VARCHAR(512) NOT NULL DEFAULT '',
  target     VARCHAR(128) NOT NULL DEFAULT '' COMMENT '操作目标，如 provider_key',
  detail     VARBINARY(2048) COMMENT 'msgpack 序列化的附加信息',
  created_at DATETIME     NOT NULL,
  KEY idx_actor_time (actor_type, actor_id, created_at),
  KEY idx_user_time  (user_id, created_at),
  KEY idx_event_time (event, created_at),
  KEY idx_time (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

记录范围：

- 记录：成功登录（`login_success`）+ 各类敏感操作
- 不记录：登录失败（失败统计由 Redis 计数承担，见 §8.1）
- `actor_type=system` 的事件（目前只有 `oidc_authorize_no_state`，接口文档 §4.2）：`actor_id=0`、`user_id=0`，`client_id` 填本次请求的 `client_id`，`ip` / `ua` 照常记录。`actor_id` 因此带 `DEFAULT 0` 而非 `NOT NULL` 无默认值——写入方不必为系统事件编造一个用户 id，`idx_actor_time` 仍可用，筛"系统事件"直接按 `actor_type=system`（接口文档 §5.6 的 `actor_type` 过滤）

`detail` 字段（msgpack，按事件类型各异）：

| 事件 | detail 内容 |
|------|-------------|
| `login_success` | `{factor, mfa_factor, session_id, device_hint}` |
| `change_password` / `reset_password` | `{pwd_epoch}` |
| `bind_phone` / `bind_email` | `{target_masked}` |
| `enable_mfa` / `disable_mfa` | `{methods:[...]}` |
| `thirdparty_bind` / `unbind` | `{provider_key, open_id}` |
| `provider_create` / `update` | `{provider_key, changed_fields:[...]}` |

写入策略：全部事件、以及 `user.last_login_at` 更新，投递到 §5.2 的延迟写入队列，登录主链路零同步写库。队列按 200 条或 2 秒批量 INSERT，并对同一 `user_id` 的 `last_login_at` 做同键合并。

清理：定时任务按 `eventlog_retention_days`（默认 180 天）删除超期数据。

### 4.7 `settings` —— 系统配置

键值表，只为**可热更新**的配置服务；键名与默认值唯一定义在接口文档 §5.6，本表不重复列举。

```sql
CREATE TABLE settings (
  k          VARCHAR(64)  PRIMARY KEY COMMENT '键名，与接口文档 §5.6 完全同名',
  v          TEXT         NOT NULL COMMENT 'JSON 编码值（标量也按 JSON 存，便于统一反序列化）',
  updated_at DATETIME     NOT NULL,
  updated_by BIGINT       NOT NULL DEFAULT 0 COMMENT '操作管理员 uid'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- 启动：全量读入内存 → 缺失键按默认值补齐并写回（幂等）→ 供 `settings` 热更新用
- 写入：`service/admin/settings.go` 校验键名 ∈ 白名单 + 值类型 → 单事务 UPSERT → `PUBLISH al:settings:chg` 让各实例秒级生效（§15.3）
- 键名不在白名单的写入一律拒绝；`settings` 表不存密钥 / 连接串（那些在 YAML，§3.2）

### 5.1 键空间总表

|----|------|-----|----------|------|
| `al:code:{target}:{purpose}` | String | 300s | 发送 1 次 | 验证码（含归属标识、尝试次数、sent_at；登录链路记 `tid`，账号域 bind 场景记 `uid`，§10.1） |
| `al:rl:send:{target}` | String | 60s | 发送 1 次（SET NX EX） | 重发冷却 |

| `al:oidc:code:{code}` | String | 120s | 授权成功 1 次 | OIDC 授权码（一次性） |
| `al:prov:v:{key}` | String | 600s | 首次读取 1 次 | Provider 缓存（整行序列化） |
| `al:prov:ver` | String | — | 后台写 Provider 时 INCR | 缓存版本号 |
| `al:prov:chg` | Pub/Sub | — | 后台写 Provider 时 PUBLISH | 秒级失效通知 |
| `al:settings:chg` | Pub/Sub | — | 后台写 settings 时 PUBLISH | 配置秒级生效通知（各实例重载内存快照） |

### 5.2 延迟写入队列

所有不影响当次响应正确性的写入统一走这里，避免主链路被辅助写入拖慢。

适用写入（白名单）

| 类型 | 内容 | 合并策略 |
|------|------|----------|
| Redis | 会话重签后延长 `al:sess:{sid}` 的 TTL | 同 sid 合并，只保留最后一次 |
| Redis | 密码失败计数清零 `DEL al:pwf / al:pwban` | 同 key 合并 |
| MariaDB | `event_log` 批量 INSERT（登录 + 审计） | 攒批 |
| MariaDB | `user.last_login_at` UPDATE | 同 user_id 合并，只保留最新时间 |
| MariaDB | WebAuthn `sign_count` UPDATE | 同 credential 合并，取最大值 |
| MariaDB | `user_credential(kind=recovery_code).meta` UPDATE | 同 `user_credential.id` 合并 |
| 对象存储 | 扫码码图删除、头像旧文件删除 | 同 key 合并 |

不适用（必须同步）：验证码 `GETDEL`、授权码 `GETDEL`、图形码 `GETDEL`、ticket 写入与读取、建会话、限流计数——这些是安全或正确性依赖，不能延迟。

实现形态

```
handler → asyncqueue.Push(task)   // 非阻塞，ring buffer
                 ↓
        N 个 worker（默认 4，可配）
                 ↓
        攒批：满 200 条 或 距上次 flush 满 2 秒
                 ↓
        合并：按 key 去重，只写最终值
                 ↓
        执行：Redis pipeline / MariaDB 批量 INSERT-UPDATE
```

约束（写进实现规范）

1. 并发可控：worker 数量与攒批参数后台可配，队列总长固定（默认 8192），防止内存无界增长
2. 优雅关闭：收到 SIGTERM 先停止接收，flush 完剩余任务再退出，超时（默认 10s）后强制退出
3. 降级：队列满时，非关键项（日志、计数清零、文件删除）直接丢弃并累加 `uc_dropped_total` 计数告警；绝不因此对登录主链路返回错误
4. 不重复投递：会话重签这类"每次校验都可能触发"的任务，必须在 handler / middleware 内先判定，只有真正需要才 Push，避免队列被无效任务灌满
5. 可观测：队列长度、`dropped` 计数、平均 flush 耗时在管理后台"系统状态"页可见（接口文档 §5.6）

## 6. 认证模型：因子 × 步骤

### 6.1 两个正交维度

```go
// 维度一：认证因子（凭证类型）
type FactorKind string
const (
    FactorPassword   FactorKind = "password"
    FactorOTPSMS     FactorKind = "otp_sms"
    FactorOTPEmail   FactorKind = "otp_email"
    FactorWebAuthn   FactorKind = "webauthn"
    FactorTOTP       FactorKind = "totp"
    FactorRecovery   FactorKind = "recovery_code"
    FactorThirdParty FactorKind = "thirdparty"
    FactorDevice     FactorKind = "device"   // 已登录设备，内部实现，不对外暴露
)

// 用途：主因子 / 二次因子
type Usage string
const (
    UsagePrimary   Usage = "primary"
    UsageSecondary Usage = "secondary"
)

// 维度二：步骤形态（前端怎么渲染这一步）—— 取值与含义见接口文档 §1.4 的 kind 枚举，步骤序列见接口文档 §1.10
type StepKind string
const (
    StepForm      StepKind = "form"      // 渲染输入框并提交
    StepChallenge StepKind = "challenge" // 无输入，向后端要挑战数据
    StepRedirect  StepKind = "redirect"  // 浏览器跳转（第三方）
    StepExternal  StepKind = "external"  // 调宿主能力取 code（wx.login）
    StepQRCode    StepKind = "qrcode"    // 展示码图
    StepPoll      StepKind = "poll"      // 长轮询等待
)
```

### 6.2 因子 → 步骤序列表

**见接口文档 §1.10**（`method` × 主/二次因子 × StepKind 序列的唯一定义）。后端约束：

- 每个因子 `Steps()` 的返回值必须与接口文档 §1.10 对应行完全一致，否则注入快照与前端分派会漂移（单测逐因子断言，§21.2 B）
- `device` 是内部因子：不出现在注入快照，也不出现在任何对外响应
- 完整登录链：`主因子` →（可选）`二次因子` → `完成 SSO`

### 6.3 统一接口

```go
type Factor interface {
    Kind() FactorKind
    Usages() []Usage
    Steps() []StepKind

    // Start 处理 challenge 步：下发验证码 / 生成 WebAuthn options / 产出跳转 URL
    Start(ctx *FactorContext) (*StepResult, error)
    // Verify 校验提交结果，返回通过 / 失败 / 需要重试
    Verify(ctx *FactorContext) (*VerifyResult, error)
}
```

- `password` 是单步特例：`Steps() = [StepForm]`，`Start` 直接返回字段 schema，`Verify` 完成校验
- 所有因子（含 password）实现同一接口，编排层只有一份状态机

## 7. 登录流程编排

### 7.1 登录过程态 `login_token`

传递规则见接口文档 §1.8，载荷见 §11.6.2，加密见 §1.4。实现要点：

- 密钥来自配置项 `sign_key.login`；签发 / 解析 / 重签集中在 `orchestrator/state.go`，`exp` 固定 10 分钟
- 统一为响应体返回 + 前端内存变量，不使用 Cookie；第三方跳转回调时才生成，由响应体返回，不塞进 URL
- CSRF 防护（`login_token` 在 body 里，不受 `SameSite` 保护）依赖 §3.3 的 Origin 校验 + 只接受 `application/json`
- 防篡改 / 防重放由加密与 `exp` 保证；验证码、挑战数据的一次性消费由 Redis 侧保证（§10）

### 7.2 步骤引擎编排

编排规则（6 步）**见接口文档 §2.2**；注册 / 重置复用同一引擎（§7.4）。

`orchestrator/engine.go` 的实现顺序与接口文档 §2.2 一一对应，落地时补两处后端专属判定：

- 第 1 步解析失败 → `status=token_invalid/token_expired`，流程回到第一步，不返回细节
- 第 3 步不满足 → `status=step_invalid`；captcha 拦截统一走 `captcha/gate.go`（触发表来自接口文档 §2.5）

`status=mfa_required` 时返回可选的二次因子列表（含 `masked_target`），目标只能取自 `uid` 的已绑定资料。

### 7.3 核心场景与正确性校验点

以"邮箱验证码登录 → 触发 MFA → 改选短信 → 完成登录"为例（完整时序见接口文档 §10.2）：

| # | 请求 | 后端动作 |
|---|------|----------|
| 1 | 打开 `/sso/login`（空壳页注入） | `orchestrator/methods.go` 按 `login_methods` 过滤已启用因子；快照附带当前 captcha Provider 与 site_key |
| 3 | `challenge`（otp_email） | ① 校验 captcha ② 校验冷却与日限额 ③ 邮箱存在性检查（不存在：返回 `status=user_not_found`，跳过 ④⑤⑥，§10.2） ④ 生成 6 位码 → `SET al:code:...` ⑤ 异步发信 ⑥ 签发 login_token |
| 4 | `verify`（otp_email） | ① 解 login_token 取 `tid`、`ch.target` ② Lua `GETDEL` 比对 code 与 `tid`（不匹配 → `tries+1` 回写；超 5 次不回写即作废）③ 查用户 ④ 已启用 MFA → 重签 login_token（`passed`、`uid`）⑤ 生成 `mfa.methods` |
| 6 | `challenge`（otp_sms，MFA） | ① 校验 `uid` 非 0、`passed` 非空（否则拒绝）② 校验 captcha（每次下发都要新的）③ `phone` 从 uid 的已绑定资料取，不接受请求传参 ④ 限额 + 存码（purpose=mfa）⑤ 重签 login_token |
| 7 | `verify`（otp_sms） | ① 校验 `ch.purpose=mfa` 且 `ch.target` 与码内 target 一致 ② `GETDEL` 比对 ③ 全部通过 → 建会话（1 次写）④ 投递登录日志 + `last_login_at` ⑤ 若有 `oidc` 载荷 → 生成授权码 `SET al:oidc:code:{code} EX 120`，拼 `sync_cookie_url` 与 `redirect_to` |

实现时必须逐条覆盖的校验点：

- [ ] 邮箱不存在时，返回 `status=user_not_found`，不写 `al:code`、不发信、不签发 login_token
- [ ] 步骤 4 的 `passed` 与步骤 6 的 `uid` 校验：任何一步缺失都拒绝，杜绝"直接打 MFA 接口绕过主因子"
- [ ] 步骤 6 的手机号只能来自 `uid` 的绑定资料
- [ ] 验证码绑定 `purpose` 与 `tid`：登录收到的码不能用于 MFA，A 会话的码不能用于 B 会话
- [ ] 步骤 7 成功后登录态成立，`login_token` 本身无状态，靠 10 分钟 `exp` 兜底
- [ ] MFA 阶段总时长受 `exp` 约束（10 分钟），超时回到第一步

### 7.4 注册与密码重置

端点与步骤见接口文档 §2.3、§2.4。请求 / 响应信封与登录端点完全同构，仅 `flow` 不同（`register` / `reset`）。后端复用同一套步骤引擎、验证码组件、captcha 校验与限流组件；禁止为注册 / 重置另写一套编排。

| flow | 要点 |
|------|------|
| `register` | 步骤与载荷见接口文档 §2.3；`password` 是否必填按 `login_token.tp` 判定（接口文档 §2.7.5）。用户名规则见接口文档 §2.3（此处不复述），设置后不可改。接受的 `login_token.flow` 为 `register` 与 `login`（后者即绑定中间态免密建号，不得因 flow 不匹配而拒）。建号写入与首用户判定（§4.2 的 `SELECT COUNT(*)`）在同一事务内完成；`set_password` 可跳过 `challenge` / `verify` 直达（用户名 + 密码注册入口，接口文档 §2.3） |
| `reset` | 仅当用户已设置密码且已绑定邮箱 / 手机号时可用；`challenge` 目标必须是已绑定且已验证的；`allow_password_reset=false` 时 `challenge` 与后续各 step 一律返回 `status=reset_disabled`，不发码、不校验（接口文档 §2.4）；成功后递增 `al:pwdep:{uid}`（使全部会话与刷新令牌失效），异步写审计 |

## 8. 各因子实现规范

### 8.1 密码（password）

- 单步 `form`；字段 `username` / `password` / `captcha`（条件必填）
- 校验顺序：`al:pwban` 键存在 → 直接 `status=locked` → 查 `user_credential(kind=password)` → argon2id 验证 → 失败 `INCR al:pwf:{ref}:{yyyymmdd}`（首次 `EXPIRE` 到当日 24:00）
- 失败处理：
  - `al:pwf` ≥ N1（默认 3）→ 后续请求必须带 `captcha`，缺失返回 `status=captcha_required`；校验失败 / 已使用返回 `status=captcha_invalid`
  - `al:pwf` ≥ N2（默认 6）→ `SET al:pwban:{ref} 1 EX Zs（默认 21600）`，返回 `status=locked`（`retry_after` = 剩余秒数）
  - N1 / N2 / Z 即 `pwd_fail_capture` / `pwd_fail_ban` / `pwd_ban_ttl`（键名与默认值见接口文档 §5.6），走热更新，改动只对后续请求生效（同 §9.3 口径）
  - `user_ref` = `user_id`（用户存在）或 `ip + 输入账号哈希`（用户不存在）
- 管理员解锁（接口文档 §5.4 `/users/{id}/unlock`）：清 uid 维度键，并按该用户当前手机号 / 邮箱重算 `ip + 账号哈希` 维度键一并清除（否则"账号不存在"阶段种下的封禁清不掉）
- 成功 → 投递 `DEL al:pwf:{ref}` / `DEL al:pwban:{ref}` 到延迟队列，主链路零额外写；队列满时该项可丢弃，最坏结果是依赖 TTL 自然过期，不影响正确性
- 除接口特殊标注外，账号不存在与密码错误同码：均返回 `status=invalid_credentials`，文案由 `error.message` 下发；账号被禁用单独返回 `status=user_disabled`（接口文档 §1.6）

### 8.2 一次性验证码（otp_sms / otp_email）

- 步骤 `challenge` → `form`；两个 method 共用一份实现，仅 target 类型不同
- 主因子场景：`challenge` 需传目标（phone/email）+ captcha
- MFA 场景：`challenge` 只传 captcha，目标取 `uid` 的已绑定资料（接口文档 §2.6）
- 验证码生成与校验见 §10.1
- 账号域（bind）额外校验：码内 `owner` 必须等于当前会话 `uid`，否则 `status=invalid_code`（接口文档 §3.4）
- 短信 / 邮件发送走 Provider（§15.2），发送失败不回滚已写的码，允许 60s 后重发

### 8.3 通行密钥（webauthn）

- `challenge` 返回标准 `PublicKeyCredentialRequestOptions`：
  - challenge 由服务端生成 32 字节随机，绑定 `login_token`（存 `ch.nonce`），默认 120 秒有效，通过相应字段下发。通过用户中心绑定时主要使用其中的 `nonce` 和 `tid(uid)`，其他字段可随意。
  - `rpId` 固定为 Authloft 根域名（配置项），`origin` 服务端强校验
  - 只有 usernameless 一种模式：`allowCredentials` 恒为空 → 注册时必须创建 resident key / discoverable credential；请求中的 `username` 一律忽略
- `verify`：校验断言签名、challenge 匹配、`origin`、`rpId` hash；`signCount` 必须递增（防克隆）。验证通过不阻塞响应，把 `UPDATE user_credential_webauthn SET sign_count=?` 投递到延迟队列，按 credential 同键合并取最大值
  - `sign_count` 只在下一次登录时用于检测克隆，延迟 2 秒内落库不影响当次正确性；同一凭据被并发使用时合并后写入的是最大值，不会误判
- 既可作主因子也可作二次因子，靠 `usage` 配置区分，代码一份
- 账号域注册场景（`/api/account/webauthn`，接口文档 §3.6）无 `login_token`：`challenge` 步改而签发独立原子 token——复用 `LoginTokenPayload` 结构与加解密实现（本质上不是 `login_token`），载荷 `purpose = "webauthn"`、`uid` = 当前会话 uid、`ch.nonce` = 本次 challenge，`exp` 与挑战有效期一致（120s，随响应 `expires_in` 下发），AAD purpose 取对应场景值不与 login_token 互解；`verify` 由服务端解析校验（篡改 / 无效 → `invalid_request`，过期 → `code_expired`），前端不感知结构

### 8.4 动态口令（totp）与恢复码

- `totp`：单步 `form`，按 RFC 6238 校验，允许 ±1 个时间步
- `recovery_code`：单步 `form`；`user_credential(kind=recovery_code).meta` 存 10 个哈希数组，命中一个即从数组移除（走延迟队列，可容许极短时间内重复使用）
- 均只作二次因子

### 8.5 已登录设备（device）

- 内部因子，不对外暴露：用户已持有有效 `al_session` 时访问 `/sso/login`，直接进入"完成登录"，不再走因子
  - 无 redirect_to 时跳 account 页面
- 多域名场景下通过 `/sso/sync_cookie` 同步 Cookie 后即可实现

### 9.1 建模

- 自绘图形码：`SET al:cap:{id} {answer} EX 300`，校验时 Lua `GETDEL`（1 读 1 删）
- 第三方 token 的一次性由厂商保证，Authloft 侧零存储
- 降级（接口文档 §2.5）复用本节实现，不另写校验路径：`type=image` 时同样按 `id` + `answer` 核 `al:cap:{id}`，一次性语义与第三方 `token` 一致
- 缺失 → `status=captcha_required`（`error` 提示刷新）；校验失败 / 已使用 → `status=captcha_invalid`（语义见接口文档 §1.6）

### 9.3 触发规则（统一拦截）

**触发表见接口文档 §2.5**（唯一定义，本文不复制）。后端落地：

- 降级不改触发表：降到 `image` 后仍需按本表校验，`status` 取值不变

## 10. 一次性验证码与限流

### 10.1 存储与消费

```
发码： SET  al:code:{target}:{purpose}  {json}  EX 300        # 1 次写
       SET  al:rl:send:{target}         1       NX EX 60      # 1 次写（冷却）
       INCR al:rl:sendday:{target}:{date}   + EXPIRE          # 1 次写
       INCR al:rl:ipday:{ip}:{date}         + EXPIRE          # 1 次写
校验： GETDEL al:code:{target}:{purpose}   （Lua 原子，1 次往返）
```

> 四个发送侧写入可用一段 Lua 合并为 1 次 Redis 往返，实现时优先采用。

归属标识（`owner`）：`al:code:{target}:{purpose}` 的值形如 `{code, owner, tries, sent_at}`。`owner` 按场景二选一，两套场景共用同一段 Lua，仅传入值语义不同：

| 场景 | `owner` | 校验时与什么比对 |
|------|---------|------------------|
| 登录 / 注册 / 重置 / MFA（有 `login_token`） | `tid` | 当前 `login_token.tid` |
| 账号域绑定 / 换绑（无 `login_token`，仅会话） | `uid` | 当前会话 `uid` |

> 语义约束：登录链路禁止用 `uid` 作归属标识（会把 A 会话的码喂给 B 会话），账号域禁止用 `tid`（无 `login_token` 可解）。

校验：Lua 脚本原子 `GETDEL`（键由请求里的 target 拼出，因此发码 target 与校验 target 天然必须一致）；比对 `code` 与 `owner`；失败则 `tries+1` 后 `SET` 回去（仅当 `tries < 5`，即尝试次数上限为 5：第 5 次错码后键作废、不再回写）。

### 10.2 未绑定目标 / 账号不存在的错误口径

- 主因子登录 `password` → `status=invalid_credentials`（与账号不存在同码，接口文档 §1.6）
- 验证码主因子 `challenge`（`otp_sms` / `otp_email`）目标未绑定任何账号 → 显式返回 `status=user_not_found`，不签发 login_token、不生成与发送验证码（实现口径见 §7.3 步骤 ③）
- 注册 `challenge` 的目标已绑定他人 → `status=target_taken`（与用户名占用同一取值，§1.6）
- 重置 `challenge` 前提不满足（目标未绑定 / 未验证）→ `status=user_not_found`
- MFA 不可能出现用户不存在 / 目标未绑定的情况（目标取 uid 绑定资料），不定义
- 账号被禁用走 `user_disabled`

### 10.3 频率限制默认值（后台可配）

> 键名与默认值以《接口文档》§5.6 为准，本表为速查。

| 项 | 默认值 |
|----|--------|
| 重发冷却（`otp_resend_interval`） | 60s |
| 单目标日限额（`otp_daily_limit_target`） | 10 次 |
| 单 IP 日限额（`otp_daily_limit_ip`） | 50 次 |
| 验证码有效期（`otp_ttl`） | 300s |
| 验证码最大尝试次数（`otp_max_attempts`） | 5 |
| 密码失败触发验证码阈值（`pwd_fail_capture`） | 3 |
| 密码失败封禁阈值（`pwd_fail_ban`） | 6 |
| 密码失败封禁时长（`pwd_ban_ttl`） | 6h（21600s） |

## 11. 会话与单点登录

### 11.1 会话令牌与校验

令牌结构见 §11.6.3，独立密钥 `sign_key.session`，带 `kid`。

- 会话 Cookie 的名称 / 属性 / 有效期以接口文档 §1.9 为准，此处不复述；实现只固定 `Path=/`、`Domain=<根域>`
- 修改密码 / 重置密码 / 管理员禁用 → 会话内 `epoch` 与 Redis 计数器 `al:pwdep:{uid}` 比对不一致即失效

校验逻辑（每请求）

1. 解 session_token（验 kid → 取密钥 → 解密，失败即未登录）
2. `exp` 校验
3. 比对 `epoch`：
   ```
   cur := localCache.Get(uid)                  // 进程内，TTL 60s
   if miss { cur = GET al:pwdep:{uid} → 缺失则回源 DB }
   if token.epoch != cur → 会话失效，清 Cookie
   ```
4. 通过 → uid/amr 直接可用（RPC / OIDC 无需再查 Redis）

### 11.2 多域名会话同步

走**跳转式同步（redirect-based）**：链路状态全部装在服务端加密的载荷里，不落 `localStorage`、不存服务端会话，也不区分登录 / 登出（接收端只管写 Cookie）。实现要点：

**发起端**（登录终点与 `GET /sso/logout` 共用同一段代码）：

1. 按 `sso_domains` 顺序生成待同步地址数组，末尾追加最终跳转地址（登录为 `redirect_to`，登出为 `post_logout_redirect_uri`）
2. 取出数组第一个 URL 作为**首跳**，它不写进载荷（避免自跳循环）
3. 构造 `SyncCookiePayload`：Cookie 名 / 值 / TTL、剩余地址 `remaining`、最终地址 `final_url`、`exp`
4. 用 `sign_key.sync_payload`（`AAD purpose=sync_payload`，封装见 §11.6.1）加密载荷，拼到首跳 URL 后：`{URL}?{payload}`
5. 登录：把该 URL 作为响应字段 `sync_cookie_url` 返回，**由前端 `location.replace` 跳转**（登录接口是 JSON 响应，后端不 302）；登出：后端直接 302 到该 URL

**接收端**（`GET /sso/sync_cookie?{payload}`，每个根域各部署一份同一实现）：

1. 解密载荷；失败或 `now > exp` → 直接返回空（不带 `Location`），链路就此中断
2. **一律写入（覆盖）本域 Cookie**：`cookie_name` / `cookie_value` / `cookie_ttl`；登出场景由发起端把 `cookie_value` 置空、`cookie_ttl` 置 `"0"`，接收端按同样逻辑写入即等价于清除，**不需要知道本次是登录还是登出**
3. `remaining` 非空 → 取下一个 URL，按发起端步骤 3～4 重新生成载荷（`exp` 按剩余地址数重算）并 302 过去
4. `remaining` 为空 → 302 到 `final_url` 结束；`final_url` 不带载荷，不会再回到本端点

`exp` = 签发时刻 + `30s × 地址总数`（首跳 + `remaining` 个数 + `final_url`）。跳转本身应在数秒内完成，超时即视为链路作废，接收端不得再写 Cookie。

```protobuf
message SyncCookiePayload {
  string cookie_name        = 1;  // 会话 Cookie 名称
  string cookie_value       = 2;  // 会话 Cookie 值；登出场景为空串
  string cookie_ttl         = 3;  // 会话 Cookie 有效期；登出场景为 "0"；接收端原样透传给 Set-Cookie，不解析数值
  repeated string remaining = 4;  // 剩余未跳转的同步地址（不含本次首跳）
  string final_url          = 5;  // 最终跳转地址，不带载荷、不会再被本端点处理
  int64  exp                = 6;  // 载荷过期时间（Unix 秒）
}
```

- 该结构只服务服务端之间的跳转，**前端不解析**，故定义在本节、不进接口文档 §12（结构归属口径见接口文档 §12 前言）
- 载荷内 `cookie_value` 与会话令牌同源，虽已加密，但会随 URL 落进各域访问日志：部署侧需对该路径的 query 做脱敏（或关闭记录），并置 `Referrer-Policy: no-referrer`

### 11.3 登出

接口见接口文档 §2.9（`GET /sso/logout`）。实现要点：

- `GET /sso/logout?post_logout_redirect_uri=...`（可选 `id_token_hint`，用于校验身份并确认最终回跳；校验后即丢弃，不沿跳转链传递）
- `post_logout_redirect_uri` 需在回调地址白名单内；不在则落回默认页
- 清本域会话 Cookie → 按 §11.2 生成登出载荷（`cookie_value` 空、`cookie_ttl="0"`、`final_url=post_logout_redirect_uri`）→ 302 进入跳转链，逐域覆盖为过期 Cookie
- 不影响业务系统已持有的 OIDC 令牌（账号中心登出只结束本站会话；业务系统持有的令牌按自身有效期到期，或由业务系统调 `POST /api/oidc/revoke` 吊销）

### 11.4 ticket 登录

- `GET /api/sso/login/ticket?ticket={ticket}&poll=…`：长轮询，单次等待上限见接口文档 §2.8
- `POST /api/sso/login/ticket {ticket_id, session?}`：`session` 缺省取 Cookie `al_session`，两者并存以 body 为准且须与 Cookie 同一 uid，否则 `invalid_request`（接口文档 §2.8）；校验会话有效 → 写入 `TicketResult`
- 存储值与常量见 §11.6.5（`TicketResult`），此处不复述
- ticket 不落库，仅 Redis；用后即销毁

### 11.5 会话续期策略

每次请求均重签 session_token 并下发，具体细节以接口文档 §1.9 为准。在 middleware 内完成。

### 11.6 令牌与内部载荷结构（Protobuf）

本节是 `login_token` / `session_token` / `ticket` / `al:ticket` 存储值 / `al_login_state` / 多域名同步载荷的**唯一定义处**。这些结构都由服务端签发并由服务端解析，前端只把它们当作不透明串透传（判定口径见接口文档 §12 前言），故定义在本文而非《接口文档》。`.proto` 源文件仍与接口报文同批生成（`server/proto/`，§1.6）。

#### 11.6.1 通用封装

令牌共用同一封装与编解码实现（`security/token.go`）：

```
token = base64url( prefix || nonce || ciphertext || tag )

prefix     2B   [version:1][kid:1]
nonce     12B   crypto/rand
ciphertext  nB   AES-256-GCM(protobuf_payload)
tag       16B

AAD = "al/" || prefix || purpose        purpose ∈ {session, login, ticket, bind, webauthn, cookie, sync_payload}
```

- `version` + `kid` 进 AAD → 防降级、防跨类型串用
- `purpose` 进 AAD → 即使将来各类令牌共用一把钥匙，`login_token` 也变不成 `session_token`
- `purpose` 是**存储加密的 AAD 前缀**，取值封闭为 `{session, login, ticket, bind, webauthn, cookie, sync_payload}`：`bind` = 账号域绑定的一次性 token、`webauthn` = 通行密钥注册的一次性 token（接口文档 §3.4 / §3.6）、`cookie` = `al_login_state`（接口文档 §2.7.2）、`sync_payload` = 多域名同步载荷（§11.2）；`al:ticket` 存储值加密（§11.6.5）复用同一口径取 `ticket`。它与 §11.6.2 载荷内的 `challenge.purpose`（令牌内业务字段，枚举 `login/register/reset/mfa`）是**两套概念**，互不约束
- 不同场景令牌用独立密钥（`sign_key.*`，§1.4；`security/keystore.go` 按 `version+kid` 取），AAD 里的 `purpose` 是第二道保险
- 算法固定 **AES-256-GCM + 12B 随机 nonce**

#### 11.6.2 `LoginTokenPayload` —— 登录过程态（`login_token`）

加密后经响应体下发、前端存内存变量、后续在请求体顶层回传（接口文档 §1.8）。

```protobuf
message LoginTokenPayload {
  string tid      = 1;   // 会话标识，用于绑定验证码 / 日志关联
  string flow     = 2;   // login|register|reset
  string factor   = 3;   // 当前因子
  repeated string passed = 4; // 已通过因子
  int64  uid      = 5;   // pending user_id，0 = 主因子未通过
  Challenge  ch   = 6;   // nil = 无进行中的挑战
  ThirdParty tp   = 7;   // nil = 非三方流程
  Oidc       oidc = 8;   // nil = 非 OIDC 流程
  repeated string amr = 9; // 认证方法
  int64  iat = 10;
  int64  exp = 11;       // 固定 10 分钟
}

message Challenge  { string purpose = 1; string target = 2; string nonce = 3; }
message ThirdParty { string provider_key = 1; string open_id = 2; string union_id = 3;
                     string nickname = 4; string avatar_url = 5; }
message Oidc       { string client_id = 1; string redirect_uri = 2;
                     string scope = 3; string nonce = 4; string code_challenge = 5;
                     string code_challenge_method = 6; string state = 7; }
```

约束：

- `tid` 用于把验证码、图形码、日志与本次登录会话绑定；`purpose` ∈ `login` / `register` / `reset` / `mfa`
- `purpose` 枚举扩充说明：复用本结构签发的独立 token 的 purpose 值 `bind` / `webauthn` 保留于本枚举命名空间（bind = 账号域绑定，接口文档 §3.4；webauthn = 通行密钥注册，§3.6），但不属于 `login_token` 的合法取值，login 校验时见到即拒绝
- 账号域绑定场景无 `login_token`：其 token 只是复用本结构（含加解密实现）签发的另一种 token，并非 `login_token`，不走本节 login_token 的生命周期约定（该 token 的取值与用途见接口文档 §3.4 / 本文 §12.6），故此处 `purpose` 不含 `bind`；该 token 复用 §11.6.1 加解密实现时 AAD purpose 取对应场景值（`bind` / `webauthn`），不与 `login_token` 互解
- `tp` 只存精简三方身份（去掉 `Raw`），三方原始资料落 `user_thirdparty_bind.extra`；每次三方成功都覆盖 `tp`，保证"仅最后一次可绑定"
- `oidc` 载荷来自 `/auth/authorize` 的原始参数，是登录成功后生成授权码的唯一来源；三方跳转场景的落盘与回传见接口文档 §2.7.2
- 前端**不解析**其内容，只做"收到就替换、请求就带上"

#### 11.6.3 `SessionTokenPayload` —— 会话令牌（`session_token` / `al_session`）

```protobuf
message SessionTokenPayload {
  int64  id        = 1;  // UID
  int64  epoch     = 2;  // 用户安全版本号（al:pwdep:{uid}）
  repeated string amr = 3;  // ["pwd","otp"]
  string sid       = 4;  // Session ID
  int64  iat       = 5;
  int64  exp       = 6;
}
```

- `epoch` 与 `al:pwdep:{uid}` 比对，不一致即会话失效；改密 / 重置 / 管理员禁用递增该计数（登出不递增）；递增到 > 30000 时回绕为 1、不回到 0（§4.2）
- 浏览器写 Cookie `al_session`（接口文档 §1.9）；小程序 / 宿主环境由响应体下发，用 Header `X-Authlofe-Token` 回传（接口文档 §1.2）

#### 11.6.4 `TicketPayload` —— 扫码票据（`ticket`）

```protobuf
message TicketPayload {
  string ticket_id = 1;   // 全链路统一名：响应字段 / Redis 键 / 轮询回传
  string provider_key = 2;
  string scene = 3; // login（默认）| bind，决定小程序端写什么、PC 端走哪条轮询（接口文档 §3.7.1）
  int64  iat = 4;
  int64  exp = 5;   // 默认 600s
}
```

- `ticket` 加密串本身即"状态载体"：过期由服务端解 ticket 判断，无需存储
- `ticket_id` 控制在 **24 字符以内**（微信 `scene` 上限 32）——本值与 TTL **在本节唯一定义**，其余章节一律引用 §11.6.4
- 授权结果写 `al:ticket:{ticket_id}`，TTL 与 `ticket.exp`（默认 600s）对齐，轮询命中后 `GETDEL`

#### 11.6.5 `TicketResult` —— `al:ticket:{ticket_id}` 的存储值

键为 String 类型，值为**整值加密**后的 `TicketResult` JSON（复用 §11.6.1 的封装实现，`purpose=ticket`），Redis 内不留明文；读取方 `GETDEL` 后解密。取值含第三方原始资料（`thirdparty_identity.raw`），故整值加密。

```jsonc
{
  "v": 1,                       // 结构版本，读取方遇未知版本按失败处理
  "scene": "login",             // login | bind，取自 TicketPayload.scene，不由客户端指定
  "status": "success",          // scanned | success | failed（映射到轮询的 ticket.status，见接口文档 §1.6）
  "provider_key": "wechat_mp_scan",
  "channel": "qrcode",          // 写入通道，当前仅 qrcode
  "created_at": 1761800000,
  "expires_at": 1761800600,     // 与 ticket.exp 一致
  "consumed": false,            // false = 就绪待消费；消费方 GETDEL 原子取走即视为已消费
  "login_result": {             // 仅 scene=login
    "uid": 10086,               // 命中的本地账号；未绑定为 0
    "binding_required": false   // true 时轮询方用 thirdparty_identity 签发 login_token 并返回 binding_required 信封
  },
  "thirdparty_identity": {      // login（binding_required=true 时）与 bind 共用
    "open_id": "oX…",
    "union_id": "uN…",          // 无则空串
    "nickname": "微信用户",
    "avatar_url": "https://…",
    "raw": { }                  // 第三方原始资料，绑定场景落 user_thirdparty_bind.extra
  }
}
```

- 写入方：小程序端 `POST /api/sso/login/oauth`（带 `ticket_id`；`stage=scanned` 写 `status=scanned` 的空结果，`stage=complete` 整体覆盖为 `status=success` / `failed`，接口文档 §2.7.4）、已登录设备 `POST /api/sso/login/ticket`（接口文档 §2.8，直接写 `status=success`）
- 读取方：`GET /api/sso/login/ticket`（`scene=login`）与 `GET /api/account/thirdparty/ticket`（`scene=bind`）；`scene` 不匹配的轮询一律拒绝
- **一次性消费**：结果写入时 `consumed=false`；读取方以 `GETDEL` 原子取走并删除键，等价于置 `consumed=true`，无需二次写。同一 ticket 只有一个读取方能取到结果，其余轮询因键不存在得到 `expired`
- 除 `thirdparty_identity` 外不含任何凭证 / 令牌；`login_result` 只为轮询方"建会话或签 `login_token`"提供最小输入，不回传统一信封本身

### 12.1 适配器接口

// 第三方因子的通道形态（仅描述 thirdparty 因子内部）

### 12.3 下发列表

注入快照 `__AUTHLOFT_INIT__.methods` 的 `thirdparty.providers` 字段（接口文档 §2.7.1）：

- 只返回 `is_enabled=1` 且 `enable_signin=1` 的 Provider；该快照只服务登录场景（login entry 注入）
- 绑定场景的"可绑定列表"由账号域 `GET /api/account/thirdparty` 的 `available` 提供（接口文档 §3.7），过滤条件同上，并排除该用户已绑定的 Provider；Union Provider 不出现在 `available`
- 两者都经 `dto/view.go` 的公开视图消息（`api.ProviderPublic`），不得返回任何凭证字段

### 12.4 跳转场景的状态传递

> 第三方跳转登录仅可用于首次登录，不可用于登录后的 MFA 验证；已登录用户「绑定已有账号」复用同一套跳转机制，但 `state` 前缀为 `b`（§12.6）

```
GET /api/sso/authorize?provider={provider_key}&scene=login|bind
  → 后端生成带前缀的随机 state（l = 登录，b = 绑定），写入 `al_login_state` Cookie（服务端加密）
  → 接口返回 authorize_url，前端跳转（不做后端 302）
```

> **该接口只收 `provider` 与 `scene` 两个参数**（接口文档 §2.7.2）。OIDC 上下文（`client_id`/`scope`/`nonce`/`code_challenge`/`code_challenge_method` 等，来自 `/auth/authorize`）**不带进本接口**：由前端在跳转前落 `localStorage`，回调后随 `POST /api/sso/login/oauth` 的 body `oidc` 字段回传（见下方实现要点与接口文档 §2.7.4）。后端拿到 OIDC 上下文的时机是 `POST /api/sso/login/oauth` 写入 `login_token.oidc` 之后——后续 MFA 续走 `/api/sso/login/default`（沿用统一信封）时它已在 `login_token` 内，登录终点据此生成授权码。

`al_login_state` Cookie 的字段、属性、`state` 前缀表（`l` / `b`）与 OIDC 上下文的落盘回传约定**见接口文档 §2.7.2**。实现要点：

- Cookie 只含 `state`（带前缀）、`b` 场景的 `uid`、服务端加密（`AAD purpose=cookie`，内嵌 10 分钟过期兜底）；不含 scene、不含 OIDC 上下文
- 属性 `HttpOnly; Secure; SameSite=Lax`，会话级（不设 `Max-Age`）；回调校验通过或失败后立即删除，重新签发即覆盖
- 加密方式见 §11.6.1（使用密钥 `sign_key.cookie`）
- OIDC 上下文的流向（接口文档 §2.7.2）：`/auth/authorize` 未登录跳登录页时注入 `__AUTHLOFT_INIT__.oidc`（接口文档 §4.2、§8）→ 前端在 `location.replace` 跳第三方之前把它落 `localStorage`（键 `al_oidc_ctx`）→ 回调后读出，随 `POST /api/sso/login/oauth` 的 body `oidc` 字段回传 → 服务端写入 `login_token.oidc`，读完即清（登录端只允许落盘 `oidc` 一类数据，不含任何凭证；多域名同步的链路状态全部装在载荷里，不落盘）；`nonce` / PKCE 校验不在三方登录链路，仍在 OIDC 侧承载——授权码以 `login_token.oidc` 为唯一来源签发（§14.2 步骤 5），`code_verifier` 校验在 `POST /api/oidc/token`（§14.2 步骤 6）

回调：

- 页面 `GET /sso/oauth/callback/{provider_key}?code=...&state=...` 不做任何业务逻辑，由前端把 `location.search` 原样 POST 出去，按 `state` 首字母分派：`l` → `/api/sso/login/oauth`，`b` → `/api/account/thirdparty/oauth`（接口文档 §2.7.3）
- 后端：校验 `al_login_state` 与 `state` 是否一致（不一致 → `status=state_mismatch` 并清 Cookie）→ Exchange / FetchUser → 查 `user_thirdparty_bind`
- 登录场景：无需 MFA 则直接建会话、设 `al_session` Cookie；若有 MFA，则创建 `login_token`（body `oidc` 若有已写入其中）并沿用统一信封，后续流程与普通登录相同
- 绑定场景：走 §12.6

### 12.5 绑定中间态

三方身份解析成功后、无绑定记录时：

1. 重签 login_token，载荷写入精简三方身份 `tp`（去掉 `Raw`，只留 pk / openid / unionid / nickname / avatar），返回 `status=binding_required`（信封 `binding.allow_signup` 由该 Provider 的 `enable_signup` 列映射而来，字段映射见接口文档 §2.7.5）
   > `Raw` 不进载荷（体积与每请求传输开销约束）：走 Cookie 的回调场景上限 2KB，纯内存场景上限 4KB。绑定完成时以本次请求内的原始资料为准落 `extra`；走中间态时 `extra` 为空可接受（昵称头像已在 `tp` 中）
2. 前端只渲染两个选项，契约**见接口文档 §2.7.5**；不再提供"绑定已有账号"分支——改由用户先正常登录、再从安全中心发起绑定（§12.6，`state` 前缀 `b`）
3. 选「创建新账号」→ 校验该 Provider 的 `enable_signup=1`（否则拒绝）→ 走 `POST /api/sso/register` 的 `set_password` 步，仅提交 `username`（`login_token.tp` 非空即免密，服务端忽略 `password`）→ 写绑定 → 完成 SSO
   > 该 `login_token` 的 `flow` 仍是 `login`（由登录流程进入），`POST /api/sso/register` 必须接受 `flow=login`（接口文档 §2.7.5）
4. 选「退出并使用其他账号登录」→ 前端清空 `login_token` 并跳 `/sso/login`，不发请求，服务端无状态可清理

自动绑定：`auto_bind=1` 时，按 `auto_bind_fields`（默认 `email,phone`）匹配已有用户并直接绑定，跳过绑定页。默认关闭——开启后存在账号接管风险（第三方返回的邮箱若未验证）。

### 12.6 绑定已有账号（`scene=bind`）

已登录用户从安全中心把第三方身份绑到当前账号（接口契约与两通道时序**见接口文档 §3.7.1**）。支持两个通道，共用同一个 `BindToCurrentUser` 内核：

| 通道 | 载体 | 请求链路 |
|------|------|----------|
| `redirect` | `al_login_state` Cookie + `state` 前缀 `b`（§12.4） | `GET /api/sso/authorize?provider={key}&scene=bind` → 第三方 → `GET /sso/oauth/callback/{key}` → `POST /api/account/thirdparty/oauth` |
| `qrcode`（§13.2b） | `TicketPayload.scene=bind` | `POST /api/sso/qrcode {scene:"bind"}` → 小程序扫码 → `POST /api/sso/login/oauth`（写 ticket）→ `GET /api/account/thirdparty/ticket`（轮询完成绑定） |

`BindToCurrentUser(ctx, uid, identity)`，两个通道共用（`service/thirdparty.go`）：

1. 校验载体并取出 `uid`：
   - redirect：解 `al_login_state` Cookie，校验 `state` 一致且前缀为 `b`（前缀不符 → `invalid_request`）；Cookie 中记录的 uid 与当前会话 uid 比对，不一致 → `invalid_request`（防"发起绑定的是 A、回调时会话已换成 B"的串号）
   - qrcode：轮询接口自带当前会话 uid（无需载体校验，ticket 的 `scene` 已在拉码时确定）
2. 校验 Provider：`is_enabled=1` 且 `enable_signin=1`，否则 `provider_disabled`
3. 取 `ExternalIdentity`：redirect 通道现算（`Exchange` / `FetchUser`）；qrcode 通道从 `al:ticket:{ticket_id}` 取出（小程序端已解析并写入）
4. 查 `user_thirdparty_bind`（`provider_key` + `open_id`）：
   - 已绑当前 uid → 幂等成功（`{ok:true}`）
   - 已绑其他 uid → `status=target_taken`（接口文档 §3.7.1）
   - 未绑定 → 写入绑定行（含 Union 联动，§12.7）；`extra` 落 `Raw`
5. 投递 `thirdparty_bind` 事件到延迟队列（主链路零同步写库）
6. 返回 `{ok:true, provider_key, display_name}`；不签发 `login_token`、不 Set-Cookie、不重建会话

约束：

- 支持 `redirect` 与 `qrcode` 两个通道；`api` 通道不用于绑定（宿主内直接完成登录，无"已登录"前提）
- 绑定不触发 MFA：用户已持有有效会话，主因子与二次因子都已通过
- 绑定不检查 `enable_signup`（那是对"建号"的约束），只检查 `enable_signin`
- 写绑定后无需失效 Provider 缓存（绑定关系不在 Provider 缓存内）
- 小程序端（qrcode）只写 ticket，绝不写绑定关系：绑定只能由持有会话的一端发起（§13.2b）

### 12.7 特殊场景：Union ID

部分 Provider 支持返回 Union ID，用于跨 Provider 绑定。管理员可在后台配置虚拟 Union ID Provider，并将其与实际 Provider 关联。

例：

- 创建微信平台 Provider：`wechat_union`
- 创建小程序 `wechat_mp_1` 和 `wechat_mp_2`，并将其关联到 `wechat_union`
- 用户在 `wechat_mp_1` 登录后，同时获取到 openid 和 unionid
- `user_thirdparty_bind` 表中同时记录 `wechat_mp_1+openid` 和 `wechat_union+unionid`
- 后续登录时，两边均可登录
- 解除任一 Provider 将会同步解绑 Union Provider（Union Provider 不计入已绑定数，接口文档 §3.7 的解绑判定口径）
- 注：`wechat_union` 无单独的登录入口和解绑入口

## 13. 微信小程序

### 13.1 接口方式（channel=api）

- `POST /api/sso/login/oauth {provider_key, code, ticket_id?}`
- `code` → `code2session` → `ExternalIdentity`
- 若带 `ticket_id`（扫码场景）→ 走 §13.2；否则作为独立登录，直接完成 SSO。小程序端的交互由小程序自行实现，Authloft 前端不承载
- 同样受 `enable_signin` / `enable_signup` / 绑定中间态 / MFA 约束
- 区别：小程序端 `session_token` 直接作为接口返回，不写 Cookie（接口文档 §1.2）

### 13.2 扫码方式（channel=qrcode）

接口与时序**见接口文档 §2.8、§10.6**；`TicketPayload` 见 §11.6.4。实现要点：

- `ticket` 用 `sign_key.ticket` 加密；"过期"由服务端解 ticket 判断，无需存储
- 拉码：`ticket_id` 长度上限见 §11.6.4 → `GetwxacodeUnlimit` → JPEG 有损压缩（75%）→ `Storage.Put`（码图始终走中转模式，与 `upload_mode` 无关）
- 状态机 `pending → scanned → success / failed`，另有终态 `expired`（分层与语义见接口文档 §1.6）：`scanned` 由小程序端 `POST /api/sso/login/oauth` 的 `stage=scanned` 写入（1 次写、幂等、不覆盖已存在的 `success`），`stage=complete` 整体覆盖为 `success` / `failed`（接口文档 §2.7.4）；轮询未命中且未过期 → `pending`，已过期 → `expired`；`failed` 时结论在信封 `status`。轮询响应的顶层 `status` 表达本次轮询结论（`pending` / `scanned` / `expired` / `success` / 失败类），与 `ticket.status` 同步取值，`success` 仅在结果就绪时出现（接口文档 §1.6）
- 每次拉码都要一次 captcha（触发规则见接口文档 §2.5）
- Authloft 不负责小程序端实现，只提供码图生成、解 code、状态读写接口；前端工程里不放置任何小程序宿主桥接组件
- 小程序端无 `Origin`，服务端校验 `Referer`（`servicewechat.com/{appid}` 白名单，接口文档 §1.1）

### 13.2b 扫码绑定（scene=bind）

登录与绑定共用拉码接口与小程序端提交接口，靠 `TicketPayload.scene` 分派（接口文档 §3.7.1 B）：

| 环节 | `scene=login` | `scene=bind` |
|------|---------------|--------------|
| 拉码 `POST /api/sso/qrcode` | 无需会话 | 需会话（否则 401）；`scene` 写入 ticket |
| 小程序端 `POST /api/sso/login/oauth` | 写 `al:ticket` = `TicketResult{login_result}` | 写 `al:ticket` = `TicketResult{thirdparty_identity}`（含 `raw`，绑定要落 `extra`）；不建会话、不查绑定、不写绑定关系 |
| PC 端轮询 | `GET /api/sso/login/ticket` → 走登录逻辑 | `GET /api/account/thirdparty/ticket` → 走 `BindToCurrentUser`（§12.6） |

服务端要点：

- 小程序端提交时先解 ticket 取 `scene` 再决定写什么；`scene` 由加密保护，客户端不可篡改
- 绑定判定一律推迟到 PC 端轮询：小程序端没有 PC 端会话，无法也不应代做绑定
- PC 端轮询命中后：`GETDEL al:ticket:{ticket_id}` → 用当前会话 uid 执行 §12.6 的 `BindToCurrentUser`，两条通道共用同一函数
- 绑定场景同样支持 `scanned` 中间态（由 `stage=scanned` 写入，接口文档 §2.7.4，`scene=bind`）；`expired` 由服务端解 ticket 判断（与登录一致）
- 码图删除（`qrcode_auto_delete`）逻辑与 scene 无关，沿用 §13.3

### 13.3 码图自动删除

由该 auth provider 的扩展字段 `qrcode_auto_delete` 控制，默认关闭。

- 开启后：PC 端完成 SSO 时，服务端用同一个 `storage_path` 模板 + `ticket_id` 重算出 object key（无需任何额外存储），把删除任务投递到延迟写入队列，由后台 worker 调用 `Storage.Delete`
- 删除失败不影响已完成的登录；失败可重试 N 次后丢弃并告警
- 关闭时：码图保留在对象存储，靠不可猜测路径 + ticket 的短有效期（§11.6.4）保证安全

## 14. OIDC

### 14.1 端点

见接口文档 §4.1。实现分布：`oidc/authorize.go`（授权）、`oidc/token.go`（令牌）、`oidc/jwt.go` + `jwks.go`（签发与密钥集）、`oidc/revoke.go`（吊销）、`handler/oidc.go`（路由与 well-known）。

### 14.2 授权流程

1. `/auth/authorize` 校验 `client_id`（存在且启用）、`redirect_uri`（白名单，支持 `*` 通配，整段匹配防子域名陷阱）、`scope`；`state` 可选（推荐传）：存在则原样回传，缺失不报错、不做 CSRF 比对、记一条审计事件 `oidc_authorize_no_state`
2. 参数错误：`client_id` / `redirect_uri` 非法 → HTTP 400，Go 直接渲染错误页，**不跳转**；`redirect_uri` 校验通过后 `scope` 含未支持值 → 302 回 `redirect_uri?error=invalid_scope&state=...`
3. 有有效会话 → 调 `oidc.IssueCode` 生成授权码 `SET al:oidc:code:{code} {json} EX 120`（1 次写）→ 302 到 `redirect_uri?code=...&state=...`，不渲染页面、不经过前端；`prompt=login` 忽略，`prompt=none` 且无会话 → 302 回 `redirect_uri?error=login_required&state=...`
4. 无会话 → 直接渲染登录空壳页（URL 保持 `/auth/authorize`），OIDC 原始参数注入 `__AUTHLOFT_INIT__.oidc`（`handler/page.go`）→ 前端首次请求（尚无 `login_token`）以 body 顶层 `oidc` 回传 → 服务端写入 `login_token.oidc`
5. 登录成功（含 MFA）→ `terminal.go` 在同一请求上下文调同一 `oidc.IssueCode` 生成授权码（同键同 TTL，值结构见接口文档 §4.2）→ 信封 `redirect_to = redirect_uri?code=...&state=...`
6. `POST /api/oidc/token`：`GETDEL al:oidc:code:{code}` → 校验 `client_id`、`code_verifier`（PKCE）、`redirect_uri` → 签发 ID Token / Access Token / Refresh Token
7. 刷新令牌：校验库中记录未吊销未过期 → 签发新 Access Token（Refresh Token 轮换可选）

> 两条路径共用 `oidc.IssueCode`，不得各写一份生成逻辑。本期无同意页（consent），首方 SSO 下授权即视为同意，`scope` 直接生效。

### 14.3 令牌

令牌形态 / 有效期 / 存储**见接口文档 §4.7**，本文不复制。实现要点：

- ID Token / Access Token：RS256 签发（`oidc/jwt.go`），密钥集与轮换在 `oidc/jwks.go`；Access Token 含 `epoch` 供业务方自校验
- Refresh Token：opaque，sha256 后落 `oidc_refresh_token`；刷新时校验未吊销未过期，轮换可选
- Authorization Code：`SET al:oidc:code:{code} EX 120`，`GETDEL` 一次性消费
- 修改密码 → 递增 `al:pwdep:{uid}`，令牌校验时比对 epoch；同时批量标记该用户 refresh token 为 revoked
- 业务系统登出 → 调吊销端点：仅影响对应令牌，不影响 SSO 会话
- `grant_type` 不按客户端限制：固定支持 `authorization_code` / `refresh_token`，其他取值返回 `unsupported_grant_type`（接口文档 §4.3）

### 14.4 Claims 来源映射

## 15. 外部服务 Provider

### 15.1 存储 Provider（category=storage）

```go
type Storage interface {
    Put(ctx context.Context, key string, body []byte, contentType string) (url string, err error)
    Get(ctx context.Context, key string) ([]byte, error)
    Delete(ctx context.Context, key string) error
    URL(key string) string   // 拼接 domain / CDN

    // PresignPut 直传模式：签发一个有时效的 PUT URL，前端据此直传对象存储
    PresignPut(ctx context.Context, key string, contentType string, size int64) (uploadURL string, headers map[string]string, err error)
}
```

两个实现：

| type | 覆盖 | 说明 |
|------|------|------|
| `s3` | MinIO、腾讯云 COS、阿里云 OSS、七牛、AWS S3 | 均兼容 S3 协议，一个 Adapter 覆盖；`endpoint` + `path_style` 区分 |
| `local` | 本地磁盘 | 写入本地目录，由 Nginx 静态分发。不支持直传模式（无预签名能力），配置为 `direct` 时自动回退 `proxy` |

上传两种模式（`proxy` / `direct`）的流程与适用场景**以接口文档 §10.8 为唯一定义**（接口契约见其 §3.2），本节只列存储 Provider 侧实现要点；按 Provider 扩展字段 `upload_mode` 选择，同一个 bucket 可分别配置。

后端要点：

- `presign`：校验登录态、MIME 在 `allowed_types` 内、size ≤ `max_size`；生成 object key（服务端决定，不接受前端传路径）；签发 PUT 预签名 URL（TTL = `presign_ttl`）
- `commit`：仅记录"该 key 已上传"，不重新下载校验（避免多一次对象存储读）；随后可异步做一次 HEAD 校验大小与 MIME
- 直传模式必须在对象存储侧为该 bucket 配置 CORS（允许 Authloft 站点的 PUT），部署文档需写明

渠道图标不在 Authloft 内上传（接口文档 §5.3）：`icon_url` 由管理员自行托管后手填，后端只做 `^https?://` 格式校验，不读写对象存储，也不提供删除 / 替换逻辑。

小程序码路径：

- 扩展字段 `storage_path` 支持 JSONata 表达式，内置变量 `ticket_id`、`timestamp`
- 例：`'qrcodes_' & $.ticket_id & '.jpg'`；渲染后的 key 再拼 `path_prefix`
- 码图始终走中转模式（由 Authloft 调微信接口取到二进制后 `Put`），与 `upload_mode` 无关；`upload_mode` 只影响头像等用户上传场景
- 开启 `qrcode_auto_delete` 时，删除用的 key 由同一模板 + `ticket_id` 重算（§13.3）

### 15.2 消息 Provider（category=sms / email）

```go
type Sender interface {
    Send(ctx context.Context, to string, tpl string, params map[string]string) error
}
```

- `sms`：`aliyun_sms`、`tencent_sms`、`twilio` 等
- `email`：`smtp`（通用）、`ses`、`sendgrid` 等
- 模板内容存 `metadata` 或系统配置，支持多语言（`internal/i18n`）
- 发送异步化（内存队列 + 重试），不阻塞登录主链路；发送失败不影响验证码已生成的状态（§8.2）
- 管理后台提供"发送测试"验证配置（接口文档 §5.2），前端无直接交互

### 15.3 注册表与配置热更新

- 注册表：`Register(type, meta, factory)` + `NewAdapter(p)`；`meta` 同时驱动管理后台 `/schema`（接口文档 §5.3）——动态 schema 由适配器声明（`provider.Ext` 字段的标签、渲染类型与默认值，`key` 与 Ext 字段同名），admin 表单按 schema 渲染，不硬编码字段
- 加载：本地 LRU + singleflight（TTL 60s）
- 写 Provider → `DEL al:prov:v:{key}` → `INCR al:prov:ver` → `PUBLISH al:prov:chg {key}`
- 各实例：后台协程每 5s 比对 `al:prov:ver`；订阅 `al:prov:chg` 实现秒级生效
- 系统配置（`settings`）：写 `settings` 表（§4.7）→ 刷新本实例内存 → `PUBLISH al:settings:chg`；各实例订阅后重载，秒级生效

| 密码策略（settings 键，与接口文档 §5.6 同名同默认值） | `pwd_min_length=8`、`pwd_max_length=64`（服务端硬上限 64，只能调低）、`pwd_require_classes=3`（字符类 = 大写 / 小写 / 数字）、`pwd_disallow_username=true`、`pwd_disallow_common=true`；校验统一在 `security/policy.go`，注册 / 重置 / 改密复用。固定不可配（写死）：长度 > 64 拒绝、与用户名或邮箱完全相同拒绝、含空白字符拒绝 |
| 解码工具 | `POST /api/admin/decode` 排障用，解码 login_token / session_token（接口文档 §5.6） |
| 监控 | 会话活跃数、队列长度 / dropped / flush 耗时（接口文档 §5.6） |

## 17. 网关与 RPC（后端实现）

接口契约见接口文档 §6、§7。

| 项 | 实现要点 |
|----|----------|
| 网关 decode | `ANY /api/gateway/decode`：`X-Gateway-Token` 校验 → 解 session_token（优先级 `X-Authlofe-Token` Header → Cookie）→ 以响应头返回 `X-Session-Status` /`X-Session-ID` / `X-Session-Epoch` 等字段。**响应恒 JSON**（`codec` 白名单），调用方传 `Accept: application/octet-stream` 也忽略 |

## 19. 扩展点：新增一件东西要改哪些文件

| 新增内容 | 改动 | 不改动 |
|---------|------|--------|
| 一个第三方渠道 | `internal/provider/oauth/<type>/` 新包（`init()` 自注册） | handler、service、前端均不改 |
| 一个短信 / 邮件 / 存储厂商 | 对应 category 目录下新包 | 同上 |
| 一个 captcha 厂商 | `internal/provider/captcha/<type>/` 新包 + 前端一个 adapter | 后端其余不改；自绘图形码仍必须带 `provider_key` |
| 一个认证因子 | `internal/factor/<name>/` 新包 + 一行注册 + 前端一个组件 | 引擎不改 |
| 一个 StepKind | `factor.go` 加常量 + 对应因子 `Steps()` | 引擎按 `Steps()` 通用处理 |
| 一个事件类型 | `eventlog/event.go` 加常量与 detail 构造 | 写入路径不改 |
| 一个接口 / 一个字段 | `proto/api/<域>/*.proto` 加消息或字段 → `buf generate` → handler 装配 | `codec`、中间件、前端 `http.ts` 均不改 |
| 改某个接口的响应形状 | 只改 `.proto` + `dto/view.go` | 不新增"编码分支"，JSON 与 Protobuf 同步生效 |

判定是否满足"可插拔"的验收标准：新增渠道的 diff 不应出现在 `handler/`、`service/orchestrator/`、`dto/` 中；新增接口的 diff 不应出现在 `codec/`、`middleware/` 中。

### 21.2 各层测法

**A. 纯单元（无 IO，占比最大）**

| 对象 | 用例 |
|------|------|
| `security/token.go` | ① round-trip；② 篡改 ciphertext/nonce/prefix 必失败；③ 跨 purpose 不可解（login→session）；④ 不同 kid 不可解；⑤ 版本降级被拒；⑥ 过期令牌被拒；⑦ 空载荷 / 超长载荷 |
| `security/keystore.go` | kid 轮换期新旧密钥并存；未知 kid 报错 |
| `security/token.go`（`purpose=cookie` / `sync_payload`） | `al_login_state` 与 `SyncCookiePayload` 的 round-trip；篡改必失败；跨 purpose（cookie ↔ sync_payload ↔ login）不互解；`exp` 过期 / `remaining` 为空的边界 |
| `security/argon2.go` | 哈希可验证、不同盐不同结果；参数与 `config.argon2` 一致 |
| `security/policy.go` | 决策矩阵：长度边界、字符类 1–3、含用户名、弱口令；固定规则（>64 / 与用户名或邮箱相同 / 含空白）不可被 settings 绕过 |
| `security/rand.go` | 位数正确、字符集正确、不重复（大样本） |

### 21.3 必须有的"安全回归清单"（每次改动登录链路都要跑）

1. 越权：主因子未通过 → 任何二次因子接口被拒
2. 篡改：`login_token` 改一个字节即失效；跨 purpose 使用失效；过期失效
3. 重放：验证码 `GETDEL` 只能成功一次；RPC nonce 30s 内重复被拒；授权码一次性
4. 目标固定：MFA / 重置下发不接受请求传参的 phone/email
5. 归属标识隔离：登录链路的码只认 `tid`、账号域 bind 的码只认 `uid`；跨场景互不可解，且 bind 的码换 uid 即失效
6. 绑定隔离：`b` 前缀 state 不会被 `/api/sso/login/oauth` 接受；Cookie uid 与会话 uid 不一致的绑定请求被拒
7. 凭证泄露：所有 `/api/sso/**`、`/api/account/**` 响应（JSON **与 Protobuf 两条编码都要跑**）与 `methods` 注入快照经 `dto/view.go` 的公开视图，不含凭证字段
8. 注入安全：空壳 HTML 的注入块转义正确
9. 编码旁路：同一接口分别用 `Accept: application/json` 与 `application/octet-stream` 请求，断言解出的消息 `proto.Equal`，且二进制路径不存在"绕过视图裁剪"的第二条组装路径

### 21.4 覆盖率与门禁

- `internal/security`、`internal/cache`、`internal/otp`、`internal/orchestrator`、`internal/oidc`、`internal/codec`：行覆盖 ≥ 90%
- 全量 ≥ 70%；CI 门禁：`go test -race ./...`、`go vet`、`golangci-lint`、集成测试每日跑一次
- protobuf 门禁：`buf lint`、`buf breaking --against '.git#branch=main'`、`buf generate` 后 `git diff --exit-code`（生成物必须与 `.proto` 同步）
- 禁止为了覆盖率写无断言的测试

### 21.5 契约一致性（前后端）

- **双格式 golden**：每个用例在 `test/fixtures/` 落两份同源文件——`<name>.json` 与 `<name>.bin`（`proto.Marshal`，`Deterministic: true`）。CI 断言：① 两文件解出的消息 `proto.Equal`；② `<name>.json` 里**不出现裸数字**（正则扫 `:\s*-?\d`，`true/false` 除外），保证接口文档 §1.12 被真正执行
- `dto` 层生成 golden JSON（含 `methods` 注入快照），与前端 `tests/fixtures/*.json` 同源比对：CI 中用一个脚本比对两者，不一致即失败
- 前端 zod schema（`contract.ts`）对同一批 golden JSON 校验，用于防"多一个 / 少一个字段"的漂移；**类型真源仍是生成的 TS 消息类型**（接口文档 §12.9）
- Go 与 TS 类型由同一批 `.proto` 生成（接口文档 §11）；生成物提交进仓库，两端 `git diff --exit-code` 均须为空

## 22. 编码约束（写进 lint / review checklist）

1. 键名只出自 `cache/keys.go`；SQL 只出自 `repo/`；Redis 访问只出自 `cache/`
2. 时间只用注入的 Clock，禁止直接 `time.Now()`（便于测跨天 / 过期）
3. 随机只用 `security/rand.go`，禁止 `math/rand`
4. 登录主链路零同步写库：除建会话与必要的 `GETDEL` 外，所有写入必须经 `asyncqueue`。Review 时用"该写入是否影响当次响应正确性"判定（§5.2 白名单）
5. 不得在 `factor` / `provider` 层引入 Gin 或 HTTP 概念
6. 前台响应必须经 `dto/view.go` 裁剪成公开视图消息，再经 `codec.Write` 写出；禁止 `c.JSON` / `c.ProtoBuf` / 手写响应体（§3.14）
7. 日志不得打印 login_token、session_token、验证码、密钥、完整手机号 / 邮箱（必要时掩码）
8. 新增渠道的 diff 不得出现在 `handler/`、`orchestrator/`、`dto/`（§19 验收标准）
9. Protobuf 结构变更必须保持向下兼容（接口文档 §12.8），`ext` 反序列化失败要能回退；`.proto` 变更必须过 `buf breaking`
10. 会话续期按 §11.5 每次请求重签
11. 业务结果只允许用 `status` 表达：取值必须落在接口文档 §1.6 的封闭集合内；禁止新增该集合外的常量、禁止在 `error` 里塞第二个分支字段；兜底文案走 `error.message`
12. 管理员判定只有 `uid == 1` 一处（`middleware/admin.go`），禁止在 service / handler 里重复判断
13. 验证码归属标识按场景固定：登录 / 注册 / 重置 / MFA 用 `tid`，账号域 bind 用 `uid`；禁止跨场景混用（§10.1）
14. 三方 state 前缀即场景：`l` = 登录、`b` = 绑定已有账号；两个入口各自只接受自己前缀的 state，绑定接口不得签发 `login_token` 或重建会话（§12.4、§12.6）
15. ticket 的 `scene` 即扫码场景：`login` / `bind` 各自只被对应的轮询接口接受；小程序端只写 ticket，绑定判定只能在持有会话的 PC 端完成（§13.2b）
16. 配置只有两个来源：**启动项读 `config`（YAML，只读一次）**、**可热更新项读 `settings`（DB + 缓存）**；禁止在业务代码里写字面量默认值，禁止在 `config` 与 `settings` 放同一语义（§3.2）
17. 静态资源前缀只来自 `settings.static_base`，`handler/page.go` 与 `assets` 路由共用；禁止在模板里写死 `/assets`（§3.13）
18. 新增数据表必须同时新增 `repo` 与 `migrations` 脚本（§3.10）；`settings` 的键名只能来自接口文档 §5.6 的白名单
19. 接口报文结构只在 `.proto`（`proto/api/**`）：禁止手写镜像 struct、禁止在 handler 里拼匿名结构体做响应；Go 侧类型一律来自 `gen/go`
20. 整型字段一律 `int64`（接口文档 §1.12）：禁止 `int32` / `uint32` / `fixed32`；JSON 中的数字必须由序列化层输出字符串，业务代码不得自己 `fmt.Sprintf` 拼数字
21. 编码协商只在 `codec` 一处：业务代码与中间件不得读 `Accept`、不得判断格式、不得为某种编码写分支
22. 凭证字段只允许出现在 Admin 视图消息里（`api.Admin*`）；公开视图消息若出现凭证字段，视为设计错误而非实现错误（§3.5）
