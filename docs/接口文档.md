## 1. 通用约定

### 1.0 响应模型（Connect 协议）

sso / account / admin / rpc / setup 五个业务域的接口全部走 **Connect 协议**（connectrpc.com；后端 connect-go v1.21.1，前端 `@connectrpc/connect`）。路径形态 `POST /api.<域>.v1.<XxxService>/<Method>`（如 `/api.sso.v1.SsoService/LoginDefault`）。

- 成功（HTTP 200）：响应体即 RPC 响应消息，**无外层信封、无 `status` 字段、数据不平铺包裹**；JSON 编码为标准 protojson 映射（字段名 lowerCamelCase、省略零值字段，见 §1.1 / §1.12 / §12.9）
- 业务失败（HTTP 非 200）：Connect 错误体（§1.5），业务细分码承载在 `ErrorInfo` detail 中
- 编解码由请求 `Content-Type` 决定（`application/json` ↔ `application/proto`），响应与请求同编码

豁免（不走 Connect，保持各自原生格式，错误形态亦为原生，见 §1.5）：

- §1.3 登录流程（`/api.sso.v1.SsoService/**` 与扫码轮询）：流程态是 HTTP 200 响应数据（含失败态），仅系统 / 协议错误走 Connect 错误体
- 头像上传 `POST /api/account/avatar`（§3.2）：multipart 表单，保持 REST
- OIDC 标准端点（§4）：按 OIDC / OAuth2 RFC 6749 格式
- 网关 decode（§6）：纯响应头，无响应体
- `/metrics`：纯文本运维端点
- 页面路由（§8）：HTML

所有响应（成功、失败、豁免端点）统一回写 `X-Request-Id` 响应头（§1.1）。

### 1.1 请求公共约定

| 项                | 约定                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 协议              | Authloft 根域名记为 `{al_root}`（如 `https://authloft.example.com`）。**明文 HTTP 部署为一等公民**（放宽既有「全站 HTTPS」冻结句）：内网 / 测试环境 / 反代 TLS 终止后明文直连均可部署；公网明文部署存在会话令牌被窃听的风险，由部署方自行负责。会话 Cookie 的 `Secure` / `SameSite` 属性随 settings 键 `https_deployment` 驱动（§1.9、§5.6）。**明确不做（写死）**：HTTP→HTTPS 强制跳转与 HSTS 由网关层负责，Authloft 不提供 |

| CSRF              | 所有写 RPC + 登录相关 RPC 强制校验 `Origin` 与当前域名同源，跨站 403。**例外**：OIDC 端点、rpc 域、`/api/gateway/**`（服务间签名鉴权，无 `Origin`）不校验                                                                                                                                                                                                                                                                    |

| `X-Request-Id`    | 所有响应（成功 / 失败 / 豁免端点）统一回写链路 ID；服务端自生成（`crypto/rand` 16 字节 hex / 32 字符），不读、不透传、不信任入站同名头，生成失败留空串；错误体内**不重复携带**                                                                                                                                                                                                                                               |

### 1.3 登录流程信封（登录 / 注册 / 重置 / 三方 / 扫码完成）

`SsoService/LoginDefault`、`SsoService/Register`、`SsoService/ResetPassword`、`SsoService/LoginOauth`、`SsoService/GetLoginTicket`（完成登录时）共用同一响应消息（`LoginFlowResponse`）：

```jsonc
{
  "loginToken": "…", // 每次重签都返回新值，前端替换内存变量；success 时不再返回
  "status": "next", // 唯一业务态，取值即 §1.6 的封闭全量表
  "nextStep": {
    // status=next
    "kind": "form", // form | challenge | redirect | external | qrcode | poll
    "method": "otp_email",
    "endpoint": "/api.sso.v1.SsoService/LoginDefault",
    "fields": [
      {
        "name": "code",
        "label": "login.field.otpCode",
        "type": "otp",
        "length": "6",
        "maxAttempts": "5",
      },
    ],
    "retryAfter": "60", // 重发冷却（秒）
    "expiresIn": "300", // 当前挑战有效期（秒）
    "challengeData": {/* ... */}, // WebAuthn 标准 options 对象（注册 PublicKeyCredentialCreationOptions / 登录 PublicKeyCredentialRequestOptions，完整结构；前端不解析、整体透传，§12.9）
  },
  "binding": {
    // status=binding_required；allowSignup 由 Provider 配置的 enable_signup 映射而来（见 §2.7.5 字段映射）
    "providerKey": "qq",
    "displayName": "QQ",
    "allowSignup": true,
    "nickname": "…",
    "avatarUrl": "…",
  },
  "error": { "message": "验证码错误", "retryAfter": "60", "attemptsLeft": "3" }, // 仅失败态出现，字段均可省略
  "sessionId": "…", // status=success
  "sessionToken": "…", // status=success，仅无 Cookie 场景（小程序）返回
  "syncCookieUrl": "...", // status=success，多域名同步的**首跳**地址（后端已把加密载荷拼好；`sso_domains` 为空时省略，§2.9）
  "redirectTo": "https://…", // status=success
  "userId": "10086",
  "ticket": { "status": "success", "ticketId": "c7Kx9…" }, // 扫码轮询专用，结构见 §2.8
  "login": {/* ... */}, // 扫码轮询结果就绪（status=success）：内层为同一信封（§2.8）
  "bind": { "providerKey": "wechat_mp_scan", "displayName": "微信扫码" }, // 扫码绑定完成（§3.7.1 B）
}
```

**字段文案口径（i18n）**：`next_step.fields[].label` 与 §2.1 注入快照的 `methods[].fields[].label` / `challengeFields[].label` 下发的不是展示文案，而是前端 i18n 键（`login.field.*`）；zh / en 语言包在 `web/src/shared/i18n/{zh,en}/login.ts`，由 `shared/components/FieldRenderer` 渲染期 `t()` 解析（label 文本与验证码控件的 aria-label 同一出口，`sso.v1.Field.label` 注释同口径）。后端各因子声明、注入快照与 orchestrator 快照均不持有任何语言文案；缺键时前端回显键本身（可见、可排查），旧版本下发的中文字面量也按原文显示。`error.message` 不受本口径约束（服务端兜底文案，前端优先按 `status` 取 i18n，见下表）。

> 前端规则：响应含 `loginToken` 即**无条件覆盖**内存变量（旧值立即作废），`status=success` 时清空；**禁止**写入 localStorage / sessionStorage / Cookie。`status` 是唯一分支依据——非 `success` 即失败（扫码轮询的 `pending` / `scanned` 为进行中，不作失败处理，见 §1.6），前端不依赖第二套错误码，`error` 只承载展示信息，动作见 §1.6。**例外**：captcha 与 step-up 的传输层失败（缺凭据 / 校验失败 / 已使用 / 缺断言 / 断言无效）不套信封，直接返回非 200 的 Connect 错误体（§1.5），前端在统一错误拦截中按 `ErrorInfo.code` 处理（§1.6）。

| 字段                 | 说明                                                                                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `error.message`      | 可选。服务端下发的兜底文案；前端优先按 `status` 取 i18n 文案                                                                                                                                                |
| `error.retryAfter`   | 可选。冷却 / 解封剩余秒数，驱动倒计时                                                                                                                                                                       |
| `error.attemptsLeft` | 可选。验证码剩余尝试次数                                                                                                                                                                                    |
| `ticket`             | 可选。仅两条扫码轮询 RPC（`SsoService/GetLoginTicket`、`AccountService/GetThirdpartyTicket`）出现，结构为 `{status, ticketId}`（`ticketId` 为拉码时下发的值），`status` 取值见 §1.6 与 §2.8；其余接口不返回 |
| `login`              | 可选。仅 `SsoService/GetLoginTicket`（`scene=login`）且结果就绪（`status=success`）时出现，值为本节同一信封；其余接口不返回                                                                                 |
| `bind`               | 可选。仅 `AccountService/GetThirdpartyTicket` 且绑定完成（`status=success`）时出现，`{providerKey, displayName}`（§3.7.1 B）；其余接口不返回                                                                |

**登录成功的终点处理与默认落点**（`status=success` 时前端按以下顺序判定，三种情形互斥且完备；登录 / 注册 / 重置 / 三方 / 扫码各流共用本信封，均按此执行）：

1. `syncCookieUrl` 非空 → `location.replace(syncCookieUrl)` 走多域名同步链，后续跳转与最终落点由服务端加密载荷驱动（前端不解析，§2.9）；有 OIDC 上下文时同步链最终落点即 `redirectTo`
2. `syncCookieUrl` 为空且 `redirectTo` 非空 → 直接 `location.replace(redirectTo)`（OIDC 场景 `redirectTo` 即 `redirect_uri?code=…&state=…`，§4.2）
3. **两者皆空（无 OIDC 上下文且 `sso_domains` 为空，即直访 `/sso/login` / `/sso/register` / `/sso/reset` 的直登场景）→ 跳默认落点 `/account#/profile`**（hash 路由形态；本域相对路径，用户端资料页路由见 §8 与《前端架构》§5；会话已由 `Set-Cookie` 建立）；**禁止停留在「登录成功」提示页**

### 1.4 `step` 枚举与 `next_step.kind` 枚举

请求侧 `step`（请求体字段，本次要做什么动作）：

| step           | 含义                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| `challenge`    | 向后端要挑战数据：下发验证码 / 取 WebAuthn options / 取第三方授权 URL                                      |
| `verify`       | 提交结果并校验                                                                                             |
| `set_password` | 注册 / 重置专用：提交 `username` + `password` 完成建号或改密（三方免密建号时仅提交 `username`，见 §2.7.5） |

渲染侧 `kind`（`next_step.kind`、`methods[].steps` 的取值，即"这一步前端长什么样"）：

| kind        | 含义                                                             |
| ----------- | ---------------------------------------------------------------- |
| `form`      | 渲染输入框并提交                                                 |
| `challenge` | 无需输入，向后端要挑战数据（下发验证码 / 取 WebAuthn options）   |
| `redirect`  | 浏览器跳转（第三方）                                             |
| `external`  | 调宿主能力取 code（`wx.login`）；由宿主承载，Authloft 前端不实现 |
| `qrcode`    | 展示码图                                                         |
| `poll`      | 长轮询等待                                                       |

> 两组取值**不可混用**：`challenge` 在两个枚举中含义不同（请求动作 vs 渲染形态）。步骤序列见 §1.10.1，前端按 `kind` 分派、后端按 `step` 校验。

### 1.5 HTTP 状态码与 Connect 错误码

登录链路的业务态（流程态，含失败态）**一律返回 HTTP 200**，由 `status` 单独表达（§1.3 / §1.6）。**例外**：captcha 与 step-up 的传输层失败（缺凭据 / 校验失败 / 已使用 / 缺断言 / 断言无效）不套信封，按非 200 的 Connect 错误体返回（`invalid_argument` / `failed_precondition`，见下表），前端在统一错误拦截中处理。其余业务域的业务失败与协议错误按 Connect 错误体返回非 200，标准码 → HTTP 映射（connect-go v1.21.1 实现）：

| Connect code          | HTTP | 场景                                                                                            |
| --------------------- | ---- | ----------------------------------------------------------------------------------------------- |
| `invalid_argument`    | 400  | 请求体解码失败（JSON / Protobuf 非法、字段缺失 / 类型不符）；captcha 缺凭据 / 校验失败 / 已使用 |
| `failed_precondition` | 400  | step-up 缺断言（`verification_required`）或断言无效 / 过期 / 重放（`verification_invalid`）     |
| `unauthenticated`     | 401  | 需要会话 / 管理员会话 / 客户端凭据而未携带或失效                                                |
| `permission_denied`   | 403  | Origin（或 Referer）跨站、网关 Token 无效、签名校验失败、nonce 重放                             |
| `not_found`           | 404  | 资源不存在（管理后台单资源）；admin 域会话有效但非管理员亦返回 404（掩护管理面存在）            |
| `already_exists`      | 409  | 用户名 / 手机号 / 邮箱占用、重复绑定                                                            |
| `resource_exhausted`  | 429  | 限流、发送冷却、日限额、请求体超限                                                              |
| `internal`            | 500  | 内部错误，不暴露细节                                                                            |
| `unavailable`         | 503  | 服务不可用                                                                                      |

> 请求 `Content-Type` 不被支持时由 Connect 框架直接返回 415（无错误体语义差异，编解码见 §1.1）。

非 200 响应体为 **Connect 错误体**（JSON 形态如下；编解码同 §1.1），业务细分码承载在 `details` 的 `ErrorInfo` 中：

```jsonc
{
  "code": "invalid_argument", // 上表 Connect 标准码
  "message": "…", // 可选展示文案；前端优先按 ErrorInfo.code 取 i18n，其次本字段
  "details": [
    {
      "type": "api.common.v1.ErrorInfo",
      "value": "<base64 的 ErrorInfo Protobuf 字节>", // 消费方以 value 解码为准（生成类型见 §12.9）
      "debug": { "domain": "sso", "code": "password_weak", "retryAfter": "60" }, // 服务端调试视图，仅供人读
    },
  ],
}
```

captcha 失败时，`details` 允许并列一个 `api.common.v1.CaptchaConfig` 元素（`type` 为 `api.common.v1.CaptchaConfig`，`value` 为 base64 编码的消息字节），用于下发当前生效的 captcha 配置；复用既有消息，不新增消息类型，结构见 §2.5。

`api.common.v1.ErrorInfo` 字段（proto 定义见 §12.9）：

| 字段           | 说明                                                  |
| -------------- | ----------------------------------------------------- |
| `domain`       | 业务域：`sso` / `account` / `admin` / `rpc` / `setup` |
| `code`         | 业务细分码，封闭集合即 §1.6 词汇表                    |
| `message`      | 可选兜底文案（i18n 之后的最终展示）                   |
| `retryAfter`   | 可选。冷却 / 封禁剩余秒数，驱动倒计时                 |
| `attemptsLeft` | 可选。剩余尝试次数                                    |

- `request_id` 不在错误体内：所有响应统一走 `X-Request-Id` 响应头（§1.1）
- 协议级错误（解码失败、超限等）由 connect-go 框架生成，`code` 为标准码、无 `ErrorInfo` detail；业务失败由服务端构造 `connect.Error` 并挂 `ErrorInfo`
- 豁免端点的错误形态为各自原生格式（§1.0）：OIDC 按 RFC 6749 `{"error","error_description"}`；gateway 仅 HTTP 状态码 + 响应头；页面路由按 HTTP 语义
- 前端对非 200 一律走统一拦截：先取 `ErrorInfo.code` 查 §1.6 映射，无 detail 时按 Connect 标准码兜底（§1.6 末尾）

**扫码轮询的两套状态**：轮询接口的顶层 `status` 表达**本次轮询结论**（`pending` / `scanned` / `needs_step_up` / `expired` / `success` / 失败类），与 `ticket.status` 保持同步语义；`success` 仅出现于结果就绪。扫码票据的生命周期由轮询响应的 `ticket.status` 单独表达，取值封闭为 `pending`（未扫码）｜ `scanned`（已扫码、未确认）｜ `success`（结果已就绪，前端随即消费 `login` / `bind` 信封）｜ `expired`（票据过期，终态）｜ `failed`（认证或业务失败）。`failed` 时认证与业务结论（`target_taken`、`provider_disabled`、`user_not_found` 等）只由**同一响应的登录流程信封 `status`** 表达；`ticket.status` 是另一套封闭集，同名取值（`success` / `failed`）语义各自独立，不随场景扩张。除本节四个轮询取值（`pending` / `scanned` / `needs_step_up` / `expired`）外，本表不因轮询新增取值；其中 `needs_step_up` 只作轮询顶层 `status`，不进登录流程信封、不作 `ticket.status` 取值。

服务端约束：

- 本表取值的呈现位置：登录流程域作响应顶层 `status`（HTTP 200 数据，含失败态，§1.3），其余域作 `ErrorInfo.code`（Connect 错误体 details，§1.5）——一套词汇，登录域同样适用；其中 `captcha_required` / `captcha_invalid` / `verification_required` / `verification_invalid` 仅作 `ErrorInfo.code`，四个码都不是 `status` 取值
- 除接口特殊标注外，密码错误与账号不存在同码（`invalid_credentials`）；账号被禁用单独返回 `user_disabled`
- 验证码类 `challenge`（登录 / 重置）在目标未绑定任何账号时，**显式返回 `status=user_not_found`**（不签发 loginToken、不生成与发送验证码；统一口径见 §2.6）；`flow=reset` 的目标还须已绑定且已验证，未验证同样返回 `user_not_found`（见 §2.4）。MFA 场景不传目标（目标取 uid 绑定资料），不会命中该状态
- 本表是 `status` / `ErrorInfo.code` 的**封闭集合**：新增取值必须同步更新本表与前端 `errors.ts` 的映射；**禁止**在错误响应里塞第二个分支字段
- 特殊情况下可以使用 `ErrorInfo.message` / 流程态 `error.message` 表达，此时文案不考虑 i18n
- 未知异常在登录流程域一律映射为 `failed` + 兜底文案，其余域映射为 Connect `internal`（无 `ErrorInfo`），不暴露内部信息
- HTTP 层的非 200（§1.5）由 Connect 标准码映射或中间件产生，标准码本身不进本表；前端对非 200 走统一拦截（§1.5 末尾）

### 1.7 分页约定（管理后台 / 日志类）

- 请求：分页与排序字段进 RPC 请求消息：`{"page": "1", "pageSize": "20", "sort": "created_at", "order": "desc"}`（`page` 从 1 开始，`pageSize` 默认 20、上限 100）；`sort` / `order` 的取值由前端限定（管理后台功能，依赖管理端自律），后端不做白名单强制校验
- 响应：`{ "items": [...], "total": "128", "page": "1", "pageSize": "20" }`（数据字段即响应消息字段，无信封；空页时 `items` 省略——空 `repeated` 不输出，§1.1）

### 1.8 `login_token` 传递规则

| 场景                         | 传递                                                                                          |
| ---------------------------- | --------------------------------------------------------------------------------------------- |
| 常规登录 / 注册 / 重置 / MFA | 请求体顶层 `loginToken` 字段（proto 字段 `login_token`），与 `method`、`step`、`payload` 同级 |
| 第三方跳转回调               | 回调后由服务端新建 login_token 并在响应体返回（不塞进 URL）                                   |
| 小程序                       | 同常规；且响应额外下发 `sessionToken`                                                         |

`login_token` 为 `base64url(prefix‖nonce‖ciphertext‖tag)`，AAD 含 `purpose=login`，有效期 10 分钟（封装见《后端架构》§11.6.1，载荷见 §11.6.2）。

### 1.9 会话与续期

- Cookie 名默认 `al_session`（键 `cookie_name`），`HttpOnly` 恒定，`Secure` / `SameSite` 受 settings 键 `https_deployment`（§5.6）驱动：判定为 HTTPS → `Secure; SameSite=None`；判定为明文 → **省略 `Secure` 且 `SameSite` 联动降为 `Lax`**（`SameSite=None` 依浏览器策略须配 `Secure`，明文下不带 `Secure` 的 `None` Cookie 被拒收）。默认有效期 7 天（键 `session_ttl`，§5.6）
- 续期策略：每次请求均重签 session_token（`iat` / `exp` 刷新，`epoch` / `sid` 不变，纯计算、无存储写入），根据原始 session_token 来源判断:
  - 来源于 Cookie，则下发 `Set-Cookie`
  - 来源于 Header，则通过 `X-Authloft-Token` 传递 session_token
  - 来源于请求体（`TokenService/DecodeSession` 的 `sessionToken`），则以响应体字段 `renewedToken` 返回（§7.1）
- 改密 / 重置 / 管理员禁用 → 递增 `al:pwdep:{uid}` → 全部会话失效；登出仅清除当前会话 Cookie、不递增 `epoch`，**已签发令牌在有效期内仍然有效**（本期无服务端逐出，《后端架构》§11.1）

**`https_deployment` 驱动的 Cookie 属性口径**（settings 键定义见 §5.6，默认 `auto`；本键是实例的**部署形态声明**，只决定 Cookie 下发属性，不改任何接口语义）：

- 受影响 Cookie 清单（逐一列出，全部经服务端**同一个 Cookie 属性构造器**下发，随本键自动生效，不逐 Cookie 配置）：
  - `al_session`：`Secure` 判定为真 → `Secure; SameSite=None`；判定为假 → 省略 `Secure`、`SameSite=Lax`（见上条）
  - `al_login_state`（§2.7.2）：`HttpOnly` / `SameSite=Lax` / 会话级不变；`Secure` 判定为真 → `HttpOnly; Secure; SameSite=Lax`；判定为假 → 省略 `Secure`
  - 多域同步中转 `GET /sso/sync_cookie` 写入的会话 Cookie（§2.9）：接收端按同一构造器写入，随本键自动生效
  - 当前无其他下发 Cookie（CSRF 类 Cookie 不存在）；**后续新增任何 Cookie 下发点必须接入本键**，不得另行写死属性
- `auto` 推断规则（与《SDK-init》§4.4 定稿规则**逐字对齐**；服务端在 Cookie 下发点按**当前请求**逐请求判定）：
  1. 请求带 `X-Forwarded-Proto` 头 → 取逗号分隔**首个值**、忽略大小写判定：`https` → 按 HTTPS 处理；`http` 及其他任意值 → 按明文处理
  2. 头不存在 → 看请求自身 TLS：TLS 直连 → 按 HTTPS 处理；无 TLS → 按明文处理（**兜底**）
  3. 头优先于 TLS 判定：反代场景 TLS 终止在反代、服务端收到明文 + 头，头是该场景唯一可靠来源；头与直连 TLS 并存且矛盾时，以显式头声明为准
- 显式 `true` / `false` 覆盖推断；本键不校验请求方身份、**不引入 gateway-token 信任门**（Cookie 下发走浏览器直连路径，与 §6 网关鉴权无关）

### 1.10 因子能力表与 `biz_purpose` 因子策略表（跨端唯一定义）

> 本节是后端 `factor.Steps()` / `factor.Usages()`、注入快照 `methods[].steps`、前端步骤分派与验证内核策略判定**各处的取值来源**。改动必须同步各处实现，禁止任一端另立一份。

#### 1.10.1 因子能力表

> 只表达能力，不表达业务策略。「可承担用途」取值 `primary` / `secondary`，与《后端架构》§6.1 的 `Usage` 常量一致。

| 认证方式（`method`）                   | 可承担用途（`usage`）   | 步骤序列（kind，§1.4） | 说明                                                                   |
| -------------------------------------- | ----------------------- | ---------------------- | ---------------------------------------------------------------------- |
| 账密 `password`                        | `primary`               | `form`                 | 一步提交 username + password（+ captcha）                              |
| 短信验证码 `otp_sms`                   | `primary` / `secondary` | `challenge` → `form`   | 先触发下发，再提交 code                                                |
| 邮箱验证码 `otp_email`                 | `primary` / `secondary` | `challenge` → `form`   | 同上                                                                   |
| 通行密钥 `webauthn`                    | `primary` / `secondary` | `challenge` → `form`   | 固定 usernameless：先取 options（`allowCredentials` 为空），再提交断言 |
| 动态口令 `totp`                        | `secondary`             | `form`                 | 六位动态码                                                             |
| 恢复码 `recovery_code`                 | `secondary`             | `form`                 | 应急使用                                                               |
| 第三方·跳转 `thirdparty`(redirect)     | `primary`               | `redirect` → 回调      | 回调后继续走 verify                                                    |
| 第三方·小程序接口 `thirdparty`(api)    | `primary`               | `external` → 提交 code | `wx.login`；宿主承载，Authloft 前端不实现                              |
| 第三方·小程序扫码 `thirdparty`(qrcode) | `primary`               | `qrcode` → `poll`      |                                                                        |
| 已登录设备 `device`                    | `primary`               | `challenge`            | 内部因子，不出现在注入快照与任何对外响应                               |

完整登录链：`主因子` →（可选）`二次因子` → 完成 SSO。

### 1.12 数值表示（JSON 与 Protobuf 同口径）

JSON 是浏览器侧的默认编码，而 JS 的 `Number` 只能精确表示 ±2^53；`uid`、时间戳、`total` 等大整数一旦以裸数字下发，前端会在无感知的情况下丢精度。因此**JSON 中不出现裸数字**：

| 类型                                        | JSON 表示        | 例                                                         |
| ------------------------------------------- | ---------------- | ---------------------------------------------------------- |
| 整型（ID、时间戳、计数、长度、序号）        | 十进制字符串     | `"userId": "10086"`、`"retryAfter": "60"`、`"length": "6"` |
| 布尔                                        | `true` / `false` | —                                                          |
| 字符串 / 对象 / 数组                        | 不变             | —                                                          |
| 浮点（当前无此类字段；将来如需金额 / 比例） | 定点十进制字符串 | `"9.90"`                                                   |

约束：

- 接口报文 `.proto`（`proto/api/**`，§12.9）中**只用 `int64`**，禁止 `int32` / `uint32` / `fixed32` 等 32 位整型——protojson 对 64 位整数本就输出字符串，与本表天然一致；Protobuf 二进制内部仍是 varint，不牺牲体积与速度。存储模型 proto（§12.1～§12.3）不受本条约束（《后端架构》§1.6）
- **严格出、宽松入**：响应恒输出字符串；请求体同时接受字符串与裸数字（兼容手写调试），服务端按字符串解析，不回写数字
- 前端解析约定：时长 / 计数类可转数值使用（`retryAfter`、`expiresIn`、`pageSize`、`total`、`length`），**ID 与时间戳保持字符串**，只在展示时格式化，禁止参与 `Number` 运算
- 本节优先于全文示例：其余章节示例为可读性保留了裸数字写法，实现以前述规则为准

## 2. 登录 / 注册 / 重置（`api.sso.v1.SsoService`）

### 2.1 登录方式列表（**无接口**，随空壳页注入）

方式列表**不提供 HTTP 接口**。Go 渲染 `/sso/login`（`/sso/register`、`/sso/reset`）空壳页时，按页面 URL 的 query 生成快照并注入 `window.__AUTHLOFT_INIT__.methods`。

快照生成入参（来自空壳页 URL query，由渲染层读取，非前端请求）：

| 参数        | 必填 | 说明                                                                     |
| ----------- | ---- | ------------------------------------------------------------------------ |
| `client_id` | 否   | OIDC / SSO 客户端标识，用于过滤该客户端可用方式                          |
| `flow`      | 否   | `login`（默认）｜ `register` ｜ `reset`，用于注册 / 重置页只展示可用方式 |

注入结构（即 `__AUTHLOFT_INIT__.methods` 的值）：

```jsonc
{

    // 入口可见性，取自 settings（§5.6），供登录页隐藏入口

          "type": "password",
          "required": true,
        },
```

约束：

- 注入内容**永不返回**任何凭证字段；不注入未启用、`usage` 不匹配的方式；`device` 因子不出现
- `flags` 两值分别镜像 `allow_password_reset` / `allow_registration`（§5.6），只用于隐藏登录页的"忘记密码""注册"入口；`flow=reset` 时 `flags.passwordReset` 与 `methods` 为空数组二者一致
- 能力检测（`capability`）由前端执行；thirdparty 具体逻辑由前端按 channel 实现，不走 steps
- 注入快照是 login entry 的**首屏** captcha 配置来源（全局仅一个 captcha Provider）；运行期以 captcha 失败错误体 details 的 `api.common.v1.CaptchaConfig` 为准（§2.5），account entry 另有 `AccountService/GetConfig`（§3.2）。三处**同结构、同字段名**，字段定义见 §2.5，不得各自扩展
- 快照随页面一次性生成，页面存活期内不刷新；需要最新配置时刷新页面
- `flow=register` 时按注册开关过滤：`allow_registration` + `allow_signup_password` / `allow_signup_phone` / `allow_signup_email`（§5.6），**不读** `login_methods`（§2.3）
- `flow=reset` 时只保留 `otp_sms` / `otp_email`（`usage` 仍为 `primary`，`steps` 为 `challenge → form`），并受 `allow_password_reset` 控制：为 `false` 时 `methods` 为空数组，前端据此隐藏重置入口（§2.4）；不读 `login_methods`
- 注入快照只表达能力（`usage` / `steps` / `fields` / `capability` / `codeLength` / `resendAfter` / `expiresIn` / `providers`），**不表达策略**——不指定「二次验证必须用哪个因子」，不带策略表的有效期 / 重试 / 限流数值；`usage` 是因子能力（可承担主 / 二次因子）而非业务用途；业务用途统一由 §1.10.2 的 `biz_purpose` 表达，且只进服务端判定，不进注入快照
- 小程序 / 宿主环境不渲染 Authloft 空壳页，**不消费**本快照（Authloft 不负责小程序端实现，需求 §4.3.5）

### 2.2 `SsoService/LoginDefault` — 统一提交端点（flow=login,除 thirdparty 外）

鉴权：无（首次不带 `loginToken`）。

| 字段         | 类型   | 必填 | 说明                                                                                                                                                                                                    |
| ------------ | ------ | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `loginToken` | string | 否   | 首次不带；后续必须带（内存变量回传，proto 字段 `login_token`）                                                                                                                                          |
| `method`     | string | 否   | 无 `login_token` 时必须带。取值：`password`｜`otp_sms`｜`otp_email`｜`webauthn`｜`totp`｜`recovery_code`；`totp` / `recovery_code` 仅由 §3.8 的二次验证使用，本端点不接受（其余取值在本端点只作主因子） |
| `step`       | string | 是   | `challenge` ｜ `verify`（注册 / 重置端点另有 `set_password`，见 §2.3 / §2.4）                                                                                                                           |
| `payload`    | object | 是   | 各因子字段，见 2.6                                                                                                                                                                                      |
| `captcha`    | object | 条件 | 请求级字段（与 `payload` 平级），提交格式见 §2.5                                                                                                                                                        |
| `oidc`       | object | 否   | OIDC 授权上下文，取自 `__AUTHLOFT_INIT__.oidc`（§8），仅在首次请求（尚无 `login_token`）时回传，服务端据此写入 `login_token.oidc`                                                                       |

响应：登录流程信封（§1.3）。

编排规则（后端单一引擎）

1. 解 `login_token`（失败 → 回到第一步，不报错给细节）
2. 按 `method` 取因子，校验其可承担**主因子**（`usage` 含 `primary`）且 `step` 属于该因子 `Steps()`；该方式已被关闭（不在 `login_methods` 内）→ `status=method_disabled`（§1.6）
3. 本端点只承载主因子；`mfa_required` 之后的二次因子步骤一律走 §3.8 的 `StartVerification` / `SubmitVerification`，本端点收到二次因子请求按 `status=step_invalid` 拒绝
4. `challenge` 步统一过 captcha 拦截（§2.5 触发规则）
5. 通过 → 重签 `login_token`（`passed += method`）；主因子通过且该用户启用 MFA → `mfa_required`
6. 无需 MFA 时全部通过 → 建会话（1 次 Redis 写）→ 日志 / `last_login_at` 走延迟队列 → `success`；需要 MFA 时由 §3.8 的 `SubmitVerification` 完成建会话并返回同一登录信封

### 2.3 `SsoService/Register` — 注册（flow=register）

与 2.2 同构，仅 `flow=register`。两种入口：

| step           | payload                      | 说明                                                                                                                                            |
| -------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `challenge`    | `{ "email" 或 "phone" }`     | 验证码注册入口；`phone` 受 `allow_signup_phone` 控制、`email` 受 `allow_signup_email` 控制（默认均 `true`，§5.6）；captcha 必须（请求级，§2.2） |
| `verify`       | `{ "code" }`                 | 校验验证码（biz_purpose=register）                                                                                                              |
| `set_password` | `{ "username", "password" }` | 用户名 `^[A-Za-z0-9_]{5,20}$`（**用户名规则的唯一定义处**，设置后不可改，其余文档一律引用本节）；密码须满足密码策略（§5.6）                     |

用户名 + 密码注册（`allow_signup_password`，默认 `true`）：直接从 `step=set_password` 进入，无 `challenge` / `verify`，payload 为 `{ "username", "password" }`（captcha 必填，请求级）；`username` / `password` 规则同上。

注册方式**只受注册开关控制**，与登录方式开关无关：`allow_registration`（整体）＋ `allow_signup_password` / `allow_signup_phone` / `allow_signup_email`（三种方式各一，默认均 `true`，清单见 §5.6）；`username + password` 注册只受 `allow_signup_password` 控。`login_methods` 只控登录，**不参与**注册页可选项的判定（§2.1）。

响应：`status=success`（直接完成登录，写 Cookie）或 `status=next`（`next_step` 声明下一 step）；整体注册关闭（`allow_registration=false`）或对应注册方式开关关闭时，一律返回 `status=signup_disabled`（§1.6 既有取值，不新增状态）。`set_password` 步的字段级失败：`username` 已被占用 → `status=username_taken`，`password` 不满足策略（§5.6）→ `status=password_weak`（§1.6）。

### 2.4 `SsoService/ResetPassword` — 重置密码（flow=reset）

与 2.2 同构，`flow=reset`。前提：用户已设置密码且已绑定并验证邮箱 / 手机号。

| step           | payload                  | 说明                                                                                                                      |
| -------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `challenge`    | `{ "email" 或 "phone" }` | 目标必须是**已绑定且已验证**的；未绑定或未验证时返回 `status=user_not_found`（§1.6 / §2.6）；captcha 必须（请求级，§2.5） |
| `verify`       | `{ "code" }`             | 验证码 biz_purpose=reset                                                                                                  |
| `set_password` | `{ "password" }`         | 新密码，需满足强度策略                                                                                                    |

成功 → 递增 `al:pwdep:{uid}`（全部会话与已颁发令牌失效）+ 异步审计。

关闭态：`allow_password_reset=false`（默认 `true`，§5.6）时，`challenge` 与后续各 `step`（`verify` / `set_password`）一律返回 `status=reset_disabled`（§1.6）：不发码、不校验验证码；前端隐藏重置入口。

### 2.5 人机校验

**全局仅启用一个 captcha Provider**。配置对象**在本节唯一定义**（`__AUTHLOFT_INIT__.captcha`、`AccountService/GetConfig` 的 `captcha`、错误体 details 的 `api.common.v1.CaptchaConfig`；三处同结构同字段名，复用既有消息，不新增消息类型）：

```jsonc
{ "providerKey": "cf_turnstile", "type": "turnstile", "siteKey": "0x4AAA…" }
```

| 字段                                  | 说明                                                                                      |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| `providerKey`（proto `provider_key`） | 当前生效的 captcha Provider；内置自绘回退固定为 `builtin_image`                           |
| `type`                                | `image` ｜ `turnstile` ｜ `recaptcha` ｜ `hcaptcha`；`image` = 内置自绘图形码（含降级态） |
| `siteKey`（proto `site_key`）         | 第三方站点 key；`type=image` 时为空串                                                     |

保留一个自绘图形码接口：

#### `SsoService/CreateCaptchaImage` — 新建自绘图形码（直接返回图）

```jsonc
// 响应
{ "id": "b7f3…", "imageBase64": "iVBORw0KGgo…", "expiresIn": 300 }
```

前端直接用 `data:image/png;base64,{imageBase64}` 渲染，**不再二次请求图片**。对应后端 §5.1 `al:cap:{id}`。

#### 提交格式（两类 Provider 统一）

```jsonc
// 请求级字段，与 payload 平级（不在 payload 内）
{
  "captcha": {
    "providerKey": "cf_turnstile", // 两类都必须带，取自当前 captcha 对象的 providerKey（见上）
    "token": "0.xxx", // 第三方：厂商 token
    "id": "b7f3…", // 自绘：图形码 id
    "answer": "123", // 自绘：用户输入
  },
}
```

自绘图形码同样必须带 `providerKey`：服务端用它定位当前 captcha Provider，再核对 `al:cap:{id}`（后端 §9.2）。

#### 降级规则（无第三方可用时）

- **判定**：`category=captcha` 的 Provider 无可用项（未配置 / 全部禁用 / 健康检查失败）时，服务端自动降级为内置自绘图形码：`providerKey=builtin_image`、`type=image`、`siteKey` 省略（零值不输出）。内置项不是 Provider 表记录，`builtin_image` 直接分派到内置实现（不查表）
- **不新增端点、不新增 `status`**：取图仍走 `SsoService/CreateCaptchaImage`，提交仍用上方统一格式（自绘带 `id` + `answer`）
- **下发一致**：三处配置（§2.1 注入快照、§3.2 `AccountService/GetConfig`、captcha 失败时错误体 details 的 `api.common.v1.CaptchaConfig`）都按"当前生效项"生成，`type` 必须能表达 `image` 回退态；降级在每次生成时重新判定，不缓存
- **错误体携带配置**：所有 captcha 失败响应（`ErrorInfo.code=captcha_required` / `captcha_invalid`）在错误体 details 中携带 `api.common.v1.CaptchaConfig`（结构同上）
- **前端不依赖注入快照**：弹窗内 widget 按错误体 details 中 `CaptchaConfig.type` 渲染（第三方 iframe / 自绘图），注入快照只作首屏预判（提前预加载厂商脚本 + 决定「点击即弹窗」的时机），不作唯一依据——因此运行期降级无需刷新页面
- **校验侧**：自绘码校验复用《后端架构》§9.2 既有实现，`id` + `answer` 的一次性语义与第三方 `token` 一致（校验即失效）；不新增 `status` 取值

前端配合形态（实现细节见《前端架构》§3.5，本节只定契约边界）：

- **一律弹窗**：`captcha_required` / `captcha_invalid` 由人机校验弹窗吸收，业务表单不内联 widget；确认后重提**同一请求**（仅请求级 `captcha` 换新），`captcha_invalid` 在窗内循环，其余 `status` 关窗交既有状态机
- **触发时机**：本表「必须」的场景（`challenge` 类、拉码、绑定 challenge、注册直达 `set_password`）前端已知必经 → 点击即弹窗、确认后只发一次请求；「密码登录」由服务端计数触发、前端不可预知 → 先发裸请求，命中 `captcha_required` 才弹窗。两种时机都不改请求 / 响应契约
- **凭据一次性**：每次重提都必须换新凭据（弹窗内每轮重挂 widget）；取消弹窗表示本次提交作废，不影响任何已有流程态与 `login_token`

触发规则（服务端统一拦截；《后端架构》§9.3 引用本表，后端中只做实现）

| 场景                                    | 是否必须                                         |
| --------------------------------------- | ------------------------------------------------ |
| 任何一次性验证码下发                    | 必须，每次下发都要新的                           |
| WebAuthn 取 options                     | 不需要                                           |
| 密码登录                                | 同账号当日失败 ≥3 次（默认阈值，后台可配）后必须 |
| 注册 / 重置的下发                       | 必须                                             |
| 两步验证阶段下发                        | 必须（与主因子各自独立校验）                     |
| 绑定 / 换绑手机号、邮箱（账号域，§3.4） | 必须                                             |
| 拉取小程序码                            | 必须                                             |
| TOTP 绑定                               | 不下发验证码，无需 captcha                       |

> 本表是 captcha 触发规则的唯一定义（后端拦截、前端配合重提均以此为准）。触发后的响应语义统一走错误体（§1.5）：`captcha_required` / `captcha_invalid` 仅作 `ErrorInfo.code`，不作 `status`；新增触发场景只加行，不新增 `status` 取值；冷却、日限额、验证码有效期与尝试次数上限的键名与默认值见 §5.6「验证码限流设置项」。
> 本表的场景名只用于 captcha 触发判定，与 step-up 的 `biz_purpose` 不是同一概念，不得互相引用取值。

### 2.6 各因子 `payload` 对照表

| method                  | step        | payload                | 说明                                                                                                                                                                                                                                                 |
| ----------------------- | ----------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `password`              | `verify`    | `{username, password}` | 单步 form；`captcha` 为请求级字段，失败≥3 次（默认阈值，后台可配）后必填，不在 `payload` 内                                                                                                                                                          |
| `otp_sms` / `otp_email` | `challenge` | `{phone}` / `{email}`  | 主因子场景传目标；`captcha` 为请求级字段                                                                                                                                                                                                             |
| `otp_sms` / `otp_email` | `challenge` | `{}`                   | **MFA 场景不传目标**，目标取 `uid` 已绑定资料                                                                                                                                                                                                        |
| `otp_sms` / `otp_email` | `verify`    | `{code}`               | 6 位；绑定 `biz_purpose` 与 `tid`                                                                                                                                                                                                                    |
| `webauthn`              | `challenge` | `{}`                   | 固定 usernameless：`allowCredentials` 为空，要求注册时创建可发现凭据（resident key）。响应 `nextStep.challengeData` 为完整 WebAuthn options 对象（`PublicKeyCredentialRequestOptions`，前端不解析、整体透传给 `navigator.credentials.get()`，§12.9） |
| `webauthn`              | `verify`    | `{credential}`         | `@simplewebauthn` 断言对象原样提交                                                                                                                                                                                                                   |
| `totp`                  | `verify`    | `{code}`               | 仅二次因子，±1 时间步                                                                                                                                                                                                                                |
| `recovery_code`         | `verify`    | `{code}`               | 格式 `xxxx-xxxx`，仅二次因子                                                                                                                                                                                                                         |

`captcha` 不属于任何因子的 `payload`：所有触发场景共用请求级 `captcha` 字段（§2.2 / §2.5），是否需要按 §2.5 触发表判定。

主因子 `challenge` 时目标未绑定任何账号：**返回 `status=user_not_found`**（不签发 `login_token`、不生成与发送验证码，见 §1.6）。用户可更换手机号 / 邮箱后重新发起（每次 `challenge` 均需新 captcha，重试成本由 captcha 与限流兜底）。`flow=reset` 的 `challenge` 在前提不满足（目标未绑定 / 未验证）时同样返回 `status=user_not_found`（见 §2.4）。MFA 场景不传目标（目标取 uid 绑定资料），不会命中该状态。

`otp_sms` / `otp_email` 的 `verify`：累计失败达 `otp_max_attempts`（默认 5，§5.6）即作废该验证码，返回 `status=too_many_attempts`（§1.6）；未达上限的失败返回 `invalid_code`（带剩余次数）。

> **`steps` 粒度**：method 级 `steps` 为**所辖渠道步骤的并集**（示例中 `redirect` / `external` / `qrcode` 分别是 `redirect` / `api` / `qrcode` 三个渠道的首个 `kind`）；每个渠道的精确序列**以 §1.10.1 对应渠道行为准**（`redirect` → 回调、`api` → 提交 code、`qrcode` → `poll`），本处不重复展开。前端按 `channel` 分派，后端 `factor.Steps()` 按 §1.10.1 逐渠道返回。

#### 2.7.2 `SsoService/Authorize` — 取第三方授权 URL（RPC，非 302）

参数

- `provider` 必填，`providerKey`
- `scene` 非必填，`login`（默认），为 `bind` 表示已登录用户从安全中心发起绑定，**需 `al_session`**，否则 401（`unauthenticated`）
- `client_id`、`scope`、`nonce`、`code_challenge`、`code_challenge_method` 等 OIDC 上下文（来自 `/auth/authorize`）由前端落 `localStorage`，不带进接口

响应：`{ "authorizeUrl": "https://graph.qq.com/oauth2.0/authorize?…&state=…" }`

服务端：生成带前缀的随机 `state` → 写入 `al_login_state` Cookie（只含 state；`scene=bind` 时额外写入当前会话 `uid`）→ 返回 URL，由前端 `location.replace` 跳转（不做后端 302）。

`state` 前缀（前端与后端都据此区分场景，后端 §12.4）：

| 前缀 | 场景          | 回调接口                                 |
| ---- | ------------- | ---------------------------------------- |
| `l`  | `scene=login` | `SsoService/LoginOauth`（§2.7.4）        |
| `b`  | `scene=bind`  | `AccountService/ThirdpartyOauth`（§3.7） |

`al_login_state` Cookie 属性：`HttpOnly` / `SameSite=Lax` 恒定；`Secure` 受 settings 键 `https_deployment` 驱动（§1.9 驱动口径：判定为真 → `HttpOnly; Secure; SameSite=Lax`，判定为假 → 省略 `Secure`）；**会话级 Cookie**（不设 `Max-Age`），服务端加密（`AAD purpose=cookie`，《后端架构》§11.6.1）内含 10 分钟过期兜底；回调校验通过或失败后立即删除，再次签发即覆盖。

OIDC 上下文不进 Cookie：跳转会丢弃前端内存态，前端在 `location.replace` 之前把 `__AUTHLOFT_INIT__.oidc`（若存在）写入 `localStorage`（键 `al_oidc_ctx`，前端 §4.1）；回调后读出，随 `SsoService/LoginOauth` 的请求体 `oidc` 字段回传（§2.7.4），读完即清。登录端允许落盘的数据只有 `oidc`（`al_oidc_ctx`）；`login_token` 仍严格内存态。

#### 2.7.3 `GET /sso/oauth/callback/{provider_key}`（页面）

**不含任何业务逻辑**（前端 §4.4）：Go 渲染空壳，`OAuthCallbackPage` 把 `location.search`（`code`、`state` 等）原样作为 body JSON，补上路径参数中的 `provider_key`，再按 `state` 首字母分派（前缀表见 §2.7.2）：

| `state` 首字母 | 目标 RPC                         | 说明                                                        |
| -------------- | -------------------------------- | ----------------------------------------------------------- |
| `l`            | `SsoService/LoginOauth`          | 登录场景（§2.7.4）；额外带上从 `localStorage` 读回的 `oidc` |
| `b`            | `AccountService/ThirdpartyOauth` | 绑定已有账号（§3.7）                                        |
| 其他 / 缺失    | —                                | 视为 `state_mismatch`，跳 `/sso/login`                      |

```jsonc
// SsoService/LoginOauth
{ "providerKey": "qq", "code": "…", "state": "l…", "oidc": {/* 可缺省 */} } // 其余 query 原样透传
```

#### 2.7.4 `SsoService/LoginOauth` — 三方登录统一入口

合并跳转回调与小程序提交。

| 字段          | 必填 | 说明                                                                                                              |
| ------------- | ---- | ----------------------------------------------------------------------------------------------------------------- |
| `providerKey` | 是   |                                                                                                                   |
| `code`        | 条件 | 第三方授权码；小程序为 `wx.login()` 的 code。`stage=complete`（默认）时必填，`stage=scanned` 时不带               |
| `state`       | 条件 | redirect 通道必填，与 `al_login_state` Cookie 比对；`stage=scanned` 时不带                                        |
| `stage`       | 否   | `complete`（默认，完成授权并写入结果）｜ `scanned`（仅上报"已扫码"，写 `ticket.status=scanned` 空结果）           |
| `ticketId`    | 否   | 扫码场景：结果写入该 ticket；`stage=scanned` 时必填                                                               |
| `loginToken`  | 否   | 小程序 `api` 通道 / 绑定中间态时回传                                                                              |
| `oidc`        | 否   | OIDC 上下文，取自跳转前落 `localStorage` 的 `__AUTHLOFT_INIT__.oidc`（§2.7.2）；服务端据此写入 `login_token.oidc` |

服务端：校验 state（redirect 通道，**必须是 `l` 前缀**）或 Referer（小程序）→ Exchange / FetchUser → 查 `user_thirdparty_bind` → 按 provider 与场景决定响应形态：

| 场景                  | 响应                                                                                                                                                                                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 带 `ticketId`         | 写 `al:ticket:{ticket_id}`（1 次 Redis 写），返回 `{status:"success", ticketId}`；写入值为 `TicketResult`（《后端架构》§11.6.5），按 ticket 的 `scene` 分派：`login` → 填 `login_result`，`bind` → 填 `thirdparty_identity`（§3.7.1）。PC 端靠轮询取走 |
| 浏览器（无 ticketId） | 登录流程信封；完成登录时 `Set-Cookie: al_session`                                                                                                                                                                                                      |
| 小程序（无 ticketId） | 登录流程信封，额外返回 `sessionToken` 字段（不写 Cookie）                                                                                                                                                                                              |
| 未绑定                | `status=binding_required` + `binding{...}`                                                                                                                                                                                                             |
| 该用户已启用 MFA      | `status=mfa_required`，后续走 §3.8 的 `StartVerification`（`bizPurpose=login`）；扫码场景（带 `ticketId`）改写 `al:ticket:{ticket_id}` 快照为 `mfa_pending`，PC 端轮询得 `needs_step_up` 后按 §2.8 MFA × 扫码 续走二次验证                             |
| `state` 为 `b` 前缀   | **不由本接口处理**：绑定已有账号走 `AccountService/ThirdpartyOauth`（§3.7）                                                                                                                                                                            |

> **扫码两阶段写入**（`stage`，不新增端点）：小程序端进入页面先 `stage=scanned`，用户确认后 `stage=complete`。
>
> - `stage=scanned`：只带 `providerKey` + `ticketId`，**不需要任何凭证**。服务端取 `al:ticket:payload:{ticket_id}` 快照（《后端架构》§11.6.4；CreateQrcode 时 1 次写入，TTL 与 ticket 同寿命，默认 600s）校验「快照存在（缺失即不存在 / 已过期）、`scene` 与本次扫码用途一致（登录 `login` / 绑定 `bind`，§3.7.1 B）、`providerKey` 匹配」——本接口 wire 仅携带 `ticketId`、无 ticket 加密串可解（微信码图 scene 上限 32 字符仅容 `ticket_id`，小程序端物理拿不到完整 ticket 串）→ 写 `al:ticket:{ticket_id}` = `TicketResult{status:"scanned"}`（`channel=qrcode`，不含 `login_result` / `thirdparty_identity`）→ 返回 `{ "status": "scanned" }`（票据状态应答，非 §1.3 登录流程信封，取值沿用 `ticket.status`）。重复上报幂等；已存在 `success` 时不覆盖。
> - `stage=complete`（默认）：带完整凭证，按上表场景整体覆盖为 `status=success`（或 `status=failed`）。

```jsonc
// stage=scanned（仅上报已扫码）
{ "providerKey": "wechat_mp_scan", "ticketId": "c7Kx9…", "stage": "scanned" }
// 响应
{ "status": "scanned" }
```

#### 2.7.5 绑定中间态

三方身份解析成功、但查不到绑定记录时返回 `status=binding_required`。前端**只给两个选项**：

| 用户选择               | 请求                                                                      | 约束                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 创建新账号             | `SsoService/Register` 的 `set_password` 步，仅提交 `username`（免密建号） | 需该 provider `enable_signup=1`；`enable_signup=0` 时本项置灰不可选（见下方口径），服务端仍会拒绝该请求；**该端点须接受 `flow=login` 的 `login_token`**（见下方说明） |
| 退出并使用其他账号登录 | 不发请求：前端清空 `login_token` → `location.replace('/sso/login')`       | 仅丢弃内存态，服务端无状态                                                                                                                                            |

> **`enable_signup=0` 的口径**：流程分支不变——未绑定用户仍返回 `status=binding_required`，并在信封下发 `binding.allowSignup=false`；前端据此把「创建新账号」置灰、只保留「退出并使用其他账号登录」，并提示"该渠道未开放注册"。**不提供"绑定已有账号"分支**（见下方说明）；也**不得**用 `status=user_not_found` 表达"渠道关闭建号"——该状态只表示账号 / 绑定目标不存在（§1.6）。

> **字段映射**（两个名字分属两层，非笔误）：Provider 的 DB 列与 §5.3 动态 schema 字段名为 `enable_signup`（"允许用于注册"策略开关，服务端校验以此为准）；信封 `binding` 对象据此组包时**字段改名为 `allowSignup`**（§1.3），语义为"本次登录该渠道是否允许创建新账号"，取值与 `enable_signup` 一一对应（`enable_signup=0` ↔ `allowSignup=false`）。前端置灰建号入口的依据即 `binding.allowSignup=false`。

`set_password` 的 `password` 是否必填，由服务端按 `login_token.tp` 判定（消除同一 step 的两种互斥口径）：

| `login_token.tp`      | `set_password` 载荷    | 说明                                            |
| --------------------- | ---------------------- | ----------------------------------------------- |
| 空（普通注册 / 重置） | `{username, password}` | 密码须满足密码策略（§5.6）；用户名规则见 §2.3   |
| 非空（三方免密建号）  | `{username}`           | 仅提交用户名；服务端**忽略**请求中的 `password` |

> `SsoService/Register` 接受的 `login_token.flow`：`register`（普通注册）与 `login`（三方免密建号，此时 `tp` 必非空）。绑定中间态由登录流程进入，`flow` 保持 `login`，**服务端不得因 `flow` 不匹配而拒绝**。

> **不提供"绑定已有账号"分支**：若需把三方身份绑到已有账号，由用户先正常登录，再从安全中心发起绑定（§3.7，走 `SsoService/Authorize`（`provider={key}&scene=bind`））。

自动绑定（`auto_bind=1`）：按 `auto_bind_fields`（默认 `email,phone`）匹配已有用户直接绑定，跳过绑定页；默认关闭。若自动绑定命中的用户已启用 MFA → 继续 `mfa_required`。

> `flow` 枚举只有 `login` / `register` / `reset`；绑定已有账号不单独开登录端点，走 §3.7 的账号域接口。

### 2.8 扫码（微信小程序，channel=qrcode）

> 本节三个接口同时服务登录与绑定两个场景，靠 `TicketPayload.scene` 分派（《后端架构》§11.6.4）：`scene=login` → 本节流程（完成登录）；`scene=bind` → §3.7.1 B（完成绑定，需会话）。

#### `SsoService/CreateQrcode` — 拉取小程序码

**必须携带 captcha**，入参走请求消息。登录与绑定共用本接口，靠 `scene` 区分。

```jsonc
// 请求
{ "providerKey": "wechat_mp_scan", "scene": "login", "captcha": { "providerKey": "cf_turnstile", "token": "0.xxx" } }
// 响应
{ "ticket": "…", "ticketId": "c7Kx9…", "qrcodeUrl": "https://cdn…/qrcodes_c7Kx9….jpg", "expiresIn": 600 }
```

| 字段          | 必填 | 说明                                                                                           |
| ------------- | ---- | ---------------------------------------------------------------------------------------------- |
| `providerKey` | 是   | 扫码类 Provider                                                                                |
| `scene`       | 否   | `login`（默认）｜ `bind`（已登录用户从安全中心发起绑定）。**`bind` 需 `al_session`，否则 401** |
| `captcha`     | 是   | 每次拉码都要新的（§2.5）                                                                       |

服务端：生成 `ticket_id`（长度上限见《后端架构》§11.6.4）→ 加密为 `ticket`（`TicketPayload{ticket_id, provider_key, scene, iat, exp}`，同节）→ 写快照键 `al:ticket:payload:{ticket_id}`（1 次 Redis 写，TTL = ticket `exp`，默认 600s；小程序端提交只带 `ticketId`，服务端据此快照校验，见 §2.7.4）→ `GetwxacodeUnlimit` → JPEG 压缩 → Storage Put（中转模式，`storage_path` JSONata 渲染）。

> `scene` 写进 ticket 并由服务端加密保护（AES-256-GCM 认证），客户端不可篡改；后续小程序端提交与 PC 端轮询都据此分派。
> 全链路统一用 `ticket_id` 这一个名字（响应字段、Redis 键、Payload 字段、轮询回传），与 `LoginTokenPayload.tid`（登录会话标识，《后端架构》§11.6.2）是两个概念。

#### `SsoService/GetLoginTicket` — 查询 / 长轮询 / 完成登录

| 字段     | 说明                                                                             |
| -------- | -------------------------------------------------------------------------------- |
| `ticket` | 是                                                                               |
| `poll`   | 否，长轮询最长等待秒数，上限 15（本上限全文档唯一定义处，其他章节一律引用 §2.8） |

> 轮询响应的 `ticket.status` 取 `pending` ｜ `scanned` ｜ `success` ｜ `expired` ｜ `failed`（分层见 §1.6）；顶层 `status` 同步取本次轮询结论（`pending` / `scanned` / `needs_step_up` / `expired` / `success` / 失败类），`success` 仅出现于结果就绪。`ticket.status` 仍是五值封闭集（`pending` / `scanned` / `success` / `expired` / `failed`），`needs_step_up` 场景下 `ticket.status` 取 `scanned`，不新增第六值。命中授权时 `login` 字段为 §1.3 的登录流程信封。`scanned` 由小程序端 `SsoService/LoginOauth` 的 `stage=scanned` 写入（§2.7.4），本接口只读——实现细节：命中未被消费的 `scanned` 中间态时，服务端可以 `SET NX` 幂等回写同值（防中间态意外丢失，不产生新状态，不属业务写入）；一次性消费（`GETDEL`）仅限终态（`success` / `failed`）。

```jsonc
// 未就绪：未扫码
{ "status": "pending", "ticket": { "status": "pending", "ticketId": "c7Kx9…" } }
// 未就绪：已扫码（顶层同步 scanned）
{ "status": "scanned", "ticket": { "status": "scanned", "ticketId": "c7Kx9…" } }
// 需二次验证：ticket 仍为 scanned，顶层 needs_step_up
{ "status": "needs_step_up", "ticket": { "status": "scanned", "ticketId": "c7Kx9…" } }
// 已授权：直接走登录逻辑
{ "status": "success", "ticket": { "status": "success", "ticketId": "c7Kx9…" }, "login": { /* ... */ } }
// 过期：终态，前端重新拉码（需 captcha）
{ "status": "expired", "ticket": { "status": "expired", "ticketId": "c7Kx9…" } }
// 结果已就绪但认证 / 业务失败：结论在信封 status，ticket 只报 failed
{ "status": "target_taken", "ticket": { "status": "failed", "ticketId": "c7Kx9…" }, "error": { "message": "该账号已被其他账号绑定" } }
```

命中 `success` 时服务端 `GETDEL al:ticket:{ticket_id}`（原子取走即删，一次性消费）→ 建会话（1 次写）→ 绑定 / 建号判定 → 完成 SSO，**不另开 complete 端点**。

未命中键时：解 ticket，`now > exp` → 顶层与 `ticket.status` 同为 `expired`（前端重新拉码，需 captcha）；否则同为 `pending`（已扫码则同为 `scanned`）。`expired` 即终态，不再派生其他取值。

> **MFA × 扫码（本节唯一定义处，《后端架构》§13.2 引用）**：扫码登录链路中用户已启用 MFA 时，小程序端 `SsoService/LoginOauth`（`stage=complete`）命中 MFA，改写 `al:ticket:{ticket_id}` 快照为 `mfa_pending`（**写点复用既有键，不新增 Redis 键**；快照结构见《后端架构》§13.2），PC 端轮询从该快照读到顶层 `status=needs_step_up`（`ticket.status` 仍为 `scanned`）。PC 端以 `mfaPendingId = ticketId` 调 `SsoService/StartVerification`（`bizPurpose=login`、`operation=mfa_verify`），按 §3.8 完成二次验证；`SubmitVerification` 成功后写入终态 `TicketResult`，PC 端下一次轮询进入 `success` 并拿到登录信封。兜底：`needs_step_up` 期间票据仍按 `exp` 过期；用户也可放弃扫码、改用密码 / 验证码等其他登录方式，但这是兜底而非唯一路径。`needs_step_up` 只出现在 `GetLoginTicket` 顶层 `status`，**不进登录信封**（`login` 字段内的 `status` 取值不变）。

#### `SsoService/ConfirmLoginTicket` — 已登录一端写入授权结果

用已登录设备的会话确认"本人同意把这次扫码结果交给另一端"，用于"一端授权、另一端登录"场景（需求 §4.4.3）。写入值为 `TicketResult`（《后端架构》§11.6.5，`scene=login`、`status=success`）。

| 字段       | 必填 | 说明                                                                                                                                                       |
| ---------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ticketId` | 是   | 拉码时下发的 `ticket_id`                                                                                                                                   |
| `session`  | 否   | 当前已登录设备的 `session_token`（§1.2）。缺省时取 Cookie `al_session`；两者同时存在时**以请求体为准**，且必须与 Cookie 属同一 uid，否则 `invalid_request` |

> `session` 的作用是证明写入方是已登录用户本人（防他人代写票据），不用于建会话——写 ticket 不改变任何登录态。鉴权缺失 / 失效走 HTTP 401（§1.5）。

> 两个写入接口保留：`SsoService/LoginOauth`（小程序端，带 `ticketId` + `code`）与 `SsoService/ConfirmLoginTicket`（已登录设备，带 session），入参语义不同。
>
> 调用方：`SsoService/ConfirmLoginTicket` 由**宿主 / 第三方客户端**在"已登录侧确认"时调用（需求 §4.1.3 明确该能力不直接对外暴露），Authloft 前端三个 entry 均不实现该调用；前端只消费 `SsoService/GetLoginTicket` 的轮询结果。

其余 `/sso/**` 页面路由见 §8。管理员登录与登出**复用上述 SSO 流程**，不单独开端点。

### 3.1 Authloft 用户信息结构（统一结构）

`AccountService/GetProfile`、`GET /api/oidc/get_user_info`、rpc 域 `UserService` 的 profile 方法（§7）共用同一字段集合（各端点响应即下列字段，无信封包裹），与数据库 `user` + `user_profile` 表一致：

```jsonc
  "email": "a***@example.com", // 同上
  "emailVerified": 1,
  "userStatus": 1, // 1 正常 0 禁用（字段名 user_status，跨端统一）
```

`phone` / `email` 的呈现按调用方决定，**掩码在服务端完成，前端不二次处理**：

| 调用方                        | 默认呈现 | 说明                                                                                                                                                                      |
| ----------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| account 域自助接口            | 掩码     | 本人自助场景（含 `AccountService/GetProfile`）                                                                                                                            |
| `GET /api/oidc/get_user_info` | 掩码     | 仅当 Access Token 的 `scope` 含 `phone_plain` / `email_plain` 时，对应字段返回明文（§4.2）；标准 `phone` / `email` 只决定 claim 是否存在，值仍掩码；无明码 scope 一律掩码 |
| `GET /api/oidc/userinfo`      | 掩码     | 与 `get_user_info` 同口径，对应标准 claim `phone_number` / `email`；Access Token 的 `scope` 含 `phone_plain` / `email_plain` 时对应字段明文                               |
| rpc 域                        | 明文     | 供 SSO 应用后端调用，已由 `X-Signature` + `client_secret` 鉴权（§7）                                                                                                      |

明码 scope 为 Authloft 自定义：`phone_plain`（手机号）/ `email_plain`（邮箱），二选一也可同时申请，由 `/auth/authorize` 的 `scope` 声明、令牌签发时写入 Access Token；不含该 scope 的令牌永远只能拿到掩码值。

掩码格式固定：手机号 `138****8000`（前 3 + `****` + 后 4），邮箱 `a***@example.com`（本地部分首字符 + `***`，域名保留）。`phone_verified` / `email_verified`（标准 claim 名 `phone_number_verified`）不受掩码影响。

```jsonc
{
  "enabled": true, // 当前用户是否已开启两步验证
  "required": false, // 策略层是否强制（管理员 / 系统策略）；true 时用户不可关闭
  "trustedDeviceDays": 0, // 预留字段：本期恒为 0（不提供"信任此设备"，每次登录都需二次验证）

    { "factor": "totp", "enabled": true, "bound": true },
    { "factor": "otp_sms", "enabled": false, "bound": true },
    { "factor": "otp_email", "enabled": false, "bound": false },
    { "factor": "webauthn", "enabled": false, "bound": false },
    { "factor": "recovery_code", "enabled": true, "bound": true },
  ],

```

- `methods[].enabled` = 该因子是否被纳入当前用户的两步验证；`bound` = 是否已绑定该因子（仅布尔投影，明细字段见 §3.5）；`mfaPolicy.enabled` 与 `methods[].enabled` 的数据源为 `user_credential` 表 `kind=mfa_setting` 行（每用户至多一行，行存在即顶层 `enabled=true`；启用因子集存于该行 CredentialMeta 的 `mfa_methods` 字段，`methods[].enabled` = factor ∈ 该集合；`recovery_code` 随 `totp` 投影，§5.6）；写入端归 `SetMfa`（§3.5）
- `trustedDeviceDays` 为**预留字段**，取值恒为 `0`：本期不提供"信任此设备"，每次登录都需二次验证，字段保留不改、无对应存储键

### 3.4 绑定 / 换绑手机号与邮箱

统一走验证码（biz_purpose=`bind_contact`）+ 请求级 captcha，两步：

| 接口                       | step        | payload         |
| -------------------------- | ----------- | --------------- |
| `AccountService/BindPhone` | `challenge` | `{phone}`       |
| `AccountService/BindPhone` | `verify`    | `{phone, code}` |
| `AccountService/BindEmail` | `challenge` | `{email}`       |
| `AccountService/BindEmail` | `verify`    | `{email, code}` |

`captcha` 为请求级字段，与 `payload` 平级（§2.5）。

新号码必须未被他人占用；换绑需验证新号码归属（需求 §4.2.1）。

服务端校验（后端 §10.1、§8.2）：

1. `challenge`：captcha 必过（§2.5）→ 存 `al:code:{target}:bind_contact`，值内 `owner` 为 `biz_purpose:subject:challengeId`（`biz_purpose=bind_contact`、`subject` = 当前会话 uid、`challengeId` = 本次发码生成的一次性 ID）
2. `verify`：用请求里的 target 拼键 → Lua `GETDEL` → 校验 `code`，并比对码内 `owner` 的 `biz_purpose` / `subject` 与当前请求一致（`biz_purpose=bind_contact`、`subject` = 当前会话 uid；本场景无挑战令牌，`challengeId` 仅随码值存回、不参与比对；不一致 → `invalid_code`）
3. 键由 target 拼出，换 target 即取不到码，同一 target 的码也只属于发起它的那个 uid → "用自己的邮箱收码、绑定到别人的邮箱"不可行

`AccountService/RegisterWebauthn` `step=challenge` 返回示例：

```jsonc
{
  "token": "xxxx", // 独立挑战令牌，载荷见《后端架构》§11.6.7 的 ChallengeTokenPayload（biz_purpose=webauthn_enroll、operation=webauthn_register），前端不解析
  "challengeData": {/* ... */}, // WebAuthn 标准 options 对象 PublicKeyCredentialCreationOptions（完整结构，§12.9；前端不解析，整体传给 navigator.credentials.create()）
  "expiresIn": 120, // 当前挑战有效期（秒）
}
```

`challengeData.user` 口径（服务端生成，前端不解析）：`id` 为不透明的 uid 字节串（W3C 要求稳定且不含可识别信息，认证始终按它匹配凭据）；`name` 与 `displayName` 均取当前会话用户在服务端 `user` 表的 `username`，供浏览器 / 密码管理器在注册弹窗与凭据列表里标识账号。**不接受请求参数传入 username**（避免伪造或填他人账号名）；username 后续变更不影响已注册凭据，空值回落 uid 字符串以保证 `name` 非空。

`token` 契约（服务端）：独立一次性挑战令牌，AAD `purpose=challenge`、独立密钥 `sign_key.challenge`，载荷 `biz_purpose=webauthn_enroll` 保持（见《后端架构》§11.6.7）；有效期 120 秒；`step=verify` 由服务端校验 challenge 匹配 + 签名 + 凭据去重（不额外加消费键）；篡改 / 无效 → `invalid_request`，过期 → `code_expired`（需重走 `step=challenge`）；前端不感知结构，仅透传。

### 3.7 第三方绑定与日志

| 接口                                   | 说明                                                                                                                                                                                                                                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AccountService/GetThirdpartyBindings` | `{items:[…], available:[…]}`；`items` = 已绑定（`{providerKey, displayName, type, channel, icon, createdAt}`），`available` = 可绑定（`{providerKey, displayName, type, channel, icon, uiGroup, sortOrder}`）；`channel` 取值与 §2.7.1 登录快照完全一致（`redirect` / `qrcode` / `api`） |
| `AccountService/UnbindThirdparty`      | `{providerKey}` 解绑。允许条件：解绑后该用户**仍持有 password 凭证，或仍绑定至少 1 个非 Union 的第三方 Provider**；否则返回 `invalid_request` 并提示                                                                                                                                     |
| `AccountService/ThirdpartyOauth`       | 绑定已有账号：三方回调的落地接口（需 `al_session`），见下方「绑定第三方流程」（channel=redirect）                                                                                                                                                                                        |
| `AccountService/GetThirdpartyTicket`   | 扫码绑定的长轮询：命中后用当前会话 uid 完成绑定（channel=qrcode，需 `al_session`）                                                                                                                                                                                                       |

`available` 的过滤条件：`is_enabled=1` 且 `enable_signin=1`，排除该用户已绑定的 Provider；**Union Provider 不出现在 `available`**（后端 §12.7）。
`channel` 决定绑定入口：`redirect` → §3.7.1 A；`qrcode` → §3.7.1 B；**`api`（小程序接口）通道不提供绑定入口**（宿主内直接完成登录，无"已登录"前提）。

解绑判定口径：`(user_credential 存在 kind=password 且 is_enabled=1) OR (user_thirdparty_bind 中非 Union Provider 的绑定数 ≥ 1)`。Union Provider 不计入。前端置灰解绑入口的两个输入：`AccountService/GetConfig` 的 `hasPassword`（§3.2）与本接口 `items` 中非 Union 项的数量；服务端仍按同一口径校验，不满足返回 `invalid_request`。

Union 归并的落地是额外一行 Union Provider 绑定记录（该行 `open_id` 即 unionid），普通 Provider 绑定行只存渠道 `open_id`、不存 unionid；Union 行不计入已绑定数，不能单独登录或解绑（后端 §12.7）。

### 3.7.1 绑定第三方流程（已登录用户，`scene=bind`）

两个通道共用同一套绑定内核（`BindToCurrentUser`）：redirect 在回调里直接完成；qrcode 因授权发生在小程序端、被绑账号在 PC 端，拆成"小程序端取身份写 ticket + PC 端轮询完成绑定"。

#### A. 跳转通道（channel=redirect）

```
0  /account#/security → AccountService/GetThirdpartyBindings 取 available[] → 用户点「绑定 QQ」
1  SsoService/Authorize（provider=qq, scene=bind）               （需 al_session，否则 401）
     → 服务端生成 state = "b" + random
     → 写 al_login_state Cookie（加密后，含 state + 当前会话 uid）
     → 返回 {authorizeUrl}，前端 location.replace 跳转
2  三方回调 GET /sso/oauth/callback/qq?code=…&state=b…      （空壳页，无逻辑）
     → OAuthCallbackPage 见 state 首字母为 b → AccountService/ThirdpartyOauth
3  服务端：校验 state 与 Cookie 一致 + Cookie 中 uid == 当前会话 uid
     → Exchange / FetchUser → 查 user_thirdparty_bind
   ├─ open_id 已绑他人   → ErrorInfo.code=target_taken
   ├─ 已绑当前用户       → ok（幂等）
   └─ 未绑定             → 写 user_thirdparty_bind（+ Union 联动，后端 §12.7）
                           → 异步审计 thirdparty_bind
4  前端：成功 → location.replace('/account#/security?bind=success')
         失败 → location.replace('/account#/security?bind={ErrorInfo.code}')
         （target_taken 提示"该账号已被其他账号绑定"；其余按 §1.6 出文案）
```

| 字段          | 必填 | 说明                                             |
| ------------- | ---- | ------------------------------------------------ |
| `providerKey` | 是   |                                                  |
| `code`        | 是   | 第三方授权码                                     |
| `state`       | 是   | 必须为 `b` 前缀，与 `al_login_state` Cookie 比对 |

响应：成功 `{ "providerKey": "qq", "displayName": "QQ" }`；失败为 Connect 错误体，`ErrorInfo.code` 取 §1.6 对应值（`state_mismatch` / `target_taken` / `provider_disabled` / `invalid_request`…）。

约束：

- 本接口**不返回统一登录信封**、不签发 `login_token`、**不 Set-Cookie**、不重建会话——绑定不改变登录态
- 仅支持 `channel=redirect`；`api` / `qrcode` 通道不用于绑定（宿主能力不在 Authloft 前端）
- 服务端同时校验「Cookie 中的 uid == 当前会话 uid」，不一致返回 `invalid_request`
- 回调页复用 login entry 的 `OAuthCallbackPage`，仅按 `state` 首字母分派（§2.7.3）

#### B. 扫码通道（channel=qrcode）

```
0  /account#/security → 用户点「绑定微信扫码」→ 渲染扫码面板（captcha 配置取自 §3.2）
1  SsoService/CreateQrcode {providerKey:"wechat_mp_scan", scene:"bind", captcha}   （需会话）
     → 生成 ticket_id → ticket（scene=bind）→ GetwxacodeUnlimit → Storage
     → {ticket, ticketId, qrcodeUrl, expiresIn}
2  长轮询 AccountService/GetThirdpartyTicket {ticket, poll:15}                    （需会话）
3  用户扫码 → 小程序 wx.login → code
     SsoService/LoginOauth {providerKey, code, ticketId}
     → code2session → Exchange / FetchUser
     → 取 al:ticket:payload:{ticket_id} 快照见 scene=bind（提交仅带 ticketId，无加密串可解，§2.7.4）→ 只写 al:ticket:{ticket_id}（TicketResult 的 `thirdparty_identity`，《后端架构》§11.6.5）
       不建会话、不做绑定判定 → 小程序端返回 {status:"success", ticketId}
4  轮询命中 → GETDEL al:ticket:{ticket_id}
     → 用**当前会话 uid** + ticket 里的身份执行 BindToCurrentUser（与 A 通道同一套逻辑）
   ├─ open_id 已绑他人   → 信封 status=target_taken（ticket.status=failed）
   ├─ 已绑当前用户       → ok（幂等）
   └─ 未绑定             → 写 user_thirdparty_bind（+ Union 联动）→ 异步审计
5  前端：成功 → 关闭面板并刷新列表；失败 → 按 status 出文案
             expired → 重新拉码（需 captcha）
```

`AccountService/GetThirdpartyTicket`

| 字段     | 说明                                |
| -------- | ----------------------------------- |
| `ticket` | 是，拉码时下发的加密票据            |
| `poll`   | 否，长轮询最长等待秒数，上限见 §2.8 |

```jsonc
// 未就绪：未扫码
{ "status": "pending", "ticket": { "status": "pending", "ticketId": "c7Kx9…" } }
// 未就绪：已扫码（顶层同步 scanned）
{ "status": "scanned", "ticket": { "status": "scanned", "ticketId": "c7Kx9…" } }
// 命中：直接完成绑定
{ "status": "success", "ticket": { "status": "success", "ticketId": "c7Kx9…" }, "bind": { "providerKey": "wechat_mp_scan", "displayName": "微信扫码" } }
// 过期：终态，前端重新拉码（需 captcha）
{ "status": "expired", "ticket": { "status": "expired", "ticketId": "c7Kx9…" } }
// 命中但失败：结论在信封 status，ticket 只报 failed（status 取值见 §1.6）
{ "status": "target_taken", "ticket": { "status": "failed", "ticketId": "c7Kx9…" }, "error": { "message": "该账号已被其他账号绑定" } }
```

约束：

- 需 `al_session`；**不签发 `login_token`、不 Set-Cookie、不重建会话**——绑定不改变登录态
- 与 `SsoService/GetLoginTicket` 是**两条独立的轮询接口**，互不复用：前者"无会话 → 有会话"（完成登录），后者"已有会话 → 加一条绑定"（完成绑定）
- **绑定判定只在 PC 端轮询时进行**：小程序端只负责取身份写 ticket，任何情况下都不写绑定关系
- ticket 的 `scene` 由服务端加密保护；`bind` 的 ticket 不会被登录轮询接口接受，反之亦然
- `al:ticket:{ticket_id}` 与 ticket 同寿命（见《后端架构》§11.6.4），用后即毁；绑定场景同样支持 `scanned` 中间态

| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `AccountService/GetEvents`（入参 `{event, page, pageSize, …}` 分页见 §1.7） | 本人登录记录（仅成功记录）：`{items:[{event, createdAt, ip, ua, amr, clientId, detail}], total, …}` |

### 3.8 敏感操作二次验证（`StartVerification` / `SubmitVerification`）

> 通用能力：执行二次验证并取得断言。消息定义在 `api.common.v1`，方法分别挂在 `SsoService`（登录 / 扫码链路）与 `AccountService`（已登录会话域），**不新建业务域**（§0、§12.9）。`challengeToken` / `verificationToken` 对前端不透明，前端只透传，载荷定义见《后端架构》§11.6.7。

#### 3.8.1 方法与主体凭证

| 方法                                | 域              | 主体凭证                                                                                                    | 成功返回                                                  |
| ----------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `SsoService/StartVerification`      | 登录 / 扫码链路 | `loginToken`（`bizPurpose=login`）或 `mfaPendingId`（扫码场景取 `ticketId`，二选一）                        | 挑战令牌 + 可用因子                                       |
| `SsoService/SubmitVerification`     | 同上            | 挑战令牌；登录链路可另附 `loginToken` 恢复流程上下文（`oidc` / `tid` / `passed`），扫码场景仍以票据链路收尾 | 登录流程结论（`status` / `redirectTo` / `syncCookieUrl`） |
| `AccountService/StartVerification`  | 已登录账号域    | 会话 `al_session` 的 uid                                                                                    | 挑战令牌 + 可用因子                                       |
| `AccountService/SubmitVerification` | 同上            | 挑战令牌                                                                                                    | `verificationToken` + `amr`                               |

写死约束：

- `StartVerification` 不接受匿名裸调：每个请求都必须能推导出确定主体
- `bizPurpose=login` 必须携带 `loginToken`；服务端沿用 §2.2 第 3 步的校验点（二次因子阶段要求 `uid != 0` 且 `passed` 非空），防止绕过主因子；扫码场景以 `mfaPendingId` 与 `loginToken` 二选一（`mfaPendingId` 取扫码票据 `ticketId`，§2.8）
- 其余 `bizPurpose` 的主体由会话 `al_session` 的 uid 推导，请求不得携带 uid；`SsoService` 组只接受 `bizPurpose=login`，`AccountService` 组接受 `mfa` / `bind_contact` / `change_password` / `unbind_totp` / `unbind_thirdparty` / `admin_sensitive`，`admin_sensitive` 另按 §5 的管理员判定校验
- `webauthn_enroll` 不经 `StartVerification`：挑战令牌由 §3.6 `RegisterWebauthn` 的 `step=challenge` 直接签发（§3.8.3）

#### 3.8.3 `biz_purpose` 封闭枚举

| `biz_purpose`       | 含义                                                          | 方法组 / 主体                                       |
| ------------------- | ------------------------------------------------------------- | --------------------------------------------------- |
| `login`             | 登录 / 注册 / 重置流程中的二次因子                            | `SsoService`；`loginToken`（扫码为 `mfaPendingId`） |
| `mfa`               | 已登录会话内单独发起一次 MFA 验证                             | `AccountService`；会话 uid                          |
| `bind_contact`      | 绑定 / 换绑手机号或邮箱前（§3.4）                             | `AccountService`；会话 uid                          |
| `change_password`   | 修改密码前（§3.3）                                            | `AccountService`；会话 uid                          |
| `unbind_totp`       | 解绑 TOTP 前（§3.5）                                          | `AccountService`；会话 uid                          |
| `unbind_thirdparty` | 解绑第三方账号前（§3.7）                                      | `AccountService`；会话 uid                          |
| `admin_sensitive`   | 管理后台敏感写操作（§5）                                      | `AccountService`；会话 uid + 管理员判定             |
| `webauthn_enroll`   | 通行密钥注册的挑战令牌用途（§3.6），不经 `SubmitVerification` | `AccountService`；会话 uid                          |

命名口径：业务用途字段一律叫 `biz_purpose`；挑战 / 验证令牌的 AAD `purpose` 只取 `challenge` / `verification`，**不进令牌载荷**——两者是两套封闭、正交的命名空间，不得同名字段混用，也不要求两者相等：`webauthn` 是 Challenge 的业务子类型、只作 `biz_purpose` 取值，不作 AAD purpose（《后端架构》§11.6.7）。登录过程态验证码的 `ch.biz_purpose` 另取 `login` / `register` / `reset` / `mfa`（《后端架构》§11.6.2），与本节的挑战 / 验证令牌枚举各自封闭，同名不代表可互换。

#### 3.8.4 `operation` 规则

`operation` 必填，由业务入口固定，不与 `biz_purpose` 合并（示例：`webauthn_enroll` → `webauthn_register`；`unbind_totp` → `unbind_totp`）。`StartVerification` 写入挑战令牌 → `SubmitVerification` 原样带入断言 → 消费方按 `biz_purpose` + `subject` + `operation` 三重校验，任一不符 → `verification_invalid`（§1.6）。

#### 3.8.5 安全与错误

- `challengeToken` / `verificationToken` 对前端不透明，前端只透传；`amr` 禁止客户端传入
- `loginToken`（`SubmitVerification` 可选）仅 `SsoService` 组可用，只用于恢复登录流程上下文（`oidc` / `tid` / `passed`），不替代挑战令牌的主体判定：其 uid 必须与挑战令牌 `subject` 一致，不一致或解析失败 → `verification_invalid`；`AccountService` 组传入一律拒绝（`invalid_request`）；不为此新增任何 Redis 状态键（沿用下条「令牌无 Redis 状态」口径）
- 令牌无 Redis 状态：`challengeToken` 的一次性由 challenge 匹配 + 断言签名 + 凭据去重保证，不额外加消费键；`verificationToken` 默认按 `nonce` + `exp` 放行，高风险 `biz_purpose`（`change_password` / `admin_sensitive`）消费时做一次 `SET NX al:once:{nonce}`，低风险（如 `unbind_totp`）不加
- 错误码：缺断言 → `verification_required`；无效 / 过期 / 重放 → `verification_invalid`（均仅 `ErrorInfo.code`，HTTP 映射见 §1.5）；OTP / TOTP / WebAuthn 因子失败沿用 `invalid_code` / `code_expired` / `too_many_attempts` / `method_disabled`；主体凭证缺失或主体不符 → `invalid_request` / `token_invalid` / `token_expired`。承载位置：`SsoService` 组的业务失败按登录流程信封 `status` 表达（§1.3、§1.6），captcha 与 step-up 令牌类失败走 Connect 错误体 + `ErrorInfo.code`；`AccountService` 组一律走 Connect 错误体 + `ErrorInfo.code`
- 限流：按 `biz_purpose` 复用《后端架构》§10.3 的键；OTP 类沿用发码冷却与日限额（取值见 §1.10.2）；`StartVerification` 不新增任何 Redis 键，禁止 `al:verif:*` 这类状态键
- captcha：需要时按 §2.5 触发表判定，凭据走请求级 `captcha` 字段；失败走 `captcha_required` / `captcha_invalid`（§1.6）

## 4. OIDC

### 4.1 端点清单

| 端点                      | 方法 | 路径                                | 鉴权                                                     |
| ------------------------- | ---- | ----------------------------------- | -------------------------------------------------------- |
| 服务发现                  | GET  | `/.well-known/openid-configuration` | 无                                                       |
| 公钥集                    | GET  | `/.well-known/jwks.json`            | 无                                                       |
| 授权                      | GET  | `/auth/authorize`                   | 会话（有则直接签发授权码 302；无则渲染登录空壳页，§4.2） |
| 令牌                      | POST | `/api/oidc/token`                   | `client_id` + `client_secret`（或 PKCE）                 |
| 吊销                      | POST | `/api/oidc/revoke`                  | `client_id` + `client_secret`                            |
| 用户信息（OIDC 标准）     | GET  | `/api/oidc/userinfo`                | Bearer Access Token                                      |
| 用户信息（Authloft 格式） | GET  | `/api/oidc/get_user_info`           | Bearer Access Token                                      |

### 4.2 `GET /auth/authorize`

| 参数                                       | 必填       | 说明                                                                                                                                                                                                                                                            |
| ------------------------------------------ | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client_id`                                | 是         |                                                                                                                                                                                                                                                                 |
| `redirect_uri`                             | 是         | 白名单匹配，支持 `*` 通配（整段匹配，防子域名陷阱）                                                                                                                                                                                                             |
| `scope`                                    | 否         | 缺省 `openid profile email`；标准 `phone` / `email` 决定 `get_user_info` 是否含对应字段（值仍掩码），同样决定 `GET /api/oidc/userinfo` 的 `phone_number` / `email` claim 是否存在；自定义 `phone_plain` / `email_plain` 决定对应取值是否明文（掩码矩阵见 §3.1） |
| `state`                                    | 否（推荐） | 原样回传（OIDC 中为 RECOMMENDED，非必填）。存在时原样拼回 `code` / `error` 跳转；缺失时仍正常签发与跳转，只是不携带 `state`，服务端不做 CSRF 比对，改记一条审计事件                                                                                             |
| `nonce`                                    | 否         | 进 ID Token                                                                                                                                                                                                                                                     |
| `code_challenge` / `code_challenge_method` | 否         | PKCE，仅 `S256`                                                                                                                                                                                                                                                 |
| `prompt`                                   | 否         | `none`：无有效会话时返回 `error=login_required`；`login`：本期忽略（不支持强制重认证），按有有效会话处理                                                                                                                                                        |

参数错误：

- `client_id` 非法（不存在 / 未启用）或 `redirect_uri` 未命中白名单 → **不跳转**，HTTP 400 由 Go 直接渲染错误页（防开放重定向）
- `state` 缺失**不属参数错误**：不拒绝请求，正常签发授权码并跳转，跳转 URL 不带 `state`；服务端不做 CSRF 比对，改记一条审计事件（`oidc_authorize_no_state`，`actor_type=system`）
- `redirect_uri` 校验通过后，`scope` 含未支持值 → `302 redirect_uri?error=invalid_scope&state=…`（`state` 缺失时省略该参数）
- `prompt=none` 且无有效会话 → 不渲染空壳页，`302 redirect_uri?error=login_required&state=…`（同上，`state` 缺失时省略）；`prompt=login` 忽略（本期不支持强制重认证）

两条路径：

1. **有有效会话**（Cookie `al_session` 有效）：后端直接完成，**不渲染页面、不经过前端**——校验通过 → 生成一次性授权码 → `302 redirect_uri?code=…&state=…`
2. **无会话**：直接渲染登录空壳页（URL 保持 `/auth/authorize`，§8），OIDC 原始参数（`client_id` / `redirect_uri` / `scope` / `state` / `nonce` / `code_challenge` / `code_challenge_method`）由 Go 原样注入 `__AUTHLOFT_INIT__.oidc` → 前端首次请求（尚无 `login_token`）以 body 顶层 `oidc` 回传（§2.2）→ 服务端写入 `login_token.oidc` → 登录成功（含 MFA）后在**同一请求上下文**内生成授权码，信封 `status=success` 的 `redirectTo` 即 `redirect_uri?code=…&state=…`，前端按 §1.6 `success` 动作（多域名同步后跳转）回到业务系统，不再重复请求 `/auth/authorize`

授权码：键 `al:oidc:code:{code}`、TTL 120s（§4.7）；值为按《后端架构》§11.6.1 封装（AAD `purpose=oidc_code`）的 `OidcCodePayload`（消息 `token.OidcCodePayload`，唯一定义见《后端架构》§11.6.6，`.proto` 位于 `server/proto/token/`、包名 `token`，随 `buf generate` 同批生成）：`client_id` / `redirect_uri` / `uid` / `scope` / `nonce` / `code_challenge` / `code_challenge_method` / `amr` / `auth_time` / `iat` / `exp`；`POST /api/oidc/token` 用 `GETDEL` 一次性消费（§4.3）。

> 原参数只在服务端注入与信封中流转，**不落 `localStorage`**；`localStorage` 仅用于三方跳转场景的 `al_oidc_ctx`（§2.7.2）。

> 本期不实现同意页（consent）：首方 SSO 场景下授权即视为同意，`scope` 直接生效（含自定义 `phone_plain` / `email_plain`）；预留扩展点——如需独立同意页，在此端点登录完成后、签发授权码之前插入。

> 未登录时尚无 `login_token`，故 OIDC 上下文先落在页面注入里、再由首次请求带回；`login_token.oidc` 是登录成功后生成授权码的唯一来源。三方跳转场景的落盘与回传见 §2.7.2。

### 4.3 `POST /api/oidc/token`

Content-Type：`application/x-www-form-urlencoded`（OIDC 标准，全站唯一例外）。

| grant_type           | 参数                                                                  | 响应                                                                              |
| -------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `authorization_code` | `code`、`redirect_uri`、`client_id`、`client_secret`、`code_verifier` | `{access_token, token_type:"Bearer", expires_in, refresh_token, id_token, scope}` |
| `refresh_token`      | `refresh_token`、`client_id`、`client_secret`                         | 同上（Refresh Token 轮换可选）                                                    |

> `grant_type` 固定支持 `authorization_code` 与 `refresh_token` 两种，**全部客户端一致，不按客户端配置**；其他取值返回标准 `error=unsupported_grant_type`（HTTP 400）。客户端管理不设授权类型字段（§5.5）。

### 4.4 `POST /api/oidc/revoke`

`{token, token_type_hint:"refresh_token"}` → HTTP 200 空响应体（RFC 7009；OIDC 标准端点，豁免 §1.0 信封）。仅影响该令牌，不影响 SSO 会话。

### 4.5 `GET /api/oidc/userinfo`

标准 Claims（语义在此唯一定义，字段来源映射见《后端架构》§14.4）：

| Claim                                    | 语义                                               |
| ---------------------------------------- | -------------------------------------------------- |
| `sub`                                    | 用户 ID（`user.id`）                               |
| `name`                                   | 昵称                                               |
| `email` / `email_verified`               | 邮箱与其验证状态（取库内 `email_verified` 标志）   |
| `phone_number` / `phone_number_verified` | 手机号与其验证状态（取库内 `phone_verified` 标志） |
| `picture`                                | 头像 URL                                           |
| `amr`                                    | 登录链路中实际通过的认证方法数组                   |

```jsonc
{
  "sub": "10086",
  "name": "…",
  "email": "a***@example.com",
  "email_verified": true,
  "phone_number": "138****8000",
  "phone_number_verified": false,
  "picture": "…",
  "amr": ["pwd", "otp"],
}
```

掩码规则见 §3.1 掩码矩阵（默认掩码）：`phone_number` / `email` 的值与 `get_user_info` 的 `phone` / `email` 同口径，仅当 Access Token 的 `scope` 含 `phone_plain` / `email_plain` 时对应字段明文；`phone_number_verified` / `email_verified` 为布尔标志，不受掩码影响。

### 4.6 `GET /api/oidc/get_user_info`（Authloft 格式）

返回 §3.1 的 Authloft 用户信息结构（无信封包裹）；`phone` / `email` 默认掩码，仅当 Access Token 的 `scope` 含 `phone_plain` / `email_plain` 时对应字段明文（规则见 §3.1 掩码矩阵）。

### 4.7 令牌规格

| 令牌               | 形态                                             | 有效期     | 存储                         |
| ------------------ | ------------------------------------------------ | ---------- | ---------------------------- |
| ID Token           | JWT RS256，`iss/sub/aud/exp/iat/nonce/amr/epoch` | 默认 3600s | 无                           |
| Access Token       | JWT RS256（JWKS 自校验），含 `epoch`             | 默认 3600s | 无                           |
| Refresh Token      | opaque，sha256 落库                              | 默认 30 天 | `oidc_refresh_token`，可吊销 |
| Authorization Code | opaque，一次性                                   | **120 秒** | Redis                        |

改密 → 递增 `al:pwdep:{uid}` → 令牌校验比对 epoch + 批量吊销 refresh token。

## 5. 管理后台（`api.admin.v1.AdminService`）

**文案口径（i18n）**：`label` / `help` 下发的不是展示文案，而是前端 i18n 键（`admin.schemaField.*`）；zh / en 两套语言包在 `web/src/shared/i18n/{zh,en}/admin.ts`，由 `ProvidersPage/edit/schema/fields/FieldRenderers.tsx` 渲染期 `t()` 解析。后端（含注册表 `FieldMeta` 声明）不持有任何语言文案：同一 Ext 字段在不同渠道可有不同标签（如 `client_id` 在 oauth 是 AppID、在阿里云短信是 AccessKeyId），故键按语义命名而非按 `key` 推导。缺键时前端回显键本身（可见、可排查），旧版本下发的中文字面量也按原文显示。`options` 恒为 **wire 取值**（如 `ui_group` 的 `social/enterprise/dev/other`、`union_provider` 的 provider_key），不是 i18n 键：前端只按 `admin.schemaOption.<fieldKey>.<value>` 翻译显示名（按字段命名空间，避免自定义 provider_key 撞上通用枚举值）、未定义取值原样显示，提交值不变。

**表达式字段约定（`user_mapping` / `storage_path`，JSONata 能力边界）**：

- 支持范围：JSONata 语法，**以服务端 JSONata 求值实现 gnata（Go 库，后端架构 §1.5）的实际支持为准**；gnata 不支持的语法由服务端在求值封装层维护不支持清单、如实公告，不以自研补齐，升级 gnata 版本时清单随之更新
- 保存预校验：`AdminService/CreateProvider` / `UpdateProvider` 对 `user_mapping` 各值与 `storage_path` 做编译预校验，非法表达式 → Connect 错误体 + `ErrorInfo`（`domain` = `admin`、`code` = `invalid_request`，§1.6 既有取值，不新增词汇）
- 运行时失败：登录链路（§2）对 `user_mapping` / `storage_path` 求值失败属服务端配置错误，按 §1.6 既有兜底口径返回（登录流程域 `failed` + 兜底文案，其余 Connect `internal`），**不透出表达式库原始错误**

## 7. RPC 接口（`api.rpc.v1.UserService` + `api.rpc.v1.TokenService`）

供 SSO 应用后端调用，域内两个 service：`UserService`（资料读写）、`TokenService`（会话解码）。鉴权（HMAC 签名；**写接口**另有 nonce 去重）为 Connect interceptor（后端 §3.3）。

**命名决定校验（长期口径）**：按方法名前缀判定读写——方法名以 `Update` / `Delete` / `Set` / `Create` / `Revoke` 任一前缀开头 = **写接口**；其余方法名 = **读接口**。该判据适用于本域全部现有与未来方法，新增方法即据此归类，无需另行约定。新增写接口若不属于上述前缀语义，必须显式申请扩展前缀集合（走契约变更评审），不得静默使用读接口命名绕过 nonce 去重。

请求头

| Header        | 说明                                                                          |
| ------------- | ----------------------------------------------------------------------------- |
| `X-Client-ID` | 客户端标识                                                                    |
| `X-Nonce-ID`  | 随机串，参与签名；写接口另做 Redis 去重 TTL 30s（读接口不去重，允许重复请求） |
| `X-Signature` | `HMAC-SHA256(签名串)`，签名串统一五项（见下）                                 |

签名串规范

- `path`：**不含 query string** 的请求路径（Connect RPC 路径，如 `/api.rpc.v1.UserService/GetUserProfile`）
- `body`：**原始请求体字节**；空 body 用空字符串
- 各项以 `:` 连接，密钥为 `client_secret`
- 读写接口统一五项 `client_id:nonce:path:body:client_secret`（读写签名一致，`nonce` 均参与；区别仅在校验顺序中的 nonce 去重，见下）

校验顺序（后端 §3.3）：**写接口：nonce 去重 → 签名 → session；读接口：签名 → session**（nonce 参与签名但不去重）。本域走 Connect 协议（§1.0）：成功响应即消息本身；业务失败为 Connect 错误体 + `ErrorInfo`。

| 接口                            | 说明                                                                                                                                                                                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `UserService/GetUserProfile`    | `{uid}` 读用户资料，响应为 §3.1 的 Authloft 结构（`phone` / `email` 明文，见 §3.1 掩码矩阵）                                                                                                                                                               |
| `UserService/GetUserProfiles`   | `{ids}` 批量读用户资料，响应条目同 `GetUserProfile`——§3.1 的 Authloft 结构（`phone` / `email` 明文）；上限 / 缺失语义 / 顺序 / 去重与 proto 变更条款见 §7.2                                                                                                |
| `UserService/UpdateUserProfile` | `{uid, …}` 改资料，入参同 §3.2 的 `AccountService/UpdateProfile`（proto3 optional 语义一并继承：未设置 = 不修改，显式设值（含 0 / 空串）= 覆盖，`gender` 可显式改回 0=保密）                                                                               |
| `TokenService/DecodeSession`    | 传入 Session Token（请求体字段 `sessionToken`，术语见 §1.2）进行解码，返回 `SessionTokenPayload` 报文视图；会话有效时同响应返回续期重签令牌 `renewedToken`；可选入参 `includeUserInfo` 为 `true` 时同响应额外携带用户信息（请求 / 响应 / 错误语义见 §7.1） |

### 7.1 `TokenService/DecodeSession`（会话解码与续期）

请求消息 `DecodeSessionRequest`：`{ "sessionToken": "…", "includeUserInfo": false }`（proto 字段 `session_token` / `include_user_info`，术语见 §1.2；`includeUserInfo` 缺省 `false`，语义见下「include_user_info 语义」条）。

响应消息 `SessionResponse`（成功即消息本身，字段与 `SessionTokenPayload` 同名同义；整型输出十进制字符串，§1.12）：

```jsonc
{
  "id": "10086", "epoch": "3", "amr": ["pwd", "otp"], "sid": "…", "iat": "1761800000", "exp": "1762404800",
  "renewedToken": "…",  // 续期重签得到的新 session_token，仅会话校验通过时返回
  "userInfo": { … }      // 仅 includeUserInfo=true 且会话校验通过时返回；结构复用 rpc 域 ProfileResponse（§3.1），见下条
}
```

- **续期时机**：与 §1.9 一致——**会话校验通过即每次都重签**，不设剩余 TTL 阈值（`iat` / `exp` 刷新，`sid` / `epoch` 不变）；重签为**纯计算、无任何存储写入**，判定与执行都在 handler 的 session 校验通过之后、返回响应之前；新令牌只经响应体字段下发（本 RPC 不写 `Set-Cookie`、不设 `X-Authloft-Token` 响应头）。
- **字段语义**：`renewedToken`（proto `renewed_token`，字段号 7）即本次重签的 `session_token`，与请求入参 `sessionToken`（旧令牌）属同一会话——**响应值覆盖请求值**，调用方收到后一律改用 `renewedToken` 继续传播（按原渠道落盘：浏览器 Cookie / 无 Cookie 用 `X-Authloft-Token`），前端只作不透明串替换、不解析内容。
- **失败语义**：session 无效 / 过期（解密失败、`epoch` 与 `al:pwdep:{uid}` 不一致、`exp` 已过）→ HTTP 401 `unauthenticated`（§1.5），响应体无 `renewedToken`；此时**不重签、不写任何存储**，错误只由 Connect 错误体表达，**不得**以 200 + 空 `renewedToken` 与错误语义混用。
- **include_user_info 语义**：请求布尔参数（proto 字段 `include_user_info`，字段号 2；JSON `includeUserInfo`，缺省 `false`）。`true` 且会话校验通过 → 响应额外携带 `user_info` 字段（proto `user_info`，字段号 8，JSON `userInfo`），**字段与 `UserService/GetUserProfile` 响应同构**——复用 rpc 域既有 `ProfileResponse` 消息（§3.1 Authloft 结构；rpc 域 `phone` / `email` 明文，§3.1 掩码矩阵），本节不复制其字段定义。`false` / 缺省 → 响应与现行完全一致，服务端**零额外查询**（不触用户资料读取；未设置的 message 字段省略不输出，§1.1）。session 无效 / 过期 → 失败语义不变（仍 401 `unauthenticated`，见上条），`include_user_info` 不改变失败分支，响应体亦无 `user_info`。

### 7.2 `UserService/GetUserProfiles`（批量读取用户资料）

批量读取多个用户的资料，是 `GetUserProfile` 的批量版：响应条目与 `GetUserProfile` 响应同构——§3.1 的 Authloft 结构（复用 rpc 域既有 `ProfileResponse` 消息；`phone` / `email` 明文，§3.1 掩码矩阵）。供 SSO 应用后端一次拉取多名用户信息（如成员列表批量展示），减少逐个调用 `GetUserProfile` 的往返。

**读写分流（点名）**：方法名 `GetUserProfiles` 不含 `Update` / `Delete` / `Set` / `Create` / `Revoke` 任一前缀，按 §7 前言命名决定校验原文「其余方法名 = **读接口**」归**读接口**，校验顺序即 §7 前言原文「**读接口：签名 → session**」——nonce 参与签名但**不去重**，允许重复请求、可安全重试；不新增写前缀语义，无需扩展前缀集合。

请求消息 `GetUserProfilesRequest`（`ids` 为 `repeated int64`，JSON 十进制字符串，§1.12）：

```jsonc
{ "ids": ["10086", "10010", "10000"] }
```

响应消息 `GetUserProfilesResponse`（成功即消息本身，§1.0；每条 `profiles[]` = §3.1 Authloft 结构全量字段，同 `GetUserProfile` 响应——复用 `ProfileResponse`，本文不复制定义）：

```jsonc
{
  "profiles": [
    { "id": "10086", "username": "zhang_san", "nickname": "张三", "…": "…" },
  ],
}
```

**批量语义（定稿）**：

| #          | 口径                                                                                                                                                                                        | 理由                                                                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 单次上限 | `ids` ≤ **100** 个（按入参列表长度计，去重前）；超出 → 业务失败：Connect 错误体 + `ErrorInfo`（`domain` = `rpc`、`code` = `invalid_request`，§1.5 / §1.6 词汇表），**整单失败、无部分返回** | 无界批量会放大单请求的资料查询成本与响应体体积；100 为批量便捷性与单请求成本的平衡点，超出属参数取值错误，归既有码 `invalid_request`（不新增词汇）                                                        |
| ② 部分缺失 | **跳过**：响应只含实际存在的用户条目；缺失 id 不占位、不报错、不终止整单                                                                                                                    | 整单失败会把单个失效 id 的代价放大到整批，调用方被迫拆分重试；空占位条目在零值省略口径（§1.1）下与「用户存在但字段为零值」不可区分；条目自带 `id`，调用方以 `profiles[].id` 对照入参 `ids` 即可识别缺失项 |
| ③ 返回顺序 | `profiles` 顺序与入参 `ids` 去重后的顺序**一致**（缺失项跳过后，其余条目相对顺序保持）                                                                                                      | 调用方可按下标对位消费，无需自建 id → 条目映射                                                                                                                                                            |
| ④ 重复 id  | 服务端按**首次出现位置**去重，同一 id 至多返回一条                                                                                                                                          | 重复 id 无独立语义；不去重会破坏「响应条目数 ≤ 有效入参数」的对位直觉，徒增响应体积                                                                                                                       |

`ids` 缺省或为空列表 → 返回空 `profiles`（protojson 零值省略口径下响应输出 `{}`，§1.1），不报错——空批量是合法的空集语义，非参数错误。

**proto 变更条款（后续实现照抄；遵守 §12.9 报文规范与 §11 契约变更——只增字段、不改既有编号）**：

- `server/proto/api/rpc/v1/profile.proto` 追加：`GetUserProfilesRequest`（`repeated int64 ids = 1;`，注释引本节上限口径）、`GetUserProfilesResponse`（`repeated ProfileResponse profiles = 1;`，复用本文件既有 `ProfileResponse`，注释引本节顺序 / 缺失 / 去重口径）
- `server/proto/api/rpc/v1/user.proto` 的 `UserService` 追加：`rpc GetUserProfiles(GetUserProfilesRequest) returns (GetUserProfilesResponse);`（注释引本节读接口归类）
- §7.1 对应变更落 `server/proto/api/rpc/v1/session.proto`：`DecodeSessionRequest` 追加 `bool include_user_info = 2;`；`SessionResponse` 追加 `ProfileResponse user_info = 8;`（复用 `profile.proto` 既有 `ProfileResponse`，`session.proto` 需新增 `import "api/rpc/v1/profile.proto";`）

**provider 贡献源（captcha，2026-11-06 定稿）**：按「当前启用且已配置的 captcha Provider」动态追加 CSP 源。Provider 在注册时以**按指令分组的数据声明**登记自身所需源（`CSPSupporter` 一类可选接口，注册契约见《后端架构》§9.4），CSP 中间件只做聚合与去重、**不出现任何厂商名 / type 分支特判**；「当前生效 Provider」判定沿 §2.5 单激活契约（settings 键 `captcha_provider_key` 单值、catalog 判定），未启用 / 未配置的 Provider 不写入任何域名。逐项约束：

- **可扩展指令白名单**仅四项：`frame-src` / `connect-src` / `style-src` / `img-src`；白名单外指令的声明一律不生效
- **`script-src` 不放通**：维持 `'nonce-…' 'strict-dynamic'`、不写入厂商域——strict-dynamic 下 host 源按 CSP3 被忽略，三家脚本经 nonce 标签信任链放行；不支持 strict-dynamic 的旧浏览器回退源可选，不强制写入
- **同名指令合并语义**：CSP 规范中**同一 policy 内同名指令仅首条生效、其余被忽略（非取并集）**，故支持者片段不得以多条同名指令拼接输出，必须**按指令名聚合后单条输出**——源并集 + 去重 + 顺序稳定（基线源在前、支持者按装配序）

## 10. 典型调用流程

> 时序中 `LT` = `login_token`（前端内存变量，每次响应后无条件替换）。

### 10.1 账密登录

```
1  打开 /sso/login?client_id=app → 空壳页注入 __AUTHLOFT_INIT__.methods（含 captcha 配置）
2  渲染 PasswordForm（username / password）
3  SsoService/LoginDefault
     {method:"password", step:"verify", payload:{username, password}}
   ├─ pwban 命中 → status=locked（retryAfter = 剩余秒数）
   ├─ 失败且当日累计 ≥3 → ErrorInfo.code=captcha_required（非 200 错误体）→ 插入 CaptchaWidget 后重提（带请求级 captcha）
   ├─ 失败且累计 ≥6 → status=locked（6h）
   └─ 通过且未启用 MFA → status=success，Set-Cookie: al_session
4  status=success 且 syncCookieUrl 非空 → location.replace(首跳) → 跳转链 → redirectTo
```

### 10.2 邮箱验证码登录 → MFA

```
1  打开 /sso/login → 空壳页注入 __AUTHLOFT_INIT__.methods
2  渲染 OTPForm（email + CaptchaWidget）
3  SsoService/LoginDefault {method:"otp_email", step:"challenge", captcha:{…}, payload:{email}}
   → status=next, LT, nextStep.kind=form, fields=[code], retryAfter=60
   （邮箱未绑定任何账号 → status=user_not_found）
4  SsoService/LoginDefault {loginToken:LT, method:"otp_email", step:"verify", payload:{code}}
   → 主因子通过，uid=10086，该用户已启用 MFA → status=mfa_required（§1.3，信封不带 `mfa` 块）
5  SsoService/StartVerification {loginToken:LT, bizPurpose:"login", operation:"mfa_verify"}
   → methods[]（totp / otp_sms / otp_email / webauthn / recovery_code，含 maskedTarget）；method 为空时不签发 challengeToken
6  用户选"短信验证码" → SsoService/StartVerification {loginToken:LT, bizPurpose:"login", method:"otp_sms", operation:"mfa_verify", captcha:{…}}
   → challengeToken，methods[]，expiresIn；手机号取自 uid 绑定资料（不接受请求传参）→ nextStep.kind=form
7  SsoService/SubmitVerification {challengeToken, method:"otp_sms", payload:{code}}
   → status=success, sessionId, syncCookieUrl, redirectTo
8  前端清空 LT → location.replace(首跳) → 跳转链 → redirectTo
```

全程 10 分钟受 `LT.exp` 约束；超时回到第 1 步。

### 10.3 注册

```
1  打开 /sso/register → 注入 __AUTHLOFT_INIT__.methods（flow=register 快照）
2  SsoService/Register {method:"otp_email", step:"challenge", captcha:{…}, payload:{email}}  → next
3  SsoService/Register {loginToken:LT, step:"verify", payload:{code}}                   → next（下一步 = set_password）
4  SsoService/Register {loginToken:LT, step:"set_password", payload:{username, password}} → success
```

### 10.4 重置密码

同 10.3，端点 `SsoService/ResetPassword`，`challenge` 的目标必须是**已绑定且已验证**的（不满足前提时返回 `status=user_not_found`，见 §2.6）；最后一步只提交 `password`。成功后 `al:pwdep` 递增 → 该用户全部会话与令牌失效。

### 10.5 第三方跳转登录（含首次绑定）

```
1  打开 /sso/login → 注入 __AUTHLOFT_INIT__.methods，取 thirdparty.providers[]
2  用户点图标 → SsoService/Authorize（provider=qq, scene=login）
     → 服务端生成 state = "l" + random（写 al_login_state Cookie，只含 state）
     → 前端把 __AUTHLOFT_INIT__.oidc 写入 localStorage（键 al_oidc_ctx）→ location.replace 跳转（非 302）
3  QQ 回调 → GET /sso/oauth/callback/qq?code=…&state=l…（空壳页，无逻辑）
4  前端按 state 首字母 l → SsoService/LoginOauth {providerKey:"qq", code, state, oidc}
     服务端：比对 Cookie 中的 state → Exchange / FetchUser → 查绑定
   ├─ 已绑定 → success（Set-Cookie）；或 mfa_required（沿用登录流程信封）
   └─ 未绑定 → status=binding_required, binding{providerKey, displayName, allowSignup}
5  未绑定 → 只有两个选项，细节见 §2.7.5：
   选「创建新账号」            → set_password 步仅提交 username，免密建号 → success
   选「退出并使用其他账号登录」→ 前端清空 LT → location.replace('/sso/login')，不发请求
   auto_bind 命中已有账号且该用户已启用 MFA → 继续 mfa_required
```

### 10.6 小程序扫码登录

```
PC                          Authloft                  微信 / 小程序
 │─ SsoService/CreateQrcode {providerKey:"wechat_mp_scan", captcha} ──→│ 生成 ticket_id → ticket → GetwxacodeUnlimit → Storage
 │←────── {ticket, ticketId, qrcodeUrl} ───────────│
 │─ 长轮询 SsoService/GetLoginTicket {ticket, poll:15} ─→│
 │                                       用户扫码 ───→│ 进页即 SsoService/LoginOauth {providerKey, ticketId, stage:"scanned"} → SET al:ticket {status:scanned}
 │                                                   │ wx.login → code，用户确认后
 │                                                   │─ SsoService/LoginOauth {providerKey, code, ticketId, stage:"complete"} →│
 │                                                   │  code2session → 覆盖 al:ticket:{ticket_id} {status:success}
 │                                                   │  已启用 MFA → 改写 {status:mfa_pending}（不建会话）
 │                                                   │  （小程序端返回 {status:"success"|"mfa_required", ticketId}）
 │←────── 轮询命中：success → 登录流程信封；needs_step_up → 顶层提示，PC 按 §3.8 二次验证后继续轮询 ──│
```

- `expired` → 重新拉码（需 captcha）
- `qrcode_auto_delete=1` → 完成登录时按同一 `storage_path` 模板 + `ticket_id` 重算 key，投递删除任务到延迟队列
- 小程序端无 Origin，Referer 校验见 §1.1

### 10.7 OIDC 授权码全流程

```
1  业务系统 → GET /auth/authorize?client_id=app&redirect_uri=…&scope=openid profile&state=…&code_challenge=…
   参数错误 → client_id / redirect_uri 非法：400 + Go 错误页（不跳转）；scope 非法：302 redirect_uri?error=invalid_scope&state=…
2a 已有有效会话（al_session 有效）→ 后端直接生成授权码（al:oidc:code:{code}，TTL 120s）
   → 302 redirect_uri?code=…&state=…（不渲染页面、不经过前端，§4.2 路径 1）
   prompt=login → 忽略；prompt=none 且无会话 → 302 redirect_uri?error=login_required&state=…
2b 无会话 → 直接渲染登录空壳页（URL 保持 /auth/authorize），原始参数注入 __AUTHLOFT_INIT__.oidc
3  走 10.1 / 10.2 完成登录（含 MFA）；首次请求带 body 顶层 oidc → 写入 login_token.oidc
4  登录成功 → 同一请求上下文生成授权码 → status=success，redirectTo = redirect_uri?code=…&state=…
   前端按 §1.6 success 动作（同步后跳转）→ 业务系统收到 code
5  业务系统 POST /api/oidc/token (grant_type=authorization_code, code, code_verifier, client_id, client_secret)
   → {access_token, id_token, refresh_token, expires_in}
6  GET /api/oidc/userinfo（Bearer access_token）→ 标准 Claims
   GET /api/oidc/get_user_info → Authloft 结构
7  过期后 POST /api/oidc/token (grant_type=refresh_token) → 新 access_token
8  业务系统登出 → POST /api/oidc/revoke（仅影响该令牌）
```

### 10.8 头像上传（两种模式由后端下发决定）

```
AccountService/GetConfig → {avatarUpload:{mode:"direct", maxSize:2097152, allowedTypes:["image/png","image/jpeg"]}, mfaPolicy, captcha, hasPassword:true}   // 后三者结构见 §3.2 / §2.5

mode=proxy  : POST /api/account/avatar（REST 豁免，multipart）→ {url}
mode=direct : AccountService/PresignAvatar {filename, contentType, size} → {key, uploadUrl, headers}
              PUT upload_url（直传对象存储，需 bucket 配 CORS）
              AccountService/CommitAvatar {key} → {url}
```

### 10.9 已登录用户绑定 / 换绑邮箱

```
1  /account#/security → AccountService/GetConfig 取 captcha 配置（account entry 不从注入快照取）
2  AccountService/BindEmail {step:"challenge", captcha:{…}, payload:{email}} → 成功（空响应），异步发信
3  用户收码 → AccountService/BindEmail {step:"verify", payload:{email, code}} → 写 user.email / email_verified=1
```

键空间与服务端校验（码内 `uid` 比对、防串号）见 §3.4。手机号同理（`AccountService/BindPhone`）。

### 10.10 已登录用户绑定第三方

完整时序见 §3.7.1。要点：`state` 前缀为 `b`、回调走 `AccountService/ThirdpartyOauth`、完成后跳回 `/account#/security?bind={success|ErrorInfo.code}`。

## 12. 公用数据模型（Protobuf）

> 本章是前后端 / 服务间共用的数据模型契约：`.proto` 源文件在后端 `proto/` 目录，生成代码提交进仓库，前端类型由同一批定义同步生成（见 §11）。凡本章出现的结构，双端不得各自手写一份；字段语义以本章为准。存储层落地方式、加解密与键空间见《后端架构》。

**结构归属**：前端要渲染 / 构造 / 校验字段的结构（`provider.Ext`、`credential.Meta`、`client.RedirectUris`、各类 API 消息）**定义在本章**，这里是唯一契约；前端只当作**不透明字符串**透传的结构（`login_token` / `session_token` / `ticket` 的载荷）、只在 Redis 里流转的存储值（`TicketResult`）、只在服务端之间流转的跳转载荷（`SyncCookiePayload`）**定义在《后端架构》**，本章只登记它们的传输形态与生命周期。新结构的归属判定口径（编码侧编写规范）见《CODE_GUIDE》§3.6。

| 结构                                                                      | 定义位置            | 前端是否解析                 |
| ------------------------------------------------------------------------- | ------------------- | ---------------------------- |
| `provider.Ext` / `credential.Meta` / `client.RedirectUris`（§12.1~§12.3） | 本章                | 是（管理后台表单按字段渲染） |
| 通用封装 + `purpose` 封闭集合                                             | 《后端架构》§11.6.1 | 否                           |
| `LoginTokenPayload`                                                       | 《后端架构》§11.6.2 | 否，只透传                   |
| `SessionTokenPayload`                                                     | 《后端架构》§11.6.3 | 否，只透传                   |
| `TicketPayload`                                                           | 《后端架构》§11.6.4 | 否，小程序端 / 宿主只回传    |
| `TicketResult`                                                            | 《后端架构》§11.6.5 | 否，无任何调用方解析         |
| `SyncCookiePayload`                                                       | 《后端架构》§11.2   | 否，前端完全不参与           |

### 12.0 结构化字段的统一约定

**数据库中不使用 JSON 列。** 需要存结构化数据的字段按"有没有固定 schema"二选一：

| 情况                     | 方案                                 | 存储        | 本文中的字段                                                           |
| ------------------------ | ------------------------------------ | ----------- | ---------------------------------------------------------------------- |
| 结构固定、需要演进和校验 | Protobuf（`.proto` 定义 + 生成代码） | `VARBINARY` | `provider.ext`、`user_credential.meta`、`oidc_client.redirect_uris`    |
| 结构不固定、纯粹透传     | msgpack（`map[string]any`）          | `VARBINARY` | `user_profile.extra`、`user_thirdparty_bind.extra`、`event_log.detail` |

配套约定：

- msgpack 字段只在应用内读写，**不参与任何 SQL 条件**；需要检索的信息一律提为真实列
- 存储层与传输层解耦：库里的 Protobuf / msgpack 只服务持久化，接口报文的编码另由 `Accept` 协商（§1.1.1、§12.9），改存储格式不影响接口契约
- 所有字段均明文存；访问控制靠接口边界（§2.1 的"公开接口不返回凭证"）

### 12.1 `provider.Ext` —— 外部服务扩展字段

对应 `provider.ext` 列（表结构见《后端架构》数据模型章节）。跨类型共有的属性作真实列（要用于筛选、排序、索引），凭证 / 端点 / 存储配置 / 厂商长尾全部进此结构。

```protobuf
syntax = "proto3";
package provider;

message Ext {
  // ---- 凭证 ----
  string client_id       = 1;
  string client_secret   = 2;   // 明文存于 ext 内
  string app_id          = 3;   // 微信/支付宝/小程序
  string cert            = 4;   // 证书 / 公钥，如支付宝公钥
  string scopes          = 5;
  map<string, string> user_mapping = 6;  // 三方字段 → Authloft 字段，值为 JSONata 表达式（能力边界见 §5.3 表达式字段约定）

  // ---- 端点 ----
  string provider_url           = 10;  // OIDC issuer / 服务地址
  string custom_auth_url        = 11;
  string custom_token_url       = 12;
  string custom_user_info_url   = 13;
  string host                   = 14;
  int32  port                   = 15;
  bool   disable_ssl            = 16;  // 内网自签场景
  string intranet_endpoint      = 17;  // 服务端回源优先使用

  // ---- 存储（category=storage 生效）----
  string bucket        = 20;
  string region_id     = 21;
  string path_prefix   = 22;
  string domain        = 23;  // 自定义 CDN 域名
  string endpoint      = 24;  // S3 endpoint
  bool   path_style    = 25;  // S3 path-style addressing
  bool   public_read   = 26;

  // ---- 小程序码（category=oauth, type=wechat_mp_scan 生效）----
  bool   qrcode_auto_delete = 30;  // 登录成功后是否删除码图，删除走延迟队列
  string storage_provider   = 31;  // 存储 Provider Key
  string storage_path       = 32;  // 存储路径模板，JSONata 表达式（能力边界见 §5.3 表达式字段约定）

  // ---- 上传模式（category=storage 生效）----
  string upload_mode   = 35;  // proxy=经 Authloft 中转（默认）| direct=前端预签名直传
  int32  presign_ttl   = 36;  // 直传预签名 URL 有效期（秒），默认 300
  int64  max_size      = 37;  // 单文件上限（字节），默认 2MB
  string allowed_types = 38;  // 允许的 MIME 白名单，逗号分隔，如 image/png,image/jpeg

  // ---- 消息（category=sms/email 生效）----
  string from          = 40;  // 邮件发件人 / 短信签名
  string sign_name     = 41;
  string template_code = 42;  // 国内短信模板 ID

  // ---- 长尾 ----
  map<string, string> metadata = 50;  // 支付宝 sign_type、飞书 app_ticket、S3 acl/storage_class ...
}
```

读写约定：

1. `provider_key` 是唯一对外契约：回调路径 `/sso/oauth/callback/{provider_key}`、扫码配置的 `storage_provider`、系统配置的 `captcha_provider_key` 引用同一个东西。字符集 `[a-z0-9_]`，创建后不可改
2. **敏感字段不做二次加密**，访问控制靠接口边界保证：注入快照 `__AUTHLOFT_INIT__.methods`（§2.1）与所有前台接口**永不返回** `ext` 中任何凭证字段；只有 `/api/admin/providers/**` 可返回明文，且必须校验管理员会话（uid == 1）

### 12.2 `credential.Meta` —— 凭证扩展元数据

```protobuf
message CredentialMeta {

  repeated string transports  = 1;  // internal|hybrid|usb|nfc|ble
  string attestation_type     = 2;  // none|basic|attca

  // kind=totp

  int32 totp_period = 21;   // 默认 30

  // kind=mfa_setting
  repeated string mfa_methods = 30;   // kind=mfa_setting 启用的二次因子集合
}
```

### 12.4 令牌与内部载荷（定义在《后端架构》）

通用封装（`purpose` 封闭集合、AAD 构造）、`LoginTokenPayload`、`SessionTokenPayload`、`TicketPayload`、`TicketResult` 与多域名同步载荷 `SyncCookiePayload` 均由服务端签发并解析，前端只做不透明透传，故**唯一定义处是《后端架构》§11.6**（同步载荷见 §11.2），本节不再复制。

本章只需记住它们的**传输形态**：出现在响应 / 请求里时一律是 base64url 不透明字符串，前端禁止解码、拼接或依赖其内部字段；生命周期（有效期、可重放次数、失效条件）见对应章节。

> 编号说明：§12.5～§12.7 编号空缺（保留空号以稳定既有引用），小节自 §12.8 续编。

### 12.8 向下兼容约定

- 所有 Protobuf 结构**只增字段、不改字段号与语义**；废弃字段保留编号并注释，不得复用于新含义
- msgpack 字段（`extra` / `detail`）是透传结构，读取方必须对缺失键做容错

### 12.9 接口报文（API 消息）

§12.1～§12.3 是**本端可感知的存储结构**；§12.4 指向《后端架构》§11.6 的令牌与内部载荷（前端不解析）；本节是**线上报文**结构。三者共用同一套生成链，但用途不同，不得混用。

- 位置与命名：`.proto` 源在 `server/proto/api/`，按域分目录（`common/`、`sso/`、`account/`、`admin/`、`oidc/`、`gateway/`、`rpc/`）；service 路径形态为 `api.<域>.v1.<XxxService>/<Method>`（如 `api.sso.v1.SsoService`、`api.common.v1`；rpc 域两个 service：`UserService` / `TokenService`，§7）；OIDC / gateway 豁免域不建 service（§1.0）。包名、service / 方法 / 消息命名的编写约定（编码侧）见《CODE_GUIDE》§3.6
- 敏感操作二次验证的消息（`StartVerificationRequest` / `StartVerificationResponse`、`SubmitVerificationRequest` / `SubmitVerificationResponse`）定义在 `api.common.v1`，方法分别挂 `SsoService` / `AccountService`，**不新建业务域**、不改 §0 域清单与 §1.2 鉴权互斥；`challengeToken` / `verificationToken` 对前端不透明，`amr` 仅服务端写入（§3.8）
- 单一结构源：Go 结构体与 TS 类型**只从 `.proto` 生成**（生成配置见《后端架构》§1.6，含 `protoc-gen-connect-go`），任何一端都不得手写镜像结构
- 字段名：**JSON 线上表示为标准 protojson 映射（lowerCamelCase）**，与各章 JSON 示例逐字一致；源侧命名（snake_case）与编号分配的编写规范见《CODE_GUIDE》§3.6；编号从 1 起连续分配，遵守 §12.8
- 响应模型：成功响应即 `XxxResponse` 消息本身，**无 `status:"success"/"error"` 信封消息**（§1.0）；业务失败 = Connect 错误体 + `api.common.v1.ErrorInfo` detail（`domain` / `code` / `message` / `retry_after` / `attempts_left`，§1.5；`code` 词汇表 = §1.6）；登录流程信封（§1.3）的流程态 `status` 是 `LoginFlowResponse` 的普通字段
- 整型一律 `int64`（§1.12），布尔用 `bool`，时间用 Unix 秒 `int64`
- JSON 映射细节（标准 protojson，双端生成链同口径）：零值标量、空 `repeated`、未设置的 message 字段**省略不输出**（§1.1 空值口径）；未知请求字段静默忽略：connect-go v1.21.1 内建 JSON 解码 `DiscardUnknown:true`，不报错、不产生 `invalid_argument`；`int64` 输出十进制字符串（§1.12）
- 与 §12.1～§12.3 的复用：响应里出现的 `provider.Ext` 等模型**不直接暴露**给前台，按需在 `api/*` 中定义裁剪后的视图消息（如 `ProviderPublic`），凭证字段只存在于 `AdminProvider` 这类管理视图
- 枚举取值：`status` / `kind` / `step` / `fields[].type` 等取值集在线上以 `string` 承载，取值由本文各章封闭集合约束（承载方式的编写策略见《CODE_GUIDE》§3.6）
- 存储模型 proto（`provider/ext.proto`、`credential/meta.proto`、`token/**`）不进 Connect 路径：包名不带 `.v1`、不建 service，不受本节 service 命名约束
- 可变 / 原样透传结构统一用 `google.protobuf.Struct`（不逐字段建模）：`oidc`（登录 / 注册 / 重置的三方补充参数）、`credential`（`@simplewebauthn` 断言对象）、`challenge_data`（WebAuthn options 对象）等。`Struct` 只解决「结构随场景变化、前端不逐字段消费」的表达问题，**不改变字段语义**——每个字段的语义、必填与约束仍由本文对应章节定义，不得借 `Struct` 下发任意字符串或无约束 map。
- WebAuthn `challenge_data` 的 proto 表达为**方案 A：`google.protobuf.Struct`**，不采用逐字段消息。类型语义固定为 WebAuthn 标准 options 对象：注册 / 创建凭据场景 = `PublicKeyCredentialCreationOptions`（`challenge`、`rp`、`user`、`pubKeyCredParams`、`timeout`、`excludeCredentials`、`authenticatorSelection`、`attestation`、`extensions` 等完整结构，MDN），登录 / 断言场景 = 同族 `PublicKeyCredentialRequestOptions`；前端不解析字段，整体透传给 `navigator.credentials.create()` / `get()`。选 A 的理由：① 与本章既有「透传 / 可变结构用 Struct」口径一致（`token/ticket.proto` 等既有生成物同口径），不引入例外；② 逐字段需手写约 10 个子结构，WebAuthn JSON 规范的字段名大小写与深嵌套（如 `pubKeyCredParams[].alg`、`authenticatorSelection.residentKey`）易与浏览器侧形态漂移，而 `Struct` 已保证 JSON 对象形状；③ 前后端都不逐字段消费该对象，类型安全的收益为零，维护成本反而更高。

## 13. 安装接口（`api.setup.v1.SetupService`，仅 setup 模式）

> 本域接口与 `/setup` 安装页只在 **setup 模式**（配置路径下无配置文件——默认进程 cwd 下 `authloft.yml`，`--config` 可指定；判定与模块见《后端架构》§3.1 / §3.15）下存在；正常模式下路由不注册，请求一律 404。本域走 Connect 协议（§1.0）：成功响应即消息本身；业务失败为 Connect 错误体，`ErrorInfo.code` 取本域定义值（`config_invalid` / `db_unreachable` / `redis_unreachable` / `migration_failed` / `admin_missing` / `username_invalid`）与 §1.6 既有值（`password_weak`）；鉴权 / 参数类错误仍走 §1.5。功能需求见需求 §4.7。

### 13.1 `SetupService/GetStatus` — 模式判定

响应：`{ "mode": "setup" }`。安装页加载时调用：正常返回即处于 setup 模式；**连接被拒 / 404 = 已处于正常模式**（该语义同时用于安装完成后的重启轮询，§13.4）。

### 13.2 `SetupService/UploadConfig` — 上传已有 config

| 字段     | 必填 | 说明                           |
| -------- | ---- | ------------------------------ |
| `config` | 是   | 配置文件（YAML）全文（字符串） |

执行顺序：① 配置完整性校验（不完整 / 非法 / 缺 `sign_key` → `ErrorInfo.code = config_invalid`）② 数据库 / Redis 连接性检查（失败 → `ErrorInfo.code = db_unreachable` / `redis_unreachable`）③ 执行迁移 `migrate up`（《后端架构》§3.16，幂等、已最新秒过；失败 → `ErrorInfo.code = migration_failed`）④ 管理员（ID=1）存在性检查——版本已最新但管理员缺失 → `ErrorInfo.code = admin_missing`（改走全新安装）⑤ 写入 config 文件 → 触发重启。成功响应 `{"restarting":true}`（重启语义与全新安装一致，见 §13.4）。

### 13.3 `SetupService/Install` — 全新安装

| 字段                                       | 必填   | 说明                                                                                                                                                                                                                         |
| ------------------------------------------ | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dbDsn`（proto `db_dsn`）                  | 是     | 数据库连接串                                                                                                                                                                                                                 |
| `redisAddr`（proto `redis_addr`）          | 是     | Redis 地址                                                                                                                                                                                                                   |
| `redisPassword` / `redisDb`                | 否     | Redis 密码 / 库号（默认空 / 0）                                                                                                                                                                                              |
| `root`                                     | **是** | 主域名（完整 URL，允许 `http://` / `https://`，《后端架构》§3.2 约定 7）；host 部分必须是**域名或 `localhost`，拒绝 IP**——IP 作 WebAuthn RP ID 会被库校验拒绝（执行顺序①）                                                   |
| `rpId`（proto `rp_id`）                    | 否     | WebAuthn RP ID；**缺省取 `root` 的 host（去 scheme 与端口），不再自动读取请求 Host**；必须是域名字符串（允许 `localhost`），填 IP / 非法 → `config_invalid`                                                                  |
| `rpDisplayName`（proto `rp_display_name`） | 否     | WebAuthn RP 展示名（通行密钥注册弹窗中显示）；写入 `authloft.rp_display_name`，**缺省 / 空白回落默认值 `Authloft`**；该配置项为空时 `config.Validate` 拒绝（`config_invalid`），且 go-webauthn 的 `BeginRegistration` 会失败 |
| `adminUsername`（proto `admin_username`）  | 是     | 管理员用户名（规则同 §2.3）                                                                                                                                                                                                  |
| `adminPassword`（proto `admin_password`）  | 是     | 管理员密码（策略同 §5.6）                                                                                                                                                                                                    |

执行顺序：**① 字段校验——`root` 必填且 host 为域名 / `localhost`（缺失、IP、非法 → `ErrorInfo.code = config_invalid`）；`rpId` 缺省按上述推导后同为域名校验（IP / 非法 → `config_invalid`）** ② 连接性检查（失败 → `ErrorInfo.code = db_unreachable` / `redis_unreachable`）③ 执行迁移 `migrate up`（《后端架构》§3.16；失败 → `ErrorInfo.code = migration_failed`）④ 插入管理员用户（固定 ID = 1，已存在则跳过（幂等）；用户名不合规 → `ErrorInfo.code = username_invalid`，密码不满足策略 → `ErrorInfo.code = password_weak`）⑤ 生成完整 config（所填项 + 随机生成的全部密钥 + 其余项默认值）原子写入 ⑥ 触发重启。成功响应 `{"restarting":true}`（见 §13.4）。

> 域名必填为 2026-11-05 定稿：安装不得靠自动推导的 IP 蒙混过关。若管理员事后手工改 config 把 `rp_id` 配成 IP，启动期 WebAuthn 初始化失败进入**降级窗口**——程序不退出，但窗口期内凡需 webauthn 的操作一律拒绝（fail-closed；拒绝码 `method_disabled`，文案「通行密钥暂不可用，请联系管理员」语义，《后端架构》§8.3）。

### 13.4 重启与前端轮询

- 两条路径（上传配置 / 全新安装）成功（响应 `restarting:true`）后**进程退出（exit 0）**，由部署环境拉起：Docker / systemd 等托管部署自动重启，裸跑部署需手动重新运行
- 前端提示"程序已退出，请手动重新运行；如使用 Docker 或 systemd，会自动重启"（两条路径共用同一文案），以 **2 秒间隔**轮询 `SetupService/GetStatus`：
  - 连接被拒 / 超时 → 服务未恢复，继续轮询
  - 返回 404（setup 路由消失）→ 已进入正常模式，跳转 `/sso/login`
  - 轮询超过 **120 秒**仍未恢复 → 提示"重启超时，请检查服务状态"，不自动重试安装
- 进程未被拉起（裸跑且未手动重跑）由部署侧排查，前端只呈现超时态

### 13.5 安全边界

- 本域仅 setup 模式可达；config 写入并重启后永久退出 setup 模式
- 请求与日志不回显 `admin_password`、不输出密钥明文
- 不设一次性令牌、不做并发首启防护；部署约束为**首启应单实例**（《后端架构》§3.15）
