## 1. 总体架构

### 1.1 技术栈与分层

| 层 | 选型 |
|----|------|
| 框架 | Modern.js（React 19 + TypeScript + Rsbuild） |
| 产物形态 | 登录端、用户端、管理后台、安装页均为 SPA（同一工程、四个 entry） |
| 页面外壳 | Go 渲染空壳 HTML，挂载对应 SPA 并注入初始变量（§1.5） |
| WebAuthn | `@simplewebauthn/browser` |
| 契约校验 | `zod`（只校验 JSON 原文，不定义类型） |
| 接口编解码 | `@bufbuild/protobuf` 运行时 + `@bufbuild/protoc-gen-es` 生成的 TS 消息类型（JSON / Protobuf 双编码，见 §3.1） |
| UI 库 | login 端不使用（保证体积）；account / admin 使用 Semi UI |

```
浏览器
 ├─ 空壳 HTML（Go 渲染，注入 window.__AUTHLOFT_INIT__，见 §1.5）
 └─ SPA bundle（本工程产物）
      │
      ├─ entry（login / account / admin）：读注入变量 → 建路由 → 挂载
      ├─ pages：页面级容器，只做布局与路由参数
      ├─ flow / containers：状态编排（登录状态机）
      ├─ components(factors / captcha / schema)：按后端下发配置分派渲染
      ├─ shared/api：HTTP 封装（消息序列化 / 内容协商 / 错误归一化）、端点表、契约校验
      └─ shared/hooks|utils：能力检测、轮询、倒计时、校验、上传、整数转换
```

### 1.2 抽象边界

能通用的是流程编排，不是交互渲染。

| 层次 | 内容 | 增长曲线 |
|------|------|----------|
| 第一层：完全通用，写一次 | 登录容器 + `challenge → verify → mfa → success` 状态机、方式列表渲染与分组排序、通用字段渲染器（12 种 `type`，见 §3.3）、失败态展示与动作、重试冷却、终点处理 | 恒定 |
| 第二层：每因子一个组件（5 个，`totp` 除外） | `PasswordForm`、`OTPForm`、`WebAuthnButton`、`ProviderButtons`、`RecoveryCodeForm`；`totp` 不设专属组件，由通用 `FormStep` + `CodeInput`（`fields[].type=totp`）渲染 | 恒定，因子种类有限 |
| 第三层：每厂商一个 adapter | 仅 Captcha 需要（各厂商 JS SDK 互不兼容）；`CaptchaWidget` 因 login / account 共用而落在 `shared/`（§3.5） | 低频 |

判定规则（新增认证方式时按顺序判断，不要硬塞进通用 schema）：

1. 用户是敲键盘输入？→ 通用字段渲染器
2. 需要调浏览器原生 API（WebAuthn）？→ 独立组件，只在 `methods` 里声明 `hint` 与能力检测条件。宿主 / 小程序能力（`wx.login`）由宿主自行实现，Authloft 前端不承载
3. 需要等待外部事件（扫码轮询）？→ 独立面板，复用通用轮询 hook
4. 只是跳转？→ 不算组件，后端给 URL 即可

> schema 驱动用来管"有哪些方式、顺序如何、要哪些字段"；不要用它管"怎么和用户 / 浏览器交互"。

新增认证方式时的判定流程与改动清单见 §7。

### 1.3 四 entry 的职责边界

| entry | 挂载路径 | 注入变量（§1.5） | 会话形态 | 主要依赖接口 |
|-------|---------|-----------------|---------|-------------|
| `login` | `/sso/**`、`/auth/**` | `al_root`、`static_base`、`methods`（必填）、`oidc`（可选） | 无会话；`login_token` 仅存内存变量 | 接口文档 §2（`/api/sso/**`） |
| `account` | `/account/**` | `al_root`、`static_base` | 依赖会话 Cookie（名称 / 属性 / 有效期见接口文档 §1.9；HttpOnly，前端不可读） | 接口文档 §3（`/api/account/**`）；另调 `GET /api/sso/authorize?scene=bind`、`POST /api/sso/qrcode`（`scene=bind`），见 §3.1 |
| `admin` | `/admin/**` | `al_root`、`static_base`（管理员信息由 `GET /api/admin/me` 获取） | 依赖管理员会话 Cookie（复用 SSO 登录，管理员为安装时创建的固定 ID 账号，接口文档 §13） | 接口文档 §5（`/api/admin/**`） |
| `setup` | `/setup` | `static_base`（仅此一项，不注入 `methods` / `oidc`） | 无会话、无业务态；仅在服务端 setup 模式（无 `config.yaml`）下有意义 | 接口文档 §13（`/api/setup/**`） |

三个业务 entry（`login` / `account` / `admin`）共享 `src/shared`，不得各自复制组件；`login` 与 `account` 共享 `FieldRenderer`、`CodeInput`、`ErrorBanner`、`CaptchaWidget`（因此 `captcha/` 落在 `shared/` 下，见 §3.5）。`setup` entry 不依赖 `shared/api`（业务契约封装），自带极简 JSON fetch，可复用 `shared/components` 等零依赖组件（见 §6b）。

### 1.4 页面渲染分工与路由

- `/api/**` 为接口，其余为页面；页面路由清单与空壳注入约定见接口文档 §8
- `/sso/**`、`/auth/**`、`/account/**`、`/admin/**` → Go 返回空壳 HTML，挂载对应 SPA；路由归属前端
- 两个例外由 Go 直接渲染真实 HTML（"无界面"中转页，不需要 SPA）：
  - `/sso/sync_cookie`：多域名 Cookie 同步的跳转中转页（302，非 SPA）
  - `/sso/logout`：登出，Go 直接处理（接口文档 §2.9）

登录端前端路由：`/sso/login`、`/sso/register`、`/sso/reset`、`/sso/oauth/callback/:provider_key`、`/auth/authorize`。`/auth/authorize` 为 OIDC 授权空壳（§1.3 挂载 `/auth/**`），复用登录页完成授权步骤（"OIDC 授权页即登录页"，见 §4.4 `LoginPage`）；`oidc` 注入见 §1.5，交互见接口文档 §4.2。**有有效会话时该路径由后端直接签发授权码并 302 到 `redirect_uri`，不渲染空壳、不进入前端**；前端只在无会话时渲染空壳完成登录。

安装端前端路由：`/setup`（仅服务端 setup 模式下可达，页面结构见 §6b，接口契约见接口文档 §13）。

### 1.5 初始变量注入（`window.__AUTHLOFT_INIT__`）

首屏就必须有的变量由 Go 在渲染空壳 HTML 时注入，避免 SPA 再发一轮请求，也避免把配置硬编码进前端。

```html
<script>window.__AUTHLOFT_INIT__ = {"al_root":"https://uc.example.com","static_base":"/assets","methods":{ /* 接口文档 §2.1 */ }};</script>
<script type="module" src="/assets/login/entry.js"></script>
```

注入白名单与每个变量的含义**见接口文档 §8**（唯一定义，本文不复制）。

前端侧约束：

- `bootstrap.ts` 读取注入变量；`methods` 必须存在，缺失时渲染错误提示并提示刷新，无回退接口
- **静态资源基址**：`entry.tsx` 在任何动态 `import()` 之前把 `__webpack_public_path__` 设为 `static_base + '/'`（缺省 `/assets/`），此后所有异步 chunk 与图片按该前缀加载；`static_base` 由后台配置（接口文档 §5.6），可为 CDN 绝对地址。**不使用资源版本号**：产物文件名自带 contenthash
- 渠道图标**不做本地文件回落**：`icon` 为空即渲染通用占位（`ProviderIcon`），工程内不存放任何渠道图标资源（接口文档 §2.7.1）
- 首次提交登录请求时，若 `oidc` 存在，以 body 顶层 `oidc` 字段原样回传（仅这一次）
- 前端不得假设其中存在任何凭证：没有会话 ID、没有 `login_token`、没有 Provider 密钥
- 落盘例外仅一处：跳转第三方前把 `oidc` 写入 `localStorage`（键 `al_oidc_ctx`），回调后读出随 body 回传并清除（接口文档 §2.7.2）；多域名同步的链路状态由后端载荷携带，前端不落盘（接口文档 §2.9）
- 注入块的转义、`no-store`、CSP nonce 由后端保证（后端架构 §3.4），前端不做二次信任

### 1.6 第三方库

- 公共依赖（所有 entry 均可使用，含 login）：`react`、`zod`、`@bufbuild/protobuf`、`@simplewebauthn/browser`
- 除公共依赖外，login 不可依赖其他第三方库，以确保首屏性能最优
- account 及 admin 使用 [Semi UI](https://semi.design/zh-CN/start/getting-started)；可适当使用其他第三方库以减少重复开发

## 3. `shared/` 文件职责

### 3.1 `shared/api`

> 报文类型**只有一个来源**：`src/gen/proto`（`@bufbuild/protoc-gen-es` 由后端同一批 `.proto` 生成，接口文档 §12.9）。组件与业务代码只使用生成的消息类型，禁止手写接口 interface，禁止在 `shared/api` 里重新描述字段。

| 文件 | 职责 | 关键约束 |
|------|------|---------|
| `http.ts` | `fetch` 封装：`credentials:'include'`、超时与中断、按端点 `format` 序列化请求与反序列化响应、非 2xx 与 200 `status:"error"` 统一按 §1.0 错误信封解 `error.{code,message,request_id}` 归一化为 `ApiError`、`Content-Type` 断言；multipart 仍走 `postForm(url, formData)`（签名另可选 `onUploadProgress`） | 编码只在 `http.ts` 决策（见下方"编解码"）；组件不得裸 `fetch`、不得自己 `JSON.parse`；不自行加自定义头触发预检；`postForm` 的 `Content-Type` **不手动设置**（交由浏览器带 boundary） |
| `endpoints.ts` | 端点表：`{ path, method, req: 消息 schema, res: 消息 schema, format: 'json' \| 'binary' }`，`sso.ts` / `account.ts` / 各 entry 的 `api.ts` 都从这里取定义 | `format` 是**每端点显式声明**的常量，不做运行时探测；改一行即可让某端点走 Protobuf（login 同样适用） |
| `errors.ts` | 两层错误口径（§1.6 词汇、两个位置）：① 登录流程域 200 信封顶层 `status`（含 `next` / `mfa_required` 等流程态）→ `{retryable, action, i18nKey}`；② 其余域 `status:"error"` 的 `error.code`——200 业务失败（§1.6 词汇）与非 200 框架码（§1.5 封闭集合：`bad_request` / `unauthorized` / `forbidden` / `not_found` / `unsupported_media_type` / `internal_error`）同一形状（接口文档 §1.0），统一拦截文案 | 不存在第二套业务错误码；未知取值走兜底文案，不暴露内部信息；`error.message` 只作兜底 |
| `types.ts` | 从 `src/gen/proto` re-export 的信封、`methods` 快照、`schema`、`thirdparty.providers` 等类型别名 | 全部结构的唯一定义在《接口文档》与 `.proto`；缺类型时先补 `.proto` 再生成，禁止双份手写 |
| `sso.ts` | 跨 entry 复用的 `/api/sso/**`：`authorize`、`qrcode`、`captcha/image`（account 的绑定与 captcha，见接口文档 §3.7.1） | 只放被 ≥2 个 entry 使用的端点；login 专属端点仍留在 `login/api.ts` |
| `account.ts` | 跨 entry 复用的 `/api/account/**`：`config`、`thirdparty/oauth`（login 的 `OAuthCallbackPage` 走 `b` 前缀分支时使用，接口文档 §2.7.3） | 同上：只做薄封装，不承载业务分支 |
| `contract.ts` | zod schema + `assertEnvelope()`：dev 环境与单测中对**响应 JSON 原文**做结构校验，结构不符即抛错 | 只做"多字段 / 少字段 / 类型错"的把关，不承担类型定义（类型来自 `gen/proto`）；json 模式下才走校验，二进制模式跳过 |

**编解码（`http.ts` 的两种 `format`）**

| 环节 | `format: 'json'` | `format: 'binary'` |
|------|------------------|--------------------|
| 请求 | `toJson(msg, {alwaysEmitImplicit: true, useProtoFieldName: true})` 后发送 | `toBinary(schema, msg)` |
| 请求头 | `Content-Type: application/json`、`Accept: application/json` | `Content-Type: application/octet-stream`、`Accept: application/octet-stream` |
| 响应 | 断言 `Content-Type` 为 JSON → `schema.fromJson(JSON.parse(text))` | 断言 `Content-Type` 为 `application/octet-stream` → `schema.fromBinary(new Uint8Array(buf))` |
| 错误体 | 按 JSON 解 `ApiError` | 按二进制解 `ApiError`（接口文档 §1.0 / §1.5：错误同样协商） |
| 返回值 | 生成的消息对象（**不是**裸 JSON） | 同一个消息对象 |

- `useProtoFieldName: true` 保持 snake_case（`login_token` 而非 `loginToken`）；`alwaysEmitImplicit: true` 让标量字段恒存在，与后端 `EmitDefaultValues` 对称
- `Accept` 只写所选的那一个值，**不写 `*/*`**——后端的协商规则以 `Accept` 为唯一依据（接口文档 §1.1.1），写 `*/*` 会把选择权让给服务端，等于放弃确定性
- `Content-Type` 断言失败直接抛 `ApiError`（视为契约错误而非重试场景），避免把 HTML 错误页当成业务响应解码
- 错误归一化：非 2xx 与 200 `status:"error"` 一律抛 `ApiError{httpStatus, code, message, requestId}`（接口文档 §1.0 错误信封）；登录域 200 的流程 `status` 分支仍走业务层（`reducer`）

**数字（接口文档 §1.12）**

- 生成的消息里 `int64` 字段是 `bigint`，JSON 文本里是十进制字符串——转换由 `toJson` / `fromJson` 完成，业务代码两端都见不到字符串
- ID / 时间戳全程保持 `bigint` 或字符串，**禁止 `Number(id)`**（超 2^53 静默丢精度）；展示用 `shared/utils/int.ts` 的 `toDisplay`
- 时长 / 计数类（`retry_after`、`expires_in`、`page_size`、`total`、`length`）可用 `utils/int.ts` 的 `toCount` 转 `number`，转换处自带 `Number.MAX_SAFE_INTEGER` 断言

状态机（接口文档 §1.3 的 `status` 即状态）：

```
idle → (选方式) → challenge? → verify → [mfa_required] → challenge? → verify → success
                                    ↘ [binding_required] → 绑定选择页 → success / 退出重登
                                    ↘ [captcha_required] → 原地插入 CaptchaWidget
                                    ↘ [too_many_requests|locked|failed] → 失败态（按接口文档 §1.6 出动作）
```

非 success 即失败（扫码轮询的 `pending` / `scanned` 为进行中，不作失败处理，见接口文档 §1.6）。

`login_token` 的传递规则与覆盖语义**见接口文档 §1.8、§1.3**（唯一定义）。前端实现五条，不可打折：

1. 由 `loginTokenStore` 以模块级变量保存；前端不解析其内容，只做"收到就替换、请求就带上"
2. 每次响应若含 `login_token`，无条件覆盖内存变量（后端每次重签，旧值立即作废）
3. `status=success` 时清空
4. 禁止写入 `localStorage` / `sessionStorage` / Cookie
5. 页面刷新 → 内存变量丢失 → 自动回到登录第一步，并提示"登录已超时，请重新开始"

其他编排约束：

- `status=mfa_required` 时原地渲染 `mfa.methods` 的选择器 + 对应因子组件，不跳页、不新开流程
- 轮询统一走 `useLongPoll`（指数退避、页面卸载中断）
- 全程受 `login_token` 10 分钟有效期约束，超时回到第一步

小程序 / 宿主环境差异：无 Cookie，Authloft 在响应体下发 `session_token`（接口文档 §1.2），宿主后续用 Header `X-Authloft-Token` 回传；`login_token` 处理与浏览器端一致（响应体返回 → 内存变量 → body 回传）。宿主侧交互与页面不在本工程（§9 第 10 条）。

### 4.2 步骤分派（`steps/`）—— 对应 `next_step.kind`

`StepKind` 是后端下发的渲染形态，前端逐个实现、按 kind 分派。

- `kind` 的 6 种取值与含义**见接口文档 §1.4**；它与请求侧 `step`（`challenge` / `verify` / `set_password`）是两组不同取值，不得混用
- **因子 → 步骤序列（含主/二次因子）见接口文档 §1.10**（唯一定义）：前端据此分段渲染，后端据此校验 `step` 合法性
- `external` 由宿主承载，`StepDispatcher` 遇到则走兜底（§9 第 10 条：`login/` 下不实现 `external` 步骤组件）

| 文件 | 职责 | 关键约束 |
|------|------|---------|
| `StepDispatcher.tsx` | 按 `next_step.kind` 分派到下列组件；未识别 kind 走兜底"请刷新重试" | 新增 StepKind 时只改这里一行 |
| `FormStep.tsx` | 渲染 `fields[]` → `FieldRenderer`，收集并提交 `payload` | 字段的必填 / 类型以下发为准 |
| `ChallengeStep.tsx` | 渲染 `challenge_fields`（如 phone/email）+ `CaptchaWidget`，触发下发 | 每次下发都需新的 captcha |
| `RedirectStep.tsx` | 展示"正在跳转…"，`location.replace(authorize_url)` | 移动端用 replace 避免回退死循环 |

## 9. 编码约束（写进 lint / review checklist）

1. 禁止 `localStorage` / `sessionStorage` / `document.cookie` 的写入；豁免仅：`login/oidcContext.ts`（键 `al_oidc_ctx`，只存 OIDC 上下文）
2. 禁止在通用层出现任何具体 `method` 字符串（如 `'otp_sms'`），只能出现在 `factors/registry.ts`
3. 禁止在组件内硬编码渠道名、字段名、失败文案，接口走统一封装；一律按 `status` 查 i18n 或取后端下发（`error.message`）
4. `fields[]` 的校验规则以下发为准，前端只做体验性校验（后端是唯一权威）
5. 所有**发往本系统接口**的写操作请求由 `http.ts` 统一发出，不允许组件内裸 `fetch`；multipart 走 `http.ts` 的 `postForm`，不例外。唯一豁免是 §3.2 `direct` 分支的直传 `PUT`（目标是对象存储的临时 URL，不带 Cookie 与本系统凭证，不经过本系统接口）
6. `login_token` 只经 `api.ts` 读写，业务组件不得直接触碰 `loginTokenStore`
7. 轮询必须可中断；倒计时必须基于时间戳
8. 新增能力时先走 §7 的判定表；若需要改 `LoginContainer` / `reducer` 才能接入，视为设计问题而非实现问题
9. 分支只认 `status`：取值必须落在接口文档 §1.6 的封闭集合内；禁止在前端定义任何 `error.code` 常量或按错误码分支
10. 小程序 / 宿主能力不在本工程实现：`login/` 下不得出现 `wx.*`、宿主桥接或 `external` 步骤组件
11. captcha 配置只由调用方注入：`shared/captcha/CaptchaWidget` 不发配置请求；首屏 login 传注入快照的 `methods.captcha`、account 传 `/api/account/config` 的 `captcha`，运行期以响应顶层的 `captcha` 覆盖（接口文档 §2.5）——`captcha` 对象不得被缓存为模块级常量
12. 三方回调按 `state` 首字母分派，不在前端判业务：`l` 走登录接口、`b` 走绑定接口；`OAuthCallbackPage` 只转发，不解析、不落盘、不自行决定跳哪个业务页
13. entry 边界由 lint 固化（Rslint，Rstack 体系自带，规则配置接入时补齐）：`login/` 禁止 import `account/`、`admin/`、`shared/app-ui/`、`@douyinfe/semi-ui`；`shared/` 禁止 import 任何 entry；跨 entry 复用只经 `shared/api`、`shared/hooks`、`shared/utils`、`shared/components`、`shared/captcha`
14. 静态资源 URL 只由 `static_base`（注入变量）拼出：禁止写死 `/assets`、`/static` 或 CDN 域名；`__webpack_public_path__` 只在 `entry.tsx` 赋值一次
15. 报文类型只来自 `src/gen/proto`：禁止手写接口 interface、禁止在组件里 `as` 断言出字段；`src/gen` 产物禁止手改
16. 编解码只在 `http.ts`：禁止组件内 `JSON.parse` / `JSON.stringify` 业务报文、禁止手拼 `Blob` 发请求；端点编码在 `endpoints.ts` 的 `format` 上改，不在调用点改
17. 数字只经 `utils/int.ts` 转换：禁止 `Number(id)`、禁止对 `bigint` 做隐式字符串比较；提交给后端的整型由序列化层输出字符串，禁止手写 `String(n)` 拼 JSON
18. `Accept` 只声明实际使用的那一种编码，禁止写 `*/*` 或同时声明两种（否则响应格式不可预期）
