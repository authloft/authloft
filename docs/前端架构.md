## 1. 总体架构

### 1.1 技术栈与分层

| 层       | 选型                                                                                                                                                                                                                                                                                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 框架     | Modern.js（React 19 + TypeScript + Rsbuild）                                                                                                                                                                                                                                                                                                                        |
| 产物形态 | 登录端、用户端、管理后台、安装页均为 SPA（同一工程、四个 entry）                                                                                                                                                                                                                                                                                                    |
| 页面外壳 | Go 渲染空壳 HTML，挂载对应 SPA 并注入初始变量（§1.5）                                                                                                                                                                                                                                                                                                               |
| 路由     | 混合模式（2026-11-07 定稿）：login = browser route（`BrowserRouter`），account / admin = hash route（`HashRouter`），setup 单页无分派；统一走 `@modern-js/runtime/router`（框架官方导出子路径，底层 react-router v7 随框架锁定，**不新增 package.json 依赖**）；模式按 entry 独立选择，entry 间全部整页跳转（`location.replace` / `<a href>`），模式不跨 entry 传播 |
| WebAuthn | `@simplewebauthn/browser`                                                                                                                                                                                                                                                                                                                                           |
| 契约校验 | 无独立校验层：响应类型全部来自 `@bufbuild/protoc-gen-es` 生成的 TS 消息类型（接口文档 §12.9）；login 表单手写简单校验，admin 表单用 Semi UI 自带校验                                                                                                                                                                                                                |
| 接口调用 | `@connectrpc/connect` + `@connectrpc/connect-web`（浏览器 transport）+ `@bufbuild/protobuf` 运行时 + `@bufbuild/protoc-gen-es` 生成的 TS 消息与 service 类型（见 §3.1）                                                                                                                                                                                             |
| UI 库    | login 端不使用（保证体积）；account / admin / setup 使用 Semi UI（setup 以 Semi 组件默认样式为主，口径见 《CODE_GUIDE》§4.1 第 13 条）                                                                                                                                                                                                                              |
| Hooks 库 | `ahooks`（获准依赖，版本按落地时最新）；ahooks 已有的能力（useRequest / useDebounce / useLocalStorage 等）不得自行重复封装，自定义 hook 只用于 ahooks 未覆盖的业务逻辑                                                                                                                                                                                              |

```
浏览器
 ├─ 空壳 HTML（Go 渲染，注入 window.__AUTHLOFT_INIT__，见 §1.5）
 └─ SPA bundle（本工程产物）
      │
      ├─ entry（login / account / admin）：框架接管挂载（去 `disableMount`，容器 `#root`）；根组件模块读注入变量 → 建路由（路由表 + `@modern-js/runtime/router`）
      ├─ pages：页面级容器，只做布局与路由参数
      ├─ flow / containers：状态编排（登录状态机）
      ├─ components(factors / captcha / schema)：按后端下发配置分派渲染
      ├─ shared/api：transport 单例、生成 client、错误归一化（ConnectError → ErrorInfo → §1.6 词汇）、multipart 上传封装
      └─ shared/hooks|utils：能力检测、轮询、倒计时、校验、上传、整数转换
```

### 1.2 抽象边界

能通用的是流程编排，不是交互渲染。

| 层次                                        | 内容                                                                                                                                                                 | 增长曲线           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| 第一层：完全通用，写一次                    | 登录容器 + `challenge → verify → mfa → success` 状态机、方式列表渲染与分组排序、通用字段渲染器（12 种 `type`，见 §3.3）、失败态展示与动作、重试冷却、终点处理        | 恒定               |
| 第二层：每因子一个组件（5 个，`totp` 除外） | `PasswordForm`、`OTPForm`、`WebAuthnButton`、`ProviderButtons`、`RecoveryCodeForm`；`totp` 不设专属组件，由通用 `FormStep` + `CodeInput`（`fields[].type=totp`）渲染 | 恒定，因子种类有限 |
| 第三层：每厂商一个 adapter                  | 仅 Captcha 需要（各厂商 JS SDK 互不兼容）；`CaptchaWidget` 因 login / account 共用而落在 `shared/`（§3.5）                                                           | 低频               |

判定规则（新增认证方式时按顺序判断，不要硬塞进通用 schema）：

1. 用户是敲键盘输入？→ 通用字段渲染器
2. 需要调浏览器原生 API（WebAuthn）？→ 独立组件，只在 `methods` 里声明 `hint` 与能力检测条件。宿主 / 小程序能力（`wx.login`）由宿主自行实现，Authloft 前端不承载
3. 需要等待外部事件（扫码轮询）？→ 独立面板，复用通用轮询 hook
4. 只是跳转？→ 不算组件，后端给 URL 即可

> schema 驱动用来管"有哪些方式、顺序如何、要哪些字段"；不要用它管"怎么和用户 / 浏览器交互"。

新增认证方式时的判定流程与改动清单见 §7。

### 1.3 四 entry 的职责边界

| entry     | 挂载路径                                            | 注入变量（§1.5）                                                   | 会话形态                                                                               | 主要依赖接口                                                                                                                   |
| --------- | --------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `login`   | `/sso/**`、`/auth/**`                               | `al_root`、`static_base`、`methods`（必填）、`oidc`（可选）        | 无会话；`login_token` 仅存内存变量                                                     | 接口文档 §2（SsoService）                                                                                                      |
| `account` | `/account`（仅根映射；子路径走 hash 路由，见 §1.4） | `al_root`、`static_base`                                           | 依赖会话 Cookie（名称 / 属性 / 有效期见接口文档 §1.9；HttpOnly，前端不可读）           | 接口文档 §3（AccountService）；另调 `SsoService/Authorize`（`scene=bind`）、`SsoService/CreateQrcode`（`scene=bind`），见 §3.1 |
| `admin`   | `/admin`（仅根映射；子路径走 hash 路由，见 §1.4）   | `al_root`、`static_base`（管理员信息由 `AdminService/GetMe` 获取） | 依赖管理员会话 Cookie（复用 SSO 登录，管理员为安装时创建的固定 ID 账号，接口文档 §13） | 接口文档 §5（AdminService）                                                                                                    |
| `setup`   | `/setup`                                            | `static_base`（仅此一项，不注入 `methods` / `oidc`）               | 无会话、无业务态；仅在服务端 setup 模式（无配置文件）下有意义                          | 接口文档 §13（`SetupService`）                                                                                                 |

三个业务 entry（`login` / `account` / `admin`）共享 `src/shared`，不得各自复制组件；`login` 与 `account` 共享 `FieldRenderer`、`CodeInput`、`ErrorBanner` 与整套 captcha 弹窗（`captchaGate` / `useCaptchaGate` / `CaptchaDialog` / `CaptchaWidget`，因此 `captcha/` 落在 `shared/` 下，见 §3.5）。captcha 弹窗只出内容，窗体按 domain 注入：调用方把 `login/components/Modal`（自绘）或 `shared/app-ui/Modal`（Semi）交给 `useCaptchaGate`，两端各自保证本 entry 内视觉一致（契约见 §3.3）。`setup` entry 与业务端共用同一 connect transport / client 封装（安装模式后端仅注册 `SetupService`，接口契约见接口文档 §13），可复用 `shared/components` 等零依赖组件（见 §6b）。各 entry 的页面与组件必须落对应 `*.module.less`——"不用 UI 库"不等于"不写样式"（样式方案见 §1.7）。

### 1.4 页面渲染分工与路由

- `/api/**` 为接口，其余为页面；页面路由清单与空壳注入约定见接口文档 §8
- `/sso/**`、`/auth/**`、`/account`、`/admin` → Go 返回空壳 HTML，挂载对应 SPA；路由归属前端。**account / admin 后端仅映射根路径（收窄，接口文档 §8）**：子路径全部走前端 hash 路由（不发往服务端），未注册子路径走 gin 原生 404（沿用后端既有兜底口径，不新增行为）
- 两个例外由 Go 直接渲染真实 HTML（"无界面"中转页，不需要 SPA）：
  - `/sso/sync_cookie`：多域名 Cookie 同步的跳转中转页（302，非 SPA）
  - `/sso/logout`：登出，Go 直接处理（接口文档 §2.9）

登录端前端路由（**browser route**：`BrowserRouter` + 路由表分派）：`/sso/login`、`/sso/register`、`/sso/reset`、`/sso/oauth/callback/:provider_key`、`/auth/authorize`。`/auth/authorize` 为 OIDC 授权空壳（§1.3 挂载 `/auth/**`），复用登录页完成授权步骤（"OIDC 授权页即登录页"，见 §4.4 `LoginPage`）；`oidc` 注入见 §1.5，交互见接口文档 §4.2。**有有效会话时该路径由后端直接签发授权码并 302 到 `redirect_uri`，不渲染空壳、不进入前端**；前端只在无会话时渲染空壳完成登录。

account / admin 前端路由（**hash route**：`HashRouter` + 路由表分派）：URL 形态 `/account#/profile`、`/admin#/users/:id`——path 与 query 一律在 hash 内（`/account#/security?bind=x`）；参数经 `useParams`、query 经 `useSearchParams`；未命中走 `path:'*'` 兜底页（必需项，用户或程序拼错 hash 的落点）。

**dev fallback 与生产收窄的行为落差**：dev server 存在 fallback——`server.routes` 只映射 `/account`、`/admin` 根路径，但开发期直接访问 `/account/profile` 这类子路径仍返回 200 并下发壳，**这不代表生产可用**：生产后端仅注册根映射，未注册子路径返回 gin 原生 404（接口文档 §8）。结论性约束：account / admin 的页面必须经 hash 访问（`/account#/profile`），**不得依赖 pathname 子路径导航或深链刷新**；开发期用子路径能打开属 dev fallback，不是行为契约。URL 形态对照（dev = 生产）：`/sso/login` 一致（login browser route，经 `server.routes` 映射）；`/account#/profile` 一致（hash 不发往服务端）；pathname 子路径不构成契约。

挂载方式（2026-11-07 定稿）：login / account / admin 三入口**去掉 `disableMount`**，由 Modern.js 框架生成入口代码并接管挂载（容器默认 `#root`，与壳层模板一致）；entry 文件只默认导出根组件，`__webpack_public_path__` 赋值、i18n 注入、错误边界、注入变量读取移入根组件模块作用域（仍在任何动态 `import()` 触发前执行）；setup 保持现状不动。三占位符注入（§1.5）是构建期 HTML 层机制，与挂载方式解耦；框架自动注入的 runtime / route manifest 脚本由 `security.nonce` 统一挂 nonce（§1.5 ①），不新增 CSP 缺口。

安装端前端路由：`/setup`（仅服务端 setup 模式下可达，页面结构见 §6b，接口契约见接口文档 §13）。

### 1.5 初始变量注入（`window.__AUTHLOFT_INIT__`）

首屏就必须有的变量由后端在渲染空壳 HTML 时注入，避免 SPA 再发一轮请求，也避免把配置硬编码进前端。

```html
<script nonce="{{AUTHLOFT_CSP_NONCE}}">
  window.__AUTHLOFT_INIT__ = {{AUTHLOFT_INIT_JSON}};
</script>
<script
  defer
  nonce="{{AUTHLOFT_CSP_NONCE}}"
  src="{{AUTHLOFT_STATIC_BASE}}/login/runtime.a1b2.js"
></script>
<script
  defer
  nonce="{{AUTHLOFT_CSP_NONCE}}"
  src="{{AUTHLOFT_STATIC_BASE}}/login/vendor.e5f6.js"
></script>
<script
  defer
  nonce="{{AUTHLOFT_CSP_NONCE}}"
  src="{{AUTHLOFT_STATIC_BASE}}/login/entry.c9d0.js"
></script>
<link rel="stylesheet" href="{{AUTHLOFT_STATIC_BASE}}/login/entry.3a4b.css" />
```

**壳层 HTML 模板由框架构建产物原样复制而来**（2026-11-05 终稿：**绝不自定义模板**，模板唯一来源即 Modern.js 构建产物，`web/` 下不得存在任何自写壳层模板文件，不许两套真相）：每个 entry 取 Modern.js 默认生成的 `dist/html/{entry}/index.html` **原样复制**为后端壳层模板（`server/internal/pages/templates/{entry}.html`，`entry` ∈ `login` / `account` / `admin` / `setup`）——不做结构改写、不删节点、不手工重排、不删 route manifest 等框架生成 HTML 自带的附加物，**框架产物是模板唯一真相源**。`pnpm build` 尾段由同步脚本将构建产物**仅复制**覆盖写入后端目录——三个占位符（`{{AUTHLOFT_STATIC_BASE}}` / `{{AUTHLOFT_CSP_NONCE}}` / `{{AUTHLOFT_INIT_JSON}}`）全部由构建期 config 注入产物，脚本零改写（新口径，取代"三件最小替换"旧口径）。后端运行期只做占位符值替换。**占位符清单、模板落位与 CSP 口径见接口文档 §8（唯一定义，本文不复制）**。

**模板同步脚本与构建期注入口径**（2026-11-05 终稿；脚本归前端仓维护，三个 config 均落 `web/modern.config.ts`）：

- **脚本与依赖**：`web/scripts/sync-templates.mjs`，仅用 node 内置模块（`fs` / `path`），零新增依赖；任何失败（`dist` 缺失、复制异常、对账不过、写入失败）以非零 exit code 结束，供 CI 与 `&&` 链感知
- **仅复制**：每个 entry 将 `dist/html/{entry}/index.html` 原样复制为 `server/internal/pages/templates/{entry}.html`——不做结构改写、不删节点、不手工重排、不删 route manifest、**不做任何改写替换**（含正则 / 文本处理），其余一切保持框架原样
- **三个占位符一律构建期 config 注入**（定稿口径，取代"脚本三件最小替换"旧口径；均落 `modern.config.ts`，同步脚本对产物不做任何替换）：
  ① **nonce 统一挂 = `security.nonce: '{{AUTHLOFT_CSP_NONCE}}'`**（Modern.js / Rsbuild 内建配置）：在标签生成阶段给 `script`（外链 + 内联，含框架自动注入的 runtime / route manifest 内联脚本）、`<style>`、`<link rel="preload" as="script">` 统一挂 nonce 属性，并注入 `import.meta.rspackNonce`（运行期动态插入的 chunk script 同享 nonce）。**已知缺口：不覆盖 `<link rel="stylesheet">`**——由 ③ 的 `html.tags` Handler 一并补挂
  ② **STATIC_BASE 前缀 = `tools.htmlPlugin: { publicPath: '{{AUTHLOFT_STATIC_BASE}}/' }`**：html 插件层 publicPath **仅改写 HTML 内 `script` / `link` 标签的资源前缀**（`@rspack/core` html-plugin 类型注释原文 "The public path used for script and link tags"），**独立于**运行期 publicPath（产物 runtime `f.p="/assets/"` 不变）、CSS `url()` 与异步 chunk 路径——占位符只出现在模板 HTML 文本层，**不会漏进外链 CSS / JS 文件内容**（后端只替换模板 HTML，硬约束）；**生成模板内禁止出现写死的 `/assets`、`/static` 或任何域名**（《CODE_GUIDE》§4.1 第 14 条同约束）
  ③ **INIT_JSON = `html.tags` 注入 init script**（A 方案，落位定稿）：为全部 entry 注入标签——`{ tag: 'script', attrs: { nonce: '{{AUTHLOFT_CSP_NONCE}}' }, children: 'window.__AUTHLOFT_INIT__ = {{AUTHLOFT_INIT_JSON}};', head: true, append: false }`，字面形态与本节上方示意一致，`head: true` + `append: false` 使其位于 `<head>` 最前。实证口径（Modern.js 随包文档与构建产物双证）：`html.tags` 与 Rsbuild 用法完全一致（随包文档 `configure/app/html/tags.md`），`children` / `attrs` 原样输出、不做 HTML 转义、不经模板（EJS / lodash）渲染，`{{…}}` 不匹配其语法故原样存活（minify 实测占位符存活；框架产物自带的内联大段 JS 原样输出即实证）；init script 的 nonce 占位符由 attrs 显式携带，与 ① 对 script 的统一挂载同值一致。**落地形态**：因 ① 的 stylesheet 补挂同用 `html.tags`，故取 Handler 形式 `(tags, ctx) => HtmlTag[]`（在 html 标签组处理阶段收全量 head / body 标签并写回）——同一 Handler 内先给 `link[rel=stylesheet]` 补挂 `nonce: '{{AUTHLOFT_CSP_NONCE}}'`，再前插上述 init script 标签一并写回；同步脚本零 INIT 处理
- **为何走构建期 config 而非产物文本改写**：config 在标签**生成阶段直接改写标签流**——不依赖产物 HTML 的文本格式（无正则 / 格式假设）、**天然覆盖框架自动注入的内联脚本**（文本改写须逐版本追踪框架注入点，易碎）、配置项是框架对外接口、跨 Modern.js / Rsbuild 版本更稳（产物文本结构非公开承诺）
- **对账自检（纯校验 fail-fast 义务，脚本零改写）**：复制完成后核对模板内 `script` + `<style>` + `<link rel="stylesheet">` 标签出现数 = `{{AUTHLOFT_CSP_NONCE}}` 出现数，逐个相等，否则整次同步失败——漏挂任意一个标签即整页被 CSP 拦；另校验三占位符均在场、无写死 `/assets` 前缀遗漏；禁止以 `'unsafe-inline'` 放宽
- **风险注记（升级回归义务）**：`security.nonce` 的标签覆盖集（isNonceTag）与 `tools.htmlPlugin.publicPath` 的作用域属 Rsbuild **实现细节、非公开承诺 API**——升级 Modern.js / Rsbuild 时必须回归验证三类标签 nonce 全覆盖与三占位符正常输出；构建期 html-minifier 对 `{{…}}` 占位符 parse 失败会产生**无害 terser 日志噪音**（不影响产物与占位符存活）
- **写入边界**：脚本对 `server/` 的写权限**仅限** `server/internal/pages/templates/{login,account,admin,setup}.html` 四个路径，覆盖式写入；不读不改后端任何 Go 代码，embedfs 消费与渲染归后端（《后端架构》§3.13）
- **命令链**：`web/package.json` 的 `build` 扩为 `modern build && node scripts/sync-templates.mjs`——**本地与 CI 一键口径统一为 `pnpm build`**（构建 + 模板同步一步完成）；另设 `sync:templates` = `node scripts/sync-templates.mjs`，供 dist 未变、仅构建配置改动时单独重跑；CI 侧前端命令即 `pnpm build`，「拷贝 dist → go build」由后端侧衔接（《后端架构》§3.13）；dev 模式由 Modern.js dev server 自渲染，不经同步脚本
- **构建配置配套**：删除 `web/modern.config.ts` 的 `filename.js` 回调（现存逻辑把 initial 非 vendor chunk 固定为 `${name}/entry.js`，属反口径逻辑）、恢复全量 contenthash 的改动仍然成立（《CODE_GUIDE》§4.1 第 23 条）；拆包规则（code splitting / 多 chunk）不变

前端侧约束：

- `bootstrap.ts` 读取注入变量；`methods` 必须存在，缺失时渲染错误提示并提示刷新，无回退接口
- **静态资源基址**：根组件模块作用域在任何动态 `import()` 之前把 `__webpack_public_path__` 设为 `static_base + '/'`（缺省 `/assets/`；框架接管挂载后的首个自有执行点，§1.4），此后所有异步 chunk 与图片按该前缀加载；`static_base` 由后台配置（接口文档 §5.6），可为 CDN 绝对地址。**不使用资源版本号**：产物文件名自带 contenthash
- 渠道图标**不做本地文件回落**：`icon` 为空即渲染通用占位（`ProviderIcon`），工程内不存放任何渠道图标资源（接口文档 §2.7.1）
- 首次提交登录请求时，若 `oidc` 存在，以 body 顶层 `oidc` 字段原样回传（仅这一次）
- 前端不得假设其中存在任何凭证：没有会话 ID、没有 `login_token`、没有 Provider 密钥
- 落盘例外仅一处：跳转第三方前把 `oidc` 写入 `localStorage`（键 `al_oidc_ctx`），回调后读出随 body 回传并清除（接口文档 §2.7.2）；多域名同步的链路状态由后端载荷携带，前端不落盘（接口文档 §2.9）
- 注入块的转义、`no-store`、CSP nonce 由后端保证（后端架构 §3.4），前端不做二次信任
- 前端壳层模板须满足接口文档 §8 CSP 终稿：全部 `script`（外链 + 内联）/ `<style>` / `<link rel="stylesheet">` 标签统一携带 `{{AUTHLOFT_CSP_NONCE}}` 占位符（由构建期 `security.nonce` + `html.tags` Handler 注入，同步脚本仅复制并对账 fail-fast，见本节）；`eval` / `new Function` 禁止；禁止以 `'unsafe-inline'` 放宽；源代码层面样式仍一律 `*.module.less` 外链产物（编码约束见 《CODE_GUIDE》§4.1 第 22 条）

## 3. `shared/` 文件职责

### 3.1 `shared/api`

> 报文类型**只有一个来源**：`src/gen/proto`（`@bufbuild/protoc-gen-es` 由后端同一批 `.proto` 生成，接口文档 §12.9）。组件与业务代码只使用生成的消息类型，禁止手写接口 interface，禁止在 `shared/api` 里重新描述字段。

| 文件         | 职责                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | 关键约束                                                                                                                                                                                                           |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `http.ts`    | transport 单例（`createConnectTransport({ baseUrl: al_root, credentials: 'include' })`）+ 超时 / 中断注入 + 生成的 service client 构造；非 2xx 由 connect-es 抛 `ConnectError`，`findDetail(ErrorInfo)` 解出业务细分码归一为 `ApiError`；multipart 仍走 `postForm(url, formData)`（签名另可选 `onUploadProgress`；REST 豁免端点，不用 transport）                                                                                                                                   | transport 与 client 只在此构造（见下方"transport 与错误归一"）；组件不得裸 `fetch`、不得自己 `JSON.parse` 业务报文；不自行加自定义头触发预检；`postForm` 的 `Content-Type` **不手动设置**（交由浏览器带 boundary） |
| `errors.ts`  | 两层错误口径（§1.6 词汇、两个位置）：① 登录流程域 200 响应顶层 `status`（含 `next` / `mfa_required` 等流程态）→ `{retryable, action, i18nKey}`；② 非 200 `ConnectError` 的 `ErrorInfo.code`——无 detail 时按 Connect 标准码（§1.5）兜底，统一拦截文案。`captcha_required` / `captcha_invalid` / `verification_required` / `verification_invalid` 一律按 ② 登记（仅 `ErrorInfo.code`，不作 `status`）：captcha 两类 → 开人机校验弹窗后重提同一请求，step-up 两类 → 重新取得断言后重提 | 不存在第二套业务错误码；未知取值走兜底文案，不暴露内部信息；`ErrorInfo.message` / `ConnectError.message` 只作兜底；登录域 reducer 继续消费 `status`，仅 captcha / step-up 传输层失败交给统一拦截                   |
| `sso.ts`     | 跨 entry 复用的 SsoService client 方法薄封装（`Authorize`、`CreateQrcode`、`CreateCaptchaImage`；account 的绑定与 captcha，见接口文档 §3.7.1）                                                                                                                                                                                                                                                                                                                                      | 只放被 ≥2 个 entry 使用的调用；login 专属调用仍留在 `login/api.ts`                                                                                                                                                 |
| `account.ts` | 跨 entry 复用的 AccountService client 方法薄封装（`GetConfig`、`ThirdpartyOauth`、`PresignAvatar`、`CommitAvatar`、proxy 上传 `postForm('/api/account/avatar')`；login 的 `OAuthCallbackPage` 走 `b` 前缀分支时使用，接口文档 §2.7.3；头像上传见接口文档 §10.8）                                                                                                                                                                                                                    | 同上：只做薄封装，不承载业务分支                                                                                                                                                                                   |

**transport 与错误归一**

- 请求 / 响应编解码由 connect-es transport 承担（JSON：标准 protojson 映射——lowerCamelCase、省略零值、int64 十进制字符串，接口文档 §1.1 / §1.12）；组件与业务代码只接触生成的消息对象
- 对缺失字段按零值兜底：`msg.field ?? 零值`，禁止假设字段恒存在
- 错误归一化：非 2xx → `ConnectError` → `findDetail(ErrorInfoSchema)` 取 `{domain, code, message, retryAfter, attemptsLeft}` → 抛 `ApiError`；登录域 200 的流程 `status` 分支仍走业务层（`reducer`），`status` 仍是登录流程的业务分支依据但不再是唯一分支——captcha 与 step-up 的传输层失败例外：不再由流程 `status` 表达，与其余域一样经 transport 归一为 `ApiError` 后由统一拦截处理（接口文档 §1.5）
- 头像直传（REST 豁免）与 `direct` 模式的对象存储 `PUT` 不走 transport，见 §3.2 `useUpload`

**数字（接口文档 §1.12）**

- 生成的消息里 `int64` 字段是 `bigint`，JSON 文本里是十进制字符串——转换由 connect-es（`@bufbuild/protobuf`）完成，业务代码两端都见不到字符串
- ID / 时间戳全程保持 `bigint` 或字符串，**禁止 `Number(id)`**（超 2^53 静默丢精度）；展示用 `shared/utils/int.ts` 的 `toDisplay`
- 时长 / 计数类（`retryAfter`、`expiresIn`、`pageSize`、`total`、`length`）可用 `utils/int.ts` 的 `toCount` 转 `number`，转换处自带 `Number.MAX_SAFE_INTEGER` 断言

| 触发时机   | 适用                                                                                                                | 行为                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `upfront`  | 后端 challenge 类恒拦截（发码、拉码、绑定 challenge、注册直达 `set_password`）                                      | 点击即开窗，确认后只发一次带凭据的请求——省掉一次注定被拦的往返 |
| `reactive` | 密码 `verify` 由当日失败计数阈值触发，前端无法预知；后端豁免路径（WebAuthn challenge、三方免密建号 `set_password`） | 先发裸请求，命中 `captcha_required` 才开窗                     |

- 提交位置：凭据作为**请求级 `captcha` 字段**提交，与 `payload` 平级（不在 `payload` 内）；`{providerKey, token}`（第三方）或 `{providerKey, id, answer}`（自绘）由 adapter 产出，接口文档 §2.5
- 重提机制：确认后以**同一请求体**重提原请求，仅请求级 `captcha` 换成新凭据；`gate.run` 包装的请求器负责把凭据挂到请求级字段，其余字段（含 `loginToken` / `payload`）原样不重算
- 配置缺失时 `upfront` 退化为先探一次（服务端未启用 captcha 的部署不该凭空弹窗）
- 取消不清任何流程态：表单原地可重提，`login_token` 仍由 `login/api.ts` 独家托管（§4.1），弹窗层不触碰
- 调用方负责把当前 `captcha` 配置（`{providerKey, type, siteKey}`）作为 prop 传入；`CaptchaWidget` 内部不发任何配置请求，也不缓存配置
- 换凭据由「每轮重挂 widget」承担，调用方不再手动 `reset()`

状态机（接口文档 §1.3 的 `status` 即状态；captcha 与 step-up 的传输层失败不进状态机，走统一错误拦截，§3.1）：

```
idle → (选方式) → challenge? → verify → [mfa_required] → challenge? → verify → success
                                    ↘ [binding_required] → 绑定选择页 → success / 退出重登
                                    ↘ [too_many_requests|locked|failed] → 失败态（按接口文档 §1.6 出动作）

扫码轮询（QRCodeStep → GetLoginTicket）：
  pending / scanned → 继续轮询
  needs_step_up → 以 mfaPendingId = ticketId 走 step-up（见下文）→ 继续轮询
  success → 终点；expired / 失败类 → 重拉码 / 失败态
```

业务失败按 `status` 分支（扫码轮询的 `pending` / `scanned` / `needs_step_up` 为进行中，不作失败处理，见接口文档 §1.6）；captcha / step-up 的传输层失败不套信封，走统一错误拦截（接口文档 §1.5 / §1.6）。

`login_token` 的传递规则与覆盖语义**见接口文档 §1.8、§1.3**（唯一定义）。前端实现五条，不可打折：

1. 由 `loginTokenStore` 以模块级变量保存；前端不解析其内容，只做"收到就替换、请求就带上"
2. 每次响应若含 `login_token`，无条件覆盖内存变量（后端每次重签，旧值立即作废）
3. `status=success` 时清空
4. 禁止写入 `localStorage` / `sessionStorage` / Cookie
5. 页面刷新 → 内存变量丢失 → 自动回到登录第一步，并提示"登录已超时，请重新开始"

其他编排约束：

- `status=mfa_required` 时先以 `loginToken` 调 `SsoService/StartVerification`（`biz_purpose=login`、`operation=mfa_verify`，不带 `method`）取 `methods[]`，原地渲染选择器 + 对应因子组件，不跳页、不新开流程；用户选中因子后再带 `method` 调一次取 `challengeToken`，最后 `SubmitVerification` 提交因子载荷
- 轮询统一走 `useLongPoll`（指数退避、页面卸载中断）
- 全程受 `login_token` 10 分钟有效期约束，超时回到第一步

**step-up 调用时序**（`SsoService/StartVerification` / `SubmitVerification`，接口文档 §3.8）：

- 登录 MFA：`StartVerification({biz_purpose:'login', loginToken, operation:'mfa_verify'})` → 选因子 / 取挑战 → `SubmitVerification({challengeToken, method, payload})` → 响应即登录流程结论（`status` / `redirectTo` / `syncCookieUrl`），交回同一状态机终点处理
- 扫码 step-up：轮询顶层 `status=needs_step_up`（`ticket.status` 仍为 `scanned`）时，以 `mfaPendingId=ticketId` 调 `StartVerification`（`biz_purpose='login'`）→ `SubmitVerification` 成功后**不直接登录**，继续轮询 `GetLoginTicket` 到 `success` 再走终点
- `challengeToken` / `verificationToken` 对前端不透明，仅透传；`amr` 只由服务端写入，前端不提交

小程序 / 宿主环境差异：无 Cookie，Authloft 在响应体下发 `session_token`（接口文档 §1.2），宿主后续用 Header `X-Authloft-Token` 回传；`login_token` 处理与浏览器端一致（响应体返回 → 内存变量 → body 回传）。宿主侧交互与页面不在本工程（《CODE_GUIDE》§4.1 第 10 条）。

## 6b. `setup/` 文件职责（安装 entry）

安装向导（接口文档 §13，需求 §4.7）。本 entry 仅在服务端 setup 模式（无配置文件）下有意义：加载时先调 `SetupService/GetStatus`，返回 404 / 连接失败即已处于正常模式，直接跳转 `/sso/login`。
